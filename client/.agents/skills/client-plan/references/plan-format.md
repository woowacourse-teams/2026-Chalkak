# 계획 형식

사람이 승인 화면에서 위에서 아래로 읽는다. 순서를 바꾸지 않는다.

```markdown
<!-- client-plan -->
## 계획 (#123)

관련 결정: ui-state-navigation   ← 없으면 "없음"

### 가정
- 화면 기준: #123 댓글의 시안 2안 (이름 아래 회색 소개, 3줄 말줄임)
- 소개는 프로필 API의 bio 필드를 쓴다
- 빈 문자열도 소개 없음으로 본다

### TC
[정상] TC 1  소개가 있으면 화면 상태에 담는다
  Given  소개가 "필름으로 찍어요"인 작가
  When   프로필을 불러온다
  Then   화면 상태의 소개가 "필름으로 찍어요"

[예외] TC 2  소개가 비어 있으면 소개 없음 상태가 된다
  Given  소개가 빈 문자열인 작가
  When   프로필을 불러온다
  Then   화면 상태의 소개가 없음(null)

### 테스트 밖 확인 항목 (화면·기기)
1. 소개가 3줄을 넘으면 말줄임으로 끝난다
   확인: Preview — 소개 4줄인 프로필 Preview
2. 소개 칸을 눌러 키보드가 올라와도 저장 버튼이 가려지지 않는다
   확인: 기기 — 바로 열기 profile-edit, 판정: 저장 버튼 아랫변이 키보드 윗변보다 위
3. 다른 작가 프로필에서 돌아오면 스크롤 위치가 유지된다
   확인: 사람 — 화면 사이 이동이 실제 데이터에 따라 달라짐
   가는 길: 홈 → 작가 이름 누르기 → 작가 프로필 → 다른 작가 → 뒤로
   데이터: 사진이 20장 넘는 테스트 작가

### 범위 밖과 공용 코드 영향
- 소개 수정 기능은 이번에 하지 않음
- core/designsystem은 바꾸지 않음
```

## 칸마다 쓰는 법

**관련 결정**: `related-adr.py`가 고른 ADR의 파일 이름(확장자 빼고). 고른 ADR의 결정과 계획이 어긋나면 가정에 적는다.

**가정** 2~3줄: 이슈에 없지만 계획이 기대고 있는 사실. 가정이 틀리면 TC가 모두 틀린 방향으로 맞아떨어지므로 TC 위에 따로 둔다. 확인 못 한 서버 동작은 `(확인 필요)`를 붙인다.

- 화면 코드를 바꾸면 첫 줄은 `화면 기준:`이다. 바뀐 뒤 모양을 보여 주는 레퍼런스(링크·그림·고른 안 번호)와 핵심 모양 한 구절을 쓴다. 승인하는 사람이 기준이 맞는지 여기서 본다. 잘못된 레퍼런스는 여기서 걸러야 가장 싸다.
  - 레퍼런스가 최신 화면인지(열린 PR 포함) 먼저 본다. 이슈 그림이 바뀌기 전 지금 화면뿐이거나 기준이 없으면 지어내지 않고 `화면 기준: 없음 — <이유> (확인 필요)`로 둔다. 승인 때 사람이 정하면 정한 기준으로 바꿔 적는다.
  - 화면 코드를 바꾸지 않으면 이 줄은 쓰지 않는다.

**TC**: 한 TC에 동작 하나. 두 플랫폼 작업이어도 동작 기준으로 한 번만 쓴다(검증 때 플랫폼마다 돌린다). 한쪽에만 해당하면 제목 끝에 `(Android만)`처럼 적는다.

- 머리줄: `[정상|예외|실패] TC <번호>  <제목>`. 제목은 그대로 테스트 이름이 된다.
  - Android: ``fun `소개가 있으면 화면 상태에 담는다`() = runTest { ... }``
  - iOS: `@Test("소개가 있으면 화면 상태에 담는다") func showsBio() async throws { ... }`
- Given / When / Then 세 줄은 테스트 본문의 주석이 된다.
- 값을 구체적으로 쓴다. "목록이 줄어든다"가 아니라 "목록이 1, 2, 3 → 1, 3".
- 실패 경우(서버 오류, 빈 값, 중복 요청)를 하나 이상 넣는다.
- Compose·SwiftUI 화면 모양은 TC로 쓰지 않는다. 테스트 밖 확인 항목으로 보낸다.
- 화면 모양만 고치는 작업은 TC가 0개일 수 있다. 그때는 `TC 없음 — 모양 수정이라 유닛 테스트로 잡을 수 없음`이라고 쓴다.

**테스트 밖 확인 항목**: TC가 다 통과해도 다 된 것처럼 보이지 않게 하는 칸. 화면에서 볼 것을 번호로 적는다(PR 📸 칸의 번호). 두 플랫폼 작업이면 같은 번호를 두 플랫폼에서 각각 본다. 화면 코드가 바뀌지 않으면 `없음`.

- 항목마다 `확인:` 줄에 확인 방법을 쓴다. 정하는 기준은 [화면 자동 확인](../../client-tdd/references/screen-auto-check.md)의 표다.
  - `확인: Preview — <어느 상태의 Preview>`: 멈춰 있는 모양. 수정 전·후 Preview 스냅샷을 비교한다.
  - `확인: 기기 — 바로 열기 <이름>, 판정: <스크립트가 참/거짓으로 볼 조건>`: 키보드·포커스·스크롤·제스처처럼 움직여야 아는 것. 판정은 숫자나 글자로 쓴다(예: `버튼 아랫변이 키보드 윗변보다 위`).
  - `확인: 사람 — <이유>`: 실제 서버 응답처럼 위 둘로 못 보는 것. 이 항목만 `가는 길:`(화면까지 누르는 순서)과 `데이터:`(로그인 여부, 필요한 게시물·계정 상태)를 쓴다(#938에서 오늘 게시물·서버 때문에 19분 막힘). 모르면 `(확인 필요)`.
- 지금 자동 확인은 Android만 한다. iOS는 `확인:`이 무엇이든 사람이 PR 리뷰에서 본다.
- 상태 유지·데이터 처리처럼 ViewModel로 확인되는 것은 이 칸이 아니라 TC로 쓴다.

**범위 밖과 공용 코드 영향** 1~2줄: 이번에 하지 않는 것, 다른 화면이 같이 쓰는 코드(`core/designsystem`, 공용 Repository)를 건드리는지.

## 하네스 작업의 계획

`client/.agents/` 등 하네스만 바꾸는 작업이다. 돌릴 유닛 테스트가 없고, 실제 이슈로 시험해서 확인한다. 칸 순서는 같고 두 칸이 다르다.

```markdown
<!-- client-plan -->
## 계획 (#123)

관련 결정: 없음

### 가정
- 시험 브랜치는 하네스 브랜치에서 따고, 시험 PR은 하네스 브랜치를 기준으로 연다

### TC
[정상] TC 1  같은 테스트 클래스의 TC는 한 번에 Red가 된다
  Given  계획의 TC 1–3이 모두 `FeedViewModelTest`에 들어간다
  When   3단계 Red
  Then   클래스를 1번 실행하고 evidence에 TC마다 실패 메시지 한 줄씩 남는다

### 시험
- 시험 이슈: #456 (두 플랫폼, 화면 변경 있음). 확인할 TC: 1–3
- 측정할 값: #931 대비 가중 토큰, 일한 시간, iOS 테스트 실행 횟수. 셋 다 줄고 추가된 테스트 수는 줄지 않는다

### 범위 밖과 공용 코드 영향
- 화면 확인 스킬은 바꾸지 않음
```

- **TC**: 시험 이슈를 돌릴 때 하네스가 보여야 할 동작이다. Given에는 시험에서 만날 상황, Then에는 세션 기록·기록 파일·PR에서 보이는 것을 구체적으로 쓴다. 실패 경우를 하나 이상 넣는다.
- **시험**(테스트 밖 확인 항목 대신): 시험 이슈 번호와 고른 이유, 어느 TC를 확인하는지, 측정할 값. 측정할 값에는 비교할 v0 작업과 기대 방향을 쓴다. 비용 목표가 없는 변경이면 `측정할 값: 없음 (<이유>)`.
  - 시험 이슈는 확인할 TC를 실제로 거치는 이슈로 고른다(예: 두 플랫폼 TDD를 바꾸면 두 플랫폼 이슈).
- 화면 코드를 바꾸지 않으므로 테스트 밖 확인 항목(화면·기기) 칸은 없다.

## 사람이 승인할 때 보는 것

- 값이 구체적인가
- 실패 경우가 들어 있는가
- TC 하나에 동작 하나인가
- 관련 결정이 빠지거나 엉뚱하지 않은가
- 화면 작업이면 화면 기준이 바뀐 뒤 모양을 가리키는가(지금 화면이나 옛 시안이 아닌가)
- 화면 항목의 `확인:`이 맞는가(`기기` 판정이 버그를 실제로 가르는 조건인가, `사람`이 꼭 필요한가)
- 하네스 작업이면 시험 이슈가 확인할 TC를 실제로 거치는가
