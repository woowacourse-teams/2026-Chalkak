# PR 본문 형식

레포 템플릿 `.github/pull_request_template.md`의 칸을 그대로 쓰고 채운다.
템플릿에 없는 칸은 `## 📸 화면 확인` 하나만 체크리스트 아래에 더한다. 그 밖의 칸은 새로 만들지 않는다.
템플릿 파일 자체는 고치지 않는다. 백엔드와 같이 쓰는 파일이라 고치면 백엔드 PR에도 칸이 생긴다.

리뷰어는 위에서부터 "무엇이 바뀌었나 → 믿을 만한가 → 화면" 순서로 읽는다. 그래서 칸마다 한 가지만 담는다.

- 작업 내용: 사용자에게 보이는 변화
- 검증 결과: TC가 실패했다가 통과했는지
- 코드 이름과 원인 설명: 🛠️ Technical Concerns

```markdown
## 🔗 연관된 이슈

- close #123

## 📋 작업 내용

작가 프로필에 소개를 보여 줘요 (Android·iOS)

| 상황 | 전 | 후 |
|---|---|---|
| 소개가 있는 작가 프로필 | 소개 안 보임 | 이름 아래에 소개 |
| 소개가 3줄을 넘을 때 | 해당 없음 | 3줄에서 말줄임 |
| 소개 앞뒤 공백 | 그대로 저장 | 지우고 보여 줌 |

검증 결과

| TC | Android | iOS |
|---|---|---|
| 1 소개가 있으면 화면 상태에 담는다 | 실패 → 통과 | 실패 → 통과 |
| 2 소개가 비어 있으면 소개 없음 상태가 된다 | 처음부터 통과 | 처음부터 통과 |
| 추가: 소개 앞뒤 공백은 지운다 | 실패 → 통과 | 해당 없음 |
| 전체 검사 | 종료 코드 0 | 종료 코드 0 |

- 처음부터 통과: 기존 동작을 지키는 TC
- 확인 못 한 것: iOS 3줄 말줄임은 시뮬레이터가 막혀 못 봤어요

<details><summary>실패 메시지</summary>

- TC 1 Android: `expected:<필름으로 찍어요> but was:<null>`
- TC 1 iOS: `Expectation failed: state.bio nil == "필름으로 찍어요"`
- 추가 Android: `expected:<필름> but was:< 필름 >`

</details>

남긴 기록
- ADR: 소개 말줄임 기준 (client/android/docs/architecture/profile-bio-ellipsis.md)

백엔드 전달 필요
- 소개 글자 수 제한 확인 요청

## ✅ 변경 사항 체크리스트

- [x] PR 대상 브랜치가 `develop`인가요? (client/develop)
- [x] Linear 동기화 여부를 확인했나요?

## 📸 화면 확인

(화면 확인 자료 형식대로)

## 📎 참고 자료

## 🛠️ Technical Concerns

- 소개는 `ProfileUiState.bio`에 담고, 비어 있으면 `null`로 바꿔 화면이 한 가지 조건만 봐요.
```

## 칸마다

- **작업 내용**
  - 첫 줄은 무엇을 바꿨는지 한 문장과 플랫폼.
  - 그 아래 전/후 표. 한 줄이 사용자가 겪는 상황 하나다. 칸에는 짧은 구절만 쓴다.
  - 코드 이름(`showMonth` 등), 원인, 구현 방법은 쓰지 않는다. 🛠️ Technical Concerns에 쓴다.
  - 화면 동작이 바뀌지 않는 작업(리팩터링 등)은 표 대신 목록 1–3줄.
- **검증 결과**
  - 표 한 개. `$EVID/evidence.md`에서 옮긴다. TC 제목은 계획과 같게 쓰고, 계획 TC를 따로 체크박스로 다시 적지 않는다.
  - 플랫폼 칸에는 다음 넷 중 하나만 쓴다: `실패 → 통과`, `처음부터 통과`(Red 없이 통과), `크래시 → 통과`, `해당 없음`.
  - 한 플랫폼만 바꿨으면 그 플랫폼 열만 둔다.
  - 마지막 줄은 전체 검사 종료 코드다. 명령은 공통 약속에 있으니 다시 적지 않는다.
  - 표 아래에는 필요한 줄만 둔다.
    - `처음부터 통과`가 있으면 그 뜻 한 줄.
    - 계획이 바뀐 TC가 있으면 `TC 4는 계획이 바뀌었어요: <무엇을 무엇으로, 왜>` 한 줄.
    - 확인 못 한 것(TC든 화면 확인 항목이든).
  - 실패 메시지는 `<details>`에 넣는다. `실패 → 통과`, `크래시 → 통과`마다 `TC 번호 플랫폼: 메시지` 한 줄이다.
  - TC가 없으면 표 대신 `유닛 TC 없음 (모양 수정)`.
  - 화면 확인 항목은 여기 적지 않는다. 📸 칸에 있다.
- **남긴 기록**: `client-record`가 남긴 것. 없으면 줄을 지운다.
- **백엔드 전달 필요**: `$EVID/backend-note.md`가 있을 때만.
- **📸 화면 확인**: [화면 확인 자료](screen-evidence.md)를 본다. 화면 코드가 바뀌지 않았으면 `없음 (화면 코드 변경 없음)`.
- **Linear 체크**: 항상 체크한다. Linear 동기화는 자동으로 된다.
- **🛠️ Technical Concerns**: 구현 방법, 원인, 이번 변경과 무관하게 발견한 것(깨지는 테스트 등). 한 줄에 하나.
- **`~` 쓰지 않기**: GitHub은 한 줄에 `~`가 두 개 있으면 그 사이를 취소선으로 그린다(`②~⑨ … 1~8월` → `⑨ … 1` 취소선). 범위는 `1–8월`, `②–⑨`처럼 `–`로 쓴다. push 확인 전에 남은 `~`를 찾아 고친다.
  ```bash
  grep -n '~' "$EVID/pr.md"   # 코드 블록 밖에 나오면 고친다
  ```
