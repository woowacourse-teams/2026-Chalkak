# client-record

먼저 [공통 약속](../client-flow/references/conventions.md)을 읽는다.
파일만 쓴다. 커밋은 `client-pr`이 한다. 사람이 따로 고르지 않고 push 확인에서 코드와 같이 본다.

## 무엇을 남기나

이번 작업에서 **다음 사람이 모르면 같은 고민을 다시 할 것**만 남긴다. 0~2개이고, `없음`도 정상이다.
기록은 다음 작업에서 저절로 읽히는 자리에 둔다. 링크만 걸어 두면 읽히지 않는다.

| 종류 | 언제 | 어디에 | 어떻게 읽히나 |
|---|---|---|---|
| ADR | 선택지가 여럿이었고 이유가 있는 구조 결정(예: 삭제 결과를 일회성 이벤트 대신 UiState로) | `client/<플랫폼>/docs/architecture/<영어-이름>.md` | `client-plan`이 바꿀 파일과 `관련 경로`를 맞춰 볼 때 |
| 함정 기록 | 플랫폼·라이브러리의 의외 동작(예: 공유 요소 전환이 끝나면 clip이 풀림) | 그 동작을 다루는 코드 바로 옆 **주석** | 그 코드를 고치는 사람이 읽을 때 |

- ADR은 [ADR 형식](references/adr-template.md)을 따르고 `관련 경로:` 줄을 꼭 넣는다. 없으면 `related-adr.py`가 찾지 못한다.
- 함정 주석에는 무엇이 의외인지, 그래서 코드가 왜 이렇게 생겼는지, 근거 이슈 번호를 쓴다.
  ```kotlin
  // 공유 요소 전환이 끝나면 clip이 풀려서 여기서 다시 건다.
  // 근거: 이슈 #123
  ```

## 남기지 않는 것

- 서비스 정책: `business-rules`는 읽기 전용이다. 정책이 없거나 서버와 다르면 **백엔드에 전달할 문구**만 써서 `$EVID/backend-note.md`에 둔다. `client-pr`이 PR 본문에 옮긴다.
  문구 형식: `현재 규칙 ID·내용 → 문제와 이유 → 원하는 변경 → 클라이언트 영향`
- 커밋 메시지·PR 본문에 이미 있는 작업 내역, 코드만 읽어도 알 수 있는 것
- 화면까지 가는 길·재현 조건: 지금은 다른 작업용으로 남기지 않는다. 같은 상태를 다시 찾느라 헤맨 일이 생기면 그때 자리를 정한다.

## 다시 들어올 때

push 확인이나 리뷰에서 고친 뒤 다시 부르면, 고친 내용 때문에 **바뀐 결정만** 반영한다. 이미 남긴 기록과 어긋나면 그 기록을 고친다.

## 알릴 것

남긴 기록마다 `종류 · 제목 · 파일 경로` 한 줄, 또는 `남길 기록 없음`과 이유 한 줄.
