01

FCM은 메시지를 기기로 전달하는 서비스

FCM(Firebase Cloud Messaging)은 서버가 앱에 메시지를 보내는 통로입니다. 서버는 “누구에게 무엇을 보낼지”를 정하고, FCM은 전달을 맡으며, Android SDK·앱·운영체제가 수신과 화면 표시를 처리합니다.

→
2FCM 백엔드
요청 접수·전달 처리
→
3Android 전송 계층
Google Play services
→
4기기의 FCM SDK
수신·앱 상태별 처리

서버가 하는 일

신뢰할 수 있는 서버에서 Admin SDK 또는 HTTP v1 API로 발송합니다. 서버 인증 자격증명을 Android 앱에 넣지 않습니다. 승인·반려 같은 업무 판단과 계정별 발송 대상은 서버의 책임입니다.

Android 앱이 하는 일

FCM 토큰을 받아 서버에 등록하고, 메시지를 수신합니다. 앱이 직접 알림을 만들거나 Firebase SDK가 표시한 알림의 클릭 Intent를 처리합니다.

FCM 메시지와 시스템 알림은 구분하기메시지는 전달되는 데이터이고, 시스템 알림은 알림창에 보이는 UI입니다. 데이터만 받고 UI를 만들지 않을 수도 있습니다. 찰칵 알림함의 기록은 서버 API로 조회하므로 시스템 알림과 수명이 다릅니다.

02

FCM 토큰은 사용자 ID가 아니다

등록 토큰은 메시지를 받을 앱 인스턴스를 식별하는 값입니다. 로그인 인증용 Access Token, 서버의 notificationId, 게시물 sourceId와 역할이 다릅니다.

2로그인 계정과 함께 서버 등록
→
3서버가 토큰 대상으로 발송

  • 토큰은 영구적인 기기 ID가 아닙니다. 재설치·앱 데이터 삭제·복원 등의 상황에서 바뀔 수 있어 onNewToken()을 처리해야 합니다.
  • 서버는 토큰의 최신 상태를 관리하고 만료·무효 응답에 맞춰 정리해야 합니다.
  • 로그아웃은 서비스의 계정 연결 해제 문제입니다. FCM 토큰을 가졌다는 사실만으로 해당 사용자의 데이터 접근이 허용되지는 않습니다.
찰칵의 연결앱 초기화의 세션 변화, onNewToken, MainActivity onResume에서 현재 로그인 기기 등록을 시도합니다. 읽음·게시물 조회는 별도의 인증된 API로 확인합니다.

구성의미사용 목적

HTTP v1 요청 본문 구조를 설명하는 예시입니다. 인증 헤더·실제 토큰·플랫폼 옵션은 생략했습니다.

04

앱 상태에 따라 수신 경로가 달라진다

메시지포그라운드백그라운드
notificationonMessageReceived 호출. 표시를 앱이 결정SDK가 시스템 알림 표시
dataonMessageReceived 호출onMessageReceived 처리 경로. 전달 시점은 절전·우선순위 등의 영향
notification + dataonMessageReceived에서 두 정보를 받음SDK가 알림 표시. 클릭하면 data가 런처 Activity의 Intent extras로 전달

찰칵이 직접 만드는 경로

ChalkakFirebaseMessagingService → PushNotificationManager.show → 앱이 만든 PendingIntent로 클릭 처리.

SDK가 만드는 경로

백그라운드의 notification + data → SDK가 표시 → 클릭 Intent를 MainActivity에서 파싱. Manifest의 기본 아이콘·색상·채널 설정도 사용합니다.

“클릭할 때 onMessageReceived가 실행된다”로 이해하면 틀립니다백그라운드의 혼합 메시지는 수신 때 SDK가 알림을 만들고, 클릭 때 Activity가 extras를 받습니다. 앱이 직접 만드는 PendingIntent의 flags를 SDK 경로에도 동일하게 적용됐다고 가정하면 안 됩니다.

수신 콜백은 긴 네트워크 작업을 계속 실행하는 공간으로 삼지 않습니다. 오래 걸리는 후속 작업은 작업 목적에 맞는 백그라운드 실행 수단을 검토합니다. 최근 앱 목록에서 제거, OS의 프로세스 종료, 설정에서 강제 종료는 서로 다른 상태입니다.

알림 카드 자체가 Compose 화면을 여는 것은 아닙니다. 알림에 붙인 contentIntent를 운영체제가 실행하고, Activity가 받은 데이터를 앱의 화면 이동 로직에 넘깁니다.

// 현재 PushNotificationManager의 핵심 구조를 축약
val openAppIntent = Intent(context, MainActivity::class.java).apply {
    flags = Intent.FLAG_ACTIVITY_CLEAR_TOP or Intent.FLAG_ACTIVITY_SINGLE_TOP
    data = Uri.parse("chalkak://notification/$stableKey")
    putExtra(NOTIFICATION_ID_KEY, payload.notificationId)
    // 실제 코드는 type, sourceId 등의 extras도 넣음
}
val contentIntent = PendingIntent.getActivity(
    context,
    stableKey.hashCode(),
    openAppIntent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE,
)
val notification = NotificationCompat.Builder(context, CHANNEL_ID)
    // 아이콘·제목·본문 설정 생략
    .setContentIntent(contentIntent)
    .setAutoCancel(true)
    .build()
setAutoCancel(true)는 서버 읽음 처리가 아닙니다클릭 후 시스템 알림을 사라지게 하는 설정입니다. 서버 읽음 API 호출은 이후 앱 코드가 수행합니다. 알림창에서 스와이프로 지워도 현재 찰칵의 서버 읽음 처리는 실행되지 않습니다.

07

Intent는 실행 요청과 데이터를 담는 객체

필드역할현재 찰칵 예시
component실행할 컴포넌트. 지정하면 명시적 IntentMainActivity::class.java
action무슨 동작을 요청하는지앱 생성 검수 클릭 Intent에는 별도 action 설정 없음
dataURI 형태의 대상 정보. Intent 식별에도 사용chalkak://notification/{stableKey}
extras추가 키·값 데이터type·notificationId·sourceId 등
flagsActivity 실행 시 스택 처리 요청CLEAR_TOP | SINGLE_TOP

명시적 Intent는 실행할 Activity를 직접 지정합니다. 암시적 Intent는 action·URI 등에 맞는 컴포넌트를 시스템이 찾습니다.

URI를 넣었다고 외부 딥링크가 완성되는 것은 아닙니다현재 코드는 MainActivity를 직접 지정하고 URI를 PendingIntent 식별에 사용합니다. Manifest에 해당 chalkak:// 알림용 intent-filter는 없습니다. 실제 목적지 분기는 extras의 type·ID로 수행합니다.

extras에 ID가 있다고 접근 권한이 생기는 것은 아닙니다. 입력 값의 누락·알 수 없는 종류를 처리하고, 데이터 접근은 인증된 서버 API가 검증해야 합니다.

08

PendingIntent: 나중에 실행할 권한을 OS에 맡기기

Intent가 “무엇을 실행할지”라면 PendingIntent는 다른 실행 주체가 나중에 그 요청을 만든 앱의 권한으로 실행할 수 있게 하는 시스템 토큰입니다. 알림창의 클릭을 맡는 시스템에 넘겨 주는 이유입니다.

시스템이 토큰을 유지하므로 생성한 앱 프로세스가 종료되어도 실행할 수 있습니다. Activity 실행 시 새 프로세스가 필요하면 시스템이 시작할 수 있습니다. 앱 메모리의 함수·코루틴을 저장한 객체로 이해하면 안 됩니다.

API / flag의미
getActivityActivity 실행용. 알림 카드 클릭에 사용
getBroadcastBroadcastReceiver 호출용. 로컬 예약 알람에 사용
FLAG_UPDATE_CURRENT같은 PendingIntent가 있으면 extras를 새 값으로 갱신
FLAG_IMMUTABLE받은 쪽이 실행 시 Intent를 수정하지 못하게 제한. 만든 앱의 UPDATE_CURRENT 갱신은 가능
extras만 다르게 넣으면 별개 PendingIntent가 되지 않습니다실행 종류·requestCode·Intent의 component/action/data 등 식별 요소를 고려합니다. extras는 동일성 비교 대상이 아닙니다. A와 B의 식별 요소가 같고 UPDATE_CURRENT를 쓰면 A 알림을 눌러도 나중에 넣은 B 데이터가 전달될 수 있습니다.

찰칵은 requestCode = stableKey.hashCode()와 ID별 data URI를 사용합니다. 다만 notify(id, notification)의 표시 ID도 해시이므로 해시 충돌 시 시스템 알림이 교체될 가능성은 남습니다. PendingIntent 식별과 표시 알림 ID는 별도 체계입니다.

09

onCreate와 onNewIntent: 새 실행과 재사용

새 Activity 인스턴스는 onCreate에서 시작 Intent를 받습니다. 재사용되는 Activity는 onNewIntent에서 새 요청을 받습니다. 따라서 onCreate만 처리하면 이미 앱이 열린 상태의 알림 클릭을 놓칠 수 있습니다.

// 현재 MainActivity의 알림 관련 코드만 축약
// enqueueNotificationNavigation은 payload를 공용 Store에 넣는 함수
// 이 예시는 클래스 전체가 아님
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    enqueueNotificationNavigation(intent)
    // 이후 setContent로 Compose UI 생성
}

override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent)
    enqueueNotificationNavigation(intent)
}
setIntent(intent)가 필요한 이유onNewIntent의 인자는 새 요청이지만, Activity의 getIntent() / Kotlin intent 프로퍼티는 자동으로 새 값으로 바뀌지 않습니다. setIntent로 이후 조회할 Intent를 갱신합니다.

onResume은 설정 화면 복귀 등에서도 호출되므로 “푸시를 클릭했다”는 신호로 삼으면 안 됩니다. 현재 찰칵은 여기서 기기 등록을 동기화하고, 클릭 데이터는 onCreate·onNewIntent에서 받습니다.

화면 회전·Activity 재생성에서도 onCreate가 다시 호출될 수 있습니다. 시작 Intent를 다시 읽는 구조라면 이미 처리한 사건의 재실행 여부를 확인해야 합니다. 현재 메모리 Store의 consume만으로 재생성·프로세스 복원까지 한 번만 처리를 보장한다고 볼 수 없습니다.

10

flags와 launchMode는 Activity 스택을 제어한다

SINGLE_TOP은 대상 Activity가 스택 맨 위에 있을 때 새 인스턴스 대신 기존 인스턴스에 전달합니다. CLEAR_TOP은 같은 task의 기존 대상 위에 쌓인 Activity들을 제거합니다. 현재 Manifest도 MainActivity에 launchMode="singleTop"을 설정합니다.

두 설정을 함께 쓰는 이유현재 앱 생성 경로의 CLEAR_TOP | SINGLE_TOP 조합은 기존 MainActivity를 앞으로 가져와 onNewIntent로 전달할 수 있게 합니다. CLEAR_TOP만 보고 무조건 인스턴스를 재사용한다고 판단하면 안 됩니다. launchMode·flags 조합에 따라 재생성될 수 있습니다.

상태를 바꿔 콜백 확인하기

같은 task에서 앱이 직접 만든 검수 알림의 flags를 적용하는 단순화 예시입니다. SDK 생성 알림·다중 task·복원 상황의 모든 동작을 재현하지 않습니다.

상황현재 앱 생성 Intent의 기본 흐름
기존 인스턴스가 없음MainActivity 생성 → onCreate
기존 MainActivity가 top인스턴스 재사용 → onNewIntent
같은 task에서 MainActivity 위에 Activity 존재위 Activity 제거 → MainActivity에 onNewIntent

Compose의 Settings·Feed 화면은 각각 Activity가 아닙니다.이 flags만으로 Compose 화면 스택이 Today로 바뀌지 않습니다. 화면 이동과 뒤로가기 이력은 NavController에서 별도로 제어합니다.

Compose 본문에서 매 재구성마다 navigate·Toast를 직접 실행하면 부작용이 반복될 수 있습니다. LaunchedEffect의 key와 소비 시점을 설계합니다. effect는 key 변화·화면 제거 등에 따라 취소될 수 있으므로 재시도·중복 처리를 검토해야 합니다.

서버가 404를 반환하면 화면 이동을 중단할 수 있습니다. 현재 목록 클릭의 404는 “삭제된 게시물입니다” 토스트 후 목록·미읽음 상태를 갱신합니다. 실제 404 원인은 삭제 외에 만료·다른 계정일 수도 있습니다.

UI 이벤트 소비

ViewModel은 pendingMessage 상태를 만들고 Route의 UiMessageEffect가 RESUMED 상태에서 토스트를 표시한 뒤 ID로 소비합니다. 일반 재구성마다 동일한 토스트를 반복하는 일을 줄입니다.

OS 푸시의 404는 현재 별도 문구 “알림이 만료되었거나 현재 계정에서 확인할 수 없어요.”를 표시하고 알림 목록으로 이동합니다. 푸시 도착·시스템 dismiss와 서버 읽음 상태는 연결돼 있지 않습니다.
