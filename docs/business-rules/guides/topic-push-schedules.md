# 관리자 주제 푸시 설정 연동 안내

## 현재 제공 범위

#493에서 설정 생성·조회·수정·삭제 API를 구현했다. 실제 배포와 관리자 클라이언트 연동은 아직 확인하지 않았다. #572의 변경에 정시 발행과 앱의 주제 푸시 메시지 계약을 포함한다. 실제 개발 서버 발행은 아직 검증하지 않았다.

## 변경 이력

설정 생성·시각 수정·삭제는 관리자 ID, 행위, 설정 ID, 변경 전후 KST 발송 시각(`sendTime`), 처리 시각과 요청 식별자를 기존 관리자 감사 로그에 기록한다. 별도 변경·삭제 사유를 요청 본문에 추가하지 않는다. 같은 시각으로 다시 수정하면 변경 이력을 추가하지 않는다. 설정이 삭제돼도 감사 로그는 남으며, 감사 로그 저장이 실패하면 설정 변경도 롤백한다. 목록 조회는 변경 이력을 생성하지 않는다.

## 설정 생성

`POST /api/v1/admin/topic-push-schedules`

관리자 액세스 토큰을 `Authorization: Bearer <adminAccessToken>`으로 전달한다. 일반 회원 토큰은 사용할 수 없다.

```json
{
  "sendTime": "09:00:00"
}
```

- `sendTime`은 필수다. 생략 또는 null을 허용하지 않는다.
- `sendTime`은 날짜·시간대 없이 전달하는 KST 시각이다. 분 단위로 설정하며 JSON은 `HH:mm:ss` 형식으로 전달하되 초는 `00`이어야 한다. 초·소수 초가 있는 값은 반올림하지 않고 `400 BUSINESS_ERROR`로 거절한다. 허용 범위는 `00:00:00`부터 `23:59:00`까지다.
- 별도 `enabled` 필드는 없다. 등록된 시각은 발송 대상으로 사용하며, 발송 중단은 설정 삭제로 처리한다. 같은 시각은 하나만 등록할 수 있다.
- 요청은 설정만 저장한다. 주제를 생성하거나 즉시 푸시를 보내지 않는다.

성공은 `201`이며 저장된 설정을 반환한다. `createdAt`·`updatedAt`은 UTC Instant, `sendTime`은 KST의 반복 발송 시각이다.

```json
{
  "scheduleId": "019a0000-0000-7000-8000-000000000493",
  "sendTime": "09:00:00",
  "createdAt": "2026-10-08T12:00:00Z",
  "updatedAt": "2026-10-08T12:00:00Z"
}
```

| 상태 | 오류 코드 | 의미 |
| --- | --- | --- |
| 400 | BUSINESS_ERROR | 필수 값 누락, 잘못된 시각, 중복 시각 |
| 401 | UNAUTHORIZED | 관리자 액세스 토큰이 없거나 유효하지 않음 |
| 403 | FORBIDDEN | 관리자 권한 없음 |

## 설정 목록 조회

`GET /api/v1/admin/topic-push-schedules`

관리자 액세스 토큰을 전달한다. 요청 본문·조회 파라미터·페이징은 없다. 등록된 모든 설정을 `sendTime` 오름차순으로 반환한다.

성공은 `200`이며 목록 항목의 필드는 생성 응답과 같다. `sendTime`은 KST 발송 시각, `createdAt`·`updatedAt`은 UTC Instant다.

```json
{
  "schedules": [
    {
      "scheduleId": "019a0000-0000-7000-8000-000000000493",
      "sendTime": "09:00:00",
      "createdAt": "2026-10-08T12:00:00Z",
      "updatedAt": "2026-10-08T12:00:00Z"
    }
  ]
}
```

등록된 설정이 없으면 `200`과 `{"schedules":[]}`를 반환한다. 인증 오류는 `401 UNAUTHORIZED`, 일반 회원의 접근은 `403 FORBIDDEN`이다.

## 설정 수정

`PUT /api/v1/admin/topic-push-schedules/{scheduleId}`

관리자 액세스 토큰과 수정할 설정의 UUID를 전달한다. 본문은 생성 요청과 동일하다.

```json
{
  "sendTime": "18:30:00"
}
```

- `sendTime`은 필수이며 생성과 동일한 KST 분 단위 검증을 적용한다.
- 다른 설정과 중복되는 시각으로 변경할 수 없다. 같은 설정의 기존 시각을 다시 보내는 요청은 허용하며 저장 시각도 유지한다.
- 성공은 `200`이며 생성과 같은 응답 필드를 반환한다. `scheduleId`·`createdAt`은 유지하고 변경된 `sendTime`·`updatedAt`을 반환한다.
- 이 요청은 설정만 변경한다. 실제 발송은 아래 적용 정책을 따르며 #572의 정시 실행 변경을 배포하고 활성화해야 제공된다.

| 상태 | 오류 코드 | 의미 |
| --- | --- | --- |
| 400 | BUSINESS_ERROR | 잘못된 UUID, 필수 값 누락, 잘못된 시각, 다른 설정과 중복 |
| 401 | UNAUTHORIZED | 관리자 액세스 토큰이 없거나 유효하지 않음 |
| 403 | FORBIDDEN | 관리자 권한 없음 |
| 404 | BUSINESS_ERROR | 해당 설정이 없음 |

## 설정 삭제

`DELETE /api/v1/admin/topic-push-schedules/{scheduleId}`

관리자 액세스 토큰과 삭제할 설정의 UUID를 전달한다. 요청 본문은 없다.

- 성공은 본문 없는 `204`다. 설정 행을 실제로 삭제하고 다른 설정은 유지한다.
- 삭제한 시각을 이후 생성 API로 다시 등록할 수 있다. 새 식별자가 부여된다.
- 없는 설정 또는 이미 삭제한 설정에 대한 요청은 `404 BUSINESS_ERROR`다.
- 해당 설정의 향후 정시 실행 대상에서 제외한다. 이미 SQS에 발행한 작업은 삭제 요청으로 취소하지 않는다. 실제 정시 실행·발행은 #572 변경의 배포·활성화 이후 적용된다.

| 상태 | 오류 코드 | 의미 |
| --- | --- | --- |
| 400 | BUSINESS_ERROR | 잘못된 UUID |
| 401 | UNAUTHORIZED | 관리자 액세스 토큰이 없거나 유효하지 않음 |
| 403 | FORBIDDEN | 관리자 권한 없음 |
| 404 | BUSINESS_ERROR | 해당 설정이 없음 |

## 합의한 설정 적용 정책

아래는 설정 API와 #572의 정시 실행이 함께 따르는 기준이다. 설정 API 구현만으로 정시 발송이 제공되는 것은 아니다.

- 생성·시각 수정은 변경 이후 도래하는 KST 시각부터 적용한다. 지난 시각은 소급 실행하지 않는다.
- 설정 삭제는 아직 실행 전인 발송부터 취소한다.
- 이미 SQS에 발행한 작업은 설정 변경·삭제만으로 취소하지 않는다. 원래 예정 시각부터 30분 기한과 최신 조건에 따라 계속 처리한다.
- 계정 단위 `topicPushEnabled`와 `moderationPushEnabled`는 별개의 설정이다. 관리자 설정은 주제 푸시의 시각을 정하며 회원의 수신 설정을 변경하지 않는다.


## 정시 발행과 운영 확인

- 주제 전용 스케줄러가 KST 매분 정각에 관리자 설정과 실행할 회차를 확인한다. 발행 처리가 길어지거나 서버가 중단되면 확인이 늦어질 수 있으며, 실제 기기 도착을 정각에 보장하지 않는다. 승인·반려 Relay의 처리 완료 후 1초 조회와 실패 후 1분 대기는 별도 설정이다.
- 정시 실행은 원래 예정 시각부터 30분 안에서 현재 설정을 확인해 실행한다. 예를 들어 09:00 회차를 09:03에 시작해도 만료는 09:30이다. 새로 등록한 09:00 설정의 변경 시각이 09:00 이후라면 오늘 소급 실행하지 않는다.
- 주제가 없거나 대상이 없으면 그 회차를 생략한다. 대상 회원은 정상·주제 수신 설정 기준이며, 발행 대상 주제에 삭제되지 않은 `VALIDATING`·`PENDING`·`APPROVED` 게시물이 있으면 제외한다. 반려·삭제된 게시물만 있거나 다른 주제에만 제출했다면 포함한다. 검수 수신 설정은 무관하다. 기기·로그인·오늘 주제의 참여 상태는 Worker가 최신 상태로 확인한다. 큐 등록 이후 제출해 처리 중·승인 대기·승인 상태가 되었다면 실제 요청 직전에 발송을 생략하고 재시도 없이 완료한다.
- 주제는 사용자별 SQS 직접 발행이며 알림함·Relay·Outbox를 사용하지 않는다. 같은 프로세스에서 최종 실패를 재발행하지 않으며 재시작 중 중복·중단 중 누락 가능성이 남는다.
- `NOTIFICATION_TOPIC_PUSH_ENABLED`가 정시 주제 발행을 켜고 끈다. 기본값은 꺼짐이며 `NOTIFICATION_RELAY_ENABLED`와 독립적이다. 큐·권한·Worker·Firebase가 준비된 환경에서 활성화한다. 기존 `NOTIFICATION_SQS_QUEUE_URL`과 AWS 리전을 사용한다.
- 실행 로그는 `topic_publication_summary` 단계에서 설정·사건 ID, 예정·만료 시각과 `targetCount`, `acceptedCount`, `failedCount`, `unknownCount`, `expiredCount`를 확인한다. 수락 건수는 SQS 수락이며 기기 수신이 아니다. 사용자별 발행 결과는 `topic_publication_result`, 예기치 않은 결과 불명은 `topic_publication_unknown`에 남는다.
- 실제 개발 서버에서 미래의 설정 시각을 등록한 뒤 주제 발행 로그 → SQS/Worker 로그 → `fcm_result`의 수락 → 실기기 수신을 각각 확인한다. 코드·로컬 테스트 통과와 서버 배포·실기기 수신은 별도다. 운영 서버 전체 발송을 테스트로 실행하지 않는다.

현재 규칙은 NOTIFICATION-009·010·011이며, 앱의 표시·클릭 처리는 [푸시 메시지 계약](notification-push-contract.md)을 참고한다.
