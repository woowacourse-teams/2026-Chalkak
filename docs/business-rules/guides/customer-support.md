# 고객센터 문의 접수·내 문의 조회·삭제 연동 안내

로그인한 사용자가 문의를 보내고 본인의 문의 목록·상세를 조회하거나 삭제하는 흐름이다. 정책은 [FEEDBACK-001~003](../rules/feedback.md), 회원 상태는 [회원 규칙](../rules/user.md)을 따른다. 접수·본인 조회·삭제의 기본 계약은 [#903](https://github.com/woowacourse-teams/2026-Chalkak/issues/903)·[PR #911](https://github.com/woowacourse-teams/2026-Chalkak/pull/911)에서 제공한다. 관리자 삭제로 문의가 숨겨지는 범위는 [#921](https://github.com/woowacourse-teams/2026-Chalkak/issues/921)에서 추가한다. 문서 갱신이 서버 배포 완료를 뜻하지는 않는다.

목록은 문의 식별자·문의 내용·접수 시각을 제공한다. 상세에서는 현재 답변의 내용과 등록 시각을 함께 확인할 수 있다.

## 화면 연결 순서

1. 고객센터 진입 시 로그인 상태를 확인하고 본인 문의 첫 페이지를 조회한다. 이용 정지 회원도 접수·조회·삭제가 가능하므로 고객센터 접근을 정지 상태만으로 막지 않는다.
2. 새 문의 작성 후 제출 API를 호출한다. `201`이면 반환된 `feedbackId`를 보관하고, 목록을 첫 페이지부터 다시 조회하거나 해당 문의 상세를 연다.
3. 목록 항목을 선택하면 그 항목의 `feedbackId`로 상세를 조회한다. 목록용 요약은 앱에서 표시 길이를 조절할 수 있으며, API는 원문을 반환한다.
4. 상세에서 본인 문의를 삭제해 `204`를 받으면 해당 항목·상세 캐시를 제거하고 목록을 새로 조회한다.
5. 상세·삭제에서 `404`이면 더 이상 이용할 수 있는 문의가 없다는 안내 후 목록을 갱신한다. 타인·삭제·없는 문의를 구분해 안내하지 않는다.

모든 요청에 회원 액세스 토큰을 전달한다. 사용자 ID는 요청으로 받지 않고 서버가 인증 정보에서 결정한다.

```http
Authorization: Bearer {accessToken}
```

| 요청 | 성공 응답 | 용도 |
| --- | --- | --- |
| `POST /api/v1/feedbacks` | `201`, 문의 ID·접수 시각 | 새 문의 등록 |
| `GET /api/v1/feedbacks?page=1&pageSize=20` | `200`, 본인 문의 목록·페이지 정보 | 내 문의 목록 |
| `GET /api/v1/feedbacks/{feedbackId}` | `200`, 선택한 본인 문의 | 문의 상세 |
| `DELETE /api/v1/feedbacks/{feedbackId}` | `204`, 본문 없음 | 문의 삭제 |

`feedbackId`는 문의 UUID이며 회원 ID가 아니다. 경로에는 축약하지 않은 UUID를 사용한다. 회원용 화면에서 관리자 API를 호출하지 않는다.

## 새 문의 등록

```http
POST /api/v1/feedbacks
Authorization: Bearer {accessToken}
Content-Type: application/json
```

```json
{
  "content": "사진 업로드 후 화면이 멈춰요."
}
```

- 본문은 `content` 한 필드다. 서버가 앞뒤 공백을 제거한 결과로 1~1,000자를 검증하고 저장한다. 공백뿐인 내용은 거절한다.
- 글자 수는 Unicode code point 기준이다. 이모지 같은 보조 평면 문자는 UTF-16의 `length`와 계산이 다를 수 있으므로 앱의 입력 제한도 이 기준에 맞춘다. 최종 검증은 서버가 수행한다.
- 첨부·유형·연락처·답변 요청 여부는 받지 않는다. 등록 후 문의 내용 수정 API도 없다.

성공 응답은 기존 피드백 제출 계약과 같다.

```json
{
  "feedbackId": "0198f6c1-62ba-7d30-8b12-0f733b6570d4",
  "createdAt": "2026-11-03T06:00:00Z"
}
```

제출 중 버튼 중복 입력을 막고, 실패했다는 이유만으로 POST를 자동 반복하지 않는다. 타임아웃은 서버에 저장됐는지 알 수 없는 상태다. 이 API에는 요청 중복을 식별하는 키가 없으므로, 목록을 확인한 뒤 사용자에게 재시도를 안내한다.

### 접수 제한 안내

정상·정지 회원 모두 **1분에 1건, 최근 24시간 최대 5건**이다. 자정에 초기화되는 일일 제한이 아니다. 성공적으로 저장한 문의만 집계하고, 문의를 삭제해도 제한 시간 동안은 접수 횟수에 포함한다.

최근 문의에서 정확히 1분이 지나면 간격 제한이 풀린다. 최근 다섯 번째 문의가 정확히 24시간을 지나 조회 범위에서 빠지면 건수 제한이 풀린다. 두 제한이 겹치면 모두 해제되는 더 늦은 시각까지 기다려야 한다.

초과 응답 예시는 다음과 같다. HTTP 상태는 `429`가 아닌 기존 `400`이다.

```json
{
  "errorCode": "BUSINESS_ERROR",
  "message": "문의는 1분에 1건, 최근 24시간에 최대 5건 접수할 수 있습니다. 다음 접수 가능 시각(UTC): 2026-11-03T06:01:00Z"
}
```

다음 접수 가능 시각은 현재 별도 JSON 필드가 아닌 `message`에 포함된다. 소수 초가 있으면 다음 초로 올려 표시하고, 정확한 초 단위 시각은 그대로 표시한다. 실제 제한 판정은 원래 접수 시각 기준이므로 이 표시 때문에 제한 시간이 늘어나지는 않는다. 입력 오류도 같은 `BUSINESS_ERROR`를 사용하므로 코드만 보고 모두 횟수 초과로 처리하지 않는다. 앱은 응답 메시지로 안내하고, UTC 시각의 표시는 기존 앱 시간 표시 방식을 따른다.

접수 제한의 5건은 새 문의를 보낼 수 있는 횟수이며, 내 문의 목록을 5개만 보여준다는 뜻은 아니다.

## 내 문의 목록과 이어보기

```http
GET /api/v1/feedbacks?page=1&pageSize=1
Authorization: Bearer {accessToken}
```

아래는 예시 요청처럼 `pageSize=1`로 조회한 응답이다.

```json
{
  "currentPage": 1,
  "pageSize": 1,
  "hasNext": false,
  "feedbacks": [
    {
      "feedbackId": "0198f6c1-62ba-7d30-8b12-0f733b6570d4",
      "content": "사진 업로드 후 화면이 멈춰요.",
      "createdAt": "2026-11-03T06:00:00Z"
    }
  ]
}
```

- `page`는 1부터 시작하고 생략하면 1이다. `pageSize`는 생략하면 20이며 1~100을 허용한다.
- 접수 시각·문의 식별자 내림차순으로 정렬한다. 사용자별로 분리된 목록이며 삭제된 문의는 제외한다. 접수 제한과 달리 목록에는 최근 24시간이라는 조회 제한이 없다.
- 항목에는 문의 ID·문의 원문·접수 시각만 있다. 현재 답변 여부·답변 내용 필드는 없다.
- `hasNext=true`이면 같은 `pageSize`로 `currentPage + 1`을 요청한다. `false`이거나 범위 밖 빈 페이지면 이어보기를 끝낸다.
- 첫 페이지의 `feedbacks: []`는 문의가 없다는 뜻이므로 빈 화면 안내를 보여준다. 정상 빈 목록은 `404`가 아닌 `200`이다.
- 새 문의 등록·삭제·새로고침 후에는 첫 페이지부터 목록을 다시 구성한다. 페이지 번호 방식이라 중간에 문의가 추가·삭제되면 페이지 경계가 이동할 수 있다. 중복 표시 방지에는 `feedbackId`를 사용할 수 있지만 전체 목록의 스냅샷은 보장하지 않는다.

## 문의 상세

```http
GET /api/v1/feedbacks/0198f6c1-62ba-7d30-8b12-0f733b6570d4
Authorization: Bearer {accessToken}
```

```json
{
  "feedbackId": "0198f6c1-62ba-7d30-8b12-0f733b6570d4",
  "content": "사진 업로드 후 화면이 멈춰요.",
  "createdAt": "2026-11-03T06:00:00Z",
  "answerContent": null,
  "answeredAt": null
}
```

`answerContent`는 답변 내용이고 `answeredAt`은 UTC 답변 등록 시각이다. 미답변이거나 관리자가 답변을 삭제했으면 두 필드 모두 null이다. 목록에서 보였더라도 상세를 열기 전에 사용자나 관리자가 삭제하면 `404`가 올 수 있다. 관리자 삭제도 사용자 목록·상세에서 숨겨지며, 앱의 기존 404 처리와 목록 갱신 흐름을 따른다. 다른 계정의 문의 ID를 알고 있어도 상세를 볼 수 없다. 접수 시각은 UTC `Instant`이며 서버가 KST 문자열로 변환하지 않는다.

## 문의 삭제

```http
DELETE /api/v1/feedbacks/0198f6c1-62ba-7d30-8b12-0f733b6570d4
Authorization: Bearer {accessToken}
```

성공은 본문 없는 `204`다. 빈 본문을 JSON으로 파싱하지 않는다. 이미 삭제된 본인 문의를 다시 삭제해도 `204`이며 서버는 최초 삭제 시각을 유지한다.

삭제 후 사용자 목록·상세에서는 제외하지만 원문은 관리자 참고용으로 보관한다. 사용자 복구 API는 없고, 정정할 내용은 새 문의로 접수한다. 새 문의에도 기존 접수 제한이 적용된다.

## 공통 오류 처리

| 응답 | 의미와 앱 처리 |
| --- | --- |
| `400 / BUSINESS_ERROR` | 내용·페이지·UUID 입력 오류 또는 접수 제한. 요청을 확인하고 `message`로 안내한다. |
| `401` | 유효하지 않은 회원 인증 또는 탈퇴 회원. 기존 토큰 갱신·로그인 공통 처리를 따른다. 정지 회원이라는 이유로 고객센터를 막는 응답은 아니다. |
| `403` | 회원 API에 접근할 수 없는 권한 등 인증·인가 공통 오류다. 관리자 토큰을 회원 토큰 대신 사용하지 않는다. |
| `404 / BUSINESS_ERROR` | 상세의 타인·삭제·없는 문의, 삭제의 타인·없는 문의. 같은 `문의를 찾을 수 없습니다.` 안내이며 원인을 추측해 구분하지 않는다. 목록을 갱신한다. |

제출 실패가 명확한 `400`이면 새 문의는 저장되지 않는다. 네트워크 실패·타임아웃은 저장 여부를 단정하지 않는다. 상세·삭제의 문의 ID는 앱이 받은 `feedbackId`를 그대로 사용한다.

## 답변 알림에서 문의 상세 열기

알림함 목록과 푸시에서 `type=FEEDBACK_ANSWERED`, `sourceType=FEEDBACK`이면 `sourceId`를 문의 ID로 사용해 `GET /api/v1/feedbacks/{feedbackId}`를 호출한다. `notificationId`는 알림 읽음 처리에 사용한다. 답변 원문은 문의 상세 응답의 `answerContent`에서 읽는다.

문의가 삭제되면 서버가 관련 알림 행을 즉시 지운다. 질문·답변 원문은 관리자 조회에 보존된다. 이미 받은 푸시를 눌러 상세에서 404가 오면 문의를 더 이상 볼 수 없다고 안내하고 목록을 갱신한다. 알림이 30일 뒤 사라져도 문의 상세에서 답변을 확인할 수 있다.

## 관리자 웹의 답변 삭제와 재답변

관리자 상세의 `answerState`로 최초 답변(`UNANSWERED`), 현재 답변 있음(`ANSWERED`), 답변 삭제됨(`DELETED`)을 구분한다. 재답변의 푸시 발송 선택은 `DELETED`에서 표시한다.

관리자 상세의 `answerVersion` 문자열을 쿼리 파라미터로 그대로 전달해 `DELETE /api/v1/admin/feedbacks/{feedbackId}/answer`를 호출한다. 현재 답변이 없으면 이 값은 null이다. 화면에는 별도 `answeredAt`을 사용해 등록 시각을 표시한다. 204를 받으면 상세를 갱신하고, 400으로 거절되면 최신 상세를 조회해 삭제 대상을 다시 확인한다.

재답변은 기존 등록 경로 `POST /api/v1/admin/feedbacks/{feedbackId}/answer`에 `answerContent`를 전달한다. 푸시 발송을 선택한 경우에만 `sendPush: true`를 함께 보낸다. 생략하면 알림함에만 저장한다. 최초 답변은 항상 기존 푸시 조건을 따른다. 사용자가 예전 푸시로 문의 상세를 열면 그 시점의 현재 답변을 표시한다.

## 기존 피드백과 적용 상태

고객센터 도입 전 피드백은 사용자 내역에서 제외한다. 기준은 전환 마이그레이션의 DB 트랜잭션 시작 시각이며, 접수 시각이 그보다 이른 기록만 숨긴다. 기준과 같거나 이후의 문의는 배포 중 이전 앱에서 접수했더라도 신규로 남긴다. 기존 기록이 보이지 않는다고 앱에서 복원하거나 임의의 과거 ID로 다시 등록하지 않는다.

관리자가 답변만 삭제하면 알림함에서 해당 알림이 사라진다. 이전 푸시로 문의 상세를 열면 질문과 미답변 상태를 표시한다.

원본 문서 커밋, `be/develop` 병합, 공통 공유본 게시, 서버 배포와 Android 적용은 별개다. [PR #911](https://github.com/woowacourse-teams/2026-Chalkak/pull/911)의 병합·서버 릴리스 상태와 앱이 읽는 공통 문서 버전을 각각 확인한 뒤 연동한다.
