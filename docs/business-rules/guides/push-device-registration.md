# 앱의 푸시 기기 등록 처리

Android·iOS에서 기기 등록 API를 연결할 때 읽는 요청 순서와 오류 처리 안내다. 서비스 정책은 [NOTIFICATION-005](../rules/notification.md#notification-005-현재-로그인-기기-등록해제)를 따른다.

1. 로그인 후 FCM 토큰이 준비되면 `PUT /api/v1/push-devices/current`에 다음 본문을 보낸다. 회원·로그인 ID는 요청 본문에 넣지 않고 회원 액세스 토큰을 `Authorization: Bearer <accessToken>`으로 전달한다.

   ```json
   {"fcmToken": "<앱에서 받은 FCM 토큰>"}
   ```

2. 기존 로그인 사용자의 JWT에 `session_id`가 없으면 기기 등록 전에 `POST /api/v1/auth/refresh`로 토큰을 자동 갱신한다. 요청 본문은 `{"refreshToken": "<현재 리프레시 토큰>"}`이다. 새 액세스 토큰에는 기존 로그인에 해당하는 `session_id`가 포함되므로 로그인 화면을 거치지 않는다.
3. 갱신된 액세스 토큰과 리프레시 토큰을 모두 저장한 뒤 새 JWT로 기기를 등록한다. 토큰 갱신은 기존 공통 갱신 처리를 사용하며, 같은 리프레시 토큰의 갱신 요청이 동시에 중복 실행되지 않게 한다.
4. 등록 성공 응답은 본문 없는 `204`다. FCM 토큰이 변경되거나 인증된 상태로 앱을 다시 시작하면 같은 API로 갱신한다.
5. 리프레시 토큰의 만료·폐기·재사용 등으로 갱신이 인증 오류로 거절될 때 재로그인한다. 기기 등록 실패 또는 갱신 중 네트워크·서버 오류만으로 로그인 상태를 해제하지 않는다.

현재 서버는 로그인 ID 없는 기기 등록 요청에도 `401 REAUTHENTICATION_REQUIRED`를 반환한다. 앱은 기존 JWT의 `session_id` 누락을 확인하면 먼저 위 자동 갱신 흐름을 수행한다. 서버가 기기 등록 과정에서 대신 토큰을 갱신하지는 않는다. 서버 배포 여부와 앱의 이 흐름 적용 여부는 별도로 확인한다.

## 로그아웃할 때

기존 `POST /api/v1/auth/logout`에 `{"refreshToken": "<현재 리프레시 토큰>"}`을 보낸다. 액세스 토큰은 필요하지 않다. 서버가 해당 로그인 RT 폐기와 푸시 기기 비활성화·FCM 토큰 제거를 함께 처리하므로 별도 기기 해제 API를 호출하지 않는다. 다른 로그인 기기는 유지한다.

성공 응답은 본문 없는 204이며, 이미 처리한 요청과 알 수 없는 RT에도 같은 응답을 유지한다. 이 안내는 서버 로그아웃 처리 범위이며 네트워크 오류 때 앱의 로그아웃 화면 처리를 새로 정하지 않는다. 서버·앱 배포 여부는 별도로 확인한다.

## 탈퇴할 때

기존 `DELETE /api/v1/users/me`에 회원 액세스 토큰을 전달한다. 성공 응답은 본문 없는 204다. 서버가 회원 탈퇴·모든 로그인 RT 폐기·모든 푸시 기기 해제를 함께 처리하므로 기기별 해제 요청을 추가하지 않는다. 기기 해제 시 FCM 토큰 원문과 해시는 제거하며 알림함 기록의 보관은 별도 정책을 따른다.

이후 탈퇴한 계정의 인증된 기능은 이용할 수 없지만, 로그인 없이 공개 피드를 조회할 수 있다. 서버·앱 배포 여부는 별도로 확인한다.
