# 알림함 조회·보관 연동 안내

현재 정책은 [알림함 규칙](../rules/notification.md)의 NOTIFICATION-001~004, NOTIFICATION-007~008, 관리자 공지 배포(NOTIFICATION-013), AI 리뷰 결과 알림(NOTIFICATION-015)을 따른다.

## 조회와 읽음 처리

- 알림 목록 조회: `GET /api/v1/notifications`
- 알림 상세 조회: `GET /api/v1/notifications/{notificationId}`
- 미읽음 여부 조회: `GET /api/v1/notifications/unread-status`
- 단건 읽음 처리: `PATCH /api/v1/notifications/{notificationId}/read`
- 전체 읽음 처리: `PATCH /api/v1/notifications/read-all`

회원 액세스 토큰으로 본인 알림만 접근한다. 목록·상세 조회만으로 읽음 처리하지 않는다. 읽음 처리 성공은 본문 없는 204이며 반복 요청은 최초 읽은 시각을 유지한다.

## 수신 설정과 알림함

승인·반려 푸시 설정이 꺼져 있어도 검수 결과는 알림함에 저장한다. 이후 설정을 켜도 꺼져 있던 동안 생성된 알림과 발행 상태 도입 전의 기존 알림을 소급 발송하지 않는다. 주제 푸시 설정은 승인·반려 발행 필요 여부에 영향을 주지 않는다. AI 리뷰 결과 알림은 'AI 리뷰 결과' 설정(`aiReviewPushEnabled`)만 따르며, 꺼져 있어도 알림함에는 저장하고 승인·반려·주제 설정의 영향을 받지 않는다. 설정은 `GET`·`PATCH /api/v1/notification-settings`에서 주제·승인·반려와 함께 다루며, 수정 요청에서 이 항목을 생략하면 기존 값을 유지하고 최초 값은 켜짐이다. 전체 푸시를 한 번에 켜고 끄는 화면이 있으면 세 항목을 모두 보낸다.

현재 [이슈 #492](https://github.com/woowacourse-teams/2026-Chalkak/issues/492)에서 서버 DB의 초기 발행 상태·Relay·PushWorker·FCM 연동 코드를 작성했다. 실제 AWS·Firebase 연동 확인과 운영 배포는 아직 완료하지 않았다. 이 단계로 앱의 API 요청·응답 형식이 바뀌지는 않는다.

## 알림 클릭 시 이동 화면

목록의 각 알림에 `sourceType`과 `sourceId`를 추가한다. 현재 승인·반려는 둘 다 `sourceType = POST`, `sourceId = 관련 게시물 UUID`이다. 대상이 없는 알림을 제공하게 되면 두 값이 함께 null일 수 있으므로 앱은 알 수 없는 종류나 대상이 없는 경우를 처리할 수 있어야 한다. 관리자 공지는 `sourceType = NOTICE`, `sourceId = 공지 UUID`이다. AI 리뷰 결과 알림은 `sourceType = POST`, `sourceId = 관련 게시물 UUID`이다. 현재 좋아요는 제공하지 않는다.

| 알림 종류 | 앱 이동 | 사용할 식별자 |
| --- | --- | --- |
| `POST_APPROVED` | 승인된 게시물 화면 | `sourceId`로 게시물 조회 |
| `POST_REJECTED` | 본인 사진 원본과 반려 사유를 보여주는 알림 상세 화면. 새로 올리기 버튼 없음 | 목록의 `id`로 알림 상세 조회 |
| `AI_REVIEW_COMPLETED` | 해당 게시물의 AI 리뷰 화면. 썸네일은 게시물 사진이며 알림 상세는 필요 없음 | `sourceId`로 AI 리뷰 조회. 제목은 "AI 피드백이 도착했어요" |
| `AI_REVIEW_FAILED` | 해당 게시물의 AI 리뷰 화면. 썸네일은 게시물 사진이며 알림 상세는 필요 없음 | `sourceId`로 AI 리뷰 조회. 제목은 "AI 피드백을 만들지 못했어요"이고 본문은 다시 요청할 수 있는지에 따라 둘로 나뉨 |
| `NOTICE` | 공지 본문을 보여주는 알림 상세 화면. 썸네일·원본 사진·반려 사유는 없음(null) | 목록의 `id`로 상세 조회. `sourceType = NOTICE`, `sourceId`는 공지 ID |

목록의 `id`는 알림 ID이며 `sourceId`는 게시물 ID다. 읽음 처리는 모든 종류에서 알림 ID를 사용한다. 기존 승인 알림 상세 API도 유지하지만, 승인 알림 클릭 시 이동을 위해 상세 API를 먼저 조회할 필요는 없다. 실제 화면 이동은 Android·iOS에서 구현해야 한다.

## 30일 보관 정책 적용 시 앱 영향

일반·정지 회원의 알림은 사건 발생 시각부터 30일 보관한다. 현재 승인·반려는 검수 확정 시각을 응답의 `createdAt`으로 제공한다. 정확한 30일 경계에는 표시하며, 경계를 넘으면 목록·상세·미읽음·읽음 대상에서 제외한다. 최근에 읽었어도 보관 기간을 연장하지 않는다.

기존 앱이 캐시한 알림이나 오래된 ID로 상세·단건 읽음을 요청하면 삭제된 게시물의 알림과 마찬가지로 404가 올 수 있다. 앱은 찾을 수 없는 알림을 안내하고 목록·미읽음 상태를 다시 조회한다. 정리 작업을 아직 실행하지 않아 DB에 행이 남아 있더라도 조회·읽음 처리할 수 없다.

탈퇴 회원의 인증된 알림 접근은 즉시 차단한다. 남은 기록은 탈퇴 후 30일 보관하는 서버 정리 예외이며 앱 조회 허용 기간을 뜻하지 않는다. 비로그인 공개 피드 정책은 별개다.

기존 요청·응답 필드와 API URI는 유지하고 목록 응답에 관련 대상 두 필드를 추가한다. 관련 구현은 [이슈 #541](https://github.com/woowacourse-teams/2026-Chalkak/issues/541), [PR #548](https://github.com/woowacourse-teams/2026-Chalkak/pull/548)에서 확인한다. 운영 서버 적용 여부는 별도로 확인한다.

### SQS 전달 단계의 적용 상태

서버가 SQS 수락을 확인해도 앱의 수신 성공을 뜻하지 않는다. 이 단계에서 앱의 요청 형식·화면 이동 계약은 바뀌지 않는다. DB → SQS 일시 실패는 1분 뒤 재시도하고 사건 후 30분부터는 새 발행을 하지 않는다(NOTIFICATION-007). 큐 URL·권한 확인은 사용자 보고이며 실제 AWS·Firebase·기기 수신과 서버 배포는 미확인이다. 실제 푸시가 동작한다고 안내하지 않는다.

## Android·iOS 푸시 연동 준비

실제 메시지 예시·필드 의미·플랫폼별 수신과 클릭 처리는 [푸시 메시지 연동 계약](notification-push-contract.md)을 참고한다.

1. 앱의 Firebase 프로젝트와 서버 발송 프로젝트가 일치하는지 확인한다. 서버용 서비스 계정 인증은 앱의 `google-services.json` 또는 `GoogleService-Info.plist`와 다르다. 비밀 서버 키는 앱·Git·채팅에 넣지 않는다.
2. 로그인 후 FCM 토큰을 [기기 등록 안내](push-device-registration.md)에 따라 등록한다. 토큰 변경·앱 재시작 시에도 갱신한다. OS 알림 권한과 포그라운드 표시 처리는 각 앱이 구현한다.
3. iOS는 Firebase 프로젝트의 APNs 인증 키 또는 인증서, Push Notifications capability·앱 권한·APNs/FCM 토큰 연결을 확인한다.
4. 푸시는 `notification` 제목·본문과 `data`의 `eventId`, `notificationId`, `type`, `sourceType`, `sourceId`를 제공한다. 반려 사유·사진 URL·회원 ID·FCM 토큰 원문은 data에 넣지 않는다. 수신자가 바뀐 계정이면 해당 회원의 API로 접근할 수 없는 알림을 임의로 보여주지 않는다.
5. 승인은 `sourceId`로 게시물 화면, 반려는 `notificationId`로 알림 상세 화면, AI 리뷰 결과는 `sourceId`로 해당 게시물의 AI 리뷰 화면을 연다. 읽음 처리는 기존 API를 사용하고 클릭 보고 API는 추가하지 않는다. 알림이 삭제됐거나 게시물이 없으면 기존 404 처리를 적용한다.
6. 개발 서버에서 두 플랫폼의 백그라운드·포그라운드 수신, 로그아웃·수신 설정·만료를 실기기로 확인한다. 현재는 연동 코드 작성 상태이며 앱 적용·실기기 수신·서버 배포는 미확인이다.

## 관리자 공지 알림

관리자가 예약한 공지는 예약 시각에 탈퇴하지 않은 회원 전체의 알림함에 `type = NOTICE`로 생성된다. 승인·반려·주제 수신 설정과 관계없이 생성되며 생성 시각(`createdAt`)은 실제 배포 시각이다. 앱은 알 수 없는 `type`이 와도 오류 없이 처리해야 하며, `NOTICE`는 알림 상세에서 제목·본문을 보여 준다. #595부터 공지 푸시도 보내며, 푸시를 누르면 `notificationId`로 알림 상세를 열고 단건 읽음 처리한다. 푸시 메시지 형식은 [푸시 메시지 연동 계약](notification-push-contract.md)을 따른다. #595가 서버에 배포되기 전에 배포된 공지는 알림함에만 나타난다. 관리자가 배포 후 공지를 삭제하면 그 공지의 알림은 목록·상세·미읽음·읽음에서 사라지며, 상세·단건 읽음은 삭제된 게시물의 알림과 같이 `404`가 된다. 이미 받은 푸시를 나중에 눌러도 마찬가지다.

## AI 리뷰 결과 알림

AI 리뷰가 완료되거나 실패로 끝나면 요청한 작성자의 알림함에 `type = AI_REVIEW_COMPLETED` 또는 `AI_REVIEW_FAILED` 알림이 한 건 생긴다. 자동 재시도를 기다리는 동안에는 생기지 않는다. 실패한 리뷰를 다시 요청해 또 끝나면 회차마다 알림이 하나씩 생기므로 한 게시물에서 최대 3건이 보일 수 있다. 사용자가 AI 리뷰 화면에서 결과를 기다리던 중에도 알림은 생기고 자동으로 읽음 처리하지 않으므로 미읽음으로 남는다.

- 알림은 `sourceType = POST`라서 승인 알림처럼 게시물 사진의 썸네일이 목록에 포함된다. `title`·`body`는 서버가 알림을 만들 때 정한 값을 그대로 보여 준다. 문구로 종류를 판단하지 않고 `type`으로 분기한다.
- 누르면 알림 상세를 조회하지 않고 `sourceId` 게시물의 AI 리뷰 화면으로 이동한다. 이동한 뒤에는 AI 리뷰 조회(`GET`)부터 시작해 `status`에 맞게 보여 준다. 알림 상세 API는 응답을 주지만 이 종류에서는 쓰지 않는다.
- 읽음 처리는 알림 `id`로 한다. 게시물이 삭제되면 승인 알림처럼 목록·상세·미읽음·읽음에서 사라지고 `404`가 될 수 있다. 게시물이 삭제되지는 않았지만 공개 조건을 벗어나 AI 리뷰 조회가 `404`이면 기존 찾을 수 없음 안내를 보여 준다.
- 생성 시각(`createdAt`)은 리뷰가 끝난 시각이며 30일 보관의 기준이다.
- 구버전 앱은 모르는 `type`을 받아도 오류 없이 처리해야 한다. 알림함 목록에서는 이동하지 않거나 안내를 보여 줄 수 있다.
- 푸시 메시지 형식과 클릭 처리는 [푸시 메시지 연동 계약](notification-push-contract.md)을 따른다. 이 변경의 서버 배포와 실제 기기 수신은 아직 확인하지 않았다.
