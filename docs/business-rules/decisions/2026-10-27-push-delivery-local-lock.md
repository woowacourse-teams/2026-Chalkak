# NOTIFICATION-008 단일 JVM의 Java 락으로 동시 발송 제어

- 결정일: 2026-10-27
- 상태: 확정
- 변경 전: 사건·회원별 DB Lease를 60초 동안 확보하고 전용 스레드에서 30초마다 갱신했다. 기기 기록·완료 갱신에는 토큰과 만료 조건을 사용했다.
- 변경 후: 하나의 앱 프로세스에서 두 Worker가 같은 `PushDeliveryService`를 공유한다. 사건 ID·회원 ID별 Java 락을 이력 조회 전 획득하고 기기 처리·결과·완료 저장 후 finally에서 해제한다. 같은 키를 처리 중이면 새 FCM 요청 없이 메시지를 SQS 재처리에 남긴다. 다른 키는 병렬 처리한다. 해제와 락 객체 제거를 획득과 같은 짧은 모니터로 보호해 사용 중인 키에 다른 락이 생기는 경쟁을 막는다. DB Lease 컬럼·갱신 실행기·인계 코드는 제거하며 기기별 JSON·시도 기록·재처리 정책은 유지한다.
- 변경 이유: 사용자가 단일 프로세스 운영 전제를 확인했고, 다중 프로세스의 처리권 인계보다 현재 스레드 간 중복 제어를 단순하게 구현하기로 했다. Java 락은 FCM 대기 중 유지해도 DB 연결을 점유하지 않는다. SQS는 중단된 작업을 다시 전달하고 새 프로세스는 저장된 수락·미확정 결과로 재처리하므로 별도의 DB Lease 만료 대기를 두지 않는다. 실제 중복 빈도나 성능 개선이 측정됐다는 뜻은 아니다.
- 영향 범위: 공통 Worker 전체와 발송 이력 저장·정리. 발송 이력 마이그레이션이 통합 브랜치에 미병합인 것을 확인해 최초 생성 SQL 하나에 최종 스키마를 정의한다. Lease 컬럼·PROCESSING 상태와 이를 제거하는 후속 마이그레이션은 두지 않는다. 이미 적용한 로컬 DB의 마이그레이션 이력은 별도로 취급하며 공유 DB의 이력을 임의 변경하지 않는다. 일반·정지 회원 생성 후 30일, 탈퇴 후 30일 보관과 정확한 경계 보존은 유지한다. 현재 유효한 사건은 원래 30분 기한을 따르며 DB Lease에 따른 정리 유예는 제거한다. 이후 사용자 승인으로 첫 이력 생성·SENDING 저장은 한 짧은 트랜잭션으로 묶고, FCM 호출과 기기 결과·사용자 완료 저장은 분리한다. 준비 커밋에 실패하면 신규 이력도 롤백하며 FCM을 호출하지 않는다. 발송 진입 시 상위 트랜잭션이 있으면 거절해 외부 응답 대기에 DB 연결을 보유하지 않게 한다. API·FCM 메시지·환경변수 계약은 바뀌지 않는다.
- 남은 한계: 여러 JVM에서 동시에 Worker를 실행하면 Java 락을 공유하지 않는다. 프로세스를 늘리거나 배포 중 중첩 실행하는 구조로 바꾸기 전에 제어 방식을 다시 결정해야 한다. FCM 수락 후 DB 저장 전 중단은 여전히 결과 불명으로 재처리하며 중복 가능성이 남는다. 외부 요청 타임아웃과 SQS Visibility Timeout 자동 연장은 유지한다. 실제 프로세스 강제 종료·AWS·FCM·기기 수신 및 성능 검증은 별도다.
