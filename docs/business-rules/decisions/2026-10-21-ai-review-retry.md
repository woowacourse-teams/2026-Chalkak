# AIREVIEW-001, AIREVIEW-002, AIREVIEW-005 AI 리뷰 자동 재시도와 재요청 도입

- 결정일: 2026-10-21
- 상태: 확정
- 변경 전: 실패가 최종이었다. 일시적인 OpenAI 장애로 한 번 실패해도 같은 건을 서버가 다시 시도하지 않았고, 사용자가 실패한 리뷰를 다시 요청할 수도 없었다. 실패한 리뷰에 `POST`하면 `200`과 `FAILED`를 그대로 돌려줬다.
- 변경 후:
  - 자동 재시도: 사용자 요청 한 번당 처리를 처음 시도를 포함해 최대 3번(재시도 2번) 시도한다. 시간 초과·요청 한도 초과·OpenAI 서버 오류만 서버가 잠시 기다렸다 다시 시도하고, 그 밖의 실패는 바로 실패한다. 배포·장애로 중단된 시도도 3번에 포함하며 이로 횟수를 모두 쓰면 실패로 끝난다. 기다리는 동안 앱에는 진행 중으로 보인다([AIREVIEW-002](../rules/ai-review.md#aireview-002-횟수)).
  - 재요청: 실패한 리뷰에 `POST`하면 같은 리뷰를 다시 대기열에 넣고 `202`와 `PROCESSING`을 돌려준다. 게시물당 요청은 처음을 포함해 최대 3번이며 4번째 요청은 `400`(`BUSINESS_ERROR`, "더 이상 AI 리뷰를 다시 요청할 수 없습니다.")이다. 이 검사는 "지금은 AI 리뷰를 요청할 수 없습니다." 검사보다 먼저 한다. 다시 요청하면 그 시점의 최신 사용 가능 버전으로 프롬프트 버전을 다시 고정한다([AIREVIEW-001](../rules/ai-review.md#aireview-001-요청-자격)).
  - 응답: `canRequestAgain`(boolean)을 추가했다. 실패이고 요청 횟수가 남았을 때만 `true`이며 횟수만 반영한다([AIREVIEW-005](../rules/ai-review.md#aireview-005-결과-표시)). 기존 필드는 그대로이고 필드만 추가했다.
  - 일일 한도는 두지 않는 정책을 유지한다. 성공한 리뷰는 다시 만들지 않으므로 완료된 리뷰에는 다시 요청할 수 없다.
- 변경 이유:
  - 반복 과금 방지: 한 게시물에 OpenAI를 호출하는 횟수를 3번(요청) × 3번(처리 시도) = 최대 9회로 묶는다. 대부분은 첫 시도에 성공해 1회다. 무한 재시도나 사용자의 반복 요청이 비용으로 이어지지 않게 한다.
  - 짧은 장애는 서버가 흡수: 시간 초과·요청 한도 초과·서버 오류는 잠시 뒤 다시 보내면 성공할 수 있어 사용자가 알 필요 없이 서버가 다시 시도한다. 결제·사용 한도 소진, 잘못된 요청, 거절, 출력 잘림·형식 오류는 기다리거나 다시 보내도 같은 결과일 가능성이 커 시도 횟수를 쓰지 않고 바로 실패로 끝낸다.
  - 긴 장애는 사용자가 나중에 재시도: 서버가 오래 붙잡지 않고 실패로 알린 뒤, 사용자가 시간을 두고 직접 다시 요청하게 한다. 횟수 상한은 위 9회 안에서 정한다.
  - 시간 초과도 다른 재시도 유형과 같은 예산을 쓴다. 시간 초과는 OpenAI가 끝까지 생성해 과금했을 수 있어 별도로 횟수를 두지 않고 9회 상한 안에서 흡수한다.
  - 4번째 요청은 `409`가 아니라 `400`으로 안내한다. 사용자에게 메시지를 보여 주는 거절이라 기본 오류 응답을 쓰고, 앱은 `canRequestAgain`으로 버튼을 미리 숨긴다.
- 영향 범위: `POST /api/v1/posts/{postId}/ai-review`, `GET`의 응답과 AI 리뷰 테이블·처리 워커·로그.
  - API 의미 변경: 실패한 리뷰에 `POST`하던 동작이 `200`과 `FAILED`에서 `202`와 `PROCESSING`으로 바뀐다. 앱은 [#689 앱 연동 안내](../guides/ai-review.md)대로 HTTP 상태 코드가 아니라 `status`로 분기하고 `2xx`를 모두 정상으로 다루도록 미리 알렸고, 구버전 앱에는 재요청 버튼이 없어 실패한 리뷰에 `POST`를 보내지 않는다. 그래서 기존 앱의 정상 동작은 깨지지 않으며(하위 호환) 새 API 버전은 만들지 않고 `v1`에 반영한다. api-versioning 기준으로 기존 응답의 상태 코드·의미가 달라지는 변경이라 검토했으며, 위 이유로 새 버전이 필요 없다고 판단했다. `canRequestAgain`은 필드 추가라 하위 호환이다.
  - 앱: 재요청 버튼은 `canRequestAgain`이 `true`일 때만 보여 주고, 폴링 시간 창을 약 5분으로 늘리며 기준 시각을 `POST`했거나 폴링을 시작한 시각으로 바꾼다([앱 연동 안내](../guides/ai-review.md)). 배포 전 서버에는 `canRequestAgain`이 없을 수 있어 없으면 `false`로 처리한다.
  - 운영: 재시도를 기다리는 건이 생긴다. 모니터링은 재시도 예약 로그를 보고, 대기열 지연 경보에서는 재시도를 기다리는 건을 제외한다([모니터링 설계](../../../backend/docs/monitoring/design.md)). DB의 오류 코드는 마지막 시도의 사유다.
  - 롤백: #690 코드를 이전 코드로 되돌리지 않고 앞으로 수정한다. 이전 코드는 새로 추가된 열을 몰라서, 새 열에 값을 넣지 못해 신규 요청이 저장되지 않고(새 열은 NOT NULL이며 기본값이 없다), 행을 가져가도 회차 시도 횟수를 올리지 않아 새 제약에 걸린다. 또 누적 시도 번호가 3 이상인 재요청 건은 가져가기 전에 시도 횟수를 모두 쓴 것으로 보아 실패로 끝난다.
  - 기존 데이터: #716 시절 dev에서 실패로 끝난 리뷰는 배포 후 다시 요청할 수 있다(`canRequestAgain`이 `true`). prod는 #690 이후에 공개하므로 영향이 없다.
