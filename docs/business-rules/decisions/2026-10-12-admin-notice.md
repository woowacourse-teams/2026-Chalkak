# NOTIFICATION-012 관리자 공지 알림 도입

- 결정일: 2026-10-12
- 상태: 확정
- 변경 전: 관리자가 전체 회원에게 공지를 보내는 기능과 정책이 없었다. 푸시 계약과 알림함 안내에는 관리자 공지를 제공하지 않는다고만 적혀 있었다.
- 변경 후: 관리자가 제목·본문·예약 시각으로 공지를 등록한다. 예약 시각이 되면 탈퇴하지 않은 전체 회원(정지 회원 포함)의 알림함에 공지를 저장하고 기존 Relay → SQS → 공통 PushWorker 경로로 푸시를 보낸다. 공지 전용 수신 설정은 두지 않는다. 발송 전에는 수정·취소할 수 있고, 발송 후 삭제하면 회원 알림함에서 숨긴다.
- 변경 이유: 공지는 푸시를 놓쳐도 다시 확인할 수 있어야 하므로 주제 푸시와 달리 알림함에 남긴다. 이미 일반화된 알림함 구조와 발행 상태·재시도·30일 보관 정책을 재사용할 수 있다. 회원별 알림 생성과 공지의 발송 완료를 한 트랜잭션으로 묶어 재시작에도 중복·누락 없이 한 번만 생성한다. 즉시 발송은 예약 시각을 현재로 보내는 방식으로 통일해 별도 API를 두지 않는다. 날짜 입력 실수로 전체 회원에게 즉시 발송되는 사고를 막기 위해 5분 넘게 과거인 예약 시각은 거절하고, 요청 지연과 관리자 기기의 시계 차이만 허용한다. 잘못 입력한 미래 시각은 발송 전에 수정·취소할 수 있어 상한을 두지 않는다.
- 영향 범위: 관리자 공지 API와 감사 로그, 예약 시각의 알림함 생성, 알림함 조회의 삭제 공지 제외, 공통 Worker의 공지 처리, Android·iOS 푸시 계약. 공지별 발송 결과는 관리자 API로 제공하지 않고, 기기별 결과를 DB에 저장하지 않는 기존 정책을 유지해 공지 ID(`eventId`)로 CloudWatch Logs Insights에서 조회한다.
- 관련 규칙: NOTIFICATION-012, NOTIFICATION-013, ADMIN-006, ADMIN-007. #594에서 NOTIFICATION-001·006에 공지 예외를 더했고, #595에서 NOTIFICATION-006·013에 공지 푸시 발송을 더했다. #593에서 NOTIFICATION-012에 수정을 더했고, 삭제 단계(#612)에서 NOTIFICATION-002·003을 함께 갱신한다.

## 감사 로그의 본문 해시 기록

- 결정일: 2026-10-13
- 변경 전: 공지 작성 감사 로그에 제목·본문·예약 시각 원문을 기록했다. 감사 로그의 민감 정보 검사가 본문에도 적용되어 `password: 8자 이상` 같은 설정값 형식 문구나 이미지 링크가 든 정상 공지가 거절됐다.
- 변경 후: 감사 로그에는 제목·예약 시각과 본문 SHA-256 해시를 기록한다. 본문 원문은 공지 행에만 둔다. 제목은 그대로 기록하므로 제목의 민감 정보 형식은 계속 거절한다.
- 변경 이유: 민감 정보 검사는 사유·상태값에 비밀값이 새지 않게 막는 장치이며 전체 회원에게 공개하는 본문에는 맞지 않는다. 발송 이후에는 본문을 바꿀 수 없고 삭제도 행을 남기는 방식이라, 최종 발송 본문은 감사 로그의 대상 ID로 공지 행에서 확인할 수 있다.
- 한계: 감사 로그로는 본문 원문을 조회·복원할 수 없다. 발송 전 수정이 생기면 공지 행에는 현재 본문만 남아 이전 본문을 확인할 수 없고, 해시로 변경 여부와 최종 본문을 기록한 작업만 구분한다. 발송 전 초안은 회원에게 노출되지 않았고 최종 발송 본문과 그 작업자는 해시로 추적할 수 있으므로, 수정 이전 본문을 별도 버전 이력으로 보관하지 않는다.
- 관련 규칙·이슈·PR: NOTIFICATION-012, ADMIN-006, [#592](https://github.com/woowacourse-teams/2026-Chalkak/issues/592), [#598](https://github.com/woowacourse-teams/2026-Chalkak/pull/598)


## 공지 배포의 실행 방식

- 결정일: 2026-10-13
- 결정: 공지 한 건을 회원별 알림으로 나눠 넣는 단계를 SQS 발행(publish)과 구분해 배포(distribute)라고 부르고, 배포 시각(`distributed_at`)만 기록한다. 관리자에게 보여 주는 상태(`SCHEDULED`·`DISTRIBUTED`)는 배포 시각 유무로 계산하며 따로 저장하지 않는다. KST 매 분 0초에 전용 스레드에서 확인하며 전용 설정(`NOTIFICATION_NOTICE_DISTRIBUTION_ENABLED`, 기본 꺼짐)으로 켠다. 서버가 멈춰 예약 시각을 지나친 공지도 다시 켜지면 배포한다.
- 이유: 상태가 둘뿐이고 전환이 배포 시각 하나로 완전히 설명되므로, 상태를 따로 저장하면 같은 사실을 두 번 적고 둘을 맞추는 제약이 필요해진다. 배포를 나눠 처리하는 등 시각만으로 구분되지 않는 상태가 생기면 그때 상태 컬럼을 둔다. 공지는 초 단위 정밀도가 필요 없고 관리자는 분 단위로 예약하므로 매 분 확인으로 충분하다. 전용 설정을 두면 승인·반려 Relay는 유지한 채 공지 배포만 멈출 수 있고, 삭제(#612) 전에는 잘못 예약한 공지를 막는 수단이 된다. 늦더라도 공지는 전달되는 편이 낫다고 보고, 푸시는 기존 30분 기한 정책을 그대로 따른다.
- 관련 규칙·이슈: NOTIFICATION-013, [#594](https://github.com/woowacourse-teams/2026-Chalkak/issues/594)

## 공지 수정의 처리 방식

- 결정일: 2026-10-14
- 결정: 수정은 제목·본문·예약 시각을 함께 받는 전체 교체(PUT)로 하고 등록과 같은 검증을 쓴다. 공지 행을 일반 행 잠금으로 잠근 뒤 배포 여부를 확인한다. 같은 내용으로 수정하면 변경 없이 현재 공지를 반환하고 감사 로그를 남기지 않는다.
- 이유: 수정할 수 있는 세 필드가 모두 필수이고 관리자 화면은 폼 전체를 제출하므로, 생략과 null을 구분해야 하는 부분 수정(PATCH)은 규칙만 늘린다. 배포는 잠긴 공지를 건너뛰고(`SKIP LOCKED`) 수정은 잠금을 기다리므로, 배포가 먼저면 수정이 배포 결과를 보고 거절하고 수정이 먼저면 다음 확인 때 수정된 내용으로 배포한다. 바꾸지 않고 저장하는 것은 관리자 화면에서 흔한 정상 동작이라 오류로 막지 않으며, 감사 로그는 실제 변경만 기록한다.
- 관련 규칙·이슈: NOTIFICATION-012, ADMIN-006, [#593](https://github.com/woowacourse-teams/2026-Chalkak/issues/593)
