# LIKE-006·NOTIFICATION-017 좋아요 달성 알림함과 푸시 도입

- 결정일: 2026-11-03
- 상태: 확정. 개발·운영 1차 호환 배포와 초기화 완료(2026-11-04 사용자 로그). #935에서 2차 활성화 코드 준비, 실제 2차 배포·기기 수신은 미확인
- 변경 전: 좋아요 등록·취소와 현재 개수 조회는 제공하지만 사용자에게 좋아요 알림은 제공하지 않았다. 작업 브랜치의 초기 초안은 푸시만 제공하고 전용 마일스톤 테이블과 Relay를 사용했다. 이 초안은 서버에 배포하지 않았다.
- 변경 후:
  - 신규 좋아요로 새로운 5개 단계(`5, 10, 15…`)에 도달하면 작성자의 알림함에 한 건을 저장하고, 좋아요 푸시 설정이 켜져 있으면 공통 Relay·SQS·PushWorker로 푸시도 발송한다. 자기 좋아요도 포함하며 게시물별로 판단한다.
  - 같은 게시물의 같은 단계는 한 번만 생성한다. 좋아요 취소·재등록이나 30일 알림 정리 후에도 처리한 최고 단계는 낮추지 않는다.
  - `likePushEnabled`는 기존·신규 회원 모두 최초 켜짐이며 다른 수신 설정과 독립적이다. OFF에서도 알림함과 최고 단계를 저장하고, ON으로 바꿔도 지난 알림을 소급 푸시하지 않는다.
  - 문구는 "게시물에서 새로운 업적을 달성했어요" / "좋아요 {단계}개 이상을 달성했어요"다. 이후 개수가 줄어도 과거 달성 사실을 유지한다. 알림함·푸시 모두 해당 게시물 상세로 이동하고 알림 ID로 읽음 처리한다.
  - 도입 시 기존 게시물의 현재 개수 이하의 최고 5개 단계만 초기화하며 과거 알림은 생성하지 않는다. 예를 들어 17개는 15로 초기화하고 이후 20개에서 새 알림을 생성한다. 신규 게시물의 최고 단계는 0이다. Flyway는 컬럼·제약조건만 추가했고, 구버전 종료 후 별도 스크립트로 개발·운영 초기화를 완료했다. 이미 높은 단계는 유지하며 공통 배포 훅에는 일회성 초기화를 넣지 않았다. 2차에서는 초기화 도구를 제거하고 다시 초기화하지 않는다.
- 변경 이유:
  - 최초 배포는 새 타입을 모르는 기존 API·Worker와 공존하므로 1차에서 알림 생성만 끄고 최고 단계는 기준값으로 갱신한다. 임시 스위치는 false를 기본값으로 하고 1차 CD 검사에서도 false만 허용한다. 개발·운영의 1차 완료·기존 프로세스 종료·최고 단계 보정 후, #935의 2차에서 조건문·설정·초기화 도구를 제거한다. 2차 배포 자체로 활성화하며 별도 SQL이나 ON 조작은 없다. 서버에 예전 false 키가 남아 있어도 사용하지 않는다. 원래 구버전이 새 DB 행을 조회하거나 새 SQS 메시지를 삭제하는 것을 막기 위한 선택이며, 단기 중단 배포와 영구 기능 스위치 대신 임시 두 단계 배포를 선택했다.
  - 5개 단위로 묶어 매 좋아요마다 알림이 쌓이는 부담을 줄인다. 별도 쿨다운이나 게시물 간 묶음은 추가하지 않는다.
  - 푸시를 놓치거나 설정을 꺼도 달성 사실을 다시 확인할 수 있도록 알림함에도 저장한다. 수신 설정은 푸시 발송만 결정한다.
  - 최고 단계를 알림함과 별도로 유지해 알림 보관 기간이 끝나도 같은 단계를 다시 생성하지 않는다. 초기화로 과거 게시물의 지난 단계 알림이 몰리는 것도 막는다.
  - 현재는 한 단계를 한 작성자에게 알리는 작업이므로 알림함의 발행 상태로 재시도할 수 있다. 별도 마일스톤 테이블·Relay 없이 기존 공통 발송 경로를 사용한다.
- 영향 범위:
  - 서버·DB: `users.like_push_enabled`, `post_like_counts.last_milestone_count`, 새 Notification 종류를 추가한다. 좋아요·개수·최고 단계·알림을 같은 트랜잭션으로 저장한다. SQS·FCM 수락 여부와 최고 단계는 서로 다른 의미다.
  - Android·iOS: 알림함·푸시의 `POST_LIKE_MILESTONE`을 게시물 상세로 연결하고 `notificationId`로 읽음 처리한다. 설정에 `likePushEnabled`를 추가하며, 전체 설정을 한 번에 바꾸는 화면은 현재 API의 모든 수신 설정 항목을 보낸다. 누락 필드는 유지하므로 기존 부분 수정 요청은 호환된다. 알 수 없는 종류를 받는 기존 앱의 실제 동작은 별도 확인한다.
  - 보관·실패: 알림함과 기기별 이력은 기존 30일 정책을 적용한다. 푸시는 알림 생성 후 30분 안에서만 새 요청을 시작하며 실패·만료가 최고 단계를 되돌리지 않는다. 읽음·설정 OFF·게시물 노출 불가·탈퇴·유효 로그인이나 기기 없음이면 생략하고, 정지 회원은 유효한 로그인과 기기가 있으면 발송한다.
  - 적용 상태: 로컬 PostgreSQL과 모의 외부 발송으로 검증했다. 1차 배포와 초기화는 사용자 로그로 확인했다(개발 0행·운영 1,663행). 2차 실제 서버 전환·FCM 기기 수신·앱 연동·CloudWatch·DLQ 상태는 미검증이다. 미배포 초안의 구버전 Relay 중지나 메시지 이관은 필요하지 않다.
- 2026-11-04 리뷰 후 배포 결정:
  - 개발 서버를 앱 구현·연동 환경으로 먼저 활성화한다. 앱 완성을 개발 배포의 선행 조건으로 두지 않으며, 개발 테스트 계정에서 미지원 앱의 이동·설정이 제한됨을 공유한다. 앱 팀이 개발에서 구현·실기기 검증한 뒤 지원 앱의 운영 제공 준비를 확인한다.
  - 운영은 현재 운영 1차 소스에 #944 최종 변경만 선택 반영한다. 개발 소스 전체를 복사하지 않으며 #933의 문의 답변 알림은 제외한다. 운영 1차는 `FEEDBACK_ANSWERED` / `FEEDBACK`를 몰라, 함께 도입하면 이전 Worker의 메시지 삭제와 롤백 후 DB 조회 실패 위험이 있다. #933은 별도의 호환 배포를 설계한다.
  - 운영 1차는 좋아요 타입을 지원하므로 위의 좋아요 전용 릴리스에서 롤백 대상으로 사용할 수 있다. 실제 DB·큐의 모든 타입과 revision을 대조한다. 임시 키는 각 환경에서 1차를 롤백 대상에서 제외한 뒤 정리한다. 실제 2차 배포·앱 검증 완료를 뜻하지 않는다.
