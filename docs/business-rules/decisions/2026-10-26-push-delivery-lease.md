# NOTIFICATION-008 단일 발송 이력과 Lease 기반 중복 제어

- 결정일: 2026-10-26
- 상태: 확정
- 변경 전: FCM 결과는 로그로만 남겨 SQS 재전달 시 이전 수락 여부를 확인하지 않았다. 발송 이력 두 테이블과 별도 결과 불명 2회·Worker 10회 제한도 검토했다.
- 변경 후: 한 테이블에 사건·회원별 기록과 기기별 JSON 결과를 저장한다. 완료 기록을 재사용하고, 미완료 작업은 60초 Lease를 확보해 30초마다 갱신한다. 기록 갱신은 현재 토큰과 DB 기준 유효 기간을 조건으로 수행한다. 별도 Worker 재시도 횟수 제한은 추가하지 않고 결과 불명도 기존 SQS 최대 수신 10회·원래 발생 후 30분 기한 내에서 재처리한다. 기기별 시작 횟수는 관측용이며 SDK 내부 HTTP 횟수와 다르다.
- 변경 이유: 회원의 완료 상태·처리 권한과 소수의 현재 기기 결과를 한 행에서 확인한다. JSON 상태 검증은 도메인에서 하고, DB 갱신은 해당 기기 항목만 조건부로 수정해 다른 기기의 수락 결과를 보존한다. 동일 사건의 다른 SQS 메시지도 같은 발송 기록을 사용한다. 재처리 횟수 정책은 SQS에 맡겨 별도 상한과의 충돌을 줄인다.
- 영향 범위: 공통 Worker의 승인·반려·주제·공지·리마인더·AI 리뷰 결과 발송. SQS/FCM 메시지 형식과 앱 API는 유지하고, Relay의 발행 상태는 계속 `notifications`에 저장한다. 시작 기록과 결과 기록은 짧은 트랜잭션으로 커밋하며 FCM 응답 대기 동안 DB 트랜잭션을 유지하지 않는다. 기기 삭제는 이력을 삭제하지 않지만 회원 물리 삭제 때는 연관 이력을 함께 삭제한다.
- 남은 한계: 시작 기록 이후 실제 요청 전에 중단될 수도 있고, FCM 수락 후 결과 저장 전에 중단될 수도 있다. DB Lease는 이미 진행 중인 요청을 취소하지 않으므로 모든 중복을 막지 못한다. 앱 Inbox에 의한 백그라운드 배너 중복 차단은 검증 전이며 서버가 이를 보장한다고 가정하지 않는다. SQS 최대 수신 10회는 메시지별 한도이고 같은 사건의 새 메시지는 별도 수신 횟수를 가진다. 30분 만료로 먼저 삭제하면 DLQ에 남지 않을 수 있다. 실제 종료/재전달 장애 검증은 후속 단계다.
