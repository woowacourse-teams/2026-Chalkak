# 알림함 규칙

## NOTIFICATION-001 검수 결과 알림 생성

- 규칙: 관리자가 게시물을 승인하거나 반려하면 작성자의 알림함에 해당 검수 결과를 한 건 저장한다. 검수 상태 변경·관리자 감사 로그·알림·SQS 발행 상태는 하나의 트랜잭션으로 저장한다. 같은 회원에게 같은 검수 사건의 알림을 중복 저장하지 않는다. 생성 당시 탈퇴하지 않은 회원의 승인·반려 푸시 수신 설정이 켜져 있으면 발행 대기(`PENDING`)와 최초 발행 가능 시각을 사건 발생 시각으로 기록한다. 설정이 꺼져 있으면 알림함만 저장하고 발행 불필요(`NOT_REQUIRED`)로 처리한다. 실제 SQS 수락을 확인하기 전에는 수락 시각을 기록하지 않는다.
- 적용 범위: 관리자 게시물 검수 확정, 승인·반려 알림함과 초기 SQS 발행 상태 저장
- 예외: 검수가 실패하거나 트랜잭션이 롤백되면 알림과 발행 상태도 남지 않는다. 정지 회원에게도 같은 기준을 적용하고, 탈퇴 회원의 알림은 발행 불필요로 저장한다. 나중에 수신 설정을 켜도 발행 불필요로 생성한 알림을 소급 발송하지 않는다. 발행 상태 도입 전에 저장한 알림도 소급 발송하지 않는다. 주제 알림은 이 규칙에 포함하지 않는다. 관리자 공지 알림의 생성은 NOTIFICATION-013을, AI 리뷰 결과 알림의 생성은 NOTIFICATION-015를 따른다. SQS 전달 정책은 NOTIFICATION-007을 따른다. SQS와 FCM의 요청 수락은 기기 수신 완료를 뜻하지 않는다.
- 결정 기록: [검수 결과 알림함 도입과 보관 기준](../decisions/2026-09-29-notification-inbox.md), [검수 알림의 발행 상태 저장](../decisions/2026-10-06-notification-publication.md)

## NOTIFICATION-002 본인 알림 조회

- 규칙: 탈퇴하지 않은 회원은 본인의 알림만 최신순으로 조회한다. 목록에는 알림 종류, 관련 대상 종류·ID(`sourceType`, `sourceId`), 게시물 사진의 썸네일 URL과 읽은 시각을 제공한다. 승인 알림을 누르면 관련 게시물 화면으로 이동하고, 반려 알림을 누르면 알림 상세에서 본인 사진 원본과 반려 사유를 보여준다. AI 리뷰 결과 알림(`AI_REVIEW_COMPLETED`, `AI_REVIEW_FAILED`)은 게시물 대상(`sourceType=POST`)이라 승인 알림처럼 게시물 사진의 썸네일을 함께 제공하고, 누르면 `sourceId` 게시물의 AI 리뷰 화면으로 이동한다(NOTIFICATION-015). 반려 상세에는 새로 올리기 버튼을 두지 않는다. 기존 상세 조회 API는 유지한다. 게시물이나 관리자 공지가 삭제되거나 사건 발생 시각부터 30일이 지나면 연결된 알림을 목록·상세·미읽음 상태에서 제외한다. 알림 기록의 삭제 시점은 NOTIFICATION-004를 따른다.
- 적용 범위: 알림 목록·상세·미읽음 상태 조회
- 예외: 정지 회원도 본인의 알림을 조회할 수 있다. 다른 회원의 알림, 삭제된 게시물·공지의 알림, 30일이 지난 알림 상세는 찾을 수 없는 것으로 처리하며 탈퇴 회원의 인증된 알림함 접근은 차단한다. 반려 사유는 승인 알림에는 없다. AI 리뷰 결과 알림도 반려 사유가 없으며 상세 화면을 거치지 않고 `sourceId`로 바로 이동한다.
- 결정 기록: [검수 결과 알림함 도입과 보관 기준](../decisions/2026-09-29-notification-inbox.md), [알림함 30일 보관 정책](../decisions/2026-10-06-notification-retention.md), [AI 리뷰 결과 알림 도입](../decisions/2026-10-22-ai-review-result-notification.md)

## NOTIFICATION-003 읽음 상태

- 규칙: 회원은 알림함에 표시되는 본인의 알림 한 건 또는 표시되는 미읽음 알림 전체를 읽음 처리할 수 있다. 이미 읽은 알림을 다시 처리해도 최초 읽은 시각을 유지한다.
- 적용 범위: 단건 읽음, 전체 읽음, 미읽음 상태
- 예외: 다른 회원의 알림, 삭제된 게시물·공지의 알림, 30일이 지난 알림은 단건 읽음 처리할 수 없다. 전체 읽음에서도 삭제된 게시물·공지의 알림과 30일이 지난 알림은 변경하지 않는다. 알림을 조회하는 것만으로는 읽음 처리하지 않는다.
- 결정 기록: [검수 결과 알림함 도입과 보관 기준](../decisions/2026-09-29-notification-inbox.md), [알림함 30일 보관 정책](../decisions/2026-10-06-notification-retention.md)

## NOTIFICATION-004 알림함 보관과 삭제

- 규칙: 일반·정지 회원의 알림은 사건 발생 시각부터 30일이 지난 뒤 정리한다. 현재 검수 알림은 검수 확정 시각을 생성 시각으로 저장하고 이 시각을 기준으로 한다. 읽음 여부나 읽은 시각으로 기간을 연장하지 않는다. 탈퇴 회원의 남아 있는 알림은 생성 시각과 관계없이 탈퇴 시각부터 30일이 지난 뒤 정리한다.
- 적용 범위: 알림 목록·상세·미읽음 조회, 단건·전체 읽음, 알림함 데이터의 주기적 삭제
- 예외: 탈퇴 요청 시 알림을 즉시 지우지 않는다. 두 기간의 정확한 경계 시각에는 보관한다. 일반·정지 회원의 알림은 30일 경계가 지난 즉시 조회·읽음 대상에서 제외하고 다음 정리 실행 때 삭제한다. 탈퇴 회원의 남은 알림은 탈퇴 후 30일 경계가 지난 다음 정리 실행 때 삭제한다. 이미 삭제된 알림을 탈퇴 때문에 복원하지 않는다.
- 결정 기록: [검수 결과 알림함 도입과 보관 기준](../decisions/2026-09-29-notification-inbox.md), [알림함 30일 보관 정책](../decisions/2026-10-06-notification-retention.md)

## NOTIFICATION-005 현재 로그인 기기 등록·해제

- 규칙: 탈퇴하지 않은 회원은 유효한 로그인으로 현재 앱의 FCM 토큰을 등록·갱신한다. 회원과 로그인 ID는 액세스 토큰에서 식별하며 요청 본문으로 받지 않는다. 로그인 하나에 기기 등록 하나를 유지하고, 같은 로그인 연결에서 반복 등록하거나 토큰을 교체해도 최초 등록 시각을 유지한다. 같은 FCM 토큰을 다른 로그인에 등록하면 이전 기기 행을 삭제한다. 기기 연결을 해제할 때는 토큰만 비우거나 비활성 행을 남기지 않고 기기 행 전체를 삭제한다. 로그아웃 후 재로그인하거나 해제된 로그인으로 다시 등록하면 새 기기 행을 생성한다. 앱 설치 식별자와 플랫폼은 등록 요청으로 받지 않는다. 로그아웃하면 해당 로그인 기기 행을 삭제하며, 같은 로그인의 RT 폐기와 함께 처리한다. 갱신 요청에서 RT 재사용·비활동 만료·절대 만료를 감지하여 로그인을 폐기할 때도 해당 기기 해제를 함께 처리한다. 다른 로그인의 기기는 유지한다. 회원 탈퇴 시에는 해당 회원의 모든 기기 행을 삭제한다. 회원 탈퇴·전체 RT 폐기·기기 해제를 하나의 트랜잭션에서 처리한다.
- 적용 범위: `PUT /api/v1/push-devices/current`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, `DELETE /api/v1/users/me`, 로그인 후 기기 등록, FCM 토큰 변경·앱 재시작에 따른 갱신
- 예외: 정지 회원도 등록할 수 있다. 탈퇴 회원의 등록은 차단한다. 로그인 ID가 없는 이전 JWT는 사용 가능한 리프레시 토큰으로 자동 갱신한 뒤 기기를 등록할 수 있다. 로그인 ID가 잘못되었거나 해당 회원의 사용 가능한 리프레시 토큰이 없는 로그인은 등록할 수 없다. 리프레시 토큰의 만료·폐기·재사용 등으로 인증 갱신이 거절될 때 재로그인한다. 기기 등록 실패가 이미 성공한 로그인을 취소하지는 않는다. 등록 응답에 FCM 토큰을 반환하지 않는다. 로그아웃은 액세스 토큰 없이 RT로 처리한다. 만료·회전·폐기된 RT도 DB에서 해당 로그인을 식별할 수 있으면 연결 기기를 해제한다. 알 수 없는 RT는 다른 기기에 영향을 주지 않고 204를 반환한다. 반복 로그아웃은 기기가 없는 상태를 유지하며, 토큰이 다른 로그인으로 이동했다면 새 연결은 해제하지 않는다. 기기 행 삭제가 실패하면 RT 폐기도 롤백한다. 재사용·만료 감지의 인증 오류 응답에도 RT 폐기·기기 해제는 함께 커밋한다. 정상 갱신은 기기 연결을 유지하고, 갱신 요청에서 만료를 감지하기 전까지 만료 시각만으로 기기를 자동 해제하지는 않는다. 탈퇴 시에는 이미 RT가 폐기된 로그인에 남은 기기 행도 삭제한다. 다른 회원에게 옮겨진 토큰 연결은 유지한다. 탈퇴 중 기기 행 삭제가 실패하면 회원 탈퇴·소셜 연결 삭제·RT 폐기도 롤백한다. 알림함 기록의 보관은 NOTIFICATION-004를 따른다. 탈퇴 회원의 인증된 기능 접근은 차단하지만 비로그인 공개 피드 조회는 유지한다.
- 결정 기록: [로그인별 푸시 기기 등록](../decisions/2026-09-30-push-device-registration.md), [재사용·만료 감지 시 푸시 기기 해제](../decisions/2026-10-01-session-revocation-push-cleanup.md), [로그인별 등록 유지와 해제 시 연결 제거](../decisions/2026-10-06-push-device-connection-cleanup.md)

앱의 요청 순서와 토큰 갱신 처리는 [푸시 기기 등록 연동 안내](../guides/push-device-registration.md)를 참고한다.

## NOTIFICATION-006 본인 푸시 수신 설정 조회·수정

- 규칙: 탈퇴하지 않은 회원은 본인 계정에 저장된 주제 푸시 수신 여부, 게시물 승인·반려 결과 푸시 수신 여부와 AI 리뷰 결과 푸시 수신 여부(`aiReviewPushEnabled`)를 조회·수정한다. 수정 요청에 값이 있는 항목만 변경하고 생략하거나 null인 항목은 기존 값을 유지한다. 변경할 값이 하나도 없으면 요청을 거부한다. 세 설정의 최초 값은 모두 켜짐이다. 설정은 기기별이 아닌 회원 계정 단위로 저장한다. 주제 푸시 수신 여부(`topicPushEnabled`)는 주제 푸시와 관리자 리마인더(NOTIFICATION-016)에 함께 적용하는 참여 알림 수신 여부다. 끄면 두 푸시를 모두 받지 않는다. API 필드 이름은 유지하며 설정 화면에 보여 줄 이름은 앱에서 정한다.
- 적용 범위: `GET /api/v1/notification-settings`, `PATCH /api/v1/notification-settings`, 앱의 알림 설정 화면
- 예외: 정지 회원도 조회·수정할 수 있다. 탈퇴 회원과 존재하지 않는 회원은 인증 오류로 거부한다. 회원 ID는 액세스 토큰에서 식별하며 요청으로 받지 않는다. 기기 등록 여부와 로그인 ID의 유무는 조회·수정 조건이 아니다. 서로 다른 설정의 수정 요청이 겹쳐도 각 변경을 유지하며, 같은 항목은 나중에 처리된 요청의 값으로 저장한다. 같은 값의 반복 요청도 허용한다. 수정 성공은 본문 없는 204로 응답한다. 반환값은 서비스에 저장된 설정이며 운영체제의 알림 권한이나 실제 푸시 수신 성공을 나타내지 않는다. 알림함의 조회·보관 기준은 별도 규칙을 따른다. 관리자 공지는 세 설정 모두의 대상이 아니며 설정과 관계없이 알림함에 배포하고 푸시를 보낸다. 리마인더 전용 수신 설정은 따로 두지 않는다. 변경할 값이 하나도 없는지는 세 항목 모두를 기준으로 판단하므로, 세 항목이 모두 비어 있는 요청은 거부한다. AI 리뷰 결과 설정은 승인·반려 설정과 별개이며 AI 리뷰 결과 알림의 푸시 발송 여부(NOTIFICATION-015)만 정한다. 이 설정을 끄거나 켜도 승인·반려·주제·리마인더 푸시에는 영향이 없다.
- 결정 기록: [회원별 푸시 수신 설정 조회·수정](../decisions/2026-09-30-notification-settings.md), [AI 리뷰 결과 알림 도입](../decisions/2026-10-22-ai-review-result-notification.md), [리마인더에 주제 푸시 수신 여부 적용](../decisions/2026-10-22-reminder-push.md#리마인더에-주제-푸시-수신-여부를-적용하는-이유)

## NOTIFICATION-007 검수 알림의 SQS 발행

- 규칙: Relay는 커밋된 승인·반려 알림 중 발행 대기이고 다음 시도 시각이 도래한 작업을 SQS로 전달한다. 정상 작업은 다음 확인 주기에 처리한다. 일시적인 SQS 오류 또는 수락 여부 불명은 해당 시도 종료 시각부터 1분 뒤 다시 시도한다. 사건 발생 시각부터 30분이 되는 시각부터는 새 발행을 하지 않고 만료로 처리한다. 다음 확인 시각이 기한을 넘지 않게 하되 기한에 도달하면 재발행 대신 만료 처리한다. 요청·권한·큐 설정 등의 영구 오류는 발행 실패로 종료한다. SQS 수락 ID를 확인하면 발행 완료와 확인 시각을 저장한다.
- 적용 범위: 승인·반려 알림의 DB → SQS 전달, 발행 실패·기한·중복 처리
- 예외: 발행 불필요·완료·만료·실패 상태는 다시 발행하지 않는다. 알림 한 건의 DB 반영 실패는 다른 알림의 처리를 롤백하지 않는다. SQS 수락 후 DB 반영이 실패하거나 수락 응답을 확인하지 못하면 같은 사건이 SQS에 중복 전달될 수 있다. 사건·알림 식별자는 재시도 시에도 유지한다. SQS 수락은 FCM 발송 또는 기기 수신 성공이 아니다. 반려 사유·사진 URL·FCM 토큰은 큐 메시지에 복사하지 않는다. 발송 직전 최신 조건 검증과 FCM 재시도는 NOTIFICATION-008을 따른다. AWS 큐·권한이 준비되지 않은 환경은 Relay를 켜지 않는다.
- 결정 기록: [검수 알림의 SQS 발행과 재시도](../decisions/2026-10-06-notification-sqs-relay.md)

## NOTIFICATION-008 검수 푸시 발송과 SQS 재처리

- 규칙: PushWorker는 승인·반려 SQS 메시지를 수신하고 발송 직전에 알림·사건 식별자와 원래 발생·만료 시각이 DB 기록과 일치하는지 확인한다. 알림이 남아 있고 미읽음이며 연결 게시물이 삭제되지 않았고, 회원이 탈퇴하지 않았으며 승인·반려 푸시 설정이 켜져 있고 해당 회원의 사용 가능한 로그인이 있는 현재 등록 기기로 보낸다. 사건 발생 후 30분 정각부터 Worker가 새 FCM 발송을 시작하지 않는다. SQS에서 다시 받은 작업에도 같은 기한을 적용한다. 발생 이후 등록한 현재 기기도 포함한다. 기기마다 최신 상태를 다시 조회한다. FCM 수락이 기록된 기기는 다시 요청하지 않고, 일시 실패하거나 결과가 불명확한 현재 대상 기기만 SQS 재전달에서 재처리한다. 다른 기기가 수락했어도 재처리할 기기가 남으면 메시지를 유지하며, 재처리할 현재 대상이 없으면 사용자 처리를 완료하고 SQS에서 삭제한다. 처리 중 숨김 시간을 연장하고 종료 시 연장을 멈춘다. Retry-After는 원래 발송 기한 안에서 존중한다.
- 적용 범위: 승인·반려 SQS → PushWorker → FCM, 현재 기기 선정·만료·재전달·오류 처리
- 예외: 정지 회원도 검수 푸시를 받는다. 알림이 읽혔거나 게시물이 삭제됐거나 수신 설정이 꺼졌거나 탈퇴·만료·기기 없음이면 발송을 생략하고 메시지를 삭제한다. 무효 등록 토큰(UNREGISTERED)은 해당 발송에 사용한 토큰이 여전히 같은 기기에 연결돼 있을 때만 기기 행을 삭제한다. 메시지 형식·프로젝트·인증 등 영구 오류는 운영 오류를 기록하고 메시지를 완료하며 유효 기기를 삭제하지 않는다. 기기별 조회·발송 중 예상하지 못한 예외가 발생해도 다른 기기 처리를 계속하고 앞선 수락 결과를 유지한다. 수락 기록은 보존하며, 다른 기기의 재시도할 오류가 있으면 수락 여부와 관계없이 메시지를 유지한다. 무효 토큰의 기기 행 삭제 실패는 조사 로그를 남기고 원래 발송 결과를 유지한다. 정리 실패만으로 재발송하지 않으며 삭제가 롤백된 기기 행은 남을 수 있다. 기기 목록 조회 등 작업 전체의 예기치 않은 처리 실패는 메시지를 유지한다. 수락·영구 실패·무효 토큰·발송 생략이 기록된 기기는 다시 요청하지 않는다. 일시 실패·결과 불명 기기는 최신 조건과 원래 발송 기한을 다시 확인한다. 발송 이력은 단일 `push_deliveries`에 사건 ID·회원 ID로 한 건을 저장하고, 기기별 시작·결과는 JSON으로 기록한다. 메시지 기본 검증·최신 발송 조건 조회에서 생략되면 새 발송 이력을 만들지 않는다. 완료 기록이 있으면 새 기기가 등록돼도 같은 사건을 다시 보내지 않는다. 기기 수락은 저장됐으나 사용자 완료 전에 중단됐으면 수락한 기기는 생략하고 미완료인 현재 등록 기기를 이어 처리한다. 재처리 전에 로그아웃·수신 해제·읽음·삭제 등으로 대상 조건이 바뀌면 해당 기기는 발송하지 않는다. COMPLETED는 처리 종료이며 모든 기기의 수락이나 실제 수신 성공을 뜻하지 않는다. Worker는 하나의 JVM에서 실행하며, 같은 사건 ID·회원 ID의 이력 조회 전 Java 락을 획득한다. 두 폴링 Worker는 같은 락 관리 객체를 공유한다. 락을 획득하지 못한 중복 작업은 FCM을 요청하거나 메시지를 삭제하지 않고 기존 SQS 재처리로 넘긴다. 락은 기기 처리와 결과·완료 저장까지 유지하고 정상·예외 종료 모두 finally에서 해제하며, 다른 사건 또는 회원은 병렬 처리한다. DB에 행이 없어도 메시지의 두 식별자로 락을 획득한다. DB Lease 토큰·만료·주기 갱신은 사용하지 않는다. 발송 이력의 시작·결과 저장을 확인하지 못하면 현재 사용자 작업의 추가 FCM 요청을 중단하고 SQS 재처리에 맡긴다. 저장소별 짧은 트랜잭션을 사용하며 FCM 응답을 기다리는 동안 DB 연결이나 트랜잭션을 유지하지 않는다. Java 락은 단일 JVM 범위이고 다중 프로세스 간 동시 발송을 막지 않는다. FCM 수락 후 DB 기록 전 중단 등 결과를 모르는 경우에는 중복 가능성을 받아들이고 기존 SQS 정책으로 다시 처리한다. 별도 Worker 발송 횟수 상한이나 결과 불명 2회 상한은 두지 않는다. JSON의 시도 횟수는 발송 시작 기록이며 SDK 내부 HTTP 재시도 수나 실제 네트워크 요청 수가 아니다. Java 락과 발송 이력으로 전체 Exactly-once나 배너 중복 차단을 보장하지 않는다. 로그아웃으로 기기를 삭제해도 발송 이력은 유지한다. 발송 이력은 매일 04:50 KST에 알림함 정리와 함께 삭제한다. 일반·정지 회원은 이력 생성 후 30일, 탈퇴 회원은 탈퇴 후 30일을 보관하며 정확한 경계에는 보관한다. 기기 결과 JSON도 이력 행과 함께 삭제한다. Android TTL은 메시지 생성 시 원래 기한까지 남은 기간으로 한 번 계산하고, iOS APNs 만료는 원래 기한의 절대 시각으로 설정한다. 기한 전에 시작한 SDK 내부 재시도는 기한이 지나도 계속될 수 있으며, 이 경우 Android의 실제 만료 시각이 원래 기한보다 늦어지는 것을 허용한다. SDK 내부 HTTP 요청마다 기한을 다시 검사하거나 TTL을 갱신하지 않으며 기기 표시 시각까지 보장하지 않는다. FCM 수락 후 오프라인 기기의 전달은 설정한 TTL·APNs 만료에 따라 FCM/APNs가 처리하고 Worker는 수신 확인을 기다리지 않는다. SQS 최대 수신 횟수는 최초 수신 포함 10회, 숨김 시간은 60초이며 SDK 내부 HTTP 재시도는 별개다. 한도 초과 메시지는 AWS Redrive policy로 DLQ에 격리한다. 기한이 먼저 지나 삭제된 메시지는 DLQ에 남지 않을 수 있다. DLQ는 최대 14일, 조사 로그는 30일 보관하고 자동·수동 Redrive는 하지 않는다. 실제 보관·경보 설정은 운영 환경에서 별도 확인한다. 클릭 보고 API는 이번 범위에 없다.

## NOTIFICATION-009 관리자 주제 푸시 설정

- 규칙: ADMIN 권한의 관리자는 KST 기준 주제 푸시 발송 시각을 여러 개 설정한다. 한 설정은 분 단위 발송 시각 하나를 가지며 같은 시각의 설정을 중복 등록할 수 없다. 초·소수 초가 있는 입력은 반올림하지 않고 거절한다. 별도 활성 여부 없이 설정의 생성·삭제로 발송을 관리한다. 생성·시각 수정은 변경 이후 도래하는 발송 시각부터 적용한다. 지난 시각은 소급 실행하지 않고 다음 날 해당 시각부터 실행한다.
- 적용 범위: 관리자 주제 푸시 설정 생성·조회·수정·삭제와 발송 시각 적용
- 예외: 설정 삭제는 아직 실행 전인 발송부터 취소한다. 이미 SQS에 발행한 작업은 설정 변경·삭제만으로 취소하지 않는다. 해당 작업은 최신 회원·주제 수신 설정·오늘 주제·로그인·기기 조건과 원래 예정 시각부터 30분 기한에 따라 처리한다. 주제 알림은 알림함·Outbox·사용자별 DB 작업으로 저장하지 않는다. SQS 재처리는 최초 수신 포함 최대 10회이며 SDK의 HTTP 재시도와 구분한다. 생성 요청 자체는 푸시를 발행하지 않는다. 설정 생성·시각 수정·삭제는 처리 관리자와 변경 전후 발송 시각을 기존 감사 로그에 같은 트랜잭션으로 기록한다. 같은 시각의 수정 재요청은 이력을 추가하지 않으며 설정 삭제 후에도 감사 이력을 유지한다. 감사 기록이 실패하면 설정 변경도 롤백한다. 별도 사유는 요청하지 않는다.
- 결정 기록: [주제 푸시 설정의 변경 적용 시점](../decisions/2026-10-08-topic-push-schedules.md)

현재 #493에서는 설정 생성·조회·수정·삭제 API를 구현했다. #572의 변경에 정시 SQS 직접 발행과 공통 Worker의 주제 처리를 포함하며, 실제 개발 서버 적용·연동은 별도로 확인한다. API 계약은 [관리자 주제 푸시 설정 연동 안내](../guides/topic-push-schedules.md)를 참고한다.

## NOTIFICATION-010 주제 푸시의 발송 조건과 화면 이동

- 규칙: 주제 메시지는 알림함 기록 없이 기존 공통 Worker에서 처리한다. 발송 직전에 탈퇴하지 않은 정상 회원, 주제 푸시 수신 설정, KST 기준 오늘의 삭제되지 않은 주제, 유효한 로그인과 현재 등록 기기를 확인한다. 메시지의 관련 주제 ID가 오늘 주제와 다르면 생략한다. 오늘 주제에 삭제되지 않은 `VALIDATING`·`PENDING`·`APPROVED` 게시물이 있는 회원은 발송하지 않는다. `REJECTED`·삭제된 게시물만 있으면 발송할 수 있다. 반려 후 다시 제출해 승인 대기 중이면 제외한다. 예정 시각 이후 등록된 현재 기기도 포함한다. 제목은 `오늘의 주제`, 본문은 조회한 주제명으로 구성한다. 푸시 클릭은 클릭한 날의 오늘 주제 화면으로 이동한다.
- 적용 범위: 주제 메시지의 SQS 수신 이후 Worker·FCM 요청, Android·iOS 메시지 해석과 화면 이동
- 예외: 정지·탈퇴 회원, 주제 수신 해제, 오늘 주제 없음·삭제·다른 주제, 만료·폐기된 로그인, 현재 기기 없음은 발송하지 않는다. 발행 대상 조회 이후 제출한 경우에도 기기별 FCM 요청 직전에 회원 ID·오늘 주제 ID로 제출 상태를 재확인하고, 참여 중이면 발송을 생략한다. 발송 가능한 기기가 모두 생략되면 메시지를 재시도 없이 완료 처리하여 SQS에서 삭제한다. 확인 직후 제출과 이미 시작한 외부 요청이 겹치는 경우까지 원자적으로 막지는 않는다. 승인·반려 수신 설정은 주제 발송 여부에 영향을 주지 않는다. 주제 메시지는 `type=TOPIC`, `sourceType=TOPIC`이며 알림함 ID를 갖지 않는다. FCM `data`에는 `notificationId`를 보내지 않고 알림 상세·읽음 API를 호출하지 않는다. `sourceId`는 원래 발송 대상 주제의 식별자이며 클릭 화면을 그 날짜의 주제로 고정하지 않는다. 원래 예정 시각부터 30분 기한을 유지한다. FCM 결과·기기별 오류·무효 토큰 처리, 수락 기기 생략과 일시 실패 기기 재처리, 숨김·DLQ 정책은 NOTIFICATION-008을 재사용한다. 클릭 보고 API는 제공하지 않는다.
- 결정 기록: [주제 메시지의 공통 Worker 처리](../decisions/2026-10-12-topic-push-worker.md), [오늘 주제 참여 상태에 따른 발행·발송 제외](../decisions/2026-10-12-topic-push-participation.md)

주제의 정시 SQS 직접 발행과 Worker·FCM 처리는 연결되어 있다. 이번 참여 상태 검증의 실제 서버 적용은 #591 변경의 배포 여부와 별도로 확인한다.


## NOTIFICATION-011 주제 푸시 정시 실행과 SQS 직접 발행

- 규칙: 관리자 설정의 변경 이후 도래한 KST 발송 시각을 기준으로 회차를 실행한다. 실행이 늦어져도 원래 예정 시각부터 30분 안에서만 발행하며 기한을 연장하지 않는다. 해당 KST 날짜의 삭제되지 않은 주제가 있으면 주제 수신 설정이 켜진 정상 회원을 대상으로 사용자별 SQS 메시지를 직접 발행한다. 발행 대상 주제의 ID를 기준으로 삭제되지 않은 `VALIDATING`·`PENDING`·`APPROVED` 게시물이 하나라도 있는 회원은 제외한다. `REJECTED`·삭제된 게시물만 있거나 다른 주제에만 제출한 회원은 포함한다. 반려 후 다시 제출해 승인 대기 중이면 제외한다. 게시물 생성 날짜가 아닌 관련 주제 ID로 판단하며 게시물 재제출 가능 여부 API의 처리 시간 초과 기준은 적용하지 않는다. 승인/반려 수신 설정·현재 기기 등록 여부는 발행 대상 선정에서 제외 조건이 아니다. 로그인·현재 기기·최신 수신 조건은 Worker가 다시 확인한다.
- 적용 범위: 관리자 주제 푸시 설정의 정시 실행 → 대상 회원 선정 → 사용자별 SQS 발행. 승인·반려 Relay와 독립된 경로다.
- 예외: 실행 직전에 설정의 삭제·시각 수정 여부를 다시 확인한다. 이미 시작한 회차의 SQS 발행과 수락된 메시지는 이후 설정 변경만으로 취소하지 않는다. 오늘 주제가 없거나 대상이 없으면 해당 회차를 생략하며 같은 프로세스에서 다시 실행하지 않는다. 같은 회차의 사용자별 메시지는 동일한 사건 ID와 원래 발생·만료 시각을 공유한다. 주제 사건 ID는 알림 종류·주제 푸시 설정 ID·원래 예정 시각으로 결정하며, 재시작·배포 후 같은 회차를 다시 실행해도 유지한다. 실제 실행 시각·수신 회원·주제 문구는 사건 ID의 입력에 포함하지 않는다. 설정 또는 예정 시각이 달라지면 다른 사건이다. 한 회원의 발행 실패·수락 여부 불명은 다른 회원 발행을 중단시키지 않는다. 발행 결과는 성공·실패·결과 불명으로 기록하며 애플리케이션에서 최종 실패를 재발행하지 않는다. 발행 도중 기한에 도달하면 남은 회원을 생략한다. 단일 서버 프로세스는 회차의 시도 여부를 메모리에서 관리하고 주제 알림·Outbox·사용자별 DB 작업·진행률은 저장하지 않는다. 대상 조회 실패나 발행 도중 중단으로 일부 또는 전체 누락이 가능하다. 재시작·배포로 메모리가 사라지면 같은 회차를 다시 실행할 수 있어 중복 발행이 가능하다. 로그에는 설정 ID·사건 ID·원래 예정 시각과 대상·수락·실패·결과 불명·기한 생략 건수를 남긴다. SQS 수락 이후 처리는 NOTIFICATION-008·010을 따른다.
- 결정 기록: [주제 메시지의 공통 Worker 처리와 직접 발행](../decisions/2026-10-12-topic-push-worker.md), [오늘 주제 참여 상태에 따른 발행 대상 제외](../decisions/2026-10-12-topic-push-participation.md), [직접 발행 회차의 사건 식별자 유지](../decisions/2026-10-26-push-occurrence-event-id.md)

#591은 SQS 발행 대상 선정과 Worker의 기기별 발송 직전에 같은 참여 상태 조건을 확인한다. 메시지 필드·앱 요청 계약은 유지하며 실제 서버 적용은 해당 변경의 배포 여부로 확인한다.

## NOTIFICATION-012 관리자 공지 작성·수정·삭제

- 규칙: ADMIN 권한의 관리자는 제목·본문·발송 예약 시각으로 공지를 등록하고, 등록한 공지를 등록 최신순 목록과 상세로 조회한다. 제목은 1~50자, 본문은 1~500자이며 앞뒤 공백을 제거한 뒤 Unicode code point 기준으로 센다. 예약 시각은 필수이고 별도 즉시 발송 요청 없이 현재 시각을 예약 시각으로 보내 즉시 발송을 요청한다. 요청 처리 시각보다 5분 넘게 과거인 예약 시각은 거절하며 5분 이내의 과거와 현재 시각은 허용한다. 미래 쪽 예약 기간에는 상한을 두지 않는다. 배포 전 공지는 제목·본문·예약 시각을 함께 보내 수정하며, 검증 기준은 등록과 같다. 공지 작성·수정은 처리 관리자와 제목·예약 시각·본문 SHA-256 해시(수정은 변경 전후)를 기존 감사 로그에 같은 트랜잭션으로 기록한다. 본문 원문은 공지에 보존한다. 공지는 앞뒤 공백을 제거한 1~500자 사유와 함께 삭제하며, 배포 전 삭제는 발송 취소, 배포 후 삭제는 회원 알림함에서 숨김이 된다. 삭제는 행을 남기는 논리 삭제이며 처리 관리자, 사유, 삭제 전후 상태(제목·예약 시각·본문 해시·삭제 시각)를 감사 로그에 같은 트랜잭션으로 기록한다. 관리자 목록·상세는 삭제된 공지도 삭제 시각과 함께 보여 준다.
- 적용 범위: 관리자 공지 등록·수정·삭제·목록·상세 조회
- 예외: 정확히 5분 전 예약 시각은 허용한다. 감사 기록이 실패하면 공지 등록·수정도 롤백한다. 본문은 원문을 감사 로그에 남기지 않으므로 설정값 형식 문구나 이미지 링크가 있어도 등록한다. 제목에 감사 로그가 민감 정보로 판정하는 값(이미지 URL, `password: …` 같은 토큰 형식 문자열 등)이 있으면 감사 기록과 함께 등록·수정을 거절한다. 감사 로그로는 본문 원문을 조회·복원할 수 없다. 공지 행에는 현재 본문만 남으므로, 발송 전 수정이 생기면 이전 본문은 확인할 수 없고 해시로 변경 여부만 구분한다. 발송 이후에는 본문을 바꿀 수 없어 최종 발송 본문은 공지 행에 보존되며, 해시로 그 본문을 기록한 작성·수정 감사 기록을 찾는다. 발송 전 초안은 회원에게 노출되지 않으므로 수정 이전 본문을 별도 이력으로 보관하지 않는다. 공지 전용 수신 설정은 두지 않으며, 수신 거부 수단이 없으므로 광고성 정보를 공지에 포함하지 않는다. 등록·수정 요청 자체는 푸시를 발송하지 않는다. 배포된 공지는 수정할 수 없다. 수정은 사유를 받지 않는다. 같은 내용으로 수정하면 변경 없이 현재 공지를 반환하고 감사 로그를 추가하지 않는다. 수정은 공지 행을 잠근 뒤 배포 여부를 확인하므로, 배포가 먼저 끝났으면 수정을 거절하고, 수정 중인 공지는 배포가 건너뛰었다가 다음 확인 때 수정된 내용으로 배포한다. 예약 시각이 5분 넘게 지났지만 아직 배포되지 않은 공지는 같은 예약 시각으로 수정할 수 없고 새 예약 시각을 지정해야 한다. 삭제된 공지는 수정할 수 없다. 이미 삭제한 공지를 다시 삭제하면 최초 삭제 결과를 유지하고 감사 로그를 추가하지 않으며, 반복 요청도 사유 조건을 충족해야 한다. 삭제도 공지 행을 잠근 뒤 처리하므로, 배포가 먼저 끝났으면 발송 후 삭제(숨김)가 되고, 삭제 중인 공지는 배포가 건너뛰며 삭제 후에는 배포하지 않는다. 감사 기록이 실패하면 삭제도 롤백한다.
- 결정 기록: [관리자 공지 알림 도입](../decisions/2026-10-12-admin-notice.md)

#592에서 공지 등록과 목록·상세 조회를, #594에서 예약 시각의 알림함 배포를, #595에서 공지 푸시 발송(NOTIFICATION-013)을 구현한다. #593에서 수정을, #612에서 삭제를 구현한다. API 계약은 [관리자 공지 연동 안내](../guides/admin-notices.md)를 참고한다.

## NOTIFICATION-013 관리자 공지의 알림함 배포와 푸시 발송

- 규칙: 서버는 KST 매 분 0초에 예약 시각이 지났고 아직 배포하지 않은 공지를 찾아, 탈퇴하지 않은 회원 전체의 알림함에 공지 알림을 한 건씩 생성하고 공지에 배포 시각을 기록한다. 정지 회원도 포함하며 공지 전용 수신 설정은 없다. 회원별 알림 생성과 배포 시각 기록은 한 트랜잭션으로 처리해 공지 하나를 한 번만 배포한다. 공지의 배포 상태(예약·배포 완료)는 배포 시각의 유무로 판단한다. 알림은 `type=NOTICE`, `sourceType=NOTICE`, `sourceId=공지 ID`이며 공지의 제목·본문을 복사한다. 알림의 생성 시각은 실제 배포 시각이고, 이 시각부터 30일 보관(NOTIFICATION-004)과 30분 푸시 기한을 적용한다. 생성한 알림은 발행 대기로 저장해 기존 Relay가 SQS로 발행한다. PushWorker는 공지 메시지(`type=NOTICE`, `sourceType=NOTICE`, 알림 ID 있음)를 받아 발송 직전에 알림·사건 식별자와 원래 발생·만료 시각이 DB 기록과 일치하는지 확인한다. 알림이 남아 있고 미읽음이며, 회원이 탈퇴하지 않았고 사용 가능한 로그인이 있는 현재 등록 기기로 공지 제목·본문을 보낸다. 승인·반려·주제 수신 설정은 확인하지 않으며 정지 회원에게도 보낸다. 배포 시각부터 30분 정각 이후에는 새 FCM 발송을 시작하지 않는다. FCM `data`는 `eventId`·`notificationId`·`type=NOTICE`·`sourceType=NOTICE`·`sourceId`이며 `eventId`와 `sourceId`는 모두 공지 ID다. 푸시를 누르면 알림 상세에서 공지 제목·본문을 보여 주고 단건 읽음 처리한다.
- 적용 범위: 예약 시각이 된 공지의 회원 알림함 배포, 관리자 공지의 배포 상태, 공지 SQS → PushWorker → FCM
- 예외: 배포 후 가입한 회원은 대상이 아니다. 서버가 멈춰 예약 시각을 지나쳤다면 다음 확인 때 배포하며, 알림 생성 시각과 푸시 기한도 그 시점부터 계산한다. 배포 도중 실패하면 알림 생성과 배포 시각 기록이 함께 롤백되어 공지는 배포되지 않은 상태로 남고 다음 확인 때 다시 배포한다. 한 공지의 실패는 다른 공지의 배포를 막지 않는다. 배포 후 Relay가 30분 안에 발행하지 못한 알림은 NOTIFICATION-007에 따라 만료되고 알림함에만 남는다. 여러 서버가 동시에 확인해도 공지 행을 잠가 한 서버만 배포한다. 배포는 서버 설정으로 켜고 끄며, 꺼진 동안 예약 시각이 지난 공지는 다시 켜질 때 배포한다. 알림이 읽혔거나 회원이 탈퇴했거나 기한이 지났거나 메시지가 DB 기록과 다르거나 현재 기기가 없으면 공지 푸시를 생략하고 메시지를 삭제한다. FCM 결과·기기별 오류·무효 토큰 처리, 수락 기기 생략과 일시 실패 기기 재처리, 숨김·DLQ 정책은 NOTIFICATION-008을 재사용한다. 공지별 발송 결과는 관리자 API로 제공하지 않고 공지 ID(`eventId`)로 조사 로그에서 확인한다. 삭제된 공지는 예약 시각이 되어도 배포하지 않는다. 배포 후 삭제한 공지의 알림은 알림함 목록·상세·미읽음·단건/전체 읽음에서 제외하고(응답 구조는 유지), Worker도 발송 직전 확인에서 푸시를 생략한다. 알림 기록은 남으며 30일 보관 후 삭제한다. 이미 FCM이 수락했거나 기기에 표시된 푸시는 회수하지 않으며, 그 푸시를 눌러도 상세는 찾을 수 없는 것으로 처리한다. 삭제된 공지의 알림도 Relay의 SQS 발행은 그대로 진행하고 발송만 Worker가 막는다.
- 결정 기록: [관리자 공지 알림 도입](../decisions/2026-10-12-admin-notice.md)

## NOTIFICATION-014 관리자 리마인더 등록·수정·삭제

- 규칙: ADMIN 권한의 관리자는 제목·본문·반복 방식·발송 대상·발송 시각으로 리마인더를 등록하고, 삭제하지 않은 리마인더를 등록 최신순 목록으로 조회한다. 리마인더는 관리자가 문구·일정·대상을 정해 보내는 참여 유도 푸시이며 회원 알림함에 저장하지 않는다. 제목은 1~50자, 본문은 1~500자이며 앞뒤 공백을 제거한 뒤 Unicode code point 기준으로 센다. 반복 방식은 일회성(`ONCE`)과 매일 반복(`DAILY`)이다. 발송 시각(`scheduledAt`)은 하나만 받으며, 일회성은 그 시각에 한 번, 매일 반복은 그 날짜부터 매일 같은 KST 시각을 뜻한다. 발송 대상은 전체(`ALL`), 오늘 주제 참여자(`TOPIC_PARTICIPANTS`), 오늘 주제 미참여자(`TOPIC_NON_PARTICIPANTS`) 중 하나다. 요청 처리 시각보다 과거인 발송 시각은 거절하며 현재 시각부터 허용한다. 지금 바로 보내려면 가까운 미래 시각을 지정한다. 미래 쪽 기간, 하루 발송 횟수, 발송 시각대에는 제한을 두지 않고 관리자 판단에 맡긴다. 수정은 다섯 필드를 함께 보내는 전체 교체이며 검증 기준은 등록과 같다. 일회성은 발송 시각 전에만 수정할 수 있고, 매일 반복은 언제든 수정할 수 있다. 수정의 과거 시각 검증은 발송 시각이나 반복 방식이 바뀔 때만 적용한다. 삭제는 사유 없이 행을 남기는 논리 삭제이며 삭제한 리마인더는 목록에서 제외한다. 등록·수정·삭제는 처리 관리자와 제목·본문 SHA-256 해시·반복 방식·대상·발송 시각(수정은 변경 전후, 삭제는 삭제 시각 포함 전후)을 기존 감사 로그에 같은 트랜잭션으로 기록한다.
- 적용 범위: 관리자 리마인더 등록·목록 조회·수정·삭제
- 예외: 1초라도 과거인 발송 시각은 거절한다. 감사 기록이 실패하면 등록·수정·삭제도 롤백한다. 본문은 원문을 감사 로그에 남기지 않으므로 설정값 형식 문구나 이미지 링크가 있어도 등록한다. 제목에 감사 로그가 민감 정보로 판정하는 값이 있으면 감사 기록과 함께 등록·수정을 거절한다. 등록·수정 요청 자체는 푸시를 발송하지 않는다. 일회성은 발송 시각 정각부터 수정할 수 없고 삭제만 할 수 있다. 이미 시작한 매일 반복은 발송 시각과 반복 방식을 그대로 두면 제목·본문·대상을 수정할 수 있으며, 발송 시각이나 반복 방식을 바꾸려면 새 발송 시각이 과거가 아니어야 한다. 발송 시각은 DB 저장 정밀도(마이크로초)까지 비교한다. 같은 내용으로 수정하면 변경 없이 현재 리마인더를 반환하고 감사 로그를 추가하지 않는다. 수정·삭제는 리마인더 행을 잠근 뒤 처리하므로 동시에 요청돼도 감사 로그의 변경 전 상태는 직전 변경 결과다. 삭제된 리마인더는 수정할 수 없다(400). 이미 삭제한 리마인더를 다시 삭제하면 최초 삭제 결과를 유지하고 감사 로그를 추가하지 않는다. 삭제를 되돌리는 API는 없다. 삭제된 리마인더는 관리자 목록에 나오지 않지만 감사 로그와 행은 남는다.
- 결정 기록: [관리자 리마인더 도입](../decisions/2026-10-21-admin-reminder.md), [발송 시각의 과거 허용 제거](../decisions/2026-10-22-reminder-push.md#발송-시각은-과거를-허용하지-않는다)

#724에서 리마인더 등록·목록 조회·수정·삭제를, #726에서 예정 시각의 대상 선정과 푸시 발송(NOTIFICATION-016)을 구현한다. API 계약은 [관리자 리마인더 연동 안내](../guides/admin-reminders.md)를 참고한다.

## NOTIFICATION-015 AI 리뷰 결과 알림

- 규칙: AI 리뷰가 최종 상태(완료 또는 실패)로 끝나면 리뷰를 요청한 작성자의 알림함에 결과를 한 건 저장한다. 완료는 `type=AI_REVIEW_COMPLETED`, 실패는 `type=AI_REVIEW_FAILED`이고 둘 다 `sourceType=POST`, `sourceId=게시물 ID`이다. 리뷰의 최종 상태는 알림과 관계없이 먼저 확정해 보존하고, 알림은 그 확정 뒤에 따로 저장한다. 알림은 요청 회차마다 한 건이며, 실패한 리뷰를 다시 요청해 또 끝나면 회차마다 알림이 생겨 게시물당 최대 3건이다(AIREVIEW-002). 같은 회차의 알림을 중복 저장하지 않는다. 문구는 서버가 결정해 생성할 때 확정하며 이후 다시 요청하거나 상태가 바뀌어도 이미 저장한 알림의 문구는 바뀌지 않는다. 완료는 제목 "AI 피드백이 도착했어요", 본문 "사진의 구도 점수와 피드백을 확인해 보세요."이고, 실패는 제목 "AI 피드백을 만들지 못했어요"에 요청 횟수가 남으면 본문 "잠시 후 다시 요청해 주세요.", 요청 횟수를 모두 썼으면 본문 "이 사진은 더 이상 AI 피드백을 요청할 수 없어요."이다. 실패 문구는 실패 사유를 나누지 않고 다시 요청할 수 있는지(AIREVIEW-005의 `canRequestAgain`)만 구분한다. 알림의 발생 시각(생성 시각)은 리뷰가 끝난 시각(완료 시각)이며 이 시각부터 30일 보관(NOTIFICATION-004)과 30분 푸시 기한을 적용한다. 생성 당시 탈퇴하지 않은 회원의 AI 리뷰 결과 푸시 수신 설정이 켜져 있으면 발행 대기(`PENDING`)로 저장해 기존 Relay가 SQS로 발행하고, 꺼져 있거나 탈퇴한 회원이면 알림함만 저장하고 발행 불필요(`NOT_REQUIRED`)로 처리한다. 정지 회원도 알림을 받는다. SQS 발행과 PushWorker·FCM 발송은 NOTIFICATION-007·008을 재사용하되 발송 직전 수신 설정은 승인·반려 설정이 아니라 AI 리뷰 결과 설정을 확인하며, 승인·반려 설정은 AI 리뷰 결과 알림에 영향이 없다. FCM `data`는 `eventId`·`notificationId`·`type`·`sourceType=POST`·`sourceId`이다. 알림함이나 푸시에서 알림을 누르면 알림 상세를 거치지 않고 `sourceId` 게시물의 AI 리뷰 화면으로 이동하고 `notificationId`로 단건 읽음 처리한다.
- 적용 범위: AI 리뷰 완료·실패 시의 알림함 저장과 초기 SQS 발행 상태, 알림함 표시와 클릭 이동, AI 리뷰 결과 푸시의 수신 설정
- 예외: 재시도를 기다리는 동안의 실패 시도, 늦게 도착해 반영하지 않은 처리 결과, 게시물을 쓸 수 없어(AIREVIEW-004) 실패한 경우는 알림을 만들지 않는다. 중단된 시도로 횟수를 모두 써서 실패로 끝난 경우는 알림을 만든다. 나중에 수신 설정을 켜도 발행 불필요로 생성한 알림을 소급 발송하지 않는다. 알림함 표시 기준은 승인 알림과 같다. 게시물이 삭제되면 목록·상세·미읽음·읽음에서 제외하고 푸시도 생략하며, 알림 기록은 30일 보관 뒤 삭제한다. 게시물의 공개 조건만 깨지고 삭제되지는 않은 경우에는 알림이 보일 수 있고 누르면 AI 리뷰 조회가 찾을 수 없음이 되는데 승인 알림도 같으며 이 틈을 없애는 일은 이 규칙의 범위 밖이다. 서버는 사용자가 해당 AI 리뷰 화면에서 결과를 기다리고 있어도 알림을 항상 만들고, 조회만으로 읽음 처리하지 않으므로(NOTIFICATION-003) 읽음 상태를 자동으로 바꾸지 않는다. 앱은 그 게시물의 AI 리뷰 화면을 보고 있는 중에 받은 푸시의 포그라운드 표시를 생략할 수 있다. 리뷰 결과는 알림 저장 성공 여부와 관계없이 항상 확정해 보존하며, 이미 만든 결과를 알림 때문에 다시 만들지 않는다. 확정 뒤 알림 저장이 실패하면 그 회차의 알림 한 건이 빠질 수 있고 이때 오류 로그를 남긴다. 결과는 AI 리뷰 조회로 확인할 수 있다. 가져간 횟수를 모두 써서 실패로 끝낸 건도 같다. 알림은 그 사건의 기록이라 실패 후 다시 요청해도 지난 회차 알림의 문구는 바뀌지 않는다. 푸시 발송 전에 다시 요청했는지는 확인하지 않아 실패 푸시가 나갈 수 있다. FCM 수락은 기기 수신 완료를 뜻하지 않는다.
- 결정 기록: [AI 리뷰 결과 알림 도입](../decisions/2026-10-22-ai-review-result-notification.md)

## NOTIFICATION-016 관리자 리마인더의 정시 발행과 푸시 발송

- 규칙: 서버는 KST 매 분 0초에 삭제되지 않은 리마인더마다 지금 보낼 회차를 판단한다. 일회성의 회차는 발송 시각이다. 매일 반복의 회차는 오늘 KST 날짜에 발송 시각의 KST 시각을 붙인 시각이며, 발송 시각(시작일) 이전에는 회차가 없다. 두 방식 모두 회차 시각부터 30분 안에서만 발행하고, 30분 정각부터는 그 회차를 보내지 않는다. 리마인더를 만들거나 마지막으로 수정한 시각과는 비교하지 않는다. 대상은 탈퇴하지 않은 정상 회원(정지 제외) 중 주제 푸시 수신을 켠 회원이다(NOTIFICATION-006). 전체 대상은 주제와 관계없이 보낸다. 오늘 주제 참여자·미참여자 대상은 회차의 KST 날짜에 삭제되지 않은 주제가 있을 때만 보내며, 주제의 참여 가능 시간과는 관계없다. 참여 판정은 NOTIFICATION-011과 같다. 그 주제에 삭제되지 않은 `VALIDATING`·`PENDING`·`APPROVED` 게시물이 있으면 참여자이고, `REJECTED`·삭제된 게시물만 있거나 다른 주제에만 제출했으면 미참여자다. 대상 회원마다 SQS 메시지를 직접 발행하며 알림함에는 저장하지 않는다. 메시지는 `type=REMINDER`, `sourceType=REMINDER`, `sourceId=리마인더 ID`이고 알림 ID가 없다. 같은 회차의 메시지는 같은 사건 ID와 원래 회차·만료 시각을 공유한다. 리마인더 사건 ID는 알림 종류·리마인더 ID·원래 회차 예정 시각으로 결정하며, 재시작 후 같은 회차를 다시 실행해도 유지한다. 문구·대상만 바뀌어도 같은 회차의 사건 ID는 유지하고, 다른 리마인더나 다른 예정 시각은 다른 사건이다. PushWorker는 기기별 FCM 요청 직전에 회원 상태, 주제 푸시 수신 여부, 리마인더 삭제 여부를 다시 확인한다. 참여자·미참여자 대상이면 회차 날짜의 주제와 그 회원의 참여 여부도 다시 확인한다. 제목·본문은 이때의 리마인더에서 읽는다. FCM `data`는 `eventId`·`type=REMINDER`·`sourceType=REMINDER`·`sourceId`이며 `notificationId`는 보내지 않는다. 푸시를 누르면 앱 메인 화면으로 이동하고 알림 상세·읽음 API는 호출하지 않는다.
- 적용 범위: 리마인더의 정시 회차 판단 → 대상 회원 선정 → 회원별 SQS 발행 → PushWorker의 발송 직전 확인 → FCM, Android·iOS 메시지 해석과 화면 이동
- 예외: 매일 반복은 자정이 지나면 전날 회차를 30분 기한 안이어도 보내지 않는다. 일회성은 회차가 날짜까지 정해져 있으므로 자정을 넘겨도 30분 기한 안이면 보내며, 대상은 회차의 KST 날짜(전날)의 주제로 판단한다. 발행 직전에 리마인더 행을 잠그고(`FOR UPDATE SKIP LOCKED`) 삭제 여부와 회차를 다시 확인한다. 관리자가 수정·삭제 중이라 행이 잠겨 있거나, 삭제됐거나, 회차가 바뀌었으면 이번 분은 건너뛰고 다음 확인 때 새 내용으로 판단한다. 그래서 수정을 마친 리마인더는 30분 기한 안이면 새 문구로 발행한다. 회차의 시도 여부는 단일 서버 프로세스의 메모리에 기록하고, 잠금을 얻은 뒤 기록한다. 기록한 회차는 같은 프로세스에서 다시 발행하지 않으며 대상 조회 실패·발행 도중 중단으로 일부 또는 전체가 누락될 수 있다. 재시작·배포로 메모리가 사라지면 같은 회차가 다시 발행될 수 있다. 이미 그날 회차를 보낸 매일 반복의 발송 시각을 같은 날 아직 오지 않은 시각으로 바꾸면, 바뀐 회차를 새 회차로 보아 그날 한 번 더 보낼 수 있다. 과거 시각은 지정할 수 없으므로 이미 보낸 회차를 다시 지정해 같은 회차를 다시 보내는 일은 없다. 참여자·미참여자 대상인데 회차 날짜의 주제가 없으면 그 회차를 생략하며, 30분 안에 주제가 생겨도 다시 시도하지 않는다. 대상 회원이 없으면 발행 없이 회차를 마친다. 한 회원의 발행 실패·수락 여부 불명은 다른 회원 발행을 중단시키지 않고, 애플리케이션에서 재발행하지 않는다. 발행 도중 기한에 도달하면 남은 회원을 생략한다. 정시 발행은 서버 설정으로 켜고 끄며, 꺼진 동안 지나간 회차는 다시 켜도 30분 기한이 지났으면 보내지 않는다. 이미 SQS에 발행한 메시지는 이후 수정·삭제만으로 취소하지 않는다. Worker는 발송 직전의 리마인더로 판단하므로, 발행 뒤 삭제하면 발송을 생략하고 문구를 고치면 고친 문구로 보낸다. 대상을 바꾸면 이미 발행한 메시지는 바뀐 대상 조건으로 확인하지만, 새로 대상이 된 회원에게 추가로 발행하지는 않는다. 발행 뒤 발송 시각을 바꿔도 이미 발행한 메시지는 원래 기한 안에서 보낸다. 정지·탈퇴, 주제 푸시 수신 해제, 리마인더 삭제, 회차 날짜의 주제 없음, 참여자 대상인데 참여하지 않음, 미참여자 대상인데 그 사이 참여함, 만료·폐기된 로그인, 현재 기기 없음, 30분 기한 경과는 발송하지 않는다. 확인 직후의 제출과 이미 시작한 외부 요청이 겹치는 경우까지 원자적으로 막지는 않는다. 승인·반려 수신 설정은 리마인더 발송 여부에 영향을 주지 않는다. FCM 결과·기기별 오류·무효 토큰 처리, 수락 기기 생략과 일시 실패 기기 재처리, 숨김·DLQ 정책은 NOTIFICATION-008을 재사용한다. 리마인더별 발송 결과는 관리자 API로 제공하지 않고 리마인더 ID·사건 ID로 조사 로그에서 확인한다. 이미 FCM이 수락했거나 기기에 표시된 푸시는 회수하지 않는다. 클릭 보고 API는 제공하지 않는다.
