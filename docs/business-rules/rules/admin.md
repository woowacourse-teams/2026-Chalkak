# 관리자 규칙

## ADMIN-001 접근 권한

- 규칙: 로그인 외 관리자 기능은 `ADMIN` 권한으로 인증된 관리자만 사용할 수 있다. 일반 회원은 접근할 수 없으며 관리자별 세부 역할은 구분하지 않는다.
- 적용 범위: 관리자 API 전체
- 예외: 인증 우회는 설정으로 명시한 로컬·테스트 환경에서만 허용한다.
- 결정 기록: 없음

## ADMIN-002 회원 상태 관리

- 규칙: 관리자는 탈퇴하지 않은 회원을 `ACTIVE`에서 `BANNED`로 차단하거나 `BANNED`에서 `ACTIVE`로 해제할 수 있다. 탈퇴 회원은 `deletedAt`을 기준으로 `WITHDRAWN`으로 표시한다.
- 적용 범위: 관리자 회원 조회와 상태 변경
- 예외: 같은 상태로의 변경과 `WITHDRAWN` 회원의 상태 변경은 허용하지 않는다. 차단과 해제에는 공백만이 아닌 사유가 필요하며, 앞뒤 공백을 제거한 후 Unicode code point 기준 최대 500자까지 허용한다.
- 결정 기록: 없음

## ADMIN-003 게시물 검수

- 규칙: 관리자는 `PENDING` 게시물을 한 번만 `APPROVED` 또는 `REJECTED`로 확정할 수 있다.
- 적용 범위: 관리자 게시물 검수
- 예외: 승인에는 사유를 입력할 수 없다. 반려에는 앞뒤 공백을 제거한 1~500자의 사유가 필요하다.
- 결정 기록: 없음

## ADMIN-004 게시물 조회와 삭제

- 규칙: 관리자는 `PENDING`, `APPROVED`, `REJECTED` 게시물과 이미 삭제된 게시물을 조회할 수 있다. `PENDING`, `APPROVED`, `REJECTED` 게시물은 사유와 함께 삭제할 수 있다. 삭제 사유는 필수이며 공백만 입력할 수 없다. 앞뒤 공백을 제거하기 전 Unicode code point 기준 최대 500자까지 허용하고, 저장 시 앞뒤 공백을 제거한다.
- 적용 범위: 관리자 게시물 관리
- 예외: `VALIDATING` 게시물은 관리자 조회·검수·삭제 대상이 아니다. 삭제는 게시물과 사진을 논리 삭제하고 좋아요를 제거하지만 실제 미디어 파일은 보존한다. 이미 삭제된 게시물에 유효한 삭제 요청을 반복하면 최초 삭제 결과를 유지하고 감사 로그를 추가하지 않는다. 반복 요청도 삭제 사유 조건을 충족해야 한다.
- 결정 기록: 없음

## ADMIN-005 주제 관리

- 규칙: 관리자는 주제를 생성하고 공개 전 수정·삭제할 수 있다. 세부 상태와 날짜 제약은 [주제 규칙](topic.md)을 따른다.
- 적용 범위: 관리자 주제 관리
- 예외: 주제 삭제에는 앞뒤 공백을 제거한 1~500자의 사유가 필요하다.
- 결정 기록: 없음

## ADMIN-006 감사 로그

- 규칙: 게시물 승인·반려·삭제, 회원 차단·해제, 주제 생성·수정·삭제, 주제 푸시 설정 생성·시각 수정·삭제, 공지 작성·수정·삭제, 배너 등록·삭제, 리마인더 등록·수정·삭제는 처리 관리자, 행위, 대상, 사유, 변경 전후 상태, 처리 시각, 요청 식별자를 감사 로그로 남긴다.
- 적용 범위: 관리자 변경 작업
- 예외: 민감정보, 토큰, 비밀번호, 이미지 URL, 스토리지 키와 바이너리는 기록하지 않는다. 주제 푸시 설정은 대상 식별자와 변경 전후의 KST 발송 시각(`sendTime`)만 기록하며 별도 변경·삭제 사유를 요구하지 않는다. 같은 시각으로 수정하는 재요청은 변경 이력을 추가하지 않는다. 설정 행이 삭제돼도 감사 로그는 유지한다. 공지 작성·수정은 제목·예약 시각과 본문 원문 대신 본문의 SHA-256 해시를 기록하며(수정은 변경 전후) 별도 사유를 요구하지 않는다. 같은 내용으로 공지를 수정하는 재요청은 변경 이력을 추가하지 않는다. 공지 삭제는 앞뒤 공백을 제거한 1~500자 사유와 함께 삭제 전후 상태(제목·예약 시각·본문 해시·삭제 시각)를 기록하며, 이미 삭제한 공지의 반복 삭제는 변경 이력을 추가하지 않는다. 감사 로그로는 공지 본문 원문을 조회·복원할 수 없다. 제목에 민감 정보로 판정되는 값이 있으면 감사 기록과 함께 작성·수정을 거절한다. 배너 등록은 제목·부제목의 SHA-256 해시만 기록하고 URL과 문구 원문은 기록하지 않으며 별도 사유를 요구하지 않는다. 배너 삭제는 별도 사유 없이 제목·부제목 해시·삭제 시각의 전후 상태를 기록한다. 배너 삭제의 감사 사유는 null이며, 삭제와 감사는 같은 트랜잭션이고 반복 삭제는 이력을 추가하지 않는다. 리마인더 등록·수정·삭제는 제목·반복 방식·대상·발송 시각과 본문 원문 대신 본문의 SHA-256 해시를 기록하며(수정은 변경 전후, 삭제는 삭제 시각을 포함한 전후) 별도 사유를 요구하지 않는다. 같은 내용으로 리마인더를 수정하는 재요청과 이미 삭제한 리마인더의 반복 삭제는 변경 이력을 추가하지 않는다. 제목에 민감 정보로 판정되는 값이 있으면 감사 기록과 함께 등록·수정을 거절한다.
- 결정 기록: [주제 푸시 설정과 감사 기록](../decisions/2026-10-08-topic-push-schedules.md#주제-푸시-설정의-감사-기록-보완), [관리자 공지 알림 도입](../decisions/2026-10-12-admin-notice.md), [배너 등록 도입](../decisions/2026-10-19-banner-registration.md), [배너 논리 삭제와 재등록](../decisions/2026-10-19-banner-deletion.md), [관리자 리마인더 도입](../decisions/2026-10-21-admin-reminder.md)

## ADMIN-007 변경과 감사의 일관성

- 규칙: 관리자 변경과 감사 로그는 같은 트랜잭션에서 처리한다. 어느 한쪽이 실패하면 둘 다 반영하지 않으며 감사 로그는 수정·삭제하지 않는다.
- 적용 범위: 관리자 게시물·회원·주제·주제 푸시 설정·공지·리마인더 변경과 배너 등록·삭제
- 예외: 없음
- 결정 기록: [배너 등록 도입](../decisions/2026-10-19-banner-registration.md), [배너 논리 삭제와 재등록](../decisions/2026-10-19-banner-deletion.md), [관리자 리마인더 도입](../decisions/2026-10-21-admin-reminder.md)

## ADMIN-008 검수 요청 알림

- 규칙: 관리자 알림이 활성화된 환경에서는 게시물이 `PENDING`에 진입한 변경이 커밋된 후 관리자 검수 요청 알림을 발송한다.
- 적용 범위: 처리 완료된 사진의 게시물 생성, 게시물 이미지 처리 완료, 관리자 알림
- 예외: 알림이 비활성화된 환경에서는 발송하지 않는다. 알림 발송 실패는 이미 완료된 게시물 변경을 되돌리지 않는다.
- 결정 기록: 없음

## ADMIN-009 피드백 조회

- 규칙: 관리자는 접수된 사용자 피드백을 작성자 정보와 함께 조회할 수 있다. 조회 항목과 범위는 [피드백 규칙](feedback.md)을 따른다.
- 적용 범위: 관리자 피드백 조회
- 예외: 피드백은 조회만 할 수 있어 관리자 변경 작업이 아니므로 ADMIN-006 감사 로그 대상이 아니다.
- 결정 기록: [피드백 수집 도입](../decisions/2026-09-16-feedback-collection.md)

## ADMIN-010 AI 프롬프트 미리보기

- 규칙: 관리자는 저장하지 않은 AI 프롬프트 초안을 공개 게시물에 실행해 결과를 확인할 수 있다. 공개 게시물은 [POST-007](post.md#post-007-공개-범위)을 따라 `APPROVED`이고 게시물·주제·사진·작성자가 모두 삭제되지 않은 게시물이며, 그 밖의 게시물은 없는 것으로 취급한다. 모델은 서버가 허용한 목록의 모델만 사용할 수 있고 허용되지 않은 모델은 OpenAI를 호출하지 않고 거절한다. 실행 결과(변환된 리뷰 결과, 모델 원점수, 토큰 사용량, 지연시간)는 저장하거나 회원에게 노출하지 않으며 감사 로그 대상이 아니다. 입력이 유효하면 OpenAI 호출의 실패(시간 초과, 요청 한도, 서버 오류, 거절, 출력 불완전·형식 오류 등)도 오류가 아닌 결과로 돌려주고, 실패 유형과 재시도 가능 여부를 함께 알린다.
- 적용 범위: 관리자 AI 프롬프트 미리보기
- 예외: 시스템 프롬프트에는 템플릿 변수를 쓸 수 없고, 사용자 프롬프트 템플릿은 용도가 허용한 변수만 쓸 수 있다. 변수 값은 항상 JSON 문자열 규칙으로 이스케이프해 넣는다. 사용량·지연시간·응답 ID는 OpenAI가 응답 본문을 준 경우에만 있다. 프롬프트·이미지 주소·주제·피드백 원문은 로그에 남기지 않는다.
- 결정 기록: [AI 프롬프트 미리보기 도입](../decisions/2026-10-19-ai-prompt-preview.md)

## ADMIN-011 AI 프롬프트 버전

- 규칙: 관리자는 AI 프롬프트 버전을 용도(type)별로 만들고 조회할 수 있다. 만든 버전은 수정하거나 삭제할 수 없으며, 내용을 바꾸거나 되돌리려면 새 버전을 만든다(예: 이전 버전의 내용으로 새 버전 생성). 버전 번호는 용도별로 1부터 시작해 하나씩 늘어나고, 동시에 만들어도 번호가 겹치지 않는다. 목록은 용도 하나의 버전을 최신(번호가 큰 것)부터 페이지 단위로 보여 주며 프롬프트 본문은 담지 않고, 상세는 본문과 호출 옵션까지 전체를 보여 준다. 없는 버전을 조회하면 404이다. 사용자 기능이 프롬프트를 쓸 때는 해당 용도의 가장 최신 버전을 사용하므로, 버전을 만들면 곧바로 적용된다(적용 시점은 예외 참고). 따라서 관리자는 미리보기([ADMIN-010](#admin-010-ai-프롬프트-미리보기))로 확인한 내용만 만든다. 용도에 버전이 하나도 없으면 그 기능은 꺼진 상태이다. 버전을 만들 때마다 같은 트랜잭션에서 관리자 감사 로그를 남기며, 로그에는 용도와 버전 번호만 담고 프롬프트 본문은 복사하지 않는다.
- 적용 범위: 관리자 AI 프롬프트 버전 생성·목록·상세 조회
- 예외: 사용자 기능(AI 리뷰 요청, [AIREVIEW-001](ai-review.md#aireview-001-요청-자격))은 [#689](https://github.com/woowacourse-teams/2026-Chalkak/issues/689)부터 용도의 가장 최신 버전을 곧바로 사용하므로, 만든 버전은 즉시 사용자에게 쓰인다. 최신 버전이 서버가 해석할 수 없는 출력 형식이거나 허용되지 않은 모델이면 이전 버전으로 대신하지 않고 기능이 꺼진 것으로 본다. 명시적 비활성화([#701](https://github.com/woowacourse-teams/2026-Chalkak/issues/701))가 생기기 전에는 데이터를 바꾸지 않고 기능을 끄려면 서버가 허용한 모델 목록에서 해당 모델을 빼고 재배포한다. 처리 대기 중인 요청도 OpenAI를 호출하기 직전에 다시 확인하며, 허용되지 않은 모델이면 호출 없이 실패로 끝낸다(현재 실패는 최종이라 그 요청은 다시 처리되지 않는다). 이와 별도로 OpenAI 예산 한도를 둔다. 입력 검증은 ADMIN-010 미리보기와 같다(허용된 템플릿 변수만 사용, 시스템 프롬프트에는 변수 사용 불가, 호출 옵션 범위, 서버가 허용한 모델). 출력 스키마 버전은 요청으로 받지 않고 서버가 만들 때 기록한다. 명시적인 활성화·비활성화는 이 규칙에 없으며 #701에서 다룬다.
- 결정 기록: [AI 프롬프트 버전 도입](../decisions/2026-10-19-ai-prompt-versions.md), [AI 리뷰 요청·조회 도입](../decisions/2026-10-20-ai-review.md)

## ADMIN-012 AI 리뷰 조회

- 규칙: 관리자는 모든 AI 리뷰를 작성자 정보(식별자·이메일·상태)와 함께 조회할 수 있다. 게시물·주제·사진 삭제, 검수 미승인, 작성자 탈퇴로 작성자 앱에서 보이지 않는 리뷰도 포함한다([AIREVIEW-003](ai-review.md#aireview-003-공개-범위), [AIREVIEW-004](ai-review.md#aireview-004-삭제탈퇴정지)). 목록은 상태와 프롬프트 버전으로 걸러 볼 수 있고 마지막 요청 시각이 최신인 것부터 페이지 단위로 보여 준다. 알 수 없는 프롬프트 버전으로 거르면 오류가 아니라 빈 목록이다. 상세는 목록 항목에 더해 변환된 리뷰 결과, 모델이 돌려준 원출력(완료된 리뷰만), 호출 기록(토큰 사용량, 지연시간, OpenAI 응답 ID)을 보여 준다. 없는 리뷰를 조회하면 404이다. 각 항목은 작성자 앱에서 이 리뷰가 보이는지(`visibleToAuthor`)를 함께 알린다. 게시물이 승인됐고 게시물·주제·사진·작성자가 모두 삭제되지 않았을 때만 참이며([POST-007](post.md#post-007-공개-범위)와 같은 조건), 이용 정지만으로는 거짓이 되지 않는다([USER-002](user.md#user-002-이용-정지)). 게시물 삭제·검수 상태·작성자 상태는 가공하지 않은 값으로 함께 보여 주며, 주제·사진 삭제는 `visibleToAuthor`로만 드러난다.
- 적용 범위: 관리자 AI 리뷰 목록·상세 조회
- 예외: 오류 코드(실패 사유)는 관리자에게만 보이며 앱에는 노출하지 않는다([AIREVIEW-005](ai-review.md#aireview-005-결과-표시)). 자동 재시도를 기다리는 동안과 그 재시도를 처리하는 동안에도 직전 시도의 오류 코드가 남는다. 사용량·지연시간·응답 ID는 마지막 호출의 값이며 OpenAI가 응답 본문을 준 경우에만 있다. 원출력은 완료된 리뷰만 있고 그 밖의 상태에서는 없다. 같은 게시물의 리뷰는 하나이며 다시 요청하면 같은 리뷰가 새 회차의 프롬프트 버전으로 다시 고정되므로, 프롬프트 버전 필터와 마지막 요청 시각 정렬은 가장 최근 회차를 기준으로 한다. 정렬 기준이 다시 요청할 때 바뀌므로, 페이지를 넘기는 사이 다시 요청된 리뷰가 있으면 같은 리뷰가 두 페이지에 보이거나 한 건을 건너뛸 수 있다. 목록의 종합 점수는 완료된 리뷰만 값이 있다. 조회 조건은 상태가 AI 리뷰 처리 상태 중 하나, 프롬프트 버전 ID가 UUID 형식, 페이지가 1 이상, 페이지 크기가 1~100(기본 20)이어야 하며 어긋나면 잘못된 조회 조건으로 거절한다. 조회만 하므로 변경 작업이 아니어서 [ADMIN-006](#admin-006-감사-로그) 감사 로그 대상이 아니다.
