# 앱 최소 지원 버전 규칙

## APPVERSION-001 플랫폼별 공개 조회

- 규칙: 앱은 로그인 전에 `GET /api/v1/app-version?platform={platform}`으로 플랫폼별 최소 지원 버전과 스토어 주소를 조회한다. 플랫폼은 `ANDROID` 또는 `IOS`이며 서로 독립적인 설정을 사용한다. 응답은 `platform`, `minimumSupportedVersion`, `storeUrl`이다.
- 적용 범위: Android·iOS 앱 최소 지원 버전 조회
- 예외: 플랫폼 누락·빈 값·지원하지 않는 값은 400이다. 정상·정지·탈퇴 회원과 관리자도 같은 설정을 조회할 수 있지만, 잘못된 인증 정보를 보내면 기존 인증 규칙에 따라 거절한다. 앱은 인증 헤더 없이 호출할 수 있다.
- 결정 기록: [관리자 입력 전에는 업데이트 제한을 적용하지 않는다](../decisions/2026-10-28-app-version-query.md)

## APPVERSION-002 최초 설정 전 이용

- 규칙: 최소 지원 버전과 스토어 주소는 관리자가 입력한다. 초기 예시 값이나 임의의 기본 버전을 만들지 않는다. 설정이 없는 플랫폼은 200으로 요청한 `platform`과 `minimumSupportedVersion: null`, `storeUrl: null`을 반환한다. 앱은 이 정상 응답에서 업데이트 제한 없이 이용을 허용한다.
- 적용 범위: 플랫폼별 최초 설정 이전의 조회와 앱 진입 판단
- 예외: 네트워크·서버 오류는 정상 미설정 응답과 다르며, 조회 실패 시 마지막 설정 사용 여부와 앱 진입 처리는 아직 합의하지 않았다. 최초 저장은 관리자 API로만 할 수 있으며 공개 조회로 설정이 생성되지는 않는다.
- 결정 기록: [관리자 입력 전에는 업데이트 제한을 적용하지 않는다](../decisions/2026-10-28-app-version-query.md)

## APPVERSION-003 설정 반영과 앱 비교

- 규칙: 서버는 현재 DB 설정을 조회하고 `Cache-Control: no-store`를 지정한다. 설정이 있으면 앱은 버전 각 자리의 숫자를 순서대로 비교한다. 최소 버전 미만이면 서비스 진입을 제한하고 업데이트 버튼으로 `storeUrl`을 연다. 최소 버전 이상이면 정상 이용한다. 예를 들어 `1.10.0 > 1.9.0`이다.
- 적용 범위: 조회의 최신성, Android·iOS의 업데이트 판단 계약
- 예외: 비교·화면·스토어 이동은 클라이언트 연동 작업이다. 이 연동이 없는 기존 앱에는 서버 설정만으로 업데이트를 강제할 수 없다. 이번 조회는 모든 업무 API에 구버전 차단을 적용하지 않는다. 호출 시점·주기와 통신 실패 처리는 앱 연동 전에 합의한다.
- 결정 기록: [관리자 입력 전에는 업데이트 제한을 적용하지 않는다](../decisions/2026-10-28-app-version-query.md)

## APPVERSION-004 관리자 조회와 저장

- 규칙: 관리자만 `GET /api/v1/admin/app-versions`로 ANDROID·IOS 순서의 두 설정을 조회하고 `PUT /api/v1/admin/app-versions/{platform}`으로 최초 입력·수정한다. 각 플랫폼은 독립적이며 저장 성공은 모두 200이다. 저장된 값은 다음 공개 조회부터 앱 재배포 없이 반영한다. 조회·저장은 최소 버전·스토어 주소·revision·최종 변경자·변경 사유·생성 및 변경 시각을 반환한다.
- 적용 범위: 관리자 앱 버전 설정 조회·최초 저장·수정
- 예외: 미설정이면 platform 외 필드는 null이다. 이전에 직접 입력한 데이터는 최종 변경자·사유가 null일 수 있다. 버전을 낮춰 잘못 적용한 업데이트 제한을 되돌릴 수 있다. 관리자 웹 화면은 별도 연동 작업이다.
- 결정 기록: [관리자 입력 검증과 안전한 변경](../decisions/2026-10-29-admin-app-version.md)

## APPVERSION-005 관리자 입력 조건

- 규칙: 최소 버전은 정확히 세 숫자의 `major.minor.patch` 형식이며 각 숫자는 0~2,147,483,647이다. 0을 제외한 숫자의 앞자리 0은 금지한다. 스토어 주소와 사유는 앞뒤 공백을 제거한다. 주소는 1~2,000자이며 HTTPS·플랫폼별 공식 호스트·앱 상세 경로·앱 ID 형식을 검증한다. 사유는 Unicode code point 기준 1~500자이다. 잘못된 입력은 400이다.
- 적용 범위: 관리자 저장과 감사 기록의 입력 검증
- 예외: Android는 `play.google.com/store/apps/details?id={패키지명}`에 선택적으로 hl·gl을 허용한다. iOS는 `apps.apple.com/[국가/]app/[앱이름/]id{양의 숫자}`에 선택적으로 l·mt=8을 허용한다. 사용자 정보·다른 포트(443 제외)·fragment·잘못된 경로 이동·인코딩된 경로 구분자·중복 쿼리·이외 쿼리는 거절한다. 서버는 실제 Chalkak 앱인지, 해당 버전이 스토어에서 설치 가능한지 자동 판정하지 않는다. 최소 버전을 올리기 전 관리자가 앱 식별자와 출시·국가·기기·단계적 배포 범위를 직접 확인한다.
- 결정 기록: [관리자 입력 검증과 안전한 변경](../decisions/2026-10-29-admin-app-version.md)

## APPVERSION-006 중복 저장·충돌·감사

- 규칙: 최초 저장은 revision=null, 수정은 조회한 revision으로 요청한다. 값이 바뀌는 저장은 플랫폼별로 직렬화하고 현재 revision과 다르면 400 RESOURCE_STATE_CHANGED로 거절한다. 최초 revision은 0이며 변경마다 1 증가한다. 변경 전후 플랫폼·최소 버전·검증된 스토어 주소·revision과 변경자·시각·사유·요청 식별자를 같은 트랜잭션으로 감사 기록에 남긴다. 어느 한쪽이 실패하면 설정과 감사 기록을 모두 취소한다.
- 적용 범위: 동시 최초 저장·수정·재시도와 기존 관리자 감사 이력 조회
- 예외: 버전과 정규화된 주소가 현재 값과 같으면 오래된 revision의 재시도도 현재 설정을 그대로 반환한다. 이때 최종 관리자·사유·변경 시각·revision·감사 이력을 바꾸지 않는다. 재시도도 입력 조건은 충족해야 한다. 감사 원문의 URL 허용은 검증된 스토어 주소에 한정하며 일반 URL과 민감정보 금지는 유지한다.
- 결정 기록: [관리자 입력 검증과 안전한 변경](../decisions/2026-10-29-admin-app-version.md)
