# 공통 비즈니스 규칙

## 작업 영역별 권한

- `backend/**` 작업에서는 사용자와 합의한 정책만 아래 절차에 따라 규칙 문서에 반영할 수 있다.
- `client/**` 작업에서는 `docs/business-rules/**`를 읽기 전용으로 사용한다. 현재 규칙이 명확하면 추가 질문 없이 그 규칙과 API 계약에 맞춰 구현하고, 규칙·결정 기록·목차·Notion 매핑을 생성·수정·삭제하지 않는다.
- client 작업에서 규칙이 없거나 규칙과 API·서버 동작이 충돌하면 관련 규칙 ID와 차이만 알리고 백엔드 확인 대상으로 남긴다. 해당 정책을 추측하거나 client 코드로 새로운 기준을 확정하지 않는다. 영향받지 않는 작업은 계속할 수 있다.

## 확인과 대조

- [목차](../../../docs/business-rules/README.md)에서 관련 도메인의 활성 규칙만 읽는다. 미등록 문서와 템플릿은 정책이 아니다. 변경 이유가 필요할 때만 연결된 결정 기록을 읽는다.
- Git의 Markdown을 원본으로 유지한다. Notion은 사람이 갱신하는 공유본이다. 이 흐름에서는 MCP·브라우저·컴퓨터 제어로 Notion을 조회하거나 수정하지 않는다.
- 인터뷰를 마칠 때 기능별 합의·예외·미결정 사항을 이슈 초안에 남기고 관련 규칙 ID와 신규·변경 여부를 연결한다. 미승인 제안은 활성 규칙으로 기록하지 않는다.
- 구현 완료와 PR 작성 전에 **합의 → 실제 코드·테스트 → 규칙**, **변경된 코드 → 문서화되지 않은 정책** 양방향으로 대조한다. 테스트 통과나 문서 파일 변경만으로 누락 없음이라고 결론 내리지 않는다.
- 관련 기능에서 권한·정지/탈퇴, 입력 경계, 상태 전이·시간 경계, 반복·동시 요청, 실패·재시도·취소, 조회·공개 범위, 데이터 삭제·외부 부수 효과를 확인한다. 모든 도메인을 매번 검사하지 않는다.
- 코드·합의가 충돌하면 쟁점을 확인한다. 현재 동작을 설명하는 누락 보완과 새로운 정책 결정을 구분하고, 확인하지 못한 범위를 완료로 표시하지 않는다.

## 문서 반영

- 합의된 정책은 관련 `rules/*.md`의 현재 내용으로 갱신한다. 규칙 ID를 유지하고 규칙·적용 범위·예외·결정 기록을 채운다. 신규 도메인은 활성 표시와 목차도 갱신한다.
- 신규 정책의 확정 또는 정책의 의미 변경·제거에는 [결정 템플릿](../../../docs/business-rules/decisions/_template.md)으로 변경 전후·이유·영향·관련 규칙·이슈를 남기고 규칙에서 연결한다. 기존 코드의 누락 문서화·표현 수정에는 새 정책을 결정한 것처럼 기록하지 않는다.
- 규칙 ID나 도메인을 추가·삭제·이름 변경하면 [수동 반영 위치](../../../docs/business-rules/notion-map.yml)도 갱신한다. URL·계정·페이지 ID는 필요하지 않다.
- 구현과 같은 합의로 바뀐 문서는 같은 PR에 포함한다. 정책 의미와 무관한 구현 세부사항은 규칙에 넣지 않는다.

## PR와 완료 안내

- PR은 저장소의 기존 양식을 사용하고 실제 규칙 변경은 `작업 내용`에 다른 변경과 함께 설명한다. 비즈니스 규칙 전용 섹션이나 체크리스트를 추가하지 않는다.
- 현재 규칙이 바뀌면 작업 종료 시 [Notion 수동 반영 절차](../../../docs/business-rules/NOTION_SYNC.md)를 읽어 변경된 규칙의 위치·수정 방법·완성 문구를 안내한다. 결정 기록은 Git에만 남긴다.
- Notion 반영 완료를 추적하거나 병합을 감시하지 않는다. 다음 작업 재개를 수동 반영 확인 때문에 막지 않는다.

## 공유 배포본과 작업 시작·재개

- 이 스킬이 `.chalkak-harness/active/` 아래 배포본에서 로드되었다면 문서·참조 경로를 그 배포본 기준으로 해석한다. 심볼릭 링크의 실제 스킬 경로를 확인하거나 `.chalkak-harness/active/docs/business-rules/README.md`를 사용한다. 배포본 전체는 읽기 전용이며 백엔드 정책 수정도 `be/develop` 기반 원본 작업 폴더에서 진행한다.
- 설치된 프로젝트에서는 정책 관련 작업의 시작·재개 때 저장소 루트에서 `python3 .chalkak-harness/manage.py status --project . --check`로 설치 버전·확인 시각·사용 가능한 버전·변경 파일을 확인한다. 자동 내려받기는 실행 중인 프로젝트의 적용 버전을 바꾸지 않는다.
- 새 버전이 있으면 관련 도메인과 스킬의 전후 내용을 대조한다. 파일 변경을 곧바로 정책 의미 변경으로 판단하지 않는다. 적용은 작업을 정리한 뒤 `apply`하고 새 AI 세션에서 진행한다. 이전 버전의 맥락에 새 지침을 섞어 진행하지 않는다.
- 실제 읽은 도메인·규칙 ID, 이번 작업에 적용할 내용과 관련 변경 영향을 짧게 알린다. 작업 기록을 사용한다면 읽은 배포 버전과 규칙을 남긴다. 매 응답마다 같은 안내를 반복하지 않는다.
- 설치 누락·원격 조회 실패·배포본 변조는 각각 그대로 알린다. 실패 시 기존 문서를 읽었더라도 최신 확인을 완료했다고 하지 않는다. 영향받지 않는 작업은 이어갈 수 있다.
- 정책 합의·코드 구현·병합·서버 배포는 별개다. 배포본이 최신이라는 이유로 해당 API가 운영 서버에 반영되었다고 가정하지 않는다. 문서와 실제 API가 충돌하면 관련 쟁점을 백엔드 확인 대상으로 남긴다.

## Android 팀에 전달할 변경 안내

- 백엔드에서 현재 규칙을 변경했다면 완료 안내에 사람이 전달할 문구를 함께 작성한다. 변경된 규칙 ID와 전후 차이, Android 화면·요청·오류 처리 영향, 관련 문서·백엔드 PR, 확인된 공통 배포 버전과 서버 적용 상태, 필요한 Android 작업·미확인 사항을 포함한다.
- 아직 등록되지 않은 PR·배포 버전은 미등록·미배포로 표시한다. 정책 설명만 다듬은 작업을 API 변경으로 안내하지 않는다.
- 이 문구는 기존 Notion 수동 반영 안내와 구분한다. 팀 채널·메일·Notion에 자동 발송하거나 반영하지 않는다. 배포·설치 성공을 AI가 실제로 문서를 읽고 올바르게 구현했다는 증거로 쓰지 않는다.

## 클라이언트에서 정책 변경을 제안할 때

- Android 팀원이나 AI는 배포받은 공통 지침·스킬·정책을 직접 고치거나 파일 권한을 풀어서 우회하지 않는다. Android 자체 개발 지침의 관리와 공통 배포본의 변경 권한은 구분한다.
- 현재 정책이 구현에 불편하거나 더 나은 정책을 제안하고 싶으면 `현재 규칙 ID·내용 → 문제와 이유 → 원하는 변경 → Android 영향`을 정리해 백엔드에 전달할 문구를 작성한다. 사람의 별도 요청 없이 자동 발송하지 않는다.
- 변경 흐름은 `백엔드와 논의·합의 → 백엔드 원본의 코드·규칙 수정 및 검토 → 공통 하네스 재배포 → Android 새 버전 적용`이다. 합의 전의 제안을 현재 정책으로 구현하거나 공통 배포본에 반영하지 않는다. 관련 없는 작업은 계속한다.
