# 공통 비즈니스 규칙

## 작업 영역별 권한

- `backend/**` 작업에서는 사용자와 합의한 정책만 아래 절차에 따라 규칙 문서에 반영할 수 있다.
- `client/**` 작업에서는 `docs/business-rules/**`를 읽기 전용으로 사용한다. 현재 규칙이 명확하면 추가 질문 없이 그 규칙과 API 계약에 맞춰 구현하고, 규칙·결정 기록·목차·Notion 매핑을 생성·수정·삭제하지 않는다.
- client 작업에서 규칙이 없거나 규칙과 API·서버 동작이 충돌하면 관련 규칙 ID와 차이만 알리고 백엔드 확인 대상으로 남긴다. 해당 정책을 추측하거나 client 코드로 새로운 기준을 확정하지 않는다. 영향받지 않는 작업은 계속할 수 있다.

## 확인과 대조

- [목차](../../../docs/business-rules/README.md)에서 관련 도메인의 활성 규칙만 읽는다. 미등록 문서와 템플릿은 정책이 아니다. 변경 이유가 필요할 때만 연결된 결정 기록을 읽는다.
- Git의 Markdown을 원본으로 유지한다. Notion은 사람이 갱신하는 공유본이다. 이 흐름에서는 MCP·브라우저·컴퓨터 제어로 Notion을 조회하거나 수정하지 않는다.
- 인터뷰를 마칠 때 기능별 합의·예외·미결정 사항을 이슈 초안에 남기고 관련 규칙 ID와 신규·변경 여부를 연결한다. 미승인 제안은 활성 규칙으로 기록하지 않는다.
- 구현 완료와 PR 작성 전에 **합의 → 실제 코드·테스트 → 규칙**, **변경된 코드 → 문서화되지 않은 정책** 양방향으로 대조한다. 테스트 통과나 문서 파일 변경만으로 누락 없음이라고 결론 내리지 않는다.
- 관련 기능에서 권한·정지/탈퇴, 입력 경계, 상태 전이·시간 경계, 반복·동시 요청, 실패·재시도·취소, 조회·공개 범위, 데이터 삭제·외부 부수 효과를 확인한다. 모든 도메인을 매번 검사하지 않는다.
- 코드·합의가 충돌하면 쟁점을 확인한다. 현재 동작을 설명하는 누락 보완과 새로운 정책 결정을 구분하고, 확인하지 못한 범위를 완료로 표시하지 않는다.

## 문서 반영

- 합의된 정책은 관련 `rules/*.md`의 현재 내용으로 갱신한다. 규칙 ID를 유지하고 규칙·적용 범위·예외·결정 기록을 채운다. 신규 도메인은 활성 표시와 목차도 갱신한다.
- 신규 정책의 확정 또는 정책의 의미 변경·제거에는 [결정 템플릿](../../../docs/business-rules/decisions/_template.md)으로 변경 전후·이유·영향·관련 규칙·이슈를 남기고 규칙에서 연결한다. 기존 코드의 누락 문서화·표현 수정에는 새 정책을 결정한 것처럼 기록하지 않는다.
- 규칙 ID나 도메인을 추가·삭제·이름 변경하면 [수동 반영 위치](../../../docs/business-rules/notion-map.yml)도 갱신한다. URL·계정·페이지 ID는 필요하지 않다.
- 구현과 같은 합의로 바뀐 문서는 같은 PR에 포함한다. 정책 의미와 무관한 구현 세부사항은 규칙에 넣지 않는다.

## PR와 완료 안내

- PR은 저장소의 기존 양식을 사용하고 실제 규칙 변경은 `작업 내용`에 다른 변경과 함께 설명한다. 비즈니스 규칙 전용 섹션이나 체크리스트를 추가하지 않는다.
- 현재 규칙이 바뀌면 작업 종료 시 [Notion 수동 반영 절차](../../../docs/business-rules/NOTION_SYNC.md)를 읽어 변경된 규칙의 위치·수정 방법·완성 문구를 안내한다. 결정 기록은 Git에만 남긴다.
- Notion 반영 완료를 추적하거나 병합을 감시하지 않는다. 다음 작업 재개를 수동 반영 확인 때문에 막지 않는다.
