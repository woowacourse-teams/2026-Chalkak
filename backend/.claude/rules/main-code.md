# 운영 코드 컨벤션

## 적용 방법

1. 변경 대상이 `src/main/java`인지 확인한다.
2. 코드 작성 전에 다음 조건에 해당하는 규칙 본문을 함께 읽는다. 이 문서나 스킬 목록을 읽은 것으로 대신하지 않는다.
   - 운영 클래스나 패키지를 생성·이동하거나 배치 위치를 정하면 [package-structure](../skills/package-structure/SKILL.md)를 읽고 경로와 `package` 선언을 결정한다.
   - 운영 코드의 변수·필드·매개변수·메서드 이름을 생성·변경하면 [naming-conventions](../skills/naming-conventions/SKILL.md)를 읽고 이름을 정한다. 테스트 이름에는 적용하지 않는다.
   - 기존 클래스 내부만 수정하면 배치 규칙을 새로 읽을 필요는 없으며, 날짜·예외·API 등 다른 조건은 `CLAUDE.md`의 적용 표에 따른다.
3. 새로 작성하거나 수정한 코드에 아래 규칙을 적용한다.
4. 관련 없는 기존 코드는 컨벤션 적용을 이유로 변경하지 않는다.
5. 완료 전 적용 대상과 실제 읽은 규칙을 대조하고 변경한 코드에 반영했는지 다시 확인한다.

## 자동 검사와 작성 기준

- Google Java Style을 기본으로 하되 팀 규칙과 저장소 포맷 설정을 우선한다.
- 포맷·운영 코드 문법은 `./gradlew checkConventions`로 확인한다. 형식 수정은 `./gradlew spotlessApply` 후 diff를 확인한다.
- 세부 설정을 변경하거나 실패 원인을 찾을 때만 [검사 범위와 설정](../../config/conventions.md)을 읽는다. 검사를 통과하려고 규칙이나 제외 대상을 임의로 바꾸지 않는다.
- 조건 분기는 단독 `if`와 Early Return으로 작성한다.
- 메서드·생성자 선언과 호출, record 컴포넌트, enum 생성자 호출은 항목이 3개 이상이면 첫 항목부터 각 항목과 닫는 괄호를 별도 줄에 둔다. 0~2개는 이 규칙으로 줄바꿈을 강제하지 않는다.
- 이 줄바꿈 규칙은 운영·테스트 코드에 동일하게 적용하며 `./gradlew checkJavaLayout`으로 검사한다. 어노테이션 속성·람다 매개변수·배열 초기화는 대상이 아니다. 포맷터는 작성한 줄바꿈을 보존하며 이 검사기는 누락을 보고한다.
- 빈 블록을 작성하지 않는다. 제어문 밖의 빈 블록은 자동 검사 범위에 포함되지 않으므로 직접 확인한다.

## 검증 로직 재사용

- 동일한 도메인 규칙을 검증하는 기존 메서드를 우선 재사용한다.
- 메시지나 행위만 다르고 변경 이유가 같은 중복 로직은 `private` 공통 메서드로 추출한다.
- 상태별 예외나 메시지처럼 정책이 다른 로직은 무리하게 통합하지 않는다.

## 상수

- 파일 내부에서 추출한 상수는 `private`으로 선언하고, `public`으로 노출하지 않는다.

## 클래스 내부 배치 순서

1. 상수
2. 필드
3. 생성자
4. `public` 메서드
5. `protected` 메서드
6. `private` 메서드
7. getter와 setter
8. `hashCode()`
9. `equals()`
