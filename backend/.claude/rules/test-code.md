# 테스트 코드 컨벤션

## 적용 방법

1. 테스트가 보호할 동작과 실패 위험을 정한다.
2. 그 동작을 확인할 수 있는 가장 작은 테스트 범위를 선택한다.
3. 아래 기준으로 작성하고 기존 테스트와 검증 목적이 겹치는지 확인한다.
4. 관련 없는 기존 테스트는 변경하지 않는다. 기존 테스트의 이관 범위는 [이관 계획](../../docs/testing/test-migration.md)을 따른다.

## 보호할 것과 생략할 것

- 비즈니스 규칙, 권한, 데이터 일관성과 HTTP 계약을 보호한다. 잘못된 공개, 중복 처리, 접근 허용이 사용자에게 직접 영향을 주기 때문이다.
- 규칙이 없는 getter, setter, `toString()`, 단순 DTO 변환, JPA 기본 기능과 라이브러리 자체 동작은 따로 테스트하지 않는다. 우리 코드의 회귀를 찾는 데 비해 유지 비용이 크기 때문이다.
- 같은 규칙의 상세 조건을 여러 계층에서 반복하지 않는다. 각 계층의 역할이 다른 검증은 유지한다. 예를 들어 제목 길이 규칙과 잘못된 요청의 HTTP 오류 변환은 검증 목적이 다르다.

## 서비스에 맞춘 선택 이유

찰캌은 사진 제출 후 이미지 처리와 검수를 거쳐 공개한다. 참여 기간, 검수 상태와 회원 권한에 따른 판단은 도메인과 서비스에서 빠르게 확인한다. 공개 조건을 적용한 조회와 저장 제약은 PostgreSQL에서, 앱과 관리자 웹이 사용하는 요청과 응답은 웹 계층에서 확인한다.

중복 제출, 동시 좋아요와 커밋 후 알림은 DB 제약, 잠금과 트랜잭션에 영향을 받으므로 실제 DB를 연결한다. 핵심 흐름은 인수 테스트로 함께 동작하는지 확인하고, 외부 API는 네트워크 상태와 호출 비용에 의존하지 않도록 대체한다.

## 테스트 수준과 의존성

| 대상 | 기본 수준 | 의존성 처리와 검증 목적 |
| --- | --- | --- |
| Domain | 단위 | 실제 도메인 객체를 생성한다. Spring과 DB 없이 규칙과 상태 전환을 검증한다. |
| Service | 단위 | Repository와 외부 연동 Port를 Mock으로 대체한다. 실제 도메인 객체로 유스케이스의 판단, 결과와 필요한 협력을 검증한다. |
| Repository | 슬라이스 | `@DataJpaTest`와 실제 테스트 PostgreSQL로 쿼리, 매핑과 DB 제약을 검증한다. 필요한 구현체만 import한다. |
| Controller | 웹 슬라이스 | `@WebMvcTest`, MockMvc와 Service `@MockitoBean`으로 요청 검증, 응답과 예외 변환을 검증한다. |
| 핵심 인수 시나리오 | 통합 | `IntegrationTestSupport`와 MockMvc로 실제 Controller, Service, Repository와 테스트 DB를 연결한다. 외부 연동은 대체한다. |
| 접근 정책 | 통합 | 실제 보안 구성을 연결해 인증과 회원 상태에 따른 접근을 검증한다. 필터 검증에 불필요한 Service는 대체할 수 있다. |
| 동시성과 트랜잭션 | 통합 | 실제 Service, Repository와 PostgreSQL로 경쟁 요청, 커밋, 롤백과 실행 시점을 검증한다. |
| 외부 연동 Adapter | 단위 또는 제한된 통합 | SDK Mock이나 로컬 HTTP Stub으로 요청 구성, 응답 해석과 오류 변환을 검증한다. |
| API 문서 계약 | 통합 | 생성된 OpenAPI에서 경로, 파라미터, 보안과 응답 코드 계약을 검증한다. |

- 단위 테스트는 Spring Context를 로딩하지 않는다. Mockito와 생성자 주입을 사용할 수 있다.
- 슬라이스 테스트는 대상 계층에 필요한 Spring 구성만 로딩한다.
- 테스트 수준은 디렉터리나 클래스 이름이 아니라 실제로 연결한 의존성으로 구분한다. 서비스 패키지에도 DB 통합 테스트를 둘 수 있다.
- 인수 테스트는 테스트 코드에서 MockMvc로 요청한다. 배포 서버나 별도 HTTP 서버를 띄울 필요는 없다. 네트워크나 실제 서블릿 컨테이너 동작이 검증 대상이면 해당 테스트에서만 서버를 띄운다.
- 별도 E2E 묶음이나 모든 상태 코드를 인수 테스트에서 반복하는 기준은 두지 않는다.

## 검증할 내용

### Domain과 Service

- 도메인에서는 실제 규칙에 영향을 주는 정상, 거부, 경계와 허용되지 않는 상태 전환을 검증한다. 경계값이 결과를 바꾸는 경우 직전, 경계와 직후를 확인한다.
- 서비스에서는 정상 흐름과 서비스가 직접 판단하는 실패를 검증한다. 도메인이 이미 확인한 상세 경계값을 반복하지 않는다.
- 도메인 객체는 실제 객체를 사용한다. Repository 조회 결과와 외부 응답을 대체하고, 저장할 객체의 상태와 반환 결과를 확인한다.
- `verify`는 저장, 알림, 불필요한 외부 호출 방지처럼 호출 자체가 요구사항인 경우에 사용한다. 내부 호출 순서와 횟수를 모두 고정하지 않는다.
- Mock의 `save` 호출 확인을 실제 저장, dirty checking, cascade나 트랜잭션 검증의 대체로 취급하지 않는다.

### Repository

- 직접 작성한 쿼리, 동적 조건 조합, 공개와 삭제 조건, 정렬과 페이징을 검증한다.
- 우리 매핑에 따른 cascade, orphanRemoval, 유니크 제약, 부분 인덱스, 잠금과 조건부 갱신을 검증한다.
- JPA 기본 메서드 자체는 반복하지 않는다. 기본 메서드를 사용하더라도 사용자 정의 매핑이나 DB 제약을 검증하는 경우는 유지한다.
- JPA 영속성 컨텍스트가 DB 결과를 가리지 않도록 필요한 시점에 `flush()`와 `clear()` 후 다시 조회한다. JDBC나 네이티브 쿼리만 사용하는 테스트에 일괄 적용하지 않는다.

### Controller와 접근 정책

- 정상 응답의 상태 코드와 필드, 입력 검증, 직렬화와 오류 변환을 확인한다. 단순 서비스 위임 코드에도 HTTP 계약이 있으면 그 계약을 검증한다.
- 같은 오류 처리 경로를 모든 비즈니스 예외와 엔드포인트의 조합으로 반복하지 않는다. 엔드포인트 고유 계약과 공통 처리기의 검증을 구분한다.
- 필터를 끈 웹 슬라이스 테스트로 인증과 인가가 검증됐다고 보지 않는다.
- 엔드포인트의 인증 요구와 정지, 탈퇴 회원의 접근 정책은 실제 보안 구성으로 검증한다. 정책을 바꾸면 영향을 받는 허용과 거부를 확인한다.

### 핵심 인수 시나리오

- 사진 제출과 공개, 로그인과 회원 처리 등 해당 변경의 핵심 흐름에서 요청, 저장 결과와 응답이 연결되는지 확인한다.
- 계층 연결에서 문제가 생길 수 있는 중요한 실패도 확인한다. 모든 유스케이스와 상태 코드를 인수 테스트로 다시 작성하지 않는다.
- 단위 테스트로 옮길 때 기존 DB 저장 검증을 확인한다. 쿼리, 매핑, 여러 저장의 원자성 등은 Repository 테스트나 필요한 통합 시나리오에 남긴다.

### 동시성과 트랜잭션

- 락, 유니크 제약과 조건부 UPDATE로 방어하는 경쟁 상황은 실제 DB와 겹쳐 실행되는 요청으로 검증한다. 스레드별 트랜잭션과 경쟁 지점을 명확히 한다.
- `AFTER_COMMIT`, `REQUIRES_NEW`와 롤백 전파는 실제 트랜잭션 경계에서 확인한다. 커밋 후 실행과 롤백 시 미실행, 별도 트랜잭션의 저장 결과를 구분한다.
- 알림 발송기 같은 외부 의존성은 Mock이어도 된다. 트랜잭션 결과를 결정하는 Service, Repository와 DB는 실제 객체를 사용한다.
- 이름에 `Concurrency`나 `Transaction`이 없는 테스트에도 해당 검증이 섞일 수 있다. 클래스 이름이나 어노테이션만 보고 일괄 전환하지 않는다.
- 동시성 방어가 없는 코드에 근거 없이 경쟁 테스트를 추가하지 않는다. `sleep`으로 실행 순서를 추측하지 않고 latch 등으로 경쟁을 조정한다.

### Infrastructure와 Architecture

- Adapter가 직접 판단하는 조건, 외부 요청 계약과 오류 변환을 검증한다. 실제 외부 시스템을 호출하는 검증은 별도 합의한 실행 범위로 구분한다.
- 아키텍처 규칙을 추가하면 통과하는 fixture와 위반하는 fixture를 확인한다.

## 가독성과 중복 정리

- 하나의 테스트에는 하나의 시나리오를 둔다. 같은 결과를 설명하는 여러 assertion은 함께 둘 수 있다.
- 같은 대상과 목적의 시나리오는 기존 클래스에 모은다. 메서드, 예외, 상태 코드마다 새 클래스를 만들지 않는다.
- 실제 DB나 별도 보안 구성 등 실행 환경이 다르거나 독립된 유스케이스를 읽기 어려울 때 클래스를 분리한다. 클래스 수를 줄이려고 서로 다른 책임을 합치지 않는다.
- 입력과 기대값만 다른 동등한 시나리오는 파라미터화한다. 준비와 처리 흐름이 다른 시나리오를 조건문으로 억지로 묶지 않는다.
- 준비 데이터는 시나리오에 중요한 값이 테스트 본문에서 보이게 한다. 작은 생성 헬퍼를 우선하고, 여러 클래스에서 실제로 반복되는 경우에만 공통 fixture를 추출한다.
- 상속, 범용 Builder나 공통 Mock 설정을 늘려 테스트의 전제와 기대 결과를 숨기지 않는다. 필요하지 않은 대량 데이터와 과도한 공통 `setUp`을 줄인다.
- 중복 제거 전 보호하는 규칙, 실패 조건과 검증 위치를 대조한다. 같은 코드를 거친다는 이유만으로 다른 책임의 검증을 삭제하지 않는다.
- 삭제하거나 옮긴 검증은 남은 테스트와 대응시킨다. 정상, 권한, 상태 경계, DB 제약, 경쟁 요청과 롤백의 보호 범위가 빠지지 않았는지 확인한다.
- 테스트와 클래스 개수, 커버리지 수치만으로 추가하거나 삭제하지 않는다. 실제 결과와 보호 범위로 판단한다.

## 외부 시스템

- S3, Lambda, OAuth, Push와 외부 API는 Port를 통해 대체한다. 실제 도메인 객체와 서비스의 비즈니스 판단을 Mock하지 않는다.
- 반환값이나 오류 주입에는 Mock을 사용한다. 상태가 필요한 Fake는 반복 Mock보다 읽기 쉬워질 때만 만들고 테스트 소스에 `Fake` 접두사로 둔다.

## DB 환경과 격리

- DB를 사용하는 슬라이스와 통합 테스트는 운영과 분리된 테스트 PostgreSQL을 사용한다. 운영 DB에 접속하지 않으며 H2로 대체하지 않는다.
- 로컬은 `compose.yaml`의 `postgres-test`, CI는 워크플로의 PostgreSQL 서비스 컨테이너를 사용한다.
- 접속 정보는 `application-test.yml`의 `TEST_POSTGRES_*`로 설정한다. 테스트 코드에서 DB 컨테이너를 직접 띄우지 않는다.
- 같은 스레드와 트랜잭션에서 끝나며 실제 커밋이 필요 없는 DB 테스트는 `@Transactional` 롤백으로 격리할 수 있다.
- 커밋 후 이벤트, `REQUIRES_NEW`, 비동기 처리, 별도 스레드, 실제 HTTP 서버나 트랜잭션 종료 이후를 검증할 때는 테스트 전체를 감싸는 `@Transactional`을 사용하지 않는다.
- 위 테스트는 필요한 실제 트랜잭션을 열고 종료하며, `DatabaseCleaner`로 `@BeforeEach`에 DB를 정리한다. 별도 스레드와 비동기 작업이 끝난 뒤 다음 테스트로 넘어간다.
- `DatabaseCleaner`의 `TRUNCATE ... RESTART IDENTITY CASCADE`를 재사용한다. DB 정리에 `deleteAll()`이나 `@DirtiesContext`를 사용하지 않는다.
- `@DirtiesContext`는 ApplicationContext 자체가 오염된 경우에만 사용한다.
- 전체 Spring 통합 테스트는 `IntegrationTestSupport`의 프로파일과 공통 외부 Mock을 재사용한다. 상위 클래스에 `@Transactional`을 추가하지 않는다.
- 슬라이스 테스트는 `IntegrationTestSupport`를 상속하지 않는다. 필요한 Context 차이가 없다면 개별 구성과 Mock을 늘려 Context 캐시를 나누지 않는다.

## 형식과 이름

- Google Java Style 기반 팀 형식과 Spotless 설정을 따른다. `./gradlew spotlessCheck`로 확인하고 포맷 변경 diff를 점검한다.
- 테스트에 운영 코드 전용 Checkstyle을 적용하지 않는다.
- 메서드와 생성자의 선언과 호출, record 컴포넌트, enum 생성자 호출은 항목이 3개 이상이면 첫 항목부터 각 항목과 닫는 괄호를 별도 줄에 둔다. 0~2개는 강제하지 않는다.
- `./gradlew checkJavaLayout`으로 위 형식을 확인한다. 어노테이션 속성, 람다 매개변수와 배열 초기화는 대상이 아니다.
- 클래스 이름은 영문과 `Test` 접미사를 사용한다. 테스트 수준만을 구분하기 위한 새 접미사나 일괄 이름 변경을 강제하지 않는다.
- 메서드는 영문 `메서드명_상황_결과`, `@DisplayName`은 같은 의미의 한글로 작성하고 함께 갱신한다.
- 테스트 패키지는 운영 코드 패키지를 미러링한다. Given/When/Then 주석을 사용하고 나누기 어려우면 `When & Then`으로 묶는다.
- `build.gradle`의 `JavaCompile`과 `Test`는 UTF-8 인코딩을 유지한다.
