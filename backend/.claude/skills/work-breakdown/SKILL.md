# 이슈·PR 작업 분할

## 입력과 승인

- 메인 이슈는 사람이 제공한다. AI가 새 메인 이슈를 임의로 만들지 않는다. 실제 번호·저장소가 없으면 초안은 준비하되 등록 전에 확인한다.
- 수동 인터뷰를 거친 작업은 인터뷰 결과 승인(①) 뒤 분할한다. 인터뷰 답변·정상 완료 자체는 결과 승인이 아니다. 이미 승인된 결과는 다시 승인받거나 자동 재인터뷰하지 않는다.
- 일반 분할 요청은 확인된 요구사항으로 제안하며 심화 인터뷰를 자동 실행하지 않는다. 분할안만 요청하면 제안에서 끝낸다.

## 완성 단위

- 목적은 팀원이 각 PR의 문제·처리 흐름·완성 결과를 이해하고 검토하기 쉽게 하는 것이다. **작업 이슈 하나 = 브랜치 하나 = PR 하나**가 기본이며 이슈 하나에 여러 커밋을 둘 수 있다.
- 각 PR은 이미 병합된 선행 코드만으로 정상 동작하고 검증할 수 있어야 한다. 앞 PR이 나중 PR의 구현을 필요로 해서는 안 된다. “나중에 완성할 테니 먼저 병합”하는 TODO·더미 응답·미완성 경로·미사용 발판 코드를 만들지 않는다.
- 사용자에게 의미 있는 동작, 독립적인 문제 해결·리팩터링으로 나눈다. 해당 결과에 필요한 권한·입력 검증·실패 처리·호환성·테스트는 함께 포함한다. Controller·Service·Repository 등 계층별 분할이나 구현과 관련 테스트의 분리는 피한다.
- 작은 작업은 하나로 유지한다. 파일 수·줄 수·예상 리뷰 시간에 고정 상한을 두지 않는다. 커밋만 나눠 큰 PR을 그대로 유지하는 것으로 대신하지 않는다.
- 큰 작업은 각 이슈가 완성할 동작의 범위를 줄여 분할한다. 메인 이슈의 모든 요구사항·완료 조건을 어느 서브 이슈가 담당하는지 대조하고, 누락·중복·몰래 축소한 조건이 없도록 한다.
- 예: 접수 저장·응답은 Slack 없이도 완성하고, Slack 알림은 별도 확장한다. 기본 목록 조회는 검색 없이도 정상 사용 가능해야 하며 미구현 검색을 노출하지 않는다.
- 완성 단위를 더 작게 만들 수 없으면 이유·대안을 설명하고 영향받는 범위를 확인한다. 억지로 작게 만들거나 합의한 요구사항을 삭제하지 않는다.

## 제시와 실행 승인

- B 구현에 A의 코드·계약이 필요한지로 실제 의존성을 판단한다. 같은 파일·기능이라는 이유로 의존 관계를 만들지 않는다. B와 C가 A에만 의존하면 관계를 그대로 표시한다.
- 의존 관계와 개발 순서는 구분한다. **독립 여부와 관계없이 승인된 순서대로 하나씩 개발·리뷰·병합한다.** 막힌 다음 이슈를 건너뛰거나 리뷰 대기 중 뒤 이슈를 개발하지 않는다.
- 순서·선행 조건을 아래 표로 보여주고, 나눈 이유와 각 단위가 독립적으로 완성되는 이유를 짧게 설명한다. 등록 전에는 A·B 등 계획 식별자를 쓰고 등록 후 실제 링크로 교체한다.

| 순서·단위 | 문제·완성 결과 | 포함·제외 범위와 이유 | 확인 가능한 완료 조건 | 선행 작업·이유 |
| --- | --- | --- | --- | --- |
| 1 · A | 하나의 완성된 동작 | 필요한 경계 | 관찰 가능한 성공·실패 | 없으면 없음 |

- [issue-pr-workflow](../issue-pr-workflow/SKILL.md)에 따라 **각 서브 이슈의 실제 제목·본문**, 작성자·담당자·라벨·저장소·통합 브랜치를 함께 제시한다. 제목만 승인받고 본문을 나중에 임의로 작성하지 않는다.
- 본문은 **현재 문제 → 이번 이슈에서 완성할 동작 → 완료 확인 방법**을 저장소 양식에 맞춘다. 핵심 정책·처리 흐름·필수 계약·권한·실패·제외 이유·선행 조건은 남기고, 내부 클래스·메서드 설계는 개발에서 정한다. 상세 구현 선택·실제 검증은 PR에 쓴다.
- 분할안만 제시하는 경우에도 나중에 실행할 때 커밋별 설명·승인과 PR 병합 후 순차 진행이 적용됨을 한 문장으로 안내한다. 이 안내를 현재 등록·개발 승인으로 해석하지 않는다.
- 전체 실행 요청의 분할안 승인(②)에는 **제공된 메인 이슈 아래 서브 이슈 등록 → 첫 이슈 착수 → 커밋마다 설명·별도 승인 → 푸시·PR 등록 → 리뷰 반영 → 병합·완료 조건·이슈 종료 확인 → 다음 이슈**, 완료한 이슈 종료와 메인 이슈 종료를 포함한다고 명시한다.
- 승인② 뒤 별도의 착수 승인 없이 등록하고 첫 커밋 단위를 시작한다. 전체 승인은 커밋별 승인·범위 변경 승인을 대신하지 않으며 PR 병합·배포·브랜치 삭제·이력 재작성 권한을 포함하지 않는다. 사용자가 좁힌 실행 범위를 우선한다.

## 변경과 재분할

- 각 단위 착수·PR 등록 전에 실제 diff와 설명 범위를 계획에 대조한다. 문구만 바뀌고 의미가 같으면 바로 반영한다. 동작·정책·완료 조건이 바뀌면 영향받는 부분만 설명하고 재승인받는다.
- 기본은 승인된 AI 분할안을 유지한다. 더 작은 완성 단위로 나눌 때도 변경된 분할표·본문·순서와 요구사항 배정을 보여주고 **영향받는 부분을 승인받은 뒤** 등록·변경한다.
- 합치기는 예외다. 독립적으로 동작할 수 없거나 분리가 불필요한 임시·중복 코드, 원자적으로 바뀌어야 하는 계약을 요구할 때 이유와 대안을 제시한다. 같은 파일·개발 편의만으로 합치지 않고 사용자 승인 없이 병합하지 않는다.
- 등록 전에는 초안을 수정한다. 등록 후에는 기존 이슈를 재사용하고 범위·관계를 갱신하며 불필요한 중복 이슈를 만들지 않는다.
- 개발 중 변경이면 영향받는 작업을 멈추고 완료한 부분·재작업·새 계획을 구분한다. 기존 코드·커밋을 임의 삭제·초기화하지 않는다. 무관한 합의는 유지하고 목적이 바뀌지 않는 한 전체 인터뷰를 반복하지 않는다.
- 착수·재개 시 GitHub 본문과 승인된 범위를 대조한다. 외부에서 수정된 본문 자체를 실행 승인으로 간주하지 않는다.
