# 브랜치 컨벤션

## 운영 방식

- Simplified Git Flow를 사용한다.
- `main`은 배포 가능한 안정 버전이고, 개발 통합 브랜치에서 다음 배포를 준비한다.
- `release/*`, `hotfix/*` 브랜치를 새로 만들지 않는다.
- 배포 시 개발 통합 브랜치를 `main`에 직접 병합한다.
- 브랜치 작성 요청만으로 배포나 병합을 실행하지 않는다.

## 작업 브랜치 이름

```text
be/<작업 유형>/#<이슈 번호>-<작업 제목>
```

- 백엔드 영역 접두사는 `be`를 사용한다.
- 작업 유형은 `feature` 또는 `fix`만 사용한다. 커밋 type인 `feat`, `chore` 등을 브랜치 유형으로 그대로 옮기지 않는다.
- 새로운 기능은 `feature`, 일반 버그와 운영 버그 수정은 모두 `fix`를 사용한다.
- 이슈 번호는 실제 등록된 번호를 사용하고 앞에 `#`을 붙인다.
- 작업 제목은 영문 소문자로 쓰고 단어 사이는 하이픈으로 구분한다.
- 하나의 브랜치는 하나의 이슈만 처리하며, 이름 맨 앞이나 뒤에는 `/`를 붙이지 않는다.

```text
be/feature/#4-kakao-sso-login
be/fix/#12-token-validation-error
```

## 생성과 정리

- 개발 통합 브랜치와 작업 유형의 분류가 기존 합의로 확인되면 그 값을 사용한다.
- 통합 브랜치가 `develop`인지 `be/develop`인지 불명확하거나, 문서·설정·리팩터링 등 비기능 작업의 유형이 정해지지 않았으면 개발자에게 확인한다.
- 생성 전 작업 트리, 현재 브랜치, 로컬·원격 브랜치를 확인한다. 진행 중인 변경을 덮어쓰거나 초기화하지 않는다.
- 같은 이슈의 작업 브랜치가 이미 있으면 확인된 브랜치를 재사용한다.
- 이슈 등록 승인에는 해당 이슈의 작업 브랜치 생성도 포함한다. 여러 이슈의 전체 개발에서는 각 단위에 착수할 때 브랜치를 생성한다. 사용자가 이슈 등록만 명시하면 브랜치를 만들지 않는다.
- 독립 작업과 첫 작업은 확정한 통합 브랜치에서 시작한다. 승인된 의존 작업은 선행 작업 브랜치에서 시작하고 PR도 그 브랜치를 대상으로 한다. 통합 브랜치 자체를 바꾸는 것으로 해석하지 않는다.
- Stacked PR 생성·갱신·선행 병합 후 정리에는 [stacked-prs](references/stacked-prs.md)를 읽는다.
- 작업 완료 후 정리 요청에는 병합 상태와 후속 PR·브랜치의 의존 해소를 확인한 뒤 브랜치를 정리한다. 미병합 커밋이나 작업 중 변경이 있으면 강제로 삭제하지 않는다.
