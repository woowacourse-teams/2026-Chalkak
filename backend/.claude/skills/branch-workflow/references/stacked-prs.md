# Stacked PR 관리

의존 작업의 PR을 생성·갱신하거나 선행 변경을 반영할 때 읽는다. 단순 브랜치 이름 추천에는 필요하지 않다.

## 준비와 승인 범위

- 저장소·인증 계정·확정한 통합 브랜치(trunk), 작업 트리와 원격 상태를 확인한다. 기본 도구는 Git과 GitHub CLI이며, 공식 스택 등록에는 GitHub Stacks API를 사용한다. 설치된 `gh stack` 확장은 선택적으로 쓸 수 있고 추가 설치를 필수로 요구하지 않는다.
- 최초 실행 안내에 **담당 작업 브랜치의 선행 변경 반영, rebase와 안전한 갱신 푸시, PR base·연결 갱신**을 포함해 승인받는다. 이 승인으로 같은 작업의 관리를 반복 확인하지 않는다. 일반 이슈·PR 등록 승인만으로 이력 재작성까지 확대하지 않는다.
- 대상은 이번 실행에서 생성했거나 사용자가 관리를 맡긴 작업 브랜치로 한정한다. `main`·통합 브랜치·다른 사람의 작업 이력을 재작성하지 않는다. 병합·배포·브랜치 삭제는 포함하지 않는다.
- 스택 기능·API와 CI는 실제 환경에서 지원되는지 확인한다. 공식 기능은 공개 미리보기이므로 사용할 시점에 아래 공식 문서와 `gh` 도움말의 지원 범위를 대조한다.
- 공식 스택 연결만 불가능하면 허용된 일반 PR 연결과 수동 Git 정리로 이어가고, 공식 스택 미등록 상태를 알린다. 아래 일반 연결 PR의 CI 확인 규칙을 적용하며 미지원 API를 반복 호출하거나 전체 개발을 중단하지 않는다. PR 등록·푸시 자체가 불가능한 경우에는 해당 단계와 종속 작업만 보류한다.

## 생성과 연결

1. 독립 작업은 통합 브랜치에서, 의존 작업은 선행 작업의 확인된 최신 커밋에서 시작한다. **작업 브랜치·직접 부모·부모 기준 SHA·확인한 원격 head SHA**를 작업 기록에 남긴다. 선행 변경을 자식 이슈의 구현으로 다시 세지 않는다.
2. 해당 단위가 준비되면 일반 푸시하고 저장소 양식으로 `gh pr create`를 실행한다. `--base`, `--head`, `--title`, `--body-file`, `--label Server`, 작업 유형 라벨을 명시한다. 다른 미완성 단위까지 일괄 게시하지 않는다.
3. 두 개 이상의 선형 PR이 준비되면 `POST /repos/{owner}/{repo}/stacks`의 `pull_requests`에 하단부터 실제 PR 번호를 전달해 공식 스택으로 등록한다. 기존 스택에는 `/stacks/{number}/add`로 준비된 후속 PR만 추가한다. 설치된 확장을 쓰면 기존 PR 번호를 지정한 `gh stack link --base <trunk> <PR 번호...>`를 사용할 수 있다. API 필드와 지원 옵션은 실행 전에 공식 문서로 확인한다.
4. 제목·본문·라벨·실제 base·스택 구성과 `stack.base.ref`를 다시 조회한다. 공식 등록 여부를 PR의 base가 선행 브랜치라는 사실만으로 추정하지 않는다. 중복 스택을 만들지 않고 생성·갱신 응답이 불명확하면 먼저 조회한다.

## 분기 관계와 CI

- 공식 스택은 선형이다. A에 B와 C가 각각 의존하면 A → B → C로 바꾸지 않는다. 분기 PR은 해당 선행 브랜치를 base로 하는 일반 PR과 본문 링크로 연결하고, 가능한 선형 관계에만 공식 스택을 적용한다. 같은 PR을 여러 공식 스택에 중복 등록하지 않는다.
- 여러 미병합 선행 작업의 코드가 모두 필요한데 현재 한 브랜치로 표현할 수 없다면 먼저 분할 경계를 재검토한다. 관계없는 변경을 복사하거나 거짓 의존 관계를 만들지 않는다. 표현·검증 가능한 기반이 없으면 해당 단위만 대기하고 다른 작업을 진행한다.
- 공식 스택은 실제 trunk의 보호 규칙·필수 검사·CI를 각 계층에 적용한다. 일반 연결 PR에는 이를 가정하지 않는다. 현재 저장소의 `../.github/workflows/backend-ci.yml`은 `main`, `be/develop` 대상에 필터가 있으므로 실제 설정과 각 PR 최신 SHA의 검사 실행 여부를 확인한다.
- CI가 실행되지 않았거나 필수 검증이 남았다면 **draft·검증 대기**로 공개하고 누락 원인을 적는다. PR 공개와 개발은 이어갈 수 있지만 검증·개발 완료로 표시하지 않는다. 허용된 검증 경로를 사용하거나 선행 병합 후 base를 갱신해 검증한다. 보호 규칙을 우회하거나 CI 설정을 승인 없이 바꾸지 않는다.
- 스택의 PR 대상 확인에는 승인된 선행 브랜치도 허용하며 의존 관계를 본문에 남긴다. 리뷰·병합은 사람이 선행 의존 관계부터 판단하며, 일반 연결 PR을 선행 작업 브랜치로 자동 병합하지 않는다.

## 선행 수정·병합 후 갱신

1. 작업 재개, 후속 단위 착수, PR 갱신 전에 선행 PR의 실제 상태·head SHA와 원격 브랜치를 조회한다. 선행 수정이 있으면 이전 부모 기준 SHA를 보존한 채 후속 고유 커밋만 새 부모 위로 재적용한다. 이미 반영한 변경이면 반복하지 않는다.
2. 선행 PR이 병합되면 원격의 자동 정리 여부와 실제 새 base를 먼저 확인한다. squash·rebase 병합은 커밋 식별자가 달라질 수 있으므로 부모의 옛 커밋을 다시 넣지 않는다. 수동 Git에서는 검증한 이전 부모 경계를 사용한 `rebase --onto`로 후속 고유 변경만 옮기고 PR base를 갱신한다. 경계를 복구할 근거가 없으면 해당 재작성을 멈추고 확인한다.
3. 아래 단계부터 순서대로 반영하고 관련 테스트·빌드 및 **새 base 대비 해당 PR 고유 diff**를 확인한다. 정책·계약 재결정이 필요한 충돌은 해당 쟁점을 확인한다. 검증 실패를 고치기 위해 다른 단위의 변경을 몰래 포함하지 않는다.
4. 원격 재작성은 작업 기록과 대조해 다른 사람의 미반영 변경이 없는지 확인하고, **예상 원격 SHA를 명시한 `--force-with-lease=<ref>:<sha>`**로 승인된 ref만 갱신한다. 일반 `--force`는 사용하지 않는다. lease가 거부되면 최신 상태를 조사하며 새 SHA만 받아 덮어쓰지 않는다.
5. 최종 head·base·스택 구성·CI 상태를 다시 조회하고 관련 이슈·PR의 범위·링크·읽는 순서를 갱신한다. 검증·푸시를 확인한 단위의 새 부모 기준 SHA와 원격 head SHA를 다음 실행 기준으로 기록하되, 아직 갱신하지 않은 후속 브랜치의 옛 부모 경계는 보존한다. 일부 푸시·API 갱신만 성공하면 성공/실패한 단위부터 구분해 재개한다. 종료 코드만으로 전체 성공을 판단하지 않는다.

- `gh stack sync`는 조회가 아니라 rebase·push·PR 갱신을 수행한다. `submit`도 여러 브랜치를 게시할 수 있다. 사용할 경우 위 승인·대상·변경 보호를 충족하는 옵션인지 확인하고 범위를 제한한다. `--prune`이나 자동 병합은 이 절차에 포함하지 않는다.
- 세션 종료 후 감시는 이 문서만으로 실행되지 않는다. 현재 상태·기준 SHA·다음 행동을 남기고 이후 실행에서 다시 확인한다.
