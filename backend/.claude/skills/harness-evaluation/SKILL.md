# 하네스 동작 평가

## 하네스를 변경할 때

- 바뀌는 행동과 [기존 사례](../../../scripts/harness_eval/cases)를 대조한다. 오탈자·표현 정리에는 사례를 늘리지 않고, 기존 사례로 확인할 수 있으면 재사용한다.
- 새 행동·예외를 확인할 사례가 부족해도 진행 중인 하네스 변경을 멈추거나 중간에 묻지 않는다. 요청받은 변경과 구조 검사를 먼저 마치고, 완료 보고 끝에서 **추가 이유와 확인할 행동을 한 번 제안**한다. 사용자가 사례 추가까지 이미 요청·승인했다면 함께 반영하고 다시 묻지 않는다.
- 사례에는 자연스러운 요청, 최소 작업 자료, 관찰할 행동을 둔다. 기대 답변·스킬 이름·판정 기준을 평가받는 AI에 미리 알려주지 않는다. 문구 일치보다 실제 도구 사용·결과물·변경 범위를 확인한다.
- 작업 완료 전에 `python3 scripts/verify_harness.py`로 구조 검사·기존 자동 테스트 전체·전체 사례 준비 검사를 수행한다. 검사 의존성을 설치한 가상환경에서 실행하며 실패 원인을 수정한 뒤 다시 검사한다.
- 판단·도구 사용·승인 경계·재개 동작 등 행동을 바꾸면 관련 실제 AI 사례도 아래 절차로 실행·판정한다. 이 지침은 하네스 변경 작업에 필요한 평가의 실행 근거다. 일반 개발·새 세션·오탈자 수정만으로 AI를 실행하지 않는다. 공통 라우팅·로딩·승인 원칙을 바꾸면 전체 사례로 넓히며 변경 파일만 보고 검사를 좁히지 않는다.
- 평가가 막히거나 미실행·실패하면 수정한 파일과 원인·미검증 범위를 보고하고 **동작 검증 완료로 처리하지 않는다**. 다른 도구의 결과로 통과를 대신하지 않는다.
- 기존 테스트·사례·판정 기준을 보존한다. 실패를 숨기기 위한 삭제·skip·assertion 약화·허용 범위 확대는 금지한다. 먼저 하네스와 도구의 원인을 고친다. 요구사항 변경이나 검사 자체 결함으로 수정해야 하면 변경 이유와 보존·대체한 검증 기준을 보고하고 기존 실패 기록도 남긴다.

## 동작 변경 검증 또는 명시적 검사 요청

1. [실행 안내](../../../scripts/harness_eval/README.md)를 읽고 요청과 관련된 사례·도구를 선택한다. 최초 전체 확인은 등록된 사례를 각각 Codex·Claude의 새 세션에서 평가한다. 이후에는 관련 사례만 선택한다.
2. 실행 전에 선택한 사례, 도구와 최대 세션 수를 짧게 알린다. 이미 요청한 검사 범위는 다시 승인받지 않는다. 자동 재시도나 다른 모델로의 교체는 하지 않는다.
3. 원본 저장소와 분리한 임시 작업 자료로 실행한다. 네이티브 도구의 격리가 확인되지 않거나 인증·환경 제약이 있으면 해당 실행을 **검사 불가**로 남긴다. 권한을 풀거나 실제 GitHub 등록으로 대신하지 않는다.
4. 원본 도구 기록·답변·전후 diff를 판정 기준과 대조한다. 기계 검사만 통과한 결과는 **판정 대기**다. 막힌 등록·푸시 등의 시도도 실패이며, 확인할 기록이 부족하면 판정 불가다.
5. 사례별 근거를 기록하고 통과·실패·판정 불가·미실행을 구분해 보고한다. 한 번의 통과를 모든 모델·대화형 환경·전체 하네스의 정확성으로 확대하지 않는다. 수정 효과를 비교하려면 같은 사례·모델·설정으로 이전 하네스와 비교한다.

일반 개발에 자동 연결하지 않는다. 결과는 Git에서 제외된 `build/harness-eval/`에 보관하며, 실패를 이유로 관련 없는 하네스나 서비스 컨벤션을 변경하지 않는다.
