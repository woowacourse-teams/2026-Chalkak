# API 버전 관리 컨벤션

## 목표

- 기존 앱이 사용하는 API 계약을 보호한다.
- 하위 호환 변경에는 불필요한 새 버전을 만들지 않는다.
- Breaking Change가 발생하면 기존 버전을 유지하고 새 버전을 추가한다.
- 리팩터링 과정에서 기존 API 버전이 의도치 않게 변경되거나 삭제되는 것을 방지한다.

## 적용 절차

1. 변경되는 기존 API 계약을 확인한다.
2. 기존 앱이 변경 후에도 정상적으로 요청하고 응답을 처리할 수 있는지 판단한다.
3. 하위 호환 변경이면 현재 API 버전에 반영한다.
4. Breaking Change이면 기존 버전을 유지하고 다음 API 버전을 추가한다.
5. Breaking Change인지 불분명하면 기존 버전을 변경하지 않고 사용자에게 확인한다.
6. 완료 전에 기존 버전이 그대로 유지됐는지 다시 확인한다.

## API 계약

다음 항목을 외부 API 계약으로 판단한다.

- Endpoint URI
- HTTP Method
- Request JSON 필드명
- Request 필드 타입과 필수 여부
- Response JSON 필드명
- Response 필드 타입
- HTTP 상태 코드
- 인증 및 권한 처리 방식
- API의 의미와 동작

## URI 버저닝

- API는 `/api/v1`, `/api/v2` 형태의 URI 버저닝을 사용한다.
- 기능 추가 자체를 이유로 API 버전을 증가시키지 않는다.
- 기존 앱의 정상적인 동작을 보장할 수 없는 Breaking Change가 발생할 때만 다음 버전을 추가한다.
- 버전별 서버나 애플리케이션 전체를 복제하지 않는다.

## 현재 버전을 유지하는 변경

다음과 같은 하위 호환 변경은 현재 버전에 반영한다.

- 새로운 Endpoint 추가
- 응답 필드 추가
- Optional 요청 필드 추가
- 기존 동작에 영향을 주지 않는 기능 추가
- 버그 수정
- 성능 개선
- 외부 API 계약에 영향을 주지 않는 내부 구현 변경

## 새로운 버전이 필요한 변경

다음 변경은 Breaking Change로 판단한다.

- 기존 Endpoint 삭제
- 기존 Endpoint URI 변경
- HTTP Method 변경
- 기존 Request 또는 Response 필드 삭제
- 기존 Request 또는 Response 필드명 변경
- 기존 필드 타입 변경
- 필수 요청 필드 추가
- Request 또는 Response 구조의 큰 변경
- 기존 상태 코드 변경
- 기존 API의 의미나 동작 변경
- 인증 또는 권한 처리 방식 변경

## Breaking Change 구현

Breaking Change를 구현할 때는 다음을 따른다.

- 기존 `vN` Endpoint, Controller, Request DTO, Response DTO의 계약을 유지한다.
- 기존 버전을 직접 수정해 새로운 계약으로 대체하지 않는다.
- 지원 중인 현재 버전을 기준으로 다음 `vN+1` 버전을 추가한다.
- 새 버전의 차이는 가능한 한 Controller, Request DTO, Response DTO, 변환 및 응답 조립에 한정한다.
- Service, Domain, Repository와 핵심 비즈니스 로직은 버전 간 공유한다.
- 새 버전을 추가했다는 이유로 기존 버전을 함께 삭제하지 않는다.

## Java 이름 변경

- Java 내부 변수명, 메서드명, 클래스 구현만 변경되고 외부 API 계약이 같다면 새 버전을 만들지 않는다.
- Request 또는 Response의 JSON 필드명이 변경되면 Breaking Change로 판단한다.
- Java 필드명을 변경하더라도 직렬화된 JSON 필드명을 유지하면 현재 버전을 유지할 수 있다.

예를 들어 기존 `v1` 응답이 다음과 같다면:

```json
{
  "description": "내용"
}
```

JSON 필드를 `content`로 변경할 때 기존 `v1`을 수정하지 않는다.

```text
v1 → description 유지
v2 → content 사용
```

## 기존 버전 보호

- 기존 API 버전은 코드에서 사용되지 않는 것처럼 보여도 임의로 삭제하지 않는다.
- 참조 검색 결과가 없다는 이유만으로 외부 앱에서 사용하지 않는다고 판단하지 않는다.
- 리팩터링이나 새 버전 추가 과정에서 기존 Endpoint, Controller, DTO를 함께 삭제하지 않는다.
- 사용자가 명시적으로 삭제를 요청하지 않았다면 기존 API 버전을 유지한다.

## 기존 버전 삭제 확인

사용자가 특정 API 버전의 삭제를 요청했지만 사용자 영향과 삭제 승인 여부가 명확하지 않다면 삭제 전에 다음 내용을 확인한다.

> 현재 이 API 버전을 사용하는 지원 대상 앱이나 클라이언트가 없으며, 제거해도 되는 상태인가요?

- 사용자가 제거해도 된다고 확인한 후에만 해당 API 버전을 삭제한다.
- 사용자가 이미 사용자 영향이 없고 제거가 승인됐다고 명확히 설명했다면 같은 내용을 다시 확인하지 않는다.
- 사용자가 확인하지 않거나 삭제 가능 여부가 불분명하면 기존 API 버전을 유지한다.
- 삭제 요청은 해당 버전의 Endpoint, Controller, DTO 제거에만 적용하며 관련 없는 버전은 변경하지 않는다.

## 완료 전 확인

- 변경이 하위 호환인지 Breaking Change인지 확인한다.
- API 버전을 유지하거나 증가시킨 이유가 규칙과 일치하는지 확인한다.
- Breaking Change에서 기존 버전의 계약이 유지됐는지 확인한다.
- 새 버전에서 핵심 비즈니스 로직을 불필요하게 복제하지 않았는지 확인한다.
- 명시적인 확인 없이 기존 API 버전을 삭제하지 않았는지 확인한다.
