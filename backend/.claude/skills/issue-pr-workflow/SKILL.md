# 이슈·PR 작성과 등록

## 양식과 근거

- `git rev-parse --show-toplevel`로 대상 저장소 루트를 확인한다.
- 이슈 작성 시 저장소의 `.github/ISSUE_TEMPLATE/`에서 작업 유형에 맞는 양식을 읽는다.
- PR 작성 시 저장소의 `.github/pull_request_template.md`를 읽는다.
- 읽은 양식에 아래 백엔드 작성 규칙을 우선 적용하고, 그 외 제목·항목·체크리스트는 유지한다. 양식 전체를 이 스킬에 복사하지 않으며 안내문·빈 예시는 실제 내용으로 대체한다. 이슈 양식의 YAML 메타데이터는 본문과 구분한다.
- 현재 대화의 기획·합의와 실제 변경·커밋·검증 결과를 근거로 한글로 작성한다. 첫 설명은 대상·상황·목적 또는 변경 결과를 1~2문장으로 전달하고, 나머지는 주제별로 묶는다. 분량을 강제로 제한하지 않는다.
- 이슈에는 문제·목표, 범위·핵심 정책·예외·선행 조건을 남기고 작업 상세는 확인 가능한 완료 조건으로 쓴다. 해당 이슈를 읽고 개발할 수 있도록 인터뷰 합의를 보존한다. 버그 이슈의 재현 방법·예상 결과·실제 결과도 생략하지 않는다.
- PR에는 실제 수행한 작업을 목적별로 묶어 빠짐없이 설명한다. 이슈 배경을 짧게 연결하고 변경 결과·선택 이유·검증 결과와 필요한 읽는 순서를 남긴다. 검증은 기존 `작업 내용`에 포함한다.
- 같은 설명·전체 파일/메서드/커밋 목록·작업 과정의 중계는 줄이되, 흐름 이해에 필요한 변경·정책·예외·의존 관계·미검증 범위는 빼지 않는다. 긴 로그나 보충 자료는 링크·접기 영역으로 옮기고 핵심 판단 근거는 본문에 둔다. `Technical Concerns`에는 실제 선택 이유나 논의할 사항을 적는다.
- 계획과 완료한 작업을 구분한다. 날짜, 이슈 번호, 팀 합의, 테스트 통과, Linear 동기화 여부를 추측하거나 미확인 항목을 완료로 표시하지 않는다.
- `Technical Concerns`의 중요한 고민은 **문제 → 해결과 선택 이유 → 결과·검증·남은 한계**로 설명한다. 긴 고민은 [decision-notes](../decision-notes/SKILL.md)의 관련 기록으로 연결한다. 실제 고민이 없으면 세 단계를 억지로 채우지 않고, 검증 명령·전체 결과는 `작업 내용`과 중복하지 않는다. PR 초안만 요청한 경우 새 고민 문서를 자동 저장하지 않는다.
- 관련 이슈는 이슈·PR 본문에 연결할 수 있다. 커밋 메시지의 이슈 번호 금지 규칙과 혼동하지 않는다.
- 작성 후 합의·실제 diff·검증 결과와 대조해 누락과 중복을 한 번 정리한다. 짧게 보이도록 실제 수행한 일을 삭제하지 않는다.

## 백엔드 양식 적용

- 이슈에서는 모든 유형의 `마감 기한`과 `이슈 확인` 항목을 제목·본문·체크박스와 함께 제외한다. 해당 항목을 채우기 위한 날짜·확인 팀원 질문도 하지 않는다. 작성자 계정 확인은 그대로 수행한다.
- 이슈의 `참고 자료`는 실제 관련 자료·링크가 있을 때만 포함한다. 없으면 제목까지 생략하며 `없음`, `미정`이나 가짜 링크로 채우지 않는다. 필요한 선행 이슈·공통 명세는 관련 자료에 해당한다.
- PR의 `연관된 이슈`에는 담당 작업 이슈를 `- #숫자` 형식으로만 적는다. 여러 개면 한 줄에 하나씩 쓰며 제목·설명·URL·종료 키워드를 덧붙이지 않는다. 선행·후속·상위 작업의 관계 설명과 링크는 `작업 내용` 또는 `참고 자료`에 둔다.
- PR 체크리스트의 브랜치 항목은 `PR 대상 브랜치가 합의한 기준과 일치하나요?`로 작성한다. 실제 또는 등록할 base가 확정한 통합 브랜치인지 확인한다. Linear 항목은 `Linear 동기화 여부를 확인했나요?`로 유지하고 관련 연동 상태를 확인한다.
- AI가 대상 브랜치를 합의한 기준과 일치시키고 Linear 상태 확인을 마친 뒤 두 항목 모두 `- [x]`로 작성한다. Linear는 동기화 여부를 확인했다는 뜻이며 동기화 성공 자체를 뜻하지 않는다. 기준에 맞지 않거나 확인할 수 없는 항목은 `- [ ]`와 짧은 사유를 남기고, 완료한 것으로 표시하지 않는다.

## 라벨·작성자·담당자

- 대상 저장소의 실제 라벨 목록을 확인하고, 모든 백엔드 이슈·PR에 `Server`를 붙인다.
- 변경 내용에 맞춰 `feat`, `fix`, `refactor`, `docs`, `test`, `style`, `chore` 등 존재하는 작업 유형 라벨을 AI가 선택한다.
- PR의 `refactor`는 기존 동작·API 계약을 유지하는 내부 구조 변경에 붙인다. 제목·브랜치·이슈 라벨을 그대로 복사하지 말고 실제 PR diff·합의한 범위와 대조한다. 함께 바뀐 문서·회귀 테스트·포맷에는 `docs`·`test`·`style`을 함께 붙일 수 있다.
- 리팩터링에 새 기능·의도한 동작 수정·설정 변경이 섞이면 해당 `feat`·`fix`·`chore` 라벨도 함께 붙인다. 자동 리뷰는 이런 혼합 변경에 일반 한도를 적용하므로 한도를 늘리려고 `refactor`만 붙이거나 다른 유형 라벨을 누락하지 않는다.
- 라벨이 없는 PR은 자동 리뷰에서 일반 변경으로 취급한다. 생성 전 초안에 분류를 표시하고, 생성·수정 후 실제 PR 라벨을 확인한다. 최초 자동 검토 이후 라벨을 바꿔도 재리뷰를 시작하지 않는다.
- `Server`가 없거나 적절한 양식을 찾을 수 없으면 초안은 준비하고 등록 전에 사용자에게 확인한다.
- 작성자는 사용자 본인의 GitHub 인증 계정으로 한다. 등록에 사용할 계정을 조회하고, 의도한 계정을 모르면 "작성자는 어떤 GitHub 계정으로 해야 하나요?"라고 질문한다.
- 계정이 이미 확인되었다면 같은 질문을 반복하지 않는다. Git 커밋 작성자 설정이나 Assignee로 GitHub 작성자를 대신 지정하지 않는다.
- 작성자(author)와 담당자(assignee)는 별개다. **모든 생성·재사용 이슈와 PR에 확인된 본인 GitHub 계정을 담당자로 지정**한다. 기존 다른 담당자를 임의 제거하지 않는다. 메인 이슈도 전체 진행을 맡긴 대상이면 본인 담당 여부를 확인한다.
- 초안에 담당자를 표시하고 생성·수정 후 실제 `assignees`를 재조회한다. 빠졌으면 보완하고 다시 확인한다. 설정 실패는 미완료로 보고하며 다른 사람을 대체 지정하지 않는다.

## 초안과 승인

- 수동 심화 인터뷰의 정상 완료 결과 승인① 뒤 초안을 작성하는 경우, 미확정인 등록용 계정·담당자·라벨·브랜치 정보는 미확정으로 표시하고 등록 전에 확인한다. 이를 확인하느라 완료한 인터뷰를 다시 열지 않는다. 초안 내용에 대한 확인만으로 등록·개발까지 승인받았다고 해석하지 않는다.

- "이슈 작성해줘", "PR 작성해줘" 요청에는 먼저 채팅으로 초안을 보여준다.
- 제목·본문·라벨·작성자·담당자 계정과 브랜치 정보를 본문과 구분해 보여준다. 복사용 Markdown을 요청하면 코드 블록으로 제공한다.
- 브랜치 이름·생성 기준·PR 대상은 [branch-workflow](../branch-workflow/SKILL.md)를 읽고 결정한다.
- 이슈 초안에는 생성할 브랜치 형식을, PR 초안에는 확인된 작업 브랜치와 대상 브랜치를 포함한다.
- 사용자가 해당 초안에 "OK", "등록해줘" 등으로 승인한 뒤 등록한다. 승인된 내용에 대해 같은 승인을 반복 요청하지 않는다.
- 필수 계정·브랜치 정보가 미확정이면 먼저 확인한다. 개별 등록 요청에서 최종 게시 내용이나 대상이 달라지면 수정된 초안을 보여준다.

## 전체 개발 흐름의 승인

- [development-workflow](../development-workflow/SKILL.md)에서 분할안·단위별 초안과 이슈·브랜치 생성부터 개발·검증·커밋·푸시·PR 등록까지의 범위를 보여주고 받은 사용자 승인은 그 범위의 등록에도 적용한다.
- 승인된 본문으로 서브 이슈를 등록하고 첫 이슈에 착수한다. 추가 분할·합치기·기능·정책·완료 기준·저장소·통합 브랜치 변경은 영향받는 부분만 재승인받는다. 단순 문구·실제 링크·진행 상태 갱신에는 같은 승인을 반복하지 않는다. 전체 실행 승인은 커밋별 승인이나 PR 병합 권한을 대신하지 않는다.
- 단순 "이슈 작성", "이슈 등록", "PR 작성" 요청을 전체 개발 승인으로 확대하지 않는다. 인터뷰 중 초안을 보여주기 전에 나온 진행 요청도 등록 승인으로 간주하지 않는다.

## 이슈 등록

1. 같은 작업의 이슈가 이미 있는지 확인한다.
2. 승인된 제목·본문·라벨·본인 담당자로 GitHub에 등록한다. 등록 후 작성자·담당자·라벨·본문을 재조회해 확인한다.
3. 기존 이슈가 있으면 재사용하고 실제 번호를 분할안에 연결한다. 전체 분할 흐름에서는 **사람이 제공한 메인 이슈 아래에 실제 sub-issue 관계로 연결**하고 부모·자식 관계를 재조회한다. 본문의 링크만으로 연결 완료라고 하지 않는다. 메인 이슈를 임의 생성하지 않는다. 사용 중인 GitHub API·CLI 지원을 확인한 후 실제 식별자를 사용한다.
4. 일부 생성·담당자 지정·부모 연결만 성공하면 성공한 번호와 실패 단계를 기록한다. 재조회 후 누락된 작업만 수행하고 이슈를 다시 생성하지 않는다. API 미지원·권한 실패로 관계를 확인할 수 없으면 등록 미완료로 알리고 개발 착수를 보류한다.
5. 단일 작업은 승인 범위에 따라 실제 번호로 브랜치를 생성한다. 여러 이슈의 전체 개발은 각 단위 착수 때 생성하며 이슈 등록만 명시한 요청이나 추적 이슈에는 브랜치를 만들지 않는다.
6. 이슈 링크와 생성한 브랜치 또는 착수 예정 단위를 알려준다.

## PR 등록

1. 현재 작업 브랜치와 확인된 통합 대상 브랜치의 커밋·diff 및 기존 PR을 확인한다.
2. PR에 포함될 실제 변경을 위 작성 규칙으로 정리하고 담당 작업 이슈를 연결한다. 이슈 종료 키워드는 사용하지 않으며 번호 연결만으로 자동 종료를 전제하지 않는다. 이 흐름에서 선행·후속·상위 추적 이슈를 함께 닫지 않는다. 현재 비즈니스 규칙이 바뀌었다면 실제 변경을 기존 `작업 내용`에 설명하고 공통 [business-rules](../../../../.claude/skills/business-rules/SKILL.md)에 따라 규칙 문서를 확인한다.
3. 미커밋 변경이 있으면 PR 포함 여부를 구분한다. 커밋 생성이 필요한 경우 사용자의 요청 범위를 확인하고 [commit-conventions](../commit-conventions/SKILL.md)를 적용한다.
4. 필요한 경우 일반 푸시하고, 확인된 대상 브랜치로 개별 승인 또는 전체 개발 승인 범위의 PR을 등록한다. 명시적으로 맡긴 기존 스택의 재정렬·재작성 푸시만 [스택 관리 절차](../branch-workflow/references/stacked-prs.md)에 따른다.
5. 여러 PR이면 `작업 내용`·`참고 자료`에 **전체 순서와 현재 위치, 선행·후속 PR 링크, 이번 범위, 핵심 파일의 읽는 순서와 확인할 내용**을 추가한다. 관계는 한 줄로 요약하고 읽는 순서는 이해에 필요한 경로로 묶는다. 아직 없는 PR은 계획 이름으로 표시하고 생성 후 연결을 갱신한다. 독립 PR에도 승인된 순서를 표시하고 핵심 파일 링크는 실제 diff에서 확인한다.
6. 위 두 체크리스트 항목의 실제 확인 결과를 반영하고 PR 링크와 지금 읽을 대상·다음 작업을 즉시 알린다. PR 등록·연결 승인으로 병합하거나 브랜치를 삭제하지 않는다.
7. PR의 실제 diff·본문·base·작성자·담당자·라벨·담당 이슈 연결을 재조회한다. 본인 담당자가 빠졌으면 추가하고 재확인한다. 현재 규칙이 바뀌면 작업 종료 응답에 Notion 반영 위치·수정 방법·완성 문구를 안내한다.

## 등록 시 주의

- GitHub CLI를 사용하면 제목·본문·라벨·`--assignee <확인된 본인 login>`·대상 브랜치를 명시한다. 기존 대상은 담당자를 추가한 뒤 `assignees`를 재조회한다. 여러 줄 본문은 임시 파일과 `--body-file`로 전달한다.
- 게시용 임시 본문은 임시 디렉터리에 두고, 요청 없이 저장소에 초안 파일을 추가하지 않는다.
- 등록 응답이 불명확하면 생성 여부를 먼저 조회해 중복 등록을 막는다. 권한·네트워크 오류로 진행할 수 없으면 완료된 단계와 실패한 단계를 알린다.
- 이슈 등록 후 브랜치 생성만 실패했다면 이슈를 다시 만들지 않는다.

## 이슈 종료

- 전체 실행 승인에는 [병합·완료 확인](../development-workflow/references/completion-gate.md)에 따른 해당 작업 이슈 종료가 포함된다. PR 본문은 번호 연결만 유지하며 자동 종료를 가정하지 않는다.
- PR 병합·실제 완료 조건을 모두 확인한 경우 열린 작업 이슈를 닫고 다시 조회한다. 닫힌 상태만 보고 완료로 판단하지 않는다. 메인 이슈는 모든 자식과 전체 요구사항을 대조한 뒤 종료한다.

## GitHub sub-issue 연결 참고

- 실제 지원은 사용 시 확인한다. REST로 연결하면 자식의 화면 번호가 아닌 숫자 `id`를 조회해 `POST /repos/{owner}/{repo}/issues/{main_number}/sub_issues`의 `sub_issue_id`로 전달한다. 이미 다른 부모가 있으면 승인 없이 `replace_parent`로 옮기지 않는다.
- 연결 뒤 자식의 `GET /repos/{owner}/{repo}/issues/{child_number}/parent`와 부모의 sub-issue 목록을 대조한다. 목록은 페이지 끝까지 확인하고 기존 연결이면 중복 요청하지 않는다.
- [GitHub sub-issues API](https://docs.github.com/en/rest/issues/sub-issues)
