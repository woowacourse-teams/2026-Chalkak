# 커밋 컨벤션

## 커밋 단위

- 커밋 하나는 하나의 완결된 논리적 변경을 담는다.
- 정리된 각 커밋은 해당 커밋만으로 빌드와 테스트를 통과해야 한다.
- 작업 중 WIP 커밋은 자유롭게 만들 수 있으며, 머지 전 `git rebase -i`로 논리 단위로 정리한다.
- 분리하면 빌드나 테스트가 깨지는 변경은 완결된 단위로 함께 묶는다.

다음 경우 커밋을 나눈다.

- 설명에 "그리고 / 및 / ~하고"로 두 개 이상의 변경이 이어질 때
- "작업함 / 수정함 / 개선함"처럼 대상과 행위가 뭉뚱그려질 때
- 하나의 type으로 정할 수 없을 때
- 되돌리면 관련 없는 변경까지 함께 사라질 때

## 메시지

```text
type: 제목

본문 (선택)
```

| type | 용도 |
| --- | --- |
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변화 없는 코드 개선 |
| `docs` | 문서 수정 |
| `test` | 테스트 추가·수정 |
| `style` | 동작 변화 없는 포맷팅 |
| `chore` | 빌드 설정, 패키지 등 잡무 |

- 제목은 한글 25~30자 이내로 짧게 작성한다.
- "추가함" 대신 "추가"처럼 명령형으로 쓰고 끝에 마침표를 붙이지 않는다.
- 하나의 커밋에는 하나의 type만 사용한다.
- 본문도 한글로 작성하며, 커밋 메시지에는 이슈 번호를 연결하지 않는다.
- 변경 대상과 행위가 드러나게 작성한다.

## 적용

- 메시지 추천만 요청하면 메시지만 제시한다.
- 실제 커밋을 요청하면 변경 내용과 스테이징 범위를 확인하고 논리 단위로 구성한다.
- 빌드·테스트를 실행하지 못했거나 실패했다면 통과했다고 쓰지 않는다.
- 커밋 정리를 요청받으면 대상 이력을 확인하고 WIP를 논리 단위로 정리한다. 공유된 이력 변경이나 강제 푸시를 임의로 수행하지 않는다.
