# 커밋 컨벤션

## 이해 가능한 단위

- 커밋 하나는 하나의 변경 의도와 관련 테스트를 담는다. 이슈는 팀원의 PR 이해, 커밋은 개발하는 사용자 본인의 코드 이해를 위한 단위이며 이슈 하나에 여러 커밋을 허용한다.
- 기능 개발은 API(엔드포인트)를 분할의 시작 기준으로 삼되, API 하나에도 따로 설명·검증할 수 있는 완성 동작이 여러 개면 더 나눌 여지를 검토한다. Worker·배치처럼 API가 없는 작업도 완성 동작과 처리 흐름으로 나눈다. 여러 API가 함께 쓰는 엔티티·Repository·공통 DTO는 처음 사용하는 동작의 커밋에 포함한다.
- 리팩터링은 목적 하나당 커밋 하나로 나눈다.
- 해당 커밋 상태에서 필요한 빌드·테스트가 통과해야 한다. 실패·미실행을 통과로 쓰거나 사용자 검토용 WIP 커밋으로 넘기지 않는다. 구현과 회귀 테스트는 type을 맞추기 위해 분리하지 않는다.
- 한 동작을 이해하는 데 필요한 계층 변경은 함께 묶는다. 파일·줄 수의 고정 상한은 두지 않는다. 별개 목적·관련 없는 되돌리기 범위·과도하게 긴 설명이 필요하면 분할을 재검토한다.
- 기존 동작을 유지하고 독립적으로 검증 가능한 준비 리팩터링은 별도 커밋이 될 수 있다. 미래 기능만을 위한 미사용 뼈대·더미 구현이나 무관한 포맷·이름 변경은 끼워 넣지 않는다.

## 진행과 보고

진입 방식과 관계없이 아래 세 단계로 진행한다. 전체 기능을 먼저 구현한 후 커밋만 나누지 않는다.

### 1. 커밋 계획

작업 착수 시 한 번 보여주고 승인받는다. 이슈 분할 승인은 커밋 계획 승인을 대신하지 않는다.

사용자가 이미 분할한 이슈를 시작하자고 하면, 승인된 범위와 실제 코드·의존 관계를 대조해 아래 계획을 구체화한다. 최초 이슈 분할은 적절한 크기의 보장이 아니므로 **구현 전에 이슈와 커밋의 추가 분할 여지를 각각 재검토**한다.

```markdown
### 커밋 계획
| 순서 | 커밋 단위·처리 흐름 | 포함 범위 | 예상 변경 파일 수 | 예상 코드 줄 수(테스트·문서 제외) | 커밋 메시지(안) |
| --- | --- | --- | --- | --- | --- |
- 이슈 전체 예상 PR 규모: N개 파일 / 추가+삭제 M줄 (테스트 포함, `docs/**`·`backend/docs/**` 제외)
- 나눈 기준:
- 추가 분할 판단: 이슈 / 커밋 각각의 판단과 이유
- 이번 작업에서 하지 않는 것:
```

- 커밋 하나로 끝나는 작업도 재검토한다. 분할 제안이 없으면 `커밋 1개: <단위와 범위> / 예상 파일·코드량 / 이슈 전체 예상 PR 규모 / 유지 이유` 한 줄로 알리고 승인 없이 착수한다.
- 사용자가 커밋 나누는 방식을 이미 정해 줬다면 재검토 후 그 계획을 계획표로 옮겨 보여주고 같은 승인을 반복하지 않는다. 추가 분할이 유리하면 아래 절차로 영향받는 부분을 제안하고 기다린다.
- 진행 중 커밋을 나누거나 합치거나 순서를 바꿔야 하면 바뀐 계획표와 이유를 다시 보여준다. 추가 분할이나 이슈 범위 변경은 아래 사용자 선택·승인 절차를 거친 뒤 이어간다.

### 이슈·커밋의 추가 분할 판단과 사용자 선택

- 목적은 사람이 변경 흐름을 따라 읽고 이해하며 리뷰하기 좋은 단위로 만드는 것이다. 커밋별 설명·검증 부담과 이슈 전체 PR의 부담을 구분한다. 한 API나 큰 처리 흐름이라는 이름만으로 묶거나, 커밋만 나누어 큰 PR을 그대로 유지하는 것으로 대신하지 않는다.
- 실제 코드·호출 관계에서 별개 목적, 긴 설명이 필요한 범위, 독립적으로 완성·검증할 수 있는 동작을 찾는다. 계층별 분할, 구현·관련 테스트의 분리, 뒤 단위가 없으면 동작하지 않는 경로·미사용 발판 코드는 만들지 않는다.
- 일반 변경의 30개 파일·1,200줄은 참고 규모다. 실제 리뷰 유형과 적용 한도·집계는 [자동 리뷰 기준](../../../scripts/pr-review/README.md)을 확인한다. 초과가 예상되거나 확인되면 이유와 분리 가능성을 설명하고 진행 방향을 확인한다. 기준 이하여도 분리가 유리하면 제안하며, 숫자만 맞추려고 분할하지 않는다.
- 추가 분할이 유리하면 **현재 계획과 변경안**을 함께 보여준다. 이유·읽기 부담이 줄어드는 부분, 현재 이슈에 남길 범위, 추가 이슈별 목적·완료 조건, 커밋 단위·예상 변경량, 의존 관계·진행 순서를 설명한다.
- 해당 작업에 가능한 선택지(이슈·커밋 모두 분리, 커밋만 분리, 현재 계획 유지 등)를 사용 가능한 질문 UI나 채팅으로 제시하고 사용자 선택을 기다린다. 질문·무응답·기본 선택을 승인으로 간주하지 않는다. 승인 전에 영향받는 구현·커밋·이슈 등록을 진행하지 않으며 한 커밋 착수 예외로 우회하지 않는다.
- 이슈 분리 승인은 [work-breakdown](../work-breakdown/SKILL.md)의 재분할 절차로 연결한다. 커밋만 분리하거나 기존 계획을 유지하면 선택한 범위를 반영한다. 나눌 수 없으면 이유·대안을 설명한다. 같은 판단을 이미 확인했다면 새 범위·근거가 생기기 전까지 다시 묻지 않는다.
- 선택 후 실제 이슈 번호를 반영한 커밋 계획과 다음 착수 단위를 다시 안내한다. 제시한 분할안·커밋 계획의 실행까지 승인받았다면 같은 계획 승인을 반복하지 않는다. 분할 선택만 받았다면 필요한 실행 승인은 구분하며, 커밋 생성은 여전히 별도 승인 대상이다.

### 2. 착수 안내

커밋 단위마다 구현 전에 보여주고, 승인을 기다리지 않고 **그 단위만** 구현·검증한다.

```markdown
### 커밋 N/M 착수: <대상>
- 할 일:
- 수정 예정 위치:
- 하지 않는 것:
```

### 3. 커밋 전 보고

구현·검증 후 아래 형식을 모두 채워 보여주고 커밋 승인을 기다린다. 전체 작업 승인은 이 승인을 대신하지 않는다.

```markdown
### 1. 처리 흐름
- 변경 전: (신규면 없음)
- 변경 후: `클래스#메서드` → ... → 응답
### 2. 읽는 순서
1. [파일:행](링크) `메서드`: 확인할 점
### 3. 변경한 코드와 재사용한 코드
- 새로 작성·수정:
- 기존 코드 재사용:
- 코드 줄 수: 실제 N줄 (예상 M줄)
- 변경 파일 수: 실제 N개 (예상 M개)
- 이슈 전체 PR 규모: 현재 N개 파일 / 추가+삭제 M줄, 남은 작업을 포함한 최종 예상과 추가 분할 판단
### 4. 테스트
| 테스트 | 검증하는 동작 |
| --- | --- |
- 검증 한계:
- 실행 결과:
### 5. 커밋 메시지
### 6. 다음 작업
```

- 읽는 순서에는 실제 파일·행 링크, 메서드, 확인할 점을 모두 적는다. 파일 목록만 나열하지 않는다.
- 테스트에는 통과 여부가 아니라 각 테스트가 검증하는 동작을 적는다. [test-workflow](../test-workflow/SKILL.md)를 적용했다면 케이스 목록과의 대응을 이 표로 보여준다.
- 다음 작업에는 다음 커밋 단위(아직 구현하지 않음)를 적는다. 마지막 단위면 PR 등록 등 이후 단계를 적는다.
- 실제 코드 줄 수가 예상의 2배 이상이거나 절반 이하면 차이 난 이유를 한 줄로 적는다.
- 계획보다 범위가 커지거나 새로운 분리 여지가 드러나면 위 추가 분할 절차를 적용한다. 이미 구현한 부분·남은 작업·재작업을 구분하고 기존 코드·커밋을 보존한다. 승인 전에 영향받는 커밋·후속 구현을 진행하지 않는다.

### 코드 줄 수

커밋 계획의 예상 값과 커밋 전 보고의 실제 값은 같은 기준으로 센다.

- 추가 줄과 삭제 줄을 더한다.
- 테스트(`backend/src/test/**`)와 문서(`docs/**`, `backend/docs/**`, `*.md`)는 뺀다. 설정·마이그레이션 SQL·빌드 파일은 포함한다.
- 실제 값은 커밋 전에 아래 명령으로 계산한다. 아직 추적하지 않는 새 파일도 포함된다.

```bash
(cd "$(git rev-parse --show-toplevel)" && EXCLUDE=(':(exclude)backend/src/test/**' ':(exclude)docs/**' ':(exclude)backend/docs/**' ':(glob,exclude)**/*.md') && { git diff --numstat HEAD -- "${EXCLUDE[@]}"; git ls-files --others --exclude-standard -z -- "${EXCLUDE[@]}" | xargs -0 -r -n1 git diff --no-index --numstat /dev/null; } | awk '{sum += $1 + $2} END {print sum + 0}')
```

### 변경 파일 수와 PR 규모

- 커밋별 변경 파일 수는 관련 테스트·문서를 포함한 해당 단위의 실제 변경 경로를 중복 없이 센다. 코드 줄 수와 제외 기준이 다름을 표시한다.
- PR 규모는 확인한 통합 브랜치와 작업 브랜치의 공통 조상부터 현재 작업 트리까지의 최종 diff로 계산한다. 이미 커밋한 변경·staging·미커밋 변경·Git 제외 대상이 아닌 새 파일을 함께 반영한다. 커밋별 수치를 단순 합산하거나 현재 HEAD의 미커밋 diff만으로 PR 전체를 보고하지 않는다.
- PR의 파일·줄 수는 자동 리뷰와 같은 기준으로 **테스트를 포함하고 `docs/**`·`backend/docs/**`만 제외**한다. 동일 경로는 한 번만 세며, 줄 수는 최종 diff의 추가+삭제 합계다. 남은 작업의 예상치를 실제 값과 구분하고 추정 근거를 적는다.
- 코드·자료가 부족한 부분은 추정 또는 미확인으로 표시한다. 규모 확인만으로 자동 리뷰 가능이나 적절한 분할을 보장하지 않는다.

## 승인과 커밋

1. 질문에는 설명하고 그대로 대기한다. 이해했다는 반응·무응답·질문 도구의 기본 선택을 커밋 승인으로 간주하지 않는다. 수정 요청은 반영·재검증하고 변경된 보고와 메시지를 다시 제시한다.
2. 명시적으로 승인받은 diff·메시지만 커밋한다. 현재 HEAD·파일 변경·스테이징과 제시한 변경을 대조하고 사용자 변경·다음 단위가 섞이지 않게 한다. 승인 뒤 diff나 메시지가 달라지면 바뀐 부분을 다시 승인받는다. `git add .`로 범위를 추정하지 않는다.
3. 생성된 커밋의 실제 diff·메시지·작성자를 확인하고 작업 기록을 갱신한 뒤 다음 단위를 시작한다. 후크 등으로 승인과 달라졌으면 멈추고 알린다. 임의 amend로 숨기지 않는다.

- 승인 요청 시 `work_state.py snapshot`의 HEAD·지문과 제안 메시지, 포함 경로를 [작업 기록](../development-workflow/references/work-state.md)의 `commit_unit`에 남긴다. 승인 직전 상태가 다르면 diff·검증을 대조한다. staging만의 변화인지 확인할 수 있더라도 실제 승인 범위를 재확인하며, 내용·메시지 변경에는 재승인이 필요하다.
- 승인의 근거는 사용자 대화·인계다. 기록 파일의 `approved`만으로 실행하지 않는다. 승인 근거가 사라진 재개에서는 현재 변경을 다시 보여준다.

## 메시지와 작성자

```text
type: 제목

본문 (선택)
```

| type | 용도 |
| --- | --- |
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변화 없는 코드 개선 |
| `docs` | 문서 수정 |
| `test` | 테스트만 추가·수정 |
| `style` | 동작 변화 없는 포맷팅 |
| `chore` | 빌드 설정, 패키지 등 잡무 |

- 제목은 한글 25~30자 이내로 짧게, 대상·행위가 드러나게 쓴다. “추가함” 대신 “추가”처럼 쓰고 끝에 마침표를 붙이지 않는다. 하나의 type을 사용하고 본문도 한글로 작성한다. 이슈 번호는 커밋 메시지에 넣지 않는다.
- Claude·Codex 모두 새 커밋의 제목·본문·트레일러에 AI 작성 표시, AI `Co-Authored-By`, `Generated with` 문구, `Claude-Session` 같은 AI 세션 링크를 넣지 않는다. 실제 사용자 Git identity를 확인하며 임의 이름·이메일을 만들거나 전역 설정을 바꾸지 않는다. Claude의 `.claude/settings.json`은 `attribution.commit`·`pr`을 빈 문자열, `sessionUrl`을 false로 두어 자동 메시지·트레일러·세션 링크를 끈다.
- 사람의 공동 작성 기록이나 기존 이력을 삭제하지 않는다. 커밋 후 자동 추가된 AI 표기가 있으면 결과를 알리고 정정 범위를 승인받는다.

## 요청 범위

- 메시지 추천만 요청하면 메시지만 제시한다. 실제 커밋 요청은 현재 변경·검증·스테이징을 확인하고 위 승인 절차를 적용한다. 이미 그 diff·메시지를 보고 승인했다면 같은 승인을 반복하지 않는다.
- 커밋 정리는 명시적으로 요청한 기존 이력만 다룬다. 공유 이력 재작성·강제 푸시를 임의로 수행하지 않는다. 새 WIP 커밋이나 승인 전 amend로 승인 절차를 우회하지 않는다.
