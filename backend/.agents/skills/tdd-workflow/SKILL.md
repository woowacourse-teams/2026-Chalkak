# TDD 작업 컨벤션

## 적용 범위

다음 작업에 TDD를 적용한다.

- 새로운 기능 또는 비즈니스 규칙 구현
- 기존 동작 변경
- 버그 수정

테스트 작성 규칙과 테스트 유형은 `test-code` 컨벤션을 따른다.

운영 코드 작성 규칙은 `main-code` 컨벤션을 따른다.

`test-code`에서 테스트 제외 대상으로 정한 코드에는 의미 없는 테스트를 추가하지 않는다.

## 작업 단위

- 한 번에 하나의 동작만 테스트하고 구현한다.
- 여러 동작을 한 테스트나 한 구현 단계에서 동시에 처리하지 않는다.
- 관련된 기존 테스트와 운영 코드를 먼저 확인한다.
- 테스트 유형은 대상 계층과 검증하려는 동작에 맞게 선택한다.

## Red

1. 구현하려는 동작을 표현하는 테스트를 먼저 작성한다.
2. 새 테스트만 실행하거나 가장 좁은 범위의 테스트를 실행한다.
3. 테스트가 기대한 이유로 실패하는지 확인한다.
4. 테스트가 처음부터 통과하면 새 동작을 실제로 검증하는지 다시 확인한다.
5. 환경 설정, 외부 시스템 또는 무관한 기존 오류로 실패한 것은 Red로 인정하지 않는다.

새 API나 메서드가 아직 없어 발생한 컴파일 오류는 새 계약의 부재가 직접적인 원인일 때 Red로 인정할 수 있다.

## Green

1. 실패한 테스트를 통과시키는 최소한의 운영 코드를 작성한다.
2. 현재 테스트에 필요하지 않은 기능이나 일반화를 미리 추가하지 않는다.
3. 대상 테스트를 다시 실행하여 통과하는지 확인한다.
4. 테스트가 통과하기 전에 다음 동작을 구현하지 않는다.

## Refactor

1. 테스트가 통과하는 상태에서 중복, 이름, 책임 또는 구조를 개선한다.
2. 리팩터링 과정에서 새로운 동작을 추가하지 않는다.
3. 리팩터링 후 대상 테스트를 다시 실행한다.
4. 관련 테스트가 계속 통과하는지 확인한 뒤 다음 TDD 사이클로 이동한다.

## 버그 수정

- 버그를 재현하는 실패 테스트를 먼저 작성한다.
- 재현 테스트가 기대한 이유로 실패하는지 확인한다.
- 테스트를 통과시키는 최소 수정으로 버그를 해결한다.
- 동일한 버그가 다시 발생하지 않도록 재현 테스트를 유지한다.

## 기존 테스트 보호

- 운영 코드를 잘못된 상태로 유지하기 위해 테스트를 삭제하거나 검증을 약화하지 않는다.
- 요구사항이 변경된 경우에만 기존 테스트의 기대 결과를 변경한다.
- 테스트를 변경했다면 어떤 요구사항이 달라졌는지 확인한다.
- 관련 없는 기존 테스트와 운영 코드는 함께 수정하지 않는다.
- 사용자가 작성 중인 기존 변경을 TDD 순서를 맞추기 위해 되돌리지 않는다.

## 완료 전 확인

- 운영 코드보다 실패 테스트를 먼저 작성했는지 확인한다.
- 테스트가 기대한 이유로 실패하는 것을 확인했는지 점검한다.
- 테스트를 통과시키는 최소 구현만 추가했는지 점검한다.
- 리팩터링 전후로 테스트가 통과하는지 확인한다.
- 변경한 동작과 관련된 테스트를 실행한다.
- 필요한 범위의 전체 테스트를 실행하여 회귀가 없는지 확인한다.
- 완료 결과에 실행한 테스트와 결과를 기록한다.
