# 찰캌 딥 인터뷰

## 시작 판단

- 첫 문장의 키워드보다 요청 목적과 기존 작업 근거로 판단한다. 새 세션·프로젝트 실행·현재 브랜치만으로 새 작업이나 인터뷰 필요 여부를 단정하지 않는다.

1. **명시한 의도 우선**: 질문을 통해 요구사항을 정하자는 명시적인 요청이면 인터뷰한다. "기획은 확정됐으니 구현해줘"처럼 인터뷰 없이 구현을 요청하면 해당 작업으로 진행하고 꼭 필요한 결정만 질문한다.
2. **기존 작업 근거 확인**: 필요한 범위에서 대화의 합의, 연결된 이슈·명세, 실제 변경을 대조한다. 같은 작업의 구현·수정·재개나 오류 해결이면 전체 인터뷰를 반복하지 않는다. 설명·가능 여부를 묻는 정보 요청, 커밋·PR 작성, 완료 작업의 이슈 정리도 그 요청만 처리한다.
3. **새 요구사항 구체화**: 새 기능·변경을 추진하려는데 목적·범위·정책·완료 기준을 정해야 한다면 인터뷰한다. "신고 기능 넣자", "신고도 되게 하고 싶어"처럼 표현이 달라도 같은 의도로 판단하며, "이슈"라는 단어를 요구하지 않는다.
4. **애매할 때 한 번 확인**: 근거를 확인해도 기획과 구현 중 무엇을 원하는지 불분명하면 "이 작업은 요구사항부터 함께 정할까요, 아니면 이미 정해진 내용대로 구현하면 될까요?"라고 한 번 묻고 답을 기다린다. 그 전에는 인터뷰 점수 평가나 전체 개발 흐름을 시작하지 않는다. 선택한 진행 방식을 같은 작업에서 다시 묻지 않는다.

- 이미 합의한 작업을 PR까지 전체 진행·재개할 때는 [development-workflow](../development-workflow/SKILL.md)를 사용한다. 단순 코드 질문이나 수정 요청을 새 이슈 기획이나 전체 개발 흐름으로 확대하지 않는다.

## 깊이와 추가 인터뷰

- 기본은 **심화: 모호함 15% 이하**다. 처음에 모드 선택을 묻지 않는다. 사용자가 원하면 기본 20%, 간단 30% 또는 지정한 0~100% 기준으로 바꾼다.
- 선택한 기준을 짧게 알린 뒤 질문을 시작한다. 모드는 허용할 모호함의 차이이며, 중요한 정책 누락을 허용하는 기준은 아니다.
- "인터뷰 더 해줘"는 기존 합의를 유지하고 미검토 시나리오나 지정한 쟁점을 더 깊게 묻는 요청이다. 같은 질문을 반복하거나 모호함을 100%로 초기화하지 않는다.
- "처음부터 다시 인터뷰해줘"는 기존 합의의 전제·목적·범위까지 재검토하는 요청이다. 기존 합의를 참고하되 확정된 답으로 강제하지 않으며, 기존 코드·이슈·브랜치를 삭제하거나 새로 만들지 않는다.

## 질문과 서비스 맥락

1. 요청과 관련된 코드·테스트, README와 설계 문서를 읽는다. 현재 동작, 사용자 결정, AI의 제안을 구분하고 문서와 코드의 충돌은 구체적으로 확인한다.
2. 다룰 기능·흐름과 제외 범위를 정리한다. 여러 기능이면 각각의 정책·완료 기준을 추적해 한 기능만 깊게 묻다가 다른 기능을 빠뜨리지 않는다.
3. 의도와 범위를 우선해 가장 중요한 불명확한 부분을 **한 번에 한 질문씩** 묻는다. 답변에 따라 후속 질문을 고르며 코드에서 확인할 수 있는 사실은 직접 조사한다.
4. 사례·반례·실패 상황으로 답변의 숨은 전제와 경계를 확인한다. 기존 답변 중 중요한 것 하나 이상을 다시 짚어 더 단순한 범위나 대안의 의미도 검토한다.
5. 답변마다 명확성을 재평가한다. 이미 해결한 질문은 반복하지 않고, 같은 쟁점에서 진전이 없으면 질문을 구체적인 상황으로 바꾼다. 질문 횟수를 채우려고 인터뷰를 늘리지 않는다.

관련 영역에만 다음 관점을 적용한다. 예시는 질문 후보이며 서비스 정책을 미리 정한 것이 아니다.

| 영역 | 확인할 경계 |
| --- | --- |
| 회원·인증·관리자 | 본인·타인·관리자 권한, 비로그인·정지·탈퇴 상태 |
| 주제·게시물·검수 | 참여 시간 경계, 상태 전환, 공개 범위, 삭제와 검수의 관계 |
| 사진·사인 이미지 | 업로드·처리·콜백 순서, 실패·재시도·중복, 이전 이미지 처리 |
| 좋아요·조회 | 반복·동시 요청, 집계와 정렬, 삭제·비공개 대상의 노출 |
| API·저장소·외부 연동 | 클라이언트 계약, 데이터 변경, 실패 응답, 트랜잭션 밖의 부수 효과 |

- 인터뷰 질문은 `request_user_input`이 제공되고 현재 모드에서 사용할 수 있을 때 그 도구로 한 번에 하나씩 묻는다. 사용할 수 없으면 채팅으로 한 질문을 하고 답을 기다린다. 실행 승인 확인은 채팅으로 한다.
- 다른 스킬로 이어갈 때는 연결된 `SKILL.md`를 읽고 현재 단계(초안 작성·등록·개발 재개)에 해당하는 지침을 적용한다.

## 모호함 평가

찰캌의 기존 시스템 변경을 기준으로 다음 명확성을 각각 0~1로 평가한다.

| 항목 | 가중치 | 판단 기준 |
| --- | --- | --- |
| 의도 | 25% | 왜 필요한지, 해결할 문제가 명확한가 |
| 결과 | 20% | 사용자가 얻을 동작과 결과가 구체적인가 |
| 범위 | 20% | 포함·제외할 기능과 AI가 결정해도 되는 범위가 명확한가 |
| 제약 | 15% | 관련 도메인 정책·권한·예외·호환 조건이 정해졌는가 |
| 완료 기준 | 10% | 성공과 실패를 검증할 사례를 작성할 수 있는가 |
| 기존 시스템 이해 | 10% | 관련 코드·계약과 변경 영향을 근거로 설명할 수 있는가 |

- 모호함(%) = `100 × (1 − 명확성 점수의 가중합)`으로 계산한다. 각 항목에 근거와 남은 빈틈을 기록한다.
- 점수 기준은 0: 정보 없음, 0.5: 방향만 확인, 0.75: 구체적이나 중요한 경계 미정, 1: 관련 근거와 검증 가능한 합의가 충분함이다. 중간값도 근거를 설명할 수 있을 때 사용한다.
- 이 수치는 AI의 추정이며 실제 누락률이나 완벽함의 증명이 아니다. 새 모순이 발견되면 점수를 낮추고, 종료를 위해 임의로 높이지 않는다.
- 매 답변 후 사용자에게 현재 모호함·기준과 가장 중요한 남은 쟁점을 짧게 보여준다. 전체 점수표는 종료 평가나 요청 시에 보여준다.
- 준비 완료에는 **기준 이하 + 기능별 누락 확인 + 중요한 미결정 사항 없음 + 심화 후속 질문 수행**이 모두 필요하다. 평균이 낮아도 핵심 권한·상태·실패 정책 등이 미정이면 종료하지 않는다.
- 더 묻더라도 구현이나 검증이 달라지지 않는다면 표현을 다듬기 위한 질문은 종료한다.

## 이슈 초안과 시작 확인

- 준비 완료 시 [work-breakdown](../work-breakdown/SKILL.md)을 읽어 이슈·PR 단위와 의존 관계를 판단하고 단위별 저장소 양식의 이슈 초안을 함께 보여준다. 작은 작업은 하나로 유지한다. 점수·근거·잔여 사항, 라벨·작성자·브랜치 기준·예상 커밋 단위도 알리며 준비 평가는 이슈 본문과 구분한다.
- 기존 이슈의 추가·재인터뷰라면 새 이슈 초안을 무조건 만들지 않고 변경된 합의·분할안·재개 범위를 보여준다. 이후 시작 확인도 새 이슈 생성 대신 해당 작업의 재개 범위로 안내한다. 기존 이슈·브랜치를 재사용하고 변경된 정책·범위에 대한 승인을 받아 이어간다.
- 중요한 미정 사항이 없음을 설명하고 **"이 분할안과 초안으로 이슈 생성부터 개발·커밋·PR 등록까지 시작할까요, 아니면 추가 심화 인터뷰를 할까요?"**라고 한 번 묻는다. "완벽하다"고 단정하지 않는다.
- 추가 심화를 선택하면 가치 있는 미검토 시나리오를 골라 질문한 뒤 수정된 초안을 보여준다. 같은 심화 선택 메뉴를 반복하지 않고, 실행 여부만 확인한다.
- **인터뷰 도중** "이대로 진행하자", "이제 시작해"라고 하면 질문을 멈추고 현재 점수를 다시 계산한다. 확정 사항·미결정 사항·영향과 처리 제안(기존 정책 유지, 범위 제외 등)을 정리한다. `work-breakdown`으로 분할안·단위별 초안과 전체 실행 범위를 함께 보여주고 **"이 내용으로 이슈 생성부터 개발·PR 등록까지 정말 시작할까요?"**라고 한 번 확인한다.
- 조기 진행은 정상 기준 통과로 표시하지 않는다. 중요한 미정 사항은 처리안을 사용자가 승인하거나 직접 결정해야 한다. 실행에 필수인 정보가 없으면 그 정보만 확인한다.
- **분할안·이슈 초안과 전체 실행 범위를 이미 보여준 뒤** 받은 "시작해", "OK"는 실행 승인으로 처리한다. 위 조기 진행 확인을 반복하지 않고 [development-workflow](../development-workflow/SKILL.md)로 이어간다.
- "초안만", "이슈만 등록" 등 사용자가 실행 범위를 좁히면 그 범위만 수행한다. 승인 전에는 이슈·브랜치 생성이나 개발을 시작하지 않는다.

## 인계와 재개

- 대화 요약에 작업 식별자, 기준·최종 점수, 기능별 합의·제외 범위·완료 기준, 미결정 사항과 승인된 처리안, 분할안·의존 관계·초안과 전체 실행/추가 분할/스택 관리의 승인 범위를 남긴다. 원문 전체나 별도의 인터뷰 기록 파일을 자동 생성하지 않는다.
- 등록할 이슈에는 구현에 필요한 합의와 완료 기준을 담는다. 작업 재개 시 대화·이슈·실제 변경을 대조하고, 승인 여부를 확인할 수 없으면 기존 초안과 실행 범위만 확인한다. 인터뷰를 처음부터 재시작하지 않는다.
- 개발 중 새 결정이 필요하면 해당 쟁점만 질문한다. 다른 기능을 추가하는 별도 작업이나 명시적인 재인터뷰 요청일 때만 새 인터뷰를 시작한다.
