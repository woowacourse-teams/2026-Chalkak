# 다음 이슈 착수 전 병합·완료 확인

첫 이슈 이후의 착수·재개, 현재 작업 이슈 종료와 메인 이슈 종료 때 읽는다. 사용자의 “다음 작업 시작”도 아래 조건을 생략하는 승인이 아니다.

1. 승인된 메인 이슈·서브 이슈 순서와 현재 위치를 확인한다. 바로 이전 이슈뿐 아니라 앞선 모든 이슈가 완료됐는지 실제 상태로 확인한다. 독립적인 이슈도 앞 작업을 건너뛰지 않는다.
2. 해당 저장소·작업 이슈·PR 번호·합의한 통합 브랜치를 확인하고 [조회 도구](../../../../scripts/workflow_gate.py)를 실행한다. 기록의 완료 표시·로컬 merge commit·PR의 단순 `closed`를 병합 증거로 쓰지 않는다.

```bash
python3 scripts/workflow_gate.py --repo OWNER/REPO --issue 123 --pr 124 --base be/develop
```

- `BLOCKED`(1): 미병합, 잘못된 대상·base·연결·종료 사유. 다음 개발을 시작하지 않고 원인을 알린다.
- `UNAVAILABLE`(3): 조회 실패·잘못된 응답. 이전 캐시나 추측으로 통과시키지 않는다.
- `MERGED_ISSUE_OPEN`(2): 병합 확인, 이슈 열림. 아직 다음 작업을 시작할 수 없다.
- `MERGED_ISSUE_CLOSED`(0): 병합·완료 사유 종료 확인. **종료 코드 0만으로 완료 조건까지 충족됐다고 판단하지 않는다.**

3. 최신 이슈의 각 완료 조건을 실제 병합 diff·검증 결과·필요한 CI와 대조해 조건별 근거를 확인한다. 체크박스·PR 작성자의 완료 주장만으로 통과시키지 않는다. 병합된 diff나 이에 대응하는 코드·필수 검증 근거를 확보하지 못하면 완료 판정을 보류한다. 로컬 파일을 근거로 삼을 때도 해당 파일이 병합된 변경과 대응하는지 확인한다. 조회 실패를 사용자에게 알리는 것만으로 다음 단계 진행을 정당화하지 않는다. 요구사항이 외부에서 바뀌었으면 승인된 범위와 대조한다. 근거 부족·실패·미충족이면 이미 닫힌 이슈라도 다음 작업을 막고 누락과 해결 방향을 알린다.
4. 모두 충족하고 이슈가 열려 있으면 승인된 전체 진행 또는 다음 작업 요청의 범위에서 **해당 이슈만** 완료 사유로 닫는다. GitHub CLI 사용 시 `gh issue close <번호> --repo <저장소> --reason completed`. 명령 성공 응답만 믿지 않고 위 조회 도구로 다시 확인한다. 종료 실패·재조회 실패·아직 열림이면 다음 작업을 시작하지 않는다.
5. PR 병합·실제 완료 조건·이슈 종료를 모두 확인했을 때만 바로 다음 이슈를 시작한다. 종료 직전에 본문·상태가 바뀌면 변경된 근거를 다시 대조한다. 최신 원격 통합 브랜치를 확인하고 현재 사용자 변경을 보존한다.
6. 메인 이슈는 실제 sub-issue 목록과 승인된 분할표를 대조해 누락·추가 이슈를 확인한다(페이지가 나뉘면 끝까지 조회). 모든 자식의 완료와 메인 요구사항별 결과를 확인한 뒤에만 닫고 닫힌 상태를 재조회한다. 취소된 요구사항을 임의로 완료 취급하지 않는다.

조회 도구는 GitHub.com의 상태·대상·연결을 읽기 전용으로 확인한다. 완료 조건의 의미나 사용자 승인을 증명하거나 Git 명령을 시스템 차원에서 금지하는 도구는 아니다. 지원하지 않는 환경은 동등한 실제 조회 근거가 확보될 때까지 보류한다. PR을 병합하거나 감시 프로그램을 자동 등록하지 않는다.
