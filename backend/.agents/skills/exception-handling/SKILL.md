# 예외 처리 컨벤션

## 기존 예외 구조 확인

예외를 추가하거나 변경하기 전에 현재 코드에서 다음 항목을 확인한다.

- 예외 기본 타입과 하위 예외 클래스
- 에러 코드 정의
- 예외 응답 DTO
- 전역 예외 처리기
- 예외 클래스와 HTTP status의 매핑 방식

하네스에 아래의 계획된 예외 계층 외의 특정 예외 클래스 목록을 기록하지 않는다. 현재 코드에 존재하는 예외 계층과 처리 구조를 기준으로 판단한다.

기존 구조를 재사용하고 별도의 예외 계층, 응답 DTO 또는 전역 처리기를 중복해서 만들지 않는다.

## 예외 클래스 선택

1. 현재 존재하는 예외 클래스와 상속 구조를 확인한다.
2. 기존 예외 클래스로 백엔드의 재시도 또는 후속 처리를 구분할 수 있는지 확인한다.
3. 기존 예외 클래스로 구분할 수 있다면 새로운 예외 클래스를 만들지 않는다.
4. 기존 예외 클래스로 백엔드 처리를 구분할 수 없을 때만 커스텀 예외 클래스를 추가한다.
5. 발생 원인, 도메인 또는 메시지만 다르고 백엔드 처리가 같다면 기존 예외 클래스를 재사용한다.
6. 새로운 예외 클래스는 현재 프로젝트의 예외 계층과 처리 방식을 따른다.

### 계획된 예외 계층

다음 네 가지는 팀이 미리 합의한 계층이다. 백엔드 처리가 아직 갈리지 않아도 클래스를 둔다.

| 예외 클래스 | HTTP status | 분리해 둔 이유 |
| --- | --- | --- |
| `BusinessException` | 400 | 기본값 |
| `UnauthorizedException` | 401 | 인증 실패 전용 로그 |
| `ForbiddenException` | 403 | 인증·인가 구현 시 추가 예정 |
| `NotFoundException` | 404 | 없는 자원 조회 모니터링·차단 |

이 계층을 근거로 클래스를 늘리지 않는다. 목록 밖의 예외 클래스는 아래 기준을 충족할 때만 추가한다.

### 백엔드 처리 차이로 인정하는 것

- 재시도 또는 보상 로직이 붙는 경우
- 별도 모니터링 지표나 차단 대상이 되는 경우
- 전용 로그 레벨이나 감사 기록이 필요한 경우

발생 위치, 도메인, 메시지만 다른 것은 백엔드 처리 차이가 아니다.

## 에러 코드 선택

1. 현재 정의된 에러 코드를 먼저 확인한다.
2. 기존 에러 코드로 클라이언트의 처리를 구분할 수 있는지 확인한다.
3. 클라이언트에서 재시도하거나 이후 연계 처리를 구분해야 할 때만 새로운 에러 코드를 추가한다.
4. 클라이언트의 처리가 같다면 기존 에러 코드를 재사용한다.
5. 메시지나 발생 원인만 다르다는 이유로 에러 코드를 추가하지 않는다.
6. 에러 코드는 클라이언트 분기용 식별자이며 예외 메시지를 보관하지 않는다.

## 예외 클래스와 에러 코드의 관계

- 백엔드 처리만 다르면 커스텀 예외 클래스만 추가하고 기존 에러 코드를 사용할 수 있다.
- 클라이언트 처리만 다르면 기존 예외 클래스와 새로운 에러 코드를 사용할 수 있다.
- 백엔드와 클라이언트 처리가 모두 다르면 커스텀 예외 클래스와 에러 코드를 모두 추가한다.
- 양쪽 처리 모두 같으면 기존 예외 클래스와 에러 코드를 재사용한다.
- **클라이언트 분기의 기준은 에러 코드다.** HTTP status는 보조 신호로만 쓴다. 응답에 둘 다 있으므로 어느 쪽으로 분기할지 미리 정해 두지 않으면 클라이언트 구현이 갈린다.
- 클라이언트가 화면 이동처럼 다른 동작을 해야 할 때만 에러 코드를 나눈다. 단순 안내 팝업으로 끝나면 기본 에러 코드에 메시지만 담아 보낸다.

## HTTP status

- 현재 프로젝트의 예외 클래스와 HTTP status 매핑 방식을 확인하고 재사용한다.
- HTTP status는 기존 예외 처리 구조가 담당하도록 한다.
- 기존 매핑으로 표현할 수 있다면 새로운 status 매핑을 추가하지 않는다.
- 새로운 예외 클래스를 추가하더라도 HTTP 처리가 같다면 기존 매핑을 재사용한다.
- **사용하는 status는 계획된 예외 계층의 400, 401, 403, 404가 전부다.** 그 밖의 status를 새로 도입하지 않는다.
- 목록으로 표현할 수 없는 상황은 **400으로 흡수**하고 구분이 필요하면 에러 코드로 한다. 422, 409 등을 새로 만들지 않는다.
- API 명세가 목록 밖의 status를 요구하더라도 이 기준을 우선한다. 이때 명세도 함께 정정하고 `api-versioning` 컨벤션을 적용한다.

## 예외 메시지

- 메시지는 예외가 발생하는 지점에서 문자열로 작성한다.
- 예외에 전달된 메시지는 공통 처리기가 응답까지 그대로 전달한다.
- 에러 코드에 고정 메시지를 추가하지 않는다.
- 공통 처리기에서 도메인별 메시지를 새로 만들거나 다른 문구로 변경하지 않는다.

## 예외 응답

기존 응답 형식을 유지한다.

```json
{
  "errorCode": "ERROR_CODE",
  "message": "예외 메시지"
}
```

- 현재 프로젝트의 예외 응답 DTO와 공통 응답 생성 방식을 재사용한다.
- 개별 예외마다 별도의 응답 DTO나 `@ExceptionHandler`를 만들지 않는다.
- 기존 공통 처리 경로로 표현할 수 없는 경우에만 예외 처리 구조 변경을 검토한다.

## 기존 코드 보호

- 컨벤션 적용을 이유로 기존 예외 계층이나 응답 구조를 일괄 변경하지 않는다.
- 관련 없는 기존 예외 클래스, 에러 코드 또는 처리기를 함께 수정하지 않는다.
- 기존 에러 코드의 이름이나 의미를 임의로 변경하지 않는다.
- 에러 코드, HTTP status 또는 응답 구조를 변경하면 외부 API 계약 변경 여부를 확인하고 `api-versioning` 컨벤션도 적용한다.
- 새로운 분기가 필요한지 불분명하면 예외 클래스나 에러 코드를 추가하기 전에 사용자에게 확인한다.

## 완료 전 확인

- 현재 예외 계층과 에러 코드 목록을 코드에서 확인했는지 점검한다.
- 기존 예외 클래스와 에러 코드를 먼저 재사용했는지 점검한다.
- 백엔드 처리를 기존 클래스로 구분할 수 없을 때만 예외 클래스를 추가했는지 점검한다.
- 계획된 예외 계층(400·401·403·404) 밖의 status를 새로 만들지 않았는지 점검한다.
- 클라이언트의 재시도나 후속 처리가 다를 때만 에러 코드를 추가했는지 점검한다.
- 현재 프로젝트의 HTTP status 매핑 방식을 재사용했는지 점검한다.
- 발생 지점의 메시지가 예외 응답까지 그대로 전달되는지 점검한다.
- 기존 공통 처리 구조를 불필요하게 중복하지 않았는지 확인한다.
