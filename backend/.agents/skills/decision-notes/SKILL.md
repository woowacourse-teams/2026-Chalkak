# 선택에 이른 고민 기록

팀원이 구현 결과뿐 아니라 선택에 이른 고민을 공유하고 나중에도 깊은 대화를 이어갈 수 있게 한다. 매번 선택 이유를 설명하거나 PR 본문에 모두 담는 부담을 줄이고, 받아들인 기술 부채를 다시 검토할 근거를 남긴다. 문서 작성 자체를 부채 해결이나 협업 개선의 검증된 성과로 표현하지 않는다.

## 기록할 때와 멈출 때

- 중요한 대안·상충 관계를 비교했거나, 새 정책 경계·실패 위험을 발견했거나, 방향을 바꾸었거나, 의도적으로 한계를 받아들인 논의를 기록한다. 사용자가 특정 고민의 기록을 요청한 경우도 포함한다.
- 단순 설명·일상적인 코드 수정·반복 질문은 기록하지 않는다. 모든 작업에 문서를 의무적으로 만들거나 분량을 채울 대화를 만들어내지 않는다.
- 대화 중에는 기록 후보와 근거만 유지한다. **인터뷰 결과 승인 또는 설계 방향 합의 후** 해당 주제를 자동 저장한다. 이미 승인된 작업 중 중요한 결정이 합의되거나 실제 구현·검증 결과가 달라지면 같은 문서를 갱신한다. 같은 내용의 저장 승인을 반복해서 묻지 않는다.
- `초안만`, `채팅만`, `저장하지 마`가 우선한다. PR 초안만 요청받으면 기존 기록을 필요한 만큼 읽어 연결하며 새 문서를 만들지 않는다.
- 진행 중인 수동 인터뷰에서는 개별 답변·부분 합의를 저장 시점으로 삼지 않고 전체 결과 승인①까지 기다린다. 사용자가 기록 저장만 별도로 요청하면 그 범위에서 현재 상태를 남기고 미정인 결정을 확정하지 않는다.
- 수동 인터뷰를 사용자 요청으로 중단하면 즉시 종료한다. 미완성 기록은 사용자가 저장을 요청한 경우에만 `논의 중`으로 남긴다. 종료를 합의로 해석하지 않는다.
- 이 스킬은 심화 인터뷰를 자동 호출하지 않는다. 기록 저장은 이슈 등록·개발 착수·커밋·푸시·PR 등록 승인이 아니다. 현재 요청과 작업 범위 안에서만 파일을 수정한다.

## 저장 위치와 읽기 범위

- backend 기준 [docs/interviews](../../../docs/interviews/README.md)에 주제별 Markdown 하나를 둔다. 인터뷰뿐 아니라 기획·개발 중 깊어진 논의도 포함한다.
- 파일명은 `사진-처리의-동기와-비동기-선택.md`처럼 한국어 주제를 드러낸다. 한글·영문·숫자를 단일 하이픈으로 연결하며 날짜·이슈 번호를 접두사로 강제하지 않는다. 물음표·공백·경로 구분자는 제목에만 쓰고 파일명에서는 제외한다.
- 목차에서 관련 주제를 찾아 필요한 문서만 읽는다. 새 세션마다 전체 기록을 읽거나 과거 대화 전체를 다시 조사하지 않는다. 대화 근거가 없으면 임의로 복원하지 않는다.
- 같은 고민은 기존 문서를 갱신한다. 중요한 이전 선택과 변경 이유는 보존하고 매 대화를 이어 붙이지 않는다. 독립된 고민일 때만 분리하며 길다는 이유만으로 나누지 않는다. 사용자 편집을 보존하고 관련 없는 부분을 재작성하지 않는다.
- 문서 맨 앞 YAML frontmatter에 `status: 논의 중`, `status: 방향 합의`, `status: 구현·검증 완료` 중 하나를 쓴다. 목차에는 제목 링크·한 줄 소개·같은 상태를 기록하고 생성·상태 변경·이름 변경 때 함께 갱신한다.
- 본문 상단에 제목, 갱신 날짜와 확인된 관련 이슈·PR 링크를 둔다. 없는 번호·PR·날짜를 만들어 채우지 않는다.

## 읽을 수 있는 이야기로 쓰기

- 대화 전문이나 문답 목록을 옮기지 않는다. **문제의 출발점 → 깊어진 질문과 새로 드러난 제약 → 비교한 선택과 판단 기준 → 선택 이유 → 확인한 결과와 남은 한계**가 자연스럽게 이어지도록 쓴다. 실제 논의에 없던 단계는 생략한다.
- 제목과 소제목은 해당 고민을 설명하는 문장으로 정한다. 고정 소제목·질문 개수·단계 수를 채우지 않는다. 짧은 문단을 기본으로 하고 비교에 도움이 될 때만 표를 쓴다.
- 보통 1,500~3,000자를 출발점으로 삼되 길이 제한으로 적용하지 않는다. 단순한 고민은 더 짧아도 되며 복잡한 고민은 길어도 된다. 반복 설명과 중계를 먼저 줄이고, 선택을 이해하는 데 필요한 근거·예외·한계는 남긴다. 긴 코드·로그는 근거 링크로 연결한다.
- 사용자의 실제 고민·확인된 코드·테스트를 근거로 쓴다. AI 제안과 사용자 합의, 계획과 구현, 기대 효과와 관찰 결과를 구분한다. 하지 않은 질문·실험·측정·팀 합의·인용문을 꾸미지 않으며 가상 예시는 예시로 표시한다.
- `방향 합의`는 구현 완료가 아니다. 기록의 주제에 필요한 구현과 검증을 확인한 경우에만 `구현·검증 완료`로 바꾼다. 남은 불확실성·검증하지 않은 범위와 다시 검토할 조건을 명시한다. 변경으로 기존 검증이 더 이상 유효하지 않으면 상태도 되돌린다.
- 비밀 값·개인 정보·불필요한 계정 및 요금 정보는 기록하지 않는다. 민감한 로그를 근거로 연결할 때도 공개 가능한 자료인지 확인한다.

## 기존 문서와 연결

- 이 문서는 선택의 맥락을 설명한다. 현재 서비스 정책은 공통 [business-rules](../../../../.agents/skills/business-rules/SKILL.md)의 현재 규칙 문서가 기준이다. 정책이 바뀌면 해당 흐름으로 합의·코드·테스트와 규칙·정책 결정 기록을 대조하고 서로 연결한다. 제안을 현재 정책으로 반영하거나 정책 전문을 중복 복사하지 않는다.
- PR 작성 전 관련 기록을 실제 diff·검증 결과와 대조한다. [issue-pr-workflow](../issue-pr-workflow/SKILL.md)의 `Technical Concerns`에는 중요한 고민을 **문제 → 해결과 선택 이유 → 결과·검증·남은 한계**로 짧게 설명하고 기록을 연결한다. 계획만 합의했다면 그 상태를 명시한다. PR에 전체 기록을 복사하거나 가짜 트러블슈팅을 만들지 않는다.
- 도구 전환·작업 재개용 [작업 기록](../development-workflow/references/work-state.md)은 현재 상태를 관리하며 이 공유 문서와 목적이 다르다. 현재 작업에 필요한 고민 문서 링크만 연결하고 대화 전문을 양쪽에 저장하지 않는다.
- 작성 후 근거와 합의, 구현·검증 상태, 링크와 목차를 대조한다. 기존 [구조 검사기](../../../scripts/check_harness.py)는 파일명·상태·목차·로컬 링크만 기계적으로 확인한다. 문장의 충분한 근거와 읽기 흐름은 직접 검토한다.
