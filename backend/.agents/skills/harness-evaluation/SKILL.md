# 하네스 동작 평가

## 하네스를 변경할 때

- 바뀌는 행동과 [기존 사례](../../../scripts/harness_eval/cases)를 대조한다. 오탈자·표현 정리에는 사례를 늘리지 않고, 기존 사례로 확인할 수 있으면 재사용한다.
- 새 행동·예외를 확인할 사례가 부족하면 **추가 이유와 확인할 행동을 하네스 변경 계획에 함께 제안**한다. 사용자 승인 후 하네스와 사례를 함께 반영하며 같은 승인을 다시 묻지 않는다.
- 사례에는 자연스러운 요청, 최소 작업 자료, 관찰할 행동을 둔다. 기대 답변·스킬 이름·판정 기준을 평가받는 AI에 미리 알려주지 않는다. 문구 일치보다 실제 도구 사용·결과물·변경 범위를 확인한다.
- 구조 검사는 기존 검사기로 수행한다. 사례를 추가했다는 이유만으로 실제 AI 평가를 실행하지 않는다.

## 동작 검사를 요청받았을 때

1. [실행 안내](../../../scripts/harness_eval/README.md)를 읽고 요청과 관련된 사례·도구를 선택한다. 최초 전체 확인은 3개 사례를 각각 Codex·Claude의 새 세션에서 평가한다. 이후에는 관련 사례만 선택한다.
2. 실행 전에 선택한 사례, 도구와 최대 세션 수를 짧게 알린다. 이미 요청한 검사 범위는 다시 승인받지 않는다. 자동 재시도나 다른 모델로의 교체는 하지 않는다.
3. 원본 저장소와 분리한 임시 작업 자료로 실행한다. 네이티브 도구의 격리가 확인되지 않거나 인증·환경 제약이 있으면 해당 실행을 **검사 불가**로 남긴다. 권한을 풀거나 실제 GitHub 등록으로 대신하지 않는다.
4. 원본 도구 기록·답변·전후 diff를 판정 기준과 대조한다. 기계 검사만 통과한 결과는 **판정 대기**다. 막힌 등록·푸시 등의 시도도 실패이며, 확인할 기록이 부족하면 판정 불가다.
5. 사례별 근거를 기록하고 통과·실패·판정 불가·미실행을 구분해 보고한다. 한 번의 통과를 모든 모델·대화형 환경·전체 하네스의 정확성으로 확대하지 않는다. 수정 효과를 비교하려면 같은 사례·모델·설정으로 이전 하네스와 비교한다.

CI나 일반 개발에 자동 연결하지 않는다. 결과는 Git에서 제외된 `build/harness-eval/`에 보관하며, 실패를 이유로 관련 없는 하네스나 서비스 컨벤션을 변경하지 않는다.
