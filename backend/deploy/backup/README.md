# DB 별도 백업

`db-backup.sh`는 PostgreSQL 18의 단일 DB를 custom 형식으로 내보내고 rclone으로
별도 저장소에 전송한다. RDS 자동 백업과 시점 복구를 대체하지 않는다.
실제 사진 파일은 포함하지 않으며 이미지 백업은 #843의 범위다.

## 현재 범위

- #842: 수동 백업 생성·전송·검증, 보관본의 격리 PostgreSQL 복원과 합성 데이터 시험.
- #844: 실제 팀 S3 권한, 운영 보관본 복구 검증, 매일 자정(Asia/Seoul) 예약 실행 적용.
- DB 파일은 최소 7일 보존 목표다. 현재 자동 삭제는 없으므로 실제로는 더 오래 쌓인다.
- 아직 이 문서와 스크립트만으로 자동 백업이나 운영 복구가 검증된 것은 아니다.

## 실행 환경과 설치 범위

| 환경 | 설치·실행 범위 | 실행 주기 |
| --- | --- | --- |
| 운영 EC2 | `db-backup.sh`와 백업 도구·설정. 이미지 도구는 #843에서 구성 | #844에서 매일 자정(Asia/Seoul) 예약 |
| 팀 계정의 임시 검증 EC2 | `db-restore.sh`, rclone, Docker, `sha256sum`과 보관본 조회 전용 설정 | 최초 실제 보관본 검증 및 매월 1회 수동 실행 |

운영 EC2에는 복구 검증용 Docker를 설치하거나 복구 스크립트를 예약 작업에 연결하지 않는다.
스크립트는 Git 저장소에서 함께 관리하되, 서버에는 역할에 필요한 파일만 설치한다.
현재 CodeDeploy 배포 묶음에는 `deploy/backup/`이 포함되지 않는다. 서버별 설치와 설정은 #844에서 준비한다.

검증 EC2는 검증할 때만 생성한다. 생성 전에 담당자의 삭제 권한과 비용을 확인하고,
운영 DB 자격 증명·운영 저장소 쓰기 권한 없이 필요한 보관본만 조회하도록 구성한다.
검증 서버 자신의 Docker를 사용하며 원격 Docker 연결로 운영 서버를 대상으로 하지 않는다.
검증 결과를 보관한 뒤 컨테이너·다운로드 파일을 정리하고 검증 EC2와 연결 저장소의 정리 여부를 확인한다.
아직 검증 EC2를 생성했거나 해당 환경에서 검증한 것은 아니다.

## 백업 실행 준비

Linux에 Bash, PostgreSQL 18의 `pg_dump`·`pg_restore`, rclone, `sha256sum`, `cmp`, GNU coreutils의 `timeout`이 필요하다.
DB에 직접 연결해 스키마·테이블·시퀀스를 내보낼 권한이 있어야 한다.
TLS 인증서 검증을 위해 RDS CA 번들을 준비한다. 스크립트는 `verify-full`을 강제한다.

`backup.env.example`을 Git 밖의 보호된 위치에 복사해 실제 설정을 채운다.
백업 설정 파일은 `source`로 읽으므로 실행 사용자가 신뢰하는 파일만 사용한다.
설정, pgpass, rclone.conf는 실행 사용자만 읽도록 소유권과 mode 600을 지정한다.
인증서도 해당 사용자가 읽을 수 있어야 한다. 앱 설정이나 CD 필수 키는 변경하지 않는다.

pgpass 형식은 `호스트:포트:DB:사용자:비밀번호`다. 특수 문자는 libpq 규칙대로 이스케이프한다.
PGPASSWORD나 명령 인자로 비밀번호를 전달하지 않는다. 소스·대상 주소를 로그에 남기지 않는다.
백업 전용 rclone remote는 팀 S3를 가리키게 하고 생성·조회 권한만 부여한다.
삭제·설정 변경 권한은 주지 않는다. 업로드와 전체 내용 검증이 가능해야 한다.

## 수동 실행

```bash
bash deploy/backup/db-backup.sh /etc/chalkak-backup/backup.env
```

날짜는 UTC로 기록하며 예약 실행의 한국 시간 기준과 구분한다.
설정 예제를 그대로 쓰면 실제 DB·S3로 연결하지 못한다.
이 스크립트는 백엔드 CodeDeploy나 앱 시작 과정에 연결하지 않는다.

```text
팀 버킷/chalkak/db/
└── chalkak-db-실행UTC시각-고유문자열/
    ├── database.dump
    ├── database.dump.sha256
    └── COMPLETE
```

`pg_dump` 성공 → 비어 있지 않은 파일·목차 확인 → SHA-256 생성 → 파일·체크섬 전송
→ `rclone check --download`로 원격 내용 비교 → COMPLETE 업로드·재조회 순서다.
서로 다른 실행은 고유 경로를 사용하고 `--immutable`로 기존 내용 교체를 제한한다.
목차 조회는 실제 DB 복원 검증을 대신하지 않는다.

완료 표시는 파일 전송·내용 검증이 끝난 회차에만 작성한다. 복원 가능한 회차를 고를 때
COMPLETE, 체크섬 파일, 백업 파일을 함께 확인한다. 완료 표식 자체는 위변조 방지 서명이 아니다.
네트워크 오류가 나면 표식 업로드가 성공했는데 응답만 실패할 수도 있어 원격 결과 확인이 필요하다.

실패하면 0이 아닌 종료 코드와 `FAILED stage=... run=...`를 남긴다.
단계는 configuration, dump, archive-list, checksum, upload-dump, upload-checksum,
verify, completion이다. 외부 명령의 원문 진단은 민감 정보 노출을 막기 위해 출력하지 않는다.
실패 시 부분 업로드가 남을 수 있지만 원격 파일은 자동 삭제하지 않는다.
재실행하면 새 회차를 만든다. 성공·실패·정상 종료 신호에서 이번 로컬 임시 경로만 정리한다.
강제 종료(SIGKILL)·호스트 장애에서는 임시 파일이 남을 수 있어 접근 권한과 디스크를 확인한다.

## 제한과 시험

### 보관본 수동 복구·검증

아래 명령은 운영 EC2가 아닌 팀 계정의 임시 검증 EC2에서 실행한다.
Bash, rclone, Docker, `sha256sum`, `mktemp`와 `postgres:18.4` 이미지가 필요하다.
이미지를 미리 준비하거나 Docker가 받을 수 있어야 한다. DB 컨테이너 자체의 외부 네트워크는 차단한다.
실행 로그에서 정확한 회차ID를 선택한다.
최신 파일을 임의로 선택하지 않으며, 신뢰하는 팀 백업 파일만 사용한다.

검증 서버에는 운영 백업 설정 전체를 복사하지 않는다. 아래 세 항목만 담은 보호된
`/etc/chalkak-restore/restore.env`와 백업 조회·다운로드 전용 `rclone.conf`를 준비한다.
PGHOST·PGUSER·PGPASSFILE과 운영 DB 비밀번호는 필요하지 않다.
두 설정 파일은 실행 사용자 소유, mode 600으로 보호한다.

```bash
RCLONE_CONFIG=/etc/chalkak-restore/rclone.conf
DB_BACKUP_DESTINATION=backup:REPLACE_WITH_BACKUP_BUCKET/chalkak/db
DB_BACKUP_TEMP_ROOT=/tmp
```

```bash
bash deploy/backup/db-restore.sh /etc/chalkak-restore/restore.env <회차ID>
```

이 도구는 COMPLETE·SHA-256·파일 크기를 검사한 뒤, 외부 네트워크·공개 포트·호스트 볼륨이
없는 새 PostgreSQL 컨테이너에만 복원한다. 기존 컨테이너나 운영 DB 주소를 입력받지 않는다.
컨테이너 내부 전용 trust 인증을 사용하며, 외부에서 DB에 접속할 수 있게 노출하지 않는다.
데이터는 컨테이너의 메모리 파일시스템에 저장하므로 DB 크기에 맞는 Docker 메모리가 필요하다.
테이블·데이터·인덱스·제약조건·시퀀스 복원을 시도하고 SQL 오류 시 실패한다.
테이블별 행 수를 읽기 전용으로 출력하지만 원본과의 값 일치까지 자동 보장하지는 않는다.

출력의 `total_seconds`는 다운로드·검증·컨테이너 준비·복원·행 수 조회를 포함하고,
`restore_seconds`는 pg_restore 실행 구간이다. 둘 다 초 단위이며 이미지 최초 다운로드에 따라
총 시간이 달라진다. 전체 서비스의 RTO나 실제 RDS 생성·전환 시간과 구분한다.
기본 실행은 종료 시 이번 컨테이너와 로컬 임시 파일을 정리한다. 원격 보관본은 삭제하지 않는다.

추가 SQL 검증이 필요하면 `--keep-container`를 붙인다. 성공한 경우에만 컨테이너가 남는다.

```bash
bash deploy/backup/db-restore.sh /etc/chalkak-restore/restore.env <회차ID> --keep-container
docker exec -it <출력된컨테이너ID> psql -X -U restore -d restored
# 사용자·게시글·사진 관계와 삭제·탈퇴 상태 등을 읽기 전용으로 확인한 뒤 정리한다.
docker rm --force <출력된컨테이너ID>
```

매월 1회 같은 절차를 수동으로 수행하고 백업 회차·검증 결과·소요 시간을 기록한다.
검증 반복 실행의 자동화나 검증 서버 자동 생성은 초기 범위에 포함하지 않는다.

위 명령은 임시 DB 복구 검증용이다. 운영 연결 전환이나 운영 RDS 복원은 수행하지 않는다.
종료 신호에서는 정리를 시도하지만 강제 종료·Docker 접속 오류에서는 자원이 남을 수 있다.
`chalkak.backup.restore=true` 라벨은 이번 도구가 만든 검증 컨테이너를 식별하는 용도다.

### 시험 실행

파일 내용 검증을 위해 원격 파일을 다시 읽으므로 추가 읽기·전송과 실행 시간이 발생한다.
덤프와 다운로드 비교는 운영 DB의 읽기·EC2 자원을 사용한다. 크기·부하·시간은 실측한다.
DB 변경에 대한 일관성은 pg_dump가 제공하지만 S3 이미지와 같은 시점의 원자적 백업은 아니다.
역할·권한·테이블스페이스와 RDS·네트워크 설정은 별도 재현이 필요하다.
`--no-owner --no-privileges`를 사용하며 원래 소유권·접근 정책까지 복원한다고 간주하지 않는다.
기본 연결 제한은 10초, 테이블 잠금 대기는 10초다. 덤프 프로세스 전체는 `timeout`으로
5분으로 제한하고, 종료 요청 후 10초 안에 끝나지 않으면 강제 종료한다. SQL별 실행 제한이 아니다.
`pg_dump`는 접속 시 `statement_timeout`을 해제하므로 해당 설정으로 덤프 시간을 제한하지 않는다.
시간 초과도 dump 단계 실패로 처리하며 업로드·완료 기록 없이 이번 임시 파일을 정리한다.
시간 제한은 CPU·I/O 사용량 자체를 제한하지 않으므로 운영 부하는 별도로 확인한다.

```bash
bash deploy/backup/tests/db-backup-test.sh
bash deploy/backup/tests/db-restore-test.sh
```

`db-backup-test.sh`는 DB 명령 대역과 실제 rclone으로 실패 처리를 확인한다.
`db-restore-test.sh`는 합성 데이터를 넣은 실제 PostgreSQL 18 컨테이너에서 TLS로 덤프하고,
실제 rclone 로컬 저장소에 보관한 뒤 새 컨테이너에 복원한다. 원본·복구 데이터의 값,
외래키·인덱스·시퀀스와 손상 파일·완료 표식 누락·잘못된 회차 거부를 확인한다.
두 시험 모두 운영 DB나 AWS에는 접속하지 않는다. 시험 종료 시 자신이 만든 자원만 정리한다.

2026-10-28 로컬 시험의 한 실행에서 합성 데이터 8,157바이트 보관본을 다운로드·검증하고
새 PostgreSQL 18.4 컨테이너에 복원·행 수 조회까지 약 2초가 걸렸다. pg_restore 구간은
초 단위 측정에서 0초로 기록됐으며 실제로 시간이 들지 않았다는 뜻은 아니다.
사용자 2건·게시글 2건·사진 1건과 한글·공백 이름 테이블 1건의 값을 비교하고,
외래키 위반 거부·인덱스 존재·다음 시퀀스 값도 확인했다. 이 작은 합성 보관본의 결과를
운영 23MB DB 복원 시간이나 서비스 RTO 달성 근거로 사용하지 않는다.
