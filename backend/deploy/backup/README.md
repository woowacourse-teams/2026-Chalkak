# DB·이미지 별도 백업

`db-backup.sh`는 PostgreSQL 18의 단일 DB를 custom 형식으로 내보내고 rclone으로
별도 저장소에 전송한다. RDS 자동 백업과 시점 복구를 대체하지 않는다.
DB 덤프에는 실제 사진 파일이 포함되지 않는다. `image-backup.sh`가 사진을 별도로 복사한다.

## 현재 범위

- #842: 수동 DB 백업 생성·전송·검증, 보관본의 격리 PostgreSQL 복원과 합성 데이터 시험.
- #843: 게시글·사인 이미지 백업·내용 검증과 별도 로컬 위치의 수동 복구·검증.
- #844: 실제 팀 S3 권한, 운영 보관본 복구 검증, 매일 자정(Asia/Seoul) 예약 실행 적용.
- DB 파일은 최소 7일 보존 목표다. 현재 자동 삭제는 없으므로 실제로는 더 오래 쌓인다.
- 아직 이 문서와 스크립트만으로 자동 백업이나 운영 복구가 검증된 것은 아니다.

## 실행 환경과 설치 범위

| 환경 | 설치·실행 범위 | 실행 주기 |
| --- | --- | --- |
| 운영 EC2 | `db-backup.sh`·`image-backup.sh`와 백업 도구·공통 설정 | #844에서 매일 자정(Asia/Seoul) 예약 |
| 팀 계정의 임시 검증 EC2 | `db-restore.sh`·`image-restore.sh`, rclone, Docker(DB 검증용), `sha256sum`과 보관본 조회 전용 설정 | 최초 실제 보관본 검증 및 매월 1회 수동 실행 |

운영 EC2에는 복구 검증용 Docker를 설치하거나 복구 스크립트를 예약 작업에 연결하지 않는다.
스크립트는 Git 저장소에서 함께 관리하되, 서버에는 역할에 필요한 파일만 설치한다.
현재 CodeDeploy 배포 묶음에는 `deploy/backup/`이 포함되지 않는다. 서버별 설치와 설정은 #844에서 준비한다.

검증 EC2는 검증할 때만 생성한다. 생성 전에 담당자의 삭제 권한과 비용을 확인하고,
운영 DB 자격 증명·운영 저장소 쓰기 권한 없이 필요한 보관본만 조회하도록 구성한다.
검증 서버 자신의 Docker를 사용하며 원격 Docker 연결로 운영 서버를 대상으로 하지 않는다.
검증 결과를 보관한 뒤 컨테이너·다운로드 파일을 정리하고 검증 EC2와 연결 저장소의 정리 여부를 확인한다.
아직 검증 EC2를 생성했거나 해당 환경에서 검증한 것은 아니다.

## 백업 실행 준비

Linux에 Bash, PostgreSQL 18의 `pg_dump`·`pg_restore`, rclone, `sha256sum`, `cmp`, GNU coreutils의 `timeout`이 필요하다.
DB에 직접 연결해 스키마·테이블·시퀀스를 내보낼 권한이 있어야 한다.
TLS 인증서 검증을 위해 RDS CA 번들을 준비한다. 스크립트는 `verify-full`을 강제한다.

`backup.env.example`을 Git 밖의 보호된 위치에 복사해 실제 설정을 채운다.
백업 설정 파일은 `source`로 읽으므로 실행 사용자가 신뢰하는 파일만 사용한다.
설정, pgpass, rclone.conf는 실행 사용자만 읽도록 소유권과 mode 600을 지정한다.
인증서도 해당 사용자가 읽을 수 있어야 한다. 앱 설정이나 CD 필수 키는 변경하지 않는다.

pgpass 형식은 `호스트:포트:DB:사용자:비밀번호`다. 특수 문자는 libpq 규칙대로 이스케이프한다.
PGPASSWORD나 명령 인자로 비밀번호를 전달하지 않는다. 소스·대상 주소를 로그에 남기지 않는다.
백업 전용 rclone remote는 팀 S3를 가리키게 하고 생성·조회 권한만 부여한다.
삭제·설정 변경 권한은 주지 않는다. 업로드와 전체 내용 검증이 가능해야 한다.

## 수동 실행

```bash
bash deploy/backup/db-backup.sh /etc/chalkak-backup/backup.env
```

날짜는 UTC로 기록하며 예약 실행의 한국 시간 기준과 구분한다.
설정 예제를 그대로 쓰면 실제 DB·S3로 연결하지 못한다.
이 스크립트는 백엔드 CodeDeploy나 앱 시작 과정에 연결하지 않는다.

```text
팀 버킷/chalkak/db/
└── chalkak-db-실행UTC시각-고유문자열/
    ├── database.dump
    ├── database.dump.sha256
    └── COMPLETE
```

`pg_dump` 성공 → 비어 있지 않은 파일·목차 확인 → SHA-256 생성 → 파일·체크섬 전송
→ `rclone check --download`로 원격 내용 비교 → COMPLETE 업로드·재조회 순서다.
서로 다른 실행은 고유 경로를 사용하고 `--immutable`로 기존 내용 교체를 제한한다.
목차 조회는 실제 DB 복원 검증을 대신하지 않는다.

완료 표시는 파일 전송·내용 검증이 끝난 회차에만 작성한다. 복원 가능한 회차를 고를 때
COMPLETE, 체크섬 파일, 백업 파일을 함께 확인한다. 완료 표식 자체는 위변조 방지 서명이 아니다.
네트워크 오류가 나면 표식 업로드가 성공했는데 응답만 실패할 수도 있어 원격 결과 확인이 필요하다.

실패하면 0이 아닌 종료 코드와 `FAILED stage=... run=...`를 남긴다.
단계는 configuration, dump, archive-list, checksum, upload-dump, upload-checksum,
verify, completion이다. 외부 명령의 원문 진단은 민감 정보 노출을 막기 위해 출력하지 않는다.
실패 시 부분 업로드가 남을 수 있지만 원격 파일은 자동 삭제하지 않는다.
재실행하면 새 회차를 만든다. 성공·실패·정상 종료 신호에서 이번 로컬 임시 경로만 정리한다.
강제 종료(SIGKILL)·호스트 장애에서는 임시 파일이 남을 수 있어 접근 권한과 디스크를 확인한다.

## 제한과 시험

### 보관본 수동 복구·검증

아래 명령은 운영 EC2가 아닌 팀 계정의 임시 검증 EC2에서 실행한다.
Bash, rclone, Docker, `sha256sum`, `mktemp`와 `postgres:18.4` 이미지가 필요하다.
이미지를 미리 준비하거나 Docker가 받을 수 있어야 한다. DB 컨테이너 자체의 외부 네트워크는 차단한다.
실행 로그에서 정확한 회차ID를 선택한다.
최신 파일을 임의로 선택하지 않으며, 신뢰하는 팀 백업 파일만 사용한다.

검증 서버에는 운영 백업 설정 전체를 복사하지 않는다. 아래 세 항목만 담은 보호된
`/etc/chalkak-restore/restore.env`와 백업 조회·다운로드 전용 `rclone.conf`를 준비한다.
PGHOST·PGUSER·PGPASSFILE과 운영 DB 비밀번호는 필요하지 않다.
두 설정 파일은 실행 사용자 소유, mode 600으로 보호한다.

```bash
RCLONE_CONFIG=/etc/chalkak-restore/rclone.conf
DB_BACKUP_DESTINATION=backup:REPLACE_WITH_BACKUP_BUCKET/chalkak/db
DB_BACKUP_TEMP_ROOT=/tmp
```

```bash
bash deploy/backup/db-restore.sh /etc/chalkak-restore/restore.env <회차ID>
```

이 도구는 COMPLETE·SHA-256·파일 크기를 검사한 뒤, 외부 네트워크·공개 포트·호스트 볼륨이
없는 새 PostgreSQL 컨테이너에만 복원한다. 기존 컨테이너나 운영 DB 주소를 입력받지 않는다.
컨테이너 내부 전용 trust 인증을 사용하며, 외부에서 DB에 접속할 수 있게 노출하지 않는다.
데이터는 컨테이너의 메모리 파일시스템에 저장하므로 DB 크기에 맞는 Docker 메모리가 필요하다.
테이블·데이터·인덱스·제약조건·시퀀스 복원을 시도하고 SQL 오류 시 실패한다.
테이블별 행 수를 읽기 전용으로 출력하지만 원본과의 값 일치까지 자동 보장하지는 않는다.

출력의 `total_seconds`는 다운로드·검증·컨테이너 준비·복원·행 수 조회를 포함하고,
`restore_seconds`는 pg_restore 실행 구간이다. 둘 다 초 단위이며 이미지 최초 다운로드에 따라
총 시간이 달라진다. 전체 서비스의 RTO나 실제 RDS 생성·전환 시간과 구분한다.
기본 실행은 종료 시 이번 컨테이너와 로컬 임시 파일을 정리한다. 원격 보관본은 삭제하지 않는다.

추가 SQL 검증이 필요하면 `--keep-container`를 붙인다. 성공한 경우에만 컨테이너가 남는다.

```bash
bash deploy/backup/db-restore.sh /etc/chalkak-restore/restore.env <회차ID> --keep-container
docker exec -it <출력된컨테이너ID> psql -X -U restore -d restored
# 사용자·게시글·사진 관계와 삭제·탈퇴 상태 등을 읽기 전용으로 확인한 뒤 정리한다.
docker rm --force <출력된컨테이너ID>
```

매월 1회 같은 절차를 수동으로 수행하고 백업 회차·검증 결과·소요 시간을 기록한다.
검증 반복 실행의 자동화나 검증 서버 자동 생성은 초기 범위에 포함하지 않는다.

위 명령은 임시 DB 복구 검증용이다. 운영 연결 전환이나 운영 RDS 복원은 수행하지 않는다.
종료 신호에서는 정리를 시도하지만 강제 종료·Docker 접속 오류에서는 자원이 남을 수 있다.
`chalkak.backup.restore=true` 라벨은 이번 도구가 만든 검증 컨테이너를 식별하는 용도다.

### 시험 실행

파일 내용 검증을 위해 원격 파일을 다시 읽으므로 추가 읽기·전송과 실행 시간이 발생한다.
덤프와 다운로드 비교는 운영 DB의 읽기·EC2 자원을 사용한다. 크기·부하·시간은 실측한다.
DB 변경에 대한 일관성은 pg_dump가 제공하지만 S3 이미지와 같은 시점의 원자적 백업은 아니다.
역할·권한·테이블스페이스와 RDS·네트워크 설정은 별도 재현이 필요하다.
`--no-owner --no-privileges`를 사용하며 원래 소유권·접근 정책까지 복원한다고 간주하지 않는다.
기본 연결 제한은 10초, 테이블 잠금 대기는 10초다. 덤프 프로세스 전체는 `timeout`으로
5분으로 제한하고, 종료 요청 후 10초 안에 끝나지 않으면 강제 종료한다. SQL별 실행 제한이 아니다.
`pg_dump`는 접속 시 `statement_timeout`을 해제하므로 해당 설정으로 덤프 시간을 제한하지 않는다.
시간 초과도 dump 단계 실패로 처리하며 업로드·완료 기록 없이 이번 임시 파일을 정리한다.
시간 제한은 CPU·I/O 사용량 자체를 제한하지 않으므로 운영 부하는 별도로 확인한다.

```bash
bash deploy/backup/tests/db-backup-test.sh
bash deploy/backup/tests/db-restore-test.sh
```

`db-backup-test.sh`는 DB 명령 대역과 실제 rclone으로 실패 처리를 확인한다.
`db-restore-test.sh`는 합성 데이터를 넣은 실제 PostgreSQL 18 컨테이너에서 TLS로 덤프하고,
실제 rclone 로컬 저장소에 보관한 뒤 새 컨테이너에 복원한다. 원본·복구 데이터의 값,
외래키·인덱스·시퀀스와 손상 파일·완료 표식 누락·잘못된 회차 거부를 확인한다.
두 시험 모두 운영 DB나 AWS에는 접속하지 않는다. 시험 종료 시 자신이 만든 자원만 정리한다.

2026-10-28 로컬 시험의 한 실행에서 합성 데이터 8,157바이트 보관본을 다운로드·검증하고
새 PostgreSQL 18.4 컨테이너에 복원·행 수 조회까지 약 2초가 걸렸다. pg_restore 구간은
초 단위 측정에서 0초로 기록됐으며 실제로 시간이 들지 않았다는 뜻은 아니다.
사용자 2건·게시글 2건·사진 1건과 한글·공백 이름 테이블 1건의 값을 비교하고,
외래키 위반 거부·인덱스 존재·다음 시퀀스 값도 확인했다. 이 작은 합성 보관본의 결과를
운영 23MB DB 복원 시간이나 서비스 RTO 달성 근거로 사용하지 않는다.

## 이미지 백업

`image-backup.sh`는 운영 버킷의 다음 네 경로에 현재 존재하는 이미지 파일을 조회한다.

- `chalkak/posts/prod/original/`
- `chalkak/posts/prod/thumbnail/`
- `chalkak/signatures/prod/original/`
- `chalkak/signatures/prod/thumbnail/`

게시글은 WebP, 사인은 PNG로 저장되며, 백업 도구는 확장자·한글·공백·하위 경로를 제한하지 않는다.
목록은 `rclone lsjson`과 `jq`로 먼저 검사한 뒤 줄 단위 key 목록으로 변환한다. 줄바꿈을 포함한
제어 문자, 역슬래시, 선행·후행 `/`, 빈 경로 구간(`//`), `.`·`..` 구간은 inventory 단계에서
실패로 처리한다. 목록 해석이나 로컬 복구에서 경로가 바뀌는 것을 막기 위한 제한이다.
rclone이 제어 문자·슬래시 등을 표시할 때 쓰는 치환·인용 문자(`␀`~`␟`, `␡`, `／`, `‛`)와
`.`·`..`의 치환 구간(`．`, `．．`)도 보수적으로 거부한다. 이 문자들이 실제 파일 이름에
포함된 경우도 현재 도구는 지원하지 않으며, 조용히 누락하지 않고 해당 회차를 실패로 기록한다.
임시 업로드·개발 이미지·다른 팀 경로와 운영 버킷의 과거 버전은 조회·백업하지 않는다.
최종 경로에 아직 생성되지 않은 처리 중 이미지는 이번 대상 목록에 없으며 다음 실행에서 조회한다.
조회 후 추가된 파일도 다음 실행에서 확인한다. DB와 이미지 전체의 같은 시점 스냅샷은 아니다.

### 설정과 실행

이미지 설정은 기존 `backup.env.example`에 함께 둔다. DB·이미지 스크립트는 각각 필요한
설정만 검사하므로 이미지 작업만 실행할 때 DB 접속 정보는 필요하지 않다.
보호된 `rclone.conf`에 운영 읽기용 `production` remote와 팀 백업용 `backup` remote를
서로 다른 자격 증명으로 준비한다. 원본은 버킷까지만, 대상은 `/images`로 끝나는 경로를 지정한다.
같은 remote 이름·버킷이 양쪽에 지정되면 거부하지만, 서로 다른 remote가 실제 같은 버킷을
가리키는 경우까지 판별하지는 않는다. 실제 계정·권한 분리는 #844에서 확인한다.

```bash
bash deploy/backup/image-backup.sh /etc/chalkak-backup/backup.env
```

Bash, rclone, `jq`, `sort`, `cmp`, `mktemp`가 필요하다. `rclone check --download`는 파일 내용을
메모리에 전부 쌓지 않고 읽어 비교하므로 이미지 전체를 임시 다운로드할 디스크는 필요하지 않다.
목록과 진단 파일만 이번 실행의 보호된 임시 경로에 만들고 종료 시 정리한다.
전송·검사를 각각 하나씩 수행하고 버퍼는 8MiB로 제한하지만, 이것이 프로세스 전체 메모리
상한은 아니다. 운영 적용 전 메모리 실측과 배포 중복 방지·자원 제한 확인은 #844에서 한다.

```text
팀 버킷/chalkak/images/
├── files/
│   └── chalkak/
│       ├── posts/prod/{original,thumbnail}/<식별자>.webp
│       └── signatures/prod/{original,thumbnail}/<식별자>.png
└── runs/chalkak-images-실행UTC시각-고유문자열/
    ├── inventory.txt  # 이번 실행에서 조회한 원래 S3 key 목록
    ├── verified.txt   # 내용을 확인한 S3 key 목록
    └── COMPLETE       # 모든 대상과 기록 검증이 끝난 뒤 생성
```

### 전송·검증과 실패 처리

대상 조회 → 대상 목록 보관 → 신규·변경 파일 복사 → 내용 비교 → 검증 목록 보관·검증
→ 완료 표식 업로드·재조회 순서다. `copy`를 사용하므로 운영에서 삭제된 이미지가 백업에서
삭제되지 않는다. 변경된 파일은 같은 백업 key로 전송하고, 변경 전 사본 보존은 대상 S3의
버저닝에 의존한다. 버저닝·이전 버전 조회 권한은 실제 사용 전 #844에서 확인해야 한다.
현재 로컬 시험만으로 과거 S3 버전 복구가 검증된 것은 아니다.

복사는 신규·변경 파일만 전송하지만 내용 비교는 매 회차 조회한 전체 파일에 수행한다.
변경 없는 파일도 운영·백업 양쪽에서 읽으므로 데이터가 늘면 시간·네트워크·조회량도 증가한다.
초기에는 전체 내용 비교를 유지한다. #844의 예약 적용 전에 실제 소요 시간·전송량·최대 메모리를
측정하고, 수동·예약 실행이 겹치지 않도록 같은 잠금에 연결한다. 전체 실행 시간 상한은 최초
전체 백업과 일별 백업을 실측한 뒤 설정하며, 현재의 `--timeout 60s`는 전체 작업 제한이 아니다.
부하가 확인되면 공통 해시를 이용한 비교와 전체 내용 비교 주기를 검토한다.

공통 해시가 없어 같은 크기 변경을 첫 복사에서 건너뛰더라도, 다운로드 내용 비교로 차이를
확인하고 해당 파일만 한 번 다시 전송·검증한다. 파일 조회·읽기 오류나 대상 누락은 성공으로
처리하지 않는다. 처음 조회한 모든 파일이 내용 비교 결과에 포함돼야 하므로, 조회 이후 파일이
삭제되어 검사에서 빠진 경우도 미완료로 남긴다. 이후 재실행은 새 목록·회차를 만든다.

실패 시 `FAILED stage=... run=...`와 0이 아닌 종료 코드를 남긴다. 단계는 configuration,
inventory, inventory-upload, copy, verify, repair, record, completion이다. 외부 도구의 원문 오류는
접속·인증 정보 노출을 막기 위해 공개 로그에 출력하지 않는다. 원격의 부분 복사·대상 목록은
삭제하지 않는다. 일부 복사 실패는 다른 파일까지 모두 완료된 것으로 기록하지 않는다.
완료 표식 업로드 뒤 응답·재조회 실패 시 표식 자체가 남을 수 있어 원격 상태도 확인한다.

실행별 목록은 대상과 검증 결과 기록이며, 각 파일의 S3 VersionId를 고정한 복구 지점은 아니다.
같은 백업 경로의 최신 파일은 다음 실행에서 바뀔 수 있다. 특정 회차 전체를 자동으로 정확히
재현하는 기능은 포함하지 않으며, 복구 시 필요한 보관 버전을 별도로 선택해야 한다.
이미지 삭제·변경 이력은 최소 30일 보존 목표지만 초기에는 자동 삭제하지 않으므로 더 쌓인다.

```bash
bash deploy/backup/tests/image-backup-test.sh
```

시험은 실제 rclone과 로컬 저장소로 게시글 WebP·사인 PNG 네 대상 경로, 신규·같은 크기 변경, 원본 삭제 유지,
해시 부재 상황의 재전송, 다음 회차 포함, 일부 실패·변조·재실행·완료 표식 실패를 확인한다.
한글·공백·다른 확장자·하위 경로의 보존과 실제 줄바꿈 파일 이름의 거부를 확인한다.
로컬 파일시스템이 정규화하는 위험한 S3 key는 조회 응답에 주입해 검사한다.
실패와 해시 부재 상황은 명령 대역으로 주입하며 실제 AWS 네트워크·권한·버저닝 시험은 아니다.
DB·이미지 공통 실행 `backup.sh`와 systemd 예약은 #844에서 구성한다. 둘의 결과를 구분하고
DB 실패에도 이미지 작업을 시도하며, 하나라도 실패하면 통합 실행은 실패하도록 연결한다.

## 이미지 수동 복구·검증

`image-restore.sh`는 신뢰하는 팀 백업 회차의 완료 표식·대상 목록·검증 목록을 확인한 뒤
선택한 파일만 새 로컬 폴더에 내려받는다. 운영 S3를 복구 대상으로 입력받지 않는다.
Docker나 운영 DB 접속은 필요하지 않으며 운영 EC2가 아닌 별도 검증 환경에서 실행한다.
복구에도 `jq`가 필요하며, 선택 목록은 백업과 같은 경로 안전성 기준으로 검사한다.
복구 파일 전체를 저장할 디스크 여유가 있어야 한다.

### 복구 준비와 최신 보관본 선택

검증 서버에는 아래 두 설정과 보관본 읽기·이전 버전 조회 전용 `rclone.conf`만 준비한다.
기존 DB 복구용 `restore.env`에 함께 두어도 된다. 운영 DB 비밀번호와 운영 S3 쓰기 권한은
가져오지 않는다. 설정과 목록 파일은 신뢰하는 위치에 두고 소유권·권한을 보호한다.

```bash
RCLONE_CONFIG=/etc/chalkak-restore/rclone.conf
IMAGE_BACKUP_DESTINATION=backup:REPLACE_WITH_BACKUP_BUCKET/chalkak/images
```

백업 실행 로그에서 완료된 실제 회차ID를 선택한다. 해당 회차의 `verified.txt`에서 필요한
원래 S3 key를 한 줄에 하나씩 골라 로컬 목록 파일로 저장한다. 파일 이름만 적지 않는다.
전체 검증이 목적이면 해당 회차의 `verified.txt` 전체를 목록으로 사용한다.
DB의 사진·사인 S3 key를 기준으로 선택할 수도 있으나, 해당 회차에 없는 key는 이 도구가 거부한다.
그 경우 다른 완료 회차·운영 버저닝·그 밖의 사본에서 찾고, 어디에도 없으면 누락으로 기록한다.

```bash
umask 077
printf '%s\n' 'chalkak/posts/prod/original/REPLACE_WITH_IMAGE_ID.webp' > /tmp/chalkak-image-keys.txt
RUN_ID='REPLACE_WITH_COMPLETED_RUN_ID'
bash deploy/backup/image-restore.sh /etc/chalkak-restore/restore.env "$RUN_ID" \
  /tmp/chalkak-image-keys.txt /tmp/chalkak-image-check-001
```

복구 위치는 아직 존재하지 않는 절대 경로여야 한다. 기존 폴더·심볼릭 링크·원격 저장소 경로는
거부한다. 폴더를 새로 만들고 원래 key 구조를 유지하며, 복사 후 내용을 다시 비교한다.
선택한 모든 key가 검사에서 확인돼야 성공한다. 성공한 폴더에는 `RESTORED` 기록이 남는다.
이 기록은 전송 결과이며 이미지가 실제로 열리는지와 사용자·게시글 연결까지 자동 보장하지 않는다.
복구 이미지 열기·원본/썸네일 대응·복구 DB와의 key 연결을 사람이 별도로 확인한다.

### 변경 전 이미지 선택

회차ID는 당시 대상 목록을 확인하기 위한 정보이며, 그 회차의 이미지 내용을 자동으로 고정하지
않는다. 옵션 없이 실행하면 선택한 파일의 **현재 최신 백업본**을 복구한다. 과거 회차를 넣어도
그 이후 같은 key가 바뀌었다면 현재 내용을 받으므로, 이전 내용이 필요할 때는 보관 시점을 지정한다.

팀 S3의 객체 버전 화면이나 rclone의 아래 조회로 변경 전 버전의 보관 시각을 확인한다.
파일 목록의 시각은 **백업 저장소에 전송된 시각**이다. 사진 촬영·운영 파일 변경 시각이나
RDS 복구 시각을 그대로 넣어 동일한 내용이 나온다고 가정하지 않는다.

```bash
rclone lsf 'backup:REPLACE_WITH_BACKUP_BUCKET/chalkak/images/files/chalkak/posts/prod/original' \
  --config /etc/chalkak-restore/rclone.conf --s3-versions
# 아래 시각은 예시다. 원하는 백업 버전이 존재했던 실제 UTC 시각으로 바꾼다.
bash deploy/backup/image-restore.sh /etc/chalkak-restore/restore.env "$RUN_ID" \
  /tmp/chalkak-image-keys.txt /tmp/chalkak-image-check-old-001 --version-at 2026-10-28T15:00:00Z
```

`--version-at`은 rclone의 `--s3-version-at`으로 전달하며, 이미지 복사와 내용 비교 모두 같은
백업 시각을 조회한다. 회차 기록 자체는 현재 보관된 내용을 읽는다. 날짜·시각·UTC를 모두
명시해야 하며, 지정 시점에 선택한 파일이 없거나 필요한 버전이 삭제됐다면 실패한다.
여러 사진이 서로 다른 보관 시점을 필요로 하면 목록·실행을 나눈다. 이 기능은 운영 DB와 이미지
전체가 특정 순간에 함께 일치하는 상태를 자동 구성하지 않는다.

S3 버저닝과 이전 버전 조회 권한, 실제 이전 내용 선택·복구는 #844에서 AWS로 확인한다.
관련 rclone 동작은 [S3 버전 조회](https://rclone.org/s3/#versions)와
[시점 조회 옵션](https://rclone.org/s3/#s3-version-at)을 따른다.

### 원래 운영 S3 key로 반영

검증한 파일을 운영에 반영할 때는 별도 승인된 운영 복구 권한을 가진 환경에서 작업한다.
검증 서버에 운영 쓰기 권한을 추가하거나 백업 조회용 자격 증명으로 운영 업로드를 시도하지 않는다.
복구 DB에서 사진·사용자 관계와 삭제·탈퇴 상태를 확인하고, 로컬 파일이 선택한 원래 key와
일치하는지 검사한다. 복구를 이유로 정당하게 삭제된 사진을 임의로 다시 공개하지 않는다.

아래는 한 파일을 원래 key에 복사하는 예시이며 이 스크립트가 자동 실행하는 명령이 아니다.
`production` remote는 운영 복구용 환경의 설정이다. 대상 버킷과 key, 파일 내용을 먼저 확인한다.

```bash
KEY='chalkak/posts/prod/original/REPLACE_WITH_IMAGE_ID.webp'
rclone copyto "/tmp/chalkak-image-check-001/$KEY" "production:REPLACE_WITH_SOURCE_BUCKET/$KEY" \
  --config /보호된/운영복구용/rclone.conf --immutable --dry-run
# 검토 후 --dry-run만 제거해 실행한다. --immutable은 유지한다.
```

같은 key에 다른 내용의 운영 파일이 있으면 `--immutable`로 교체를 거부한다. 덮어쓰기가 필요한
사고라면 현재 운영 객체의 버전·내용과 선택한 복구본을 비교하고, 운영 버저닝 상태·현재 버전의
보존 여부를 기록한 뒤 사람이 교체 여부를 결정한다. 결정 전 플래그를 제거해 재시도하지 않는다.
반영 후 운영 파일 내용과 DB key 연결, 앱·CloudFront 경유 표시까지 확인한다.

### 실패·정리와 시험

실패하면 `FAILED stage=... run=...`와 0이 아닌 종료 코드로 끝나며 `RESTORED`를 쓰지 않는다.
단계는 configuration, record, selection, download, verify다. 외부 명령의 원문 오류를 공개
로그에 출력하지 않는다. 내부 임시 파일은 정리하지만 이미 내려받은 복구 폴더는 남을 수 있다.
부분 다운로드를 성공으로 사용하지 말고 원인을 확인한 뒤 새로운 폴더로 재실행한다.
검증이 끝나면 필요한 결과를 보관하고 해당 복구 폴더만 사람이 정리한다. 원격 백업은 삭제하지 않는다.

```bash
bash deploy/backup/tests/image-restore-test.sh
```

시험은 실제 이미지 백업 도구로 로컬 보관본을 만든 뒤 실제 rclone으로 선택·전체 복구와
내용 비교를 한다. 누락·변조·불완전 회차·잘못된 목록·기존 경로 거부도 확인한다.
과거 시점 옵션은 합성 과거 저장소로 연결해 전달·선택·비교 흐름만 시험한다.
실제 AWS의 버전 API·계정 간 권한·복구 시간 검증 결과로 표현하지 않는다.
