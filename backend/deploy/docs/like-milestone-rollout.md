# 좋아요 알림 2차 활성화 배포

관련 작업: [1차 PR #914](https://github.com/woowacourse-teams/2026-Chalkak/pull/914), [운영 릴리스 PR #941](https://github.com/woowacourse-teams/2026-Chalkak/pull/941), [2차 이슈 #935](https://github.com/woowacourse-teams/2026-Chalkak/issues/935)

**현재 코드는 2차 활성화용이다. 이 버전을 배포하면 다음 새 단계부터 알림이 생성된다.** 추가 SQL 실행이나 환경변수 ON 전환은 필요하지 않다. 2차의 실제 서버 배포·기기 수신은 아직 확인하지 않았다.

## 1차에서 완료한 준비

새 타입을 모르는 서버와 새 알림이 동시에 존재하지 않도록 1차에서는 알림 생성만 차단했다. 좋아요·개수·최고 단계는 계속 갱신했고, 기존 서버 종료 후 과거 게시물의 최고 단계를 한 번 초기화했다.

아래는 사용자가 제공한 배포·초기화 성공 로그 기준이다. 초기화는 Notification이나 SQS 메시지를 생성하지 않았다.

| 환경 | 1차 배포 ID | 초기화 결과 |
| --- | --- | --- |
| 개발 | `d-AEOT0KBQL` | `initialized_rows = 0`, COMMIT·완료 |
| 운영 | `d-UKAMO0CQL` | `initialized_rows = 1663`, COMMIT·완료 |

예를 들어 좋아요 17개인 게시물은 최고 단계 15부터 시작하며 이후 20개에서 새 알림을 만든다. 이미 높은 최고 단계는 낮추지 않는다. 초기화 이후에는 1차 앱이 신규 좋아요의 최고 단계를 계속 갱신했다.

## 이번 배포에서 달라지는 것

| 항목 | 1차 호환 버전 | 2차 활성 버전 |
| --- | --- | --- |
| 신규 좋아요의 새 단계 | 최고 단계만 갱신 | 최고 단계와 Notification을 함께 저장 |
| 서버용 생성 스위치 | `NOTIFICATION_LIKE_MILESTONE_ENABLED=false` 필수 | 코드·설정·CD 검사에서 제거 |
| 회원 `likePushEnabled` | 설정 저장 가능 | ON이면 푸시 발행 대기, OFF이면 알림함만 생성 |
| 기존 데이터 초기화 | 구버전 종료 후 한 번 실행 | 재실행하지 않음 |
| 초기화 도구 | 배포 파일에 포함 | 저장소·신규 배포 파일에서 제거 |

서버 `/etc/chalkak/application.env`에 예전 키가 `false`로 남아 있어도 새 앱과 CD 검사는 사용하지 않는다. **이번 배포를 위해 서버 설정을 수동 수정하거나 컨테이너를 따로 재시작할 필요가 없다.** 공통 Relay·Worker 설정은 그대로 사용한다.

이미 적용한 Flyway 파일·이력·최고 단계는 변경하지 않는다. 새 초기화 마이그레이션도 추가하지 않는다. 1차와 2차가 배포 중 공존해도 양쪽 API·Worker 모두 `POST_LIKE_MILESTONE`을 처리할 수 있다. 다만 1차가 처리한 좋아요의 단계는 준비 기간으로 취급하며 나중에 소급 생성하지 않는다.

## 배포 순서

현재 개발·운영의 1차 준비가 모두 끝났으므로 **개발 2차 → 검증 → 운영 2차** 순서로 진행한다.

1. 앱이 `POST_LIKE_MILESTONE`, `likePushEnabled`, 게시물 이동·읽음을 처리할 수 있는지 확인한다. 개발·운영의 1차 기준값 초기화 완료 기록을 대조한다.
2. 2차 변경을 `be/develop`에 병합하고 [공통 배포 절차](operations.md)로 개발에 배포한다. 배포가 활성화 시점이며 별도 ON 명령은 없다.
3. 아래 기능·로그 확인을 마친다. 문제가 있으면 운영 배포를 진행하지 않는다.
4. 확인한 소스를 운영 릴리스 PR로 `main`에 반영하고 운영 파이프라인을 실행한다. 운영 배포 후 같은 항목을 확인한다.
5. 환경별 소스 SHA·배포 ID·확인 결과를 기록한다. 1차 초기화 도구는 다시 실행하지 않는다.

### 배포 후 확인

- 새 단계에서 작성자 알림함에 한 건만 생기고 최고 단계가 갱신된다. 이미 초기화한 과거 단계는 생성하지 않는다.
- 회원 푸시 ON은 `PENDING`에서 공통 Relay·SQS·Worker를 거쳐 발송된다. OFF는 `NOT_REQUIRED`로 알림함에만 남는다.
- 같은 단계 재도달·중복 좋아요·알림 보관 만료 후에도 동일 단계를 다시 만들지 않는다.
- 실제 기기에서 수신·게시물 이동·읽음을 확인한다. 읽음 선처리·게시물 삭제·설정 OFF·다중 기기도 기존 발송 정책을 따른다.
- 기존 승인·반려·주제 등 알림과 알림함이 정상인지, 공통 오류 알람·DLQ·생략 사유에 이상이 없는지 확인한다.

## 초기화 파일 정리

`initialize_like_milestones.sh`, `.sql`, `_test.sh`는 2차 배포 소스에 포함하지 않는다. 기존 AppSpec이 `deploy/scripts`를 `/opt/chalkak/bin/`에 설치하므로, 같은 deployment group의 다음 배포에서는 CodeDeploy가 이전 설치 목록의 파일을 제거하고 새 파일을 설치한다. 이번 기능만을 위한 삭제 코드를 공통 훅에 추가하지 않는다. [AWS 파일 정리 설명](https://docs.aws.amazon.com/codedeploy/latest/userguide/deployments-rollback-and-redeploy.html)

이 동작은 기존 CodeDeploy 설치 목록을 사용하는 경우를 전제로 한다. 수동으로 복사한 파일이나 다른 deployment group의 파일까지 정리하는 기능은 아니다. 실제 서버의 파일 정리는 2차 배포 후 확인 대상이며, 자동 테스트로 AWS 에이전트 동작까지 검증한 것은 아니다.

## 롤백

- 활성화 후에는 **새 타입을 처리할 수 있는 1차 호환 revision까지만** 롤백한다. 이전 enum이 없는 버전으로 돌아가면 알림함 조회·Worker 처리가 실패할 수 있다.
- 1차 revision의 설정 검사는 예전 키의 명시적 `false`를 요구한다. 서버에 남겨둔 키를 사용할 수 있으며, 별도로 제거했다면 롤백 전에 복구해야 한다.
- 1차로 돌아가면 새 알림 생성은 멈추지만 이미 생성한 알림 조회·Worker 처리는 유지된다. DB 마이그레이션이나 최고 단계를 되돌리지 않으며 초기화도 다시 실행하지 않는다.
- 이미 SQS·FCM이 수락한 작업을 회수하는 방식은 아니다. [공통 롤백 절차](operations.md#롤백)를 함께 따른다.
