# 좋아요 알림 1차 호환 배포와 2차 활성화

관련 작업: [이슈 #864](https://github.com/woowacourse-teams/2026-Chalkak/issues/864), [PR #914](https://github.com/woowacourse-teams/2026-Chalkak/pull/914)

현재 코드는 **1차 배포용**이다. 실제 서버 배포와 기기 수신은 아직 확인하지 않았다. 2차의 조건문·설정 제거는 1차 개발·운영 배포 완료 후 별도 커밋으로 진행한다.

## 두 번 배포하는 이유

기존 앱은 `POST_LIKE_MILESTONE`을 모른다. 배포 안정화 중 두 버전이 같은 DB·SQS를 사용하므로, 새 알림이 생기면 기존 앱의 알림함 조회가 실패하거나 기존 Worker가 해석하지 못한 메시지를 삭제할 수 있다.

| 버전 | 새 알림 조회·처리 | 신규 좋아요 알림 생성 |
| --- | --- | --- |
| 기존 버전 | 불가 | 없음 |
| 1차 호환 버전 | 가능 | 임시 스위치 OFF로 차단 |
| 2차 활성 버전 — 후속 작업 | 가능 | 조건문·설정 제거 후 생성 |

1차의 `NOTIFICATION_LIKE_MILESTONE_ENABLED=false`는 **알림함 저장 자체**를 막는다. 좋아요·개수·최고 단계는 계속 갱신한다. 회원 설정 `likePushEnabled`와 다른 서버용 스위치이며, 공통 Relay·Worker와 다른 알림은 끄지 않는다. 기본값은 false이고, 배포 설정 검사는 이 1차 버전에서 false만 허용한다.

## 환경별 진행 순서

권장 순서는 `개발 1차 → 운영 1차 → 개발 2차 → 운영 2차`다. 각 환경의 DB·컨테이너·배포 결과를 별도로 확인한다. 1차의 Git SHA와 CodeDeploy 성공 revision을 기록하고, 운영에 최신 브랜치를 무조건 배포해 1차를 건너뛰지 않는다.

개발에서 2차까지 먼저 확인하는 것도 가능하지만, 그 경우 운영에 배포할 1차 revision을 별도로 지정해야 한다. 어떤 순서든 **각 환경에서 기존 버전 종료·기준값 보정이 끝나기 전에 2차를 배포하지 않는다.**

## 1차 배포 — 개발에서 확인한 뒤 운영에서 반복

### 1. 서버 설정과 revision 준비

- 대상 서버의 `/etc/chalkak/application.env`에 `NOTIFICATION_LIKE_MILESTONE_ENABLED=false`를 추가한다. 비밀 값은 출력하거나 문서에 옮기지 않는다.
- 공통 Relay·Worker 등 기존 설정은 유지한다. 회원별 푸시 설정으로 이번 배포 스위치를 대체하지 않는다.
- 이 임시 스위치가 포함된 1차 revision을 CodeDeploy로 배포한다. 환경변수는 컨테이너 생성 시 읽으므로 `docker restart`만 해서는 변경되지 않는다.

### 2. 배포 완료와 기존 프로세스 종료 확인

[공통 배포 절차](operations.md)에 따라 트래픽 전환과 약 10분 안정화를 마친다. 배포 스크립트는 이전 앱 종료 실패를 경고로 남기고 성공 처리할 수 있으므로, 성공 표시만으로 종료를 판단하지 않는다.

```bash
sudo docker ps --filter name=chalkak-backend- --format 'table {{.Names}}\t{{.Status}}\t{{.Label "chalkak.release"}}'
sudo systemctl is-active chalkak-backend.service
```

실행 중 컨테이너의 release 라벨을 이번 배포 ID와 대조한다. 레거시 systemd 앱·이전 컨테이너·다른 실행 인스턴스가 기존 코드를 실행하고 있지 않아야 한다. 남아 있으면 운영 절차로 종료한 뒤 다음 단계로 진행한다. 상태 출력의 `inactive`는 정상적으로 비활성 상태를 뜻할 수 있다.

### 3. 최고 단계 보정 — 1차의 마지막 단계

대상 환경의 PostgreSQL에 연결한 것을 확인하고 실행한다. 이 작업은 배포 스크립트가 자동 실행하지 않는다. SQL 오류 시 중단하는 세션에서 실행하고, 실패 시 롤백한 뒤 원인을 확인한다.

```sql
BEGIN;
SET LOCAL lock_timeout = '5s';

UPDATE post_like_counts
SET last_milestone_count = like_count / 5 * 5
WHERE last_milestone_count < like_count / 5 * 5;

COMMIT;
```

Flyway 초기화 후에도 기존 앱이 좋아요를 처리할 수 있으므로, **기존 버전이 모두 종료된 뒤** 마지막으로 맞춘다. 최고 단계를 올리는 경우만 처리하며 알림·SQS 메시지는 만들지 않는다. 재실행해도 이미 높은 단계는 낮추지 않는다. 완료 후에는 1차 앱이 신규 좋아요의 최고 단계를 계속 갱신한다.

### 4. 1차 완료 확인

- 신규 좋아요의 응답·개수가 정상이며, 5개 단계를 넘으면 최고 단계가 갱신된다.
- `notifications`에 `POST_LIKE_MILESTONE`이 생성되지 않는다. 예기치 않은 행이나 메시지가 있으면 활성화를 멈추고 출처를 확인한다.
- 기존 승인·반려·주제 등 알림과 알림함 조회가 정상이다.
- 알 수 없는 타입 오류·`INVALID_MESSAGE_DELETED` 증가 여부를 기존 알림 로그에서 확인한다.
- 기존 버전 종료, 보정 결과, 배포 SHA·revision을 해당 환경의 배포 기록에 남긴다. Worker의 새 타입 처리 검증은 자동 테스트에서 확인하며, 기존 앱이 살아 있는 실서버에 새 타입 시험 데이터를 넣지 않는다.

## 2차 활성화 — 아직 구현하지 않음

개발·운영의 1차 완료 후 별도 작업으로 다음을 진행한다.

1. 서비스의 임시 조건문·필드·주입 인자, YAML 설정과 테스트 프로파일 설정을 제거한다. 최고 단계 조건부 UPDATE와 알림 저장은 유지한다.
2. `.env`·예제·서버 환경변수와 CD의 필수 키·false 제한 검사를 함께 정리한다. 변수만 지우면 기본값 false로 계속 꺼지므로 코드까지 제거한다.
3. 기능 활성 상태의 테스트와 환경변수 계약을 다시 검증한다. 1차가 끝나기 전에 제거 커밋을 운영에 반영하지 않는다.
4. 개발 2차에서 알림함·설정 OFF·푸시·읽음·게시물 삭제를 확인한 뒤 운영 2차를 배포한다. 과거 단계는 생성하지 않고 다음 새 단계부터 알린다.

2차 배포의 두 버전은 모두 새 알림을 처리할 수 있다. 안정화 중 1차 OFF 버전이 처리한 좋아요는 준비 기간으로 취급한다. 실제 SQS·FCM·기기와 앱의 새 타입 지원은 각 환경에서 확인한다.

## 롤백

- 1차에서 원래 구버전으로 돌아가기 전에는 새 타입의 DB 행·SQS 메시지가 없는지 확인한다. DB migration은 되돌아가지 않는다.
- 2차 활성화 후에는 **새 타입을 처리할 수 있는 1차 revision까지만** 롤백한다. 1차가 요구하는 서버 키를 false로 복구하고 그 revision을 재배포한다.
- 1차로 돌아가면 알림 생성은 멈추지만 기존 알림 조회·Worker 처리는 유지된다. 이미 발행·수락된 푸시를 회수하는 스위치는 아니다.
- 원래 구버전으로의 강제 롤백이나 알림 데이터 삭제는 이 절차에 포함하지 않는다. [공통 롤백 절차](operations.md#롤백)를 함께 따른다.
