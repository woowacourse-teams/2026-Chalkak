# 같은 회차를 다시 실행해도 같은 사건으로 식별한다

- 갱신일: 2026-10-26
- 관련 작업: [#827](https://github.com/woowacourse-teams/2026-Chalkak/issues/827), [#826](https://github.com/woowacourse-teams/2026-Chalkak/issues/826)

## 발송 기록 전에 사건의 기준을 고정한다

발송 결과를 `(eventId, userId)`로 저장하려면 재발행된 메시지도 같은 사건 ID를 가져야 한다. 그런데 주제·리마인더는 실행마다 랜덤 UUID를 만들었다. 서버가 재시작하면 같은 예정 회차를 다시 실행할 수 있고, 새 ID 때문에 과거 발송 기록과 연결할 수 없다. SQS 메시지 ID도 발행 요청마다 달라질 수 있어 사건의 기준으로 쓸 수 없다.

이 문제는 발송 이력과 분리해 먼저 고친다. 알림 종류·설정 ID·원래 예정 시각으로 이름 기반 UUID를 만들고, 실제 실행 시각과 회원은 제외한다. 입력 형식은 버전 접두사와 UTF-8로 고정한다. 형식을 바꾸면 같은 사건의 ID도 달라지므로 고정된 예시 ID를 회귀 테스트로 보호한다.

주제 ID만 쓰면 같은 주제를 여러 시각에 보내는 설정을 구분할 수 없다. 따라서 주제 푸시 설정 ID를 사용한다. 리마인더도 원본 ID와 회차 시각을 사용하므로 매일 반복의 다음 날은 새 사건이다. 문구·대상만 바뀌어도 같은 회차는 같은 사건으로 유지한다.

## 식별과 중복 차단을 구분한다

DB 실행 기록을 추가하거나 기존 메모리 회차 관리를 없애지 않는다. 재시작하면 여전히 같은 회차를 다시 발행할 수 있고 중간에 중단되면 일부 누락도 가능하다. 이번에는 그때의 사건 ID만 유지한다. 완료 기록 확인·동시 처리 제어·불명 결과의 재시도 판단은 후속 #826의 범위다. 동시 처리 제어는 이후 단일 JVM Java 락으로 결정했다.

배포 전에 큐에 들어간 랜덤 ID를 소급 변경하지 않는다. 기존 메시지와 새 규칙의 메시지가 같은 회차여도 같은 ID라는 보장은 없다. 앱도 ID가 같다는 이유로 자동으로 배너 중복을 제거하지 않는다. 현재 정책은 [NOTIFICATION-011·016](../../../docs/business-rules/rules/notification.md)을 따른다.

## 검증 상태

변경 전 PostgreSQL 통합 테스트에서 서비스 재생성 후 주제·일회성/매일 반복 리마인더의 ID만 달라짐을 재현했다. 구현 후 도메인 7건·주제 서비스 23건·리마인더 서비스 16건, 총 46건이 통과했다. 같은 ID·원래 기한 유지와 다른 종류·설정·회차 구분, 같은 프로세스의 재발행 제한을 확인했다. 아키텍처 12건과 포맷·컨벤션 검사도 통과했다. 개인 `.env`의 기존 필수 키 누락 때문에 해당 환경 계약 검사는 제외했고, 기존 로컬 테스트 DB의 과거 마이그레이션 충돌을 피하기 위해 이번 작업 전용 로컬 DB를 사용했다. 실제 서버 재시작·AWS 발행·기기 표시는 이번 로컬 테스트에서 확인하지 않는다.
