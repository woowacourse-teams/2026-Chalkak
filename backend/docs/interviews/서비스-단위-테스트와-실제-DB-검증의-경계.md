# 서비스 판단은 빠르게 확인하고 DB 경계는 실제로 검증한다

갱신: 2026-11-02 / [이슈 #893](https://github.com/woowacourse-teams/2026-Chalkak/issues/893)

기존 테스트 규칙은 모든 서비스 테스트에서 실제 Repository와 PostgreSQL을 사용하도록 했다. 서비스의 조건 판단을 확인할 때도 사용자, 주제와 사진 데이터를 DB에 준비해야 했다. 테스트가 많아지면서 무엇을 보호하는지 찾기 어렵고, 같은 조건이 여러 계층에 반복되는 문제가 논의의 출발점이었다.

서비스의 Repository를 Mock으로 바꾸면 DB 준비를 줄이고 원하는 성공과 실패를 직접 만들 수 있다. 그러나 저장 호출을 확인하는 것만으로는 쿼리, 매핑, dirty checking과 롤백을 보장할 수 없다. 테스트를 전부 Mock으로 바꾸면 기존에 보호하던 DB 연결 문제가 빠질 수 있다는 제약이 있다.

따라서 일반적인 서비스 판단은 실제 도메인 객체와 Repository Mock을 쓰는 단위 테스트로 확인하기로 했다. 쿼리와 DB 제약은 PostgreSQL 슬라이스, HTTP 계약은 웹 슬라이스, 핵심 요청부터 저장까지의 연결은 인수 테스트에 둔다. 인수 테스트는 MockMvc에서 실행할 수 있으므로 배포 서버를 호출하거나 별도 E2E 묶음을 필수로 만들지는 않는다.

동시성과 트랜잭션 테스트는 실제 Service, Repository와 DB를 유지한다. 커밋 후 알림, 롤백 시 미발송, 잠금과 중복 요청 처리는 Mock으로 대체할 수 없는 검증이다. 서비스 패키지에 있더라도 이 테스트들은 통합 테스트다. 클래스 이름이 아닌 실제 검증 목적을 보고 분류한다.

사용자는 가독성을 높이고 중복을 없애면서 클래스가 무작정 늘지 않게 하되 안정성을 떨어뜨리지 말라고 요청했다. 같은 대상과 목적은 기존 클래스에 모으고 입력만 다른 경우 파라미터화하기로 했다. 실제 DB나 보안 구성처럼 환경이 다르거나 책임을 구분해야 할 때는 클래스를 분리한다. 개수만 줄이려고 서로 다른 검증을 합치거나 삭제하지 않는다.

규칙 정비는 `3987d2b7`로 커밋했다. 이어 앱 버전 조회의 서비스 테스트를 Mock 단위 테스트로, 시각과 매핑 테스트를 PostgreSQL 슬라이스로 전환하고 있다. 이전 서비스 테스트의 DB 검증은 기존 Repository와 관리자 통합 테스트에 대응시켰으며, 경쟁 요청과 관리자 트랜잭션 검증은 실제 DB로 유지한다. 대응 관계는 [이관 계획](../testing/test-migration.md)에 남긴다. 나머지 기능의 전환과 전체 테스트 속도 개선은 아직 확인하지 않았으므로 방향 합의 상태를 유지한다.


앱 버전 네 파일은 사용자 확인 후 `3255fd78`로 커밋했다. 이후 조회 서비스와 Repository 정리는 미커밋 상태로 진행한다. 피드의 일반 판단을 단위로 옮기는 과정에서 실제 쿼리 수와 변경 후 재조회 검증은 DB가 필요하다는 구분이 드러나 별도 통합 클래스로 보존했다. 반대로 한 메서드짜리 주제 Repository 통합 클래스는 기존 슬라이스로 합칠 수 있었다. 클래스 수를 무조건 줄이거나 늘리기보다 실행 환경과 검증 목적에 맞춰 묶는 선택이며, 전체 이관은 아직 진행 중이다.

- 로그인 세션 판단과 알림 수신 설정도 Repository Mock 단위로 옮겼다. 세션 유효성의 SQL 조건과 수신 설정 필드 저장은 기존 PostgreSQL Repository 테스트에 남겼으며 설정 변경의 실제 잠금 경쟁도 유지한다. 기기 Repository 준비에 필요했던 로그인 발급 서비스는 실제 토큰 fixture 저장으로 교체했다.
