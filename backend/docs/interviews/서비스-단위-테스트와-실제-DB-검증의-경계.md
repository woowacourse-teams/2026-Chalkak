# 서비스 판단은 빠르게 확인하고 DB 경계는 실제로 검증한다

갱신: 2026-11-02 / [이슈 #893](https://github.com/woowacourse-teams/2026-Chalkak/issues/893)

기존 테스트 규칙은 모든 서비스 테스트에서 실제 Repository와 PostgreSQL을 사용하도록 했다. 서비스의 조건 판단을 확인할 때도 사용자, 주제와 사진 데이터를 DB에 준비해야 했다. 테스트가 많아지면서 무엇을 보호하는지 찾기 어렵고, 같은 조건이 여러 계층에 반복되는 문제가 논의의 출발점이었다.

서비스의 Repository를 Mock으로 바꾸면 DB 준비를 줄이고 원하는 성공과 실패를 직접 만들 수 있다. 그러나 저장 호출을 확인하는 것만으로는 쿼리, 매핑, dirty checking과 롤백을 보장할 수 없다. 테스트를 전부 Mock으로 바꾸면 기존에 보호하던 DB 연결 문제가 빠질 수 있다는 제약이 있다.

따라서 일반적인 서비스 판단은 실제 도메인 객체와 Repository Mock을 쓰는 단위 테스트로 확인하기로 했다. 쿼리와 DB 제약은 PostgreSQL 슬라이스, HTTP 계약은 웹 슬라이스, 핵심 요청부터 저장까지의 연결은 인수 테스트에 둔다. 인수 테스트는 MockMvc에서 실행할 수 있으므로 배포 서버를 호출하거나 별도 E2E 묶음을 필수로 만들지는 않는다.

동시성과 트랜잭션 테스트는 실제 Service, Repository와 DB를 유지한다. 커밋 후 알림, 롤백 시 미발송, 잠금과 중복 요청 처리는 Mock으로 대체할 수 없는 검증이다. 서비스 패키지에 있더라도 이 테스트들은 통합 테스트다. 클래스 이름이 아닌 실제 검증 목적을 보고 분류한다.

사용자는 가독성을 높이고 중복을 없애면서 클래스가 무작정 늘지 않게 하되 안정성을 떨어뜨리지 말라고 요청했다. 같은 대상과 목적은 기존 클래스에 모으고 입력만 다른 경우 파라미터화하기로 했다. 실제 DB나 보안 구성처럼 환경이 다르거나 책임을 구분해야 할 때는 클래스를 분리한다. 개수만 줄이려고 서로 다른 검증을 합치거나 삭제하지 않는다.

규칙 정비는 `3987d2b7`, 앱 버전 첫 이관은 `3255fd78`, 조회 서비스와 Repository 이관은 `aa5bc724`로 커밋했다. 이후 쓰기 서비스와 Worker, 전체 테스트 대조까지 같은 이슈로 정리했으며 사용자가 최종 변경의 커밋과 PR 등록을 승인했다. 검증을 옮긴 위치와 실제 DB를 유지한 이유는 [이관 기록](../testing/test-migration.md)에 남겼다.

후속 검토에서는 게시물 요청 거부와 업로드 발급, 사인 URL과 발급, 관리자 로그인 판단, Worker 메시지 검증을 단위 테스트로 모았다. 실제 도메인 객체와 BCrypt는 사용하고 Repository와 외부 발급은 대체했다. 업로드의 실제 저장과 만료, JWT 검증과 리프레시 토큰 해시 저장은 기존 DB 클래스에 보존했다.

Worker는 이름만 보고 Mock으로 바꾸기 어려웠다. 같은 사건의 중복 발송 방지, 수락 이력 복구, 커밋 실패와 재claim은 DB 상태에 의존했다. 이 검증은 유지하고, 잘못되거나 만료된 메시지를 DB 작업 전에 거르는 판단만 단위로 분리했다. 다섯 Worker 클래스에 반복된 세션 INSERT는 동일한 준비 값을 쓰는 fixture 하나로 모았다.

피드의 쿼리 수와 저장 후 재조회, 회원 변경과 발송 이력은 실제 DB 검증을 따로 읽도록 분리했다. 한 메서드였던 주제 제약 테스트는 기존 Repository 클래스에 합쳤다. 해당 단계의 클래스 파일 수는 344개였다. 개수를 줄이는 대신 같은 목적을 모으고, 실행 환경이 다른 경우에만 분리하는 기준을 적용한 결과다.

최종 전체 회귀와 DB 없는 단위 실행, 형식 및 문서 구조 검사를 확인했다. 동시성과 트랜잭션은 실제 PostgreSQL로 실행했다. 개인 .env에 누락된 키가 있어 환경변수 계약 검사는 제외했고 실제 값은 변경하지 않았다. 운영 환경 외부 연동은 검증 범위에 포함하지 않았다.


속도를 측정하니 이관 직후의 전체 실행 중앙값은 97.5초로 최초 90.9초보다 느렸다. 단위 테스트가 늘어도 전체 구동 비용이 줄어드는 것은 아니었다. Repository마다 다른 import를 두면서 같은 엔티티와 DB를 쓰는 슬라이스가 서로 다른 컨텍스트를 생성했다.

이에 28개 PostgreSQL 슬라이스의 저장 계층 구현 22개를 공통 어노테이션으로 묶었다. 각 테스트가 서비스나 외부 연동까지 로딩하지 않는 범위는 지키면서 같은 구성을 재사용하는 선택이다. 기존 테스트 트랜잭션과 DB assertion을 바꾸지 않고, 동시성과 커밋 검증 클래스는 기존 실제 구성을 유지했다.

같은 클래스의 동일 본문 4그룹은 입력을 모두 남겨 하나씩 합쳤다. 다른 API와 알림 종류에 걸친 동일 본문 8그룹은 각각의 계약을 확인하므로 유지한다. 같은 모양의 코드와 불필요한 중복 실행을 구분해야 한다는 한계도 기록한다.

동일 조건 3회 측정 중앙값은 85.8초로 직전보다 약 12.1%, 최초보다 약 5.7% 줄었다. 전체 실행 3,690개는 그대로 통과했다. 테스트 Java는 이번에 82줄 줄었지만 최초보다 557줄 많다. 코드 양, 실행 건수와 속도가 모두 함께 줄었다고 설명하지 않는다.


추가 검토에서 규칙 적용이 충분하지 않았던 부분도 확인했다. 단위 테스트로 옮겼다는 사실만으로 필요성 판단까지 끝난 것은 아니었다. 배너의 단순 필드 복사, 두 번의 동일한 실제 로그인, 별도의 AI 페이지 준비, Mock의 연속 반환만 확인하는 테스트를 기존 계약과 저장 시나리오에 합쳤다. 만료 상세 경계는 정책 단위에 두고 DB 테스트는 저장된 알림이 발송되는 연결을 확인하도록 줄였다.

고정 대기도 모두 불가피한 것은 아니었다. OpenAI 테스트는 실제 읽기 제한 200ms를 확인하면서 서버가 1.5초씩 잠들어 정리가 늦어졌다. 응답을 latch로 막고 검증 후 즉시 해제해 실제 타임아웃 조건을 유지했다. SQS의 5초 요청 제한처럼 운영 코드가 정한 복구 경계는 그대로 확인한다.

이번 검토로 207줄을 줄여 최초 대비 순증가는 350줄이 됐다. 실제 실행 3,677개가 통과했다. 전체 상세 중복까지 모두 제거했다고 단정하지 않고, 계층 분류와 검증 필요성 검토를 구분한다. 클래스 수와 줄 수를 줄이는 것만으로 안정성이나 전체 실행 속도를 대신 평가하지 않는다.


이후에는 남은 전체 테스트 파일 343개와 준비 도구 10개를 기준과 대조했다. 제목 상세 조건은 값 객체에 모으고 실제 로그인과 가입의 성공 검증을 한 번의 요청에 합쳤다. 기존 회원 로그인 판단은 단위 테스트로 옮기되, JWT와 토큰의 실제 저장 및 제공자 조회는 기존 DB 테스트에 남겼다. 레거시 소셜 연결을 확인한다고 하면서 연결을 삭제하던 준비도 바로잡았다.

이번 정리에서 Java 480줄을 줄였고, 최초 기준보다 130줄 적어졌다. 메서드 선언은 2,408개, 실제 실행은 3,659건이다. 전체 회귀와 형식 검사가 통과했으며 동시성과 트랜잭션 파일, 실제 DB 검증과 운영 코드는 유지했다. 파일별 유지 이유와 옮긴 50개 메서드의 대응표는 이관 기록에 연결했다. 서로 다른 계약과 실패 원인을 보호하는 테스트는 비슷한 본문이어도 남겼으며, 해당 전체 대조 단계에서 별도 클래스는 만들지 않았으며 검토 후 사용자가 최종 커밋과 PR 등록을 승인했다.


PR 등록 전에는 처음과 최종 코드를 같은 환경에서 번갈아 각각 3회 실행했다. test 태스크 중앙값은 95.855초에서 91.769초로 약 4.3% 줄었고, 6회 모두 통과했다. 앞서 기록한 85.773초는 중간 소스의 과거 측정값이다. 최종 수치와 직접 섞어 비교하지 않으며, 새 측정의 조건과 원자료는 이관 기록의 마지막 절에 남겼다.
