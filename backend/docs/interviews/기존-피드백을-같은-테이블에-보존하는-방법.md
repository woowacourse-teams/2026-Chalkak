# 기존 피드백을 같은 테이블에 보존한다

갱신: 2026-11-03 · [문의 접수·본인 조회·삭제 #903](https://github.com/woowacourse-teams/2026-Chalkak/issues/903)

고객센터의 본인 문의 목록을 추가하면서, 기존 피드백을 새 목록에서 제외할 기준이 필요해졌다. 기존 기록과 신규 문의는 작성자·내용·접수 시각이라는 구조를 공유하므로 같은 테이블에 저장하는 데 문제는 없었다. 필요한 것은 저장 공간의 분리가 아니라 사용자 조회 범위의 구분이었다.

처음에는 기존 기록을 별도 보관 테이블로 옮기는 방안을 제안했다. 데이터의 물리 삭제 없이 신규 문의만 기존 테이블에서 조회할 수 있지만, 사용자는 보관용 테이블이 추가되는 이유를 물었고 기존 테이블에 기록을 그대로 둘 수 있는지 확인했다. 유형 컬럼도 이미 사용하지 않기로 합의한 상태였다.

사용자가 기존 피드백에 소프트 딜리트를 적용하자고 제안했다. 이 선택은 이미 계획된 `deleted_at`을 사용하므로 보관 테이블이나 유형 컬럼을 추가할 필요가 없다. 도입 전 행은 내용·작성자·접수 시각을 유지하고 삭제 시각만 채운다. 사용자 목록에는 `deleted_at IS NULL`인 본인 문의만 나오고, 관리자 기존 조회에는 기록이 남는다.

컬럼은 원래 사용자 삭제 API 단위에서 추가할 예정이었지만, 목록 조회에서 곧바로 사용하므로 목록 단위에 먼저 포함했다. 이어 사용자 삭제 API도 같은 컬럼을 사용하도록 구현했다. 도메인이 최초 삭제 시각을 기록하고 반복 삭제에서는 유지한다. 서비스는 본인 문의 행을 잠가 동시에 삭제해도 최초 시각을 보존한다. 접수 제한 조회에는 삭제 조건을 넣지 않아 삭제로 제한을 우회할 수 없게 한다.

마이그레이션 적용 시점에 존재하는 피드백 전체가 삭제 표시의 대상이다. 변경 이후의 새 문의는 삭제 시각이 기본 `NULL`이고, Flyway가 완료된 버전을 다시 실행하지 않으므로 재시작할 때 신규 문의까지 숨기지 않는다. 향후 기존 피드백을 다시 사용자에게 보여주거나 복구하는 기능이 필요해지면, 삭제 상태와 도입 전 자료의 구분을 다시 검토해야 한다. 이번 범위에서는 복구 기능을 제공하지 않는다.

구현은 같은 테이블의 nullable 시각 컬럼, 기존 행 백필, 본인 목록의 소유권·삭제 조건으로 구성한다. 실제 PostgreSQL 전환 테스트에서 원문 보존·백필·새 행의 기본값·재시작을, 저장소와 API 테스트에서 삭제 제외와 접수 제한 집계 유지를 확인했다. 운영 배포는 아직 진행하지 않았다.
