# 문의 통로를 유지하면서 반복 접수를 제한한다

- 갱신: 2026-11-03
- 관련 작업: [#903](https://github.com/woowacourse-teams/2026-Chalkak/issues/903)

피드백에 답변하는 고객센터를 기획하면서 정지 회원의 반복 문의가 관리자에게 부담이 될 수 있다는 문제가 나왔다. 정지 사유 문의나 이의 제기 통로는 유지해야 하므로 정상·정지 회원에게 같은 자동 제한을 적용하기로 했다. 회원별 차단·해제 화면은 이번 범위에서 제외하고, 1분에 한 건과 최근 24시간 최대 다섯 건으로 시작한다.

제한은 성공적으로 저장된 접수를 기준으로 한다. 실패 요청을 세면 입력 오류만으로 문의를 못 보내는 상황이 생긴다. 사용자 또는 관리자의 삭제로 접수 횟수를 초기화하면 등록과 삭제를 반복해 제한을 우회할 수 있으므로 삭제 후에도 제한 시간 동안 접수 이력은 집계하기로 했다. 삭제 API는 아직 구현하지 않았으며 해당 커밋에서 이 조건을 검증한다.

접수 이력만 잠그는 방식은 첫 문의에는 잠글 행이 없다는 빈틈이 있다. 기존 회원 저장소의 회원 행 잠금을 재사용해 같은 계정의 검사와 저장을 한 트랜잭션으로 직렬화한다. 잠금을 얻은 후 현재 시각을 읽어 잠금 대기 시간이 접수 검사 시각을 낡게 만들지 않도록 한다. 회원이 다르면 서로 다른 행을 잠근다. 같은 회원의 다른 변경 작업과 경합할 수 있다는 한계는 남는다.

접수 판단은 처음에 정적 Policy로 분리했지만, 사용자의 설계 검토 후 `FeedbackSubmissionHistory` 일급 컬렉션으로 변경했다. 문의 한 건은 같은 회원의 전체 접수 이력을 모르므로 해당 책임을 맡기지 않고, 접수 시각 목록을 가진 객체가 직접 판단한다. 생성 시 목록을 복사·정렬하고 외부에 노출하지 않아 원본 목록 변경이 판단에 영향을 주지 않게 한다. 서비스는 이력을 조회해 객체를 생성하고 검사와 저장을 연결한다.

다시 보낼 수 있는 시각은 두 제한 중 더 늦은 시각이다. 정확히 1분 또는 24시간이 지나면 접수를 허용한다. 프로젝트의 기존 예외 계약에 맞춰 별도 상태 코드나 오류 응답을 추가하지 않고, `400 / BUSINESS_ERROR` 메시지에 UTC 시각을 안내한다. 기본 성공 응답의 문의 ID·접수 시각은 유지한다.

고객센터 접수 Slack 알림은 최종 인터뷰에서 제외했다. 기존 게시물 검수 Slack 알림과 향후 사용자 답변 알림은 서로 다른 범위다. 이번 단위는 접수 제한만 구현하며 문의 목록·상세·삭제와 관리자 답변·알림은 후속 작업이다. 시간 경계·저장 거절·실제 PostgreSQL 동시 접수, 기존 인증 정책과 성공 응답을 검증했다. 원래 테스트 DB에는 현재 브랜치에 없는 마이그레이션 이력이 있어 별도 테스트 DB를 사용했다. 로컬 `.env`의 기존 키 누락은 남아 있어 기본 테스트 명령의 환경 사전 검사는 실패한다. 운영 적용은 하지 않았다.
