# 주제 푸시 누락과 발송 추적을 어떻게 관측할까

갱신: 2026-11-16 · 관련 이슈 [#1031](https://github.com/woowacourse-teams/2026-Chalkak/issues/1031)

## 실패 로그를 셌을 때 놓치는 회차

발송 작업이 시작되기도 전에 멈추면 발행 실패 로그와 큐 적체가 둘 다 없을 수 있다. 개발 주제 푸시의 감시 작업은 예약과 활성 주제로 기대 회차를 계산하고, 같은 `eventId`의 발행 집계·실행 생략·실행 실패 중 하나가 있는지 확인한다. 하나라도 있으면 어떤 결과가 남은 회차다. 결과가 하나도 보이지 않으면 회차 누락 후보로 집계한다.

| 최초 검사 시점 | 얻는 점 | 잃는 점 |
| --- | --- | --- |
| 예약 후 1분 | 실제 누락을 더 일찍 조사할 수 있다. | 매분 실행하는 발송 작업이나 로그 수집이 늦으면 정상 회차도 누락으로 볼 가능성이 높다. |
| 예약 후 5분 | 발송 작업과 로그 수집에 여유를 주면서 기존 30분 발송 기한 안에 조사할 시간을 남긴다. | 실제 누락도 최소 5분 기다린다. 이후 검사와 CloudWatch 평가 시간도 더해진다. |
| 예약 후 10분 | 더 긴 로그 수집 지연을 기다릴 수 있다. | 5분 기준보다 조사에 쓸 수 있는 시간이 줄어든다. |

5분을 초기값으로 정했다. 예약 시각부터 결과가 CloudWatch에서 처음 조회될 때까지의 시간과 Slack 수신 시각을 확인한 뒤 조정한다. 발행과 감시는 다른 스케줄러에서 실행하지만 같은 앱을 공유한다. 앱이나 로그 수집이 멈추면 회차를 계산할 수 없으므로, CloudWatch의 데이터 부족 상태로 관측 중단을 별도로 알리도록 설계했다.

## SQS 경계를 넘겨 추적하고 스팬 출력은 발송 흐름에서 분리

스케줄러가 처리하기 시작한 회차의 OTel 트레이스를 만들고, SQS 메시지 속성의 W3C `traceparent`로 Worker에 넘긴다. Worker의 처리와 FCM 호출에 각각 스팬을 열어 큐 대기와 외부 호출 시간을 구분한다. 발송 자체가 시작되지 않은 회차는 감시 로그의 `eventId`를 사용한다.

완료된 스팬을 발송 스레드에서 곧바로 쓰면 메모리에 머무는 시간이 짧아지지만, 로그 출력 지연이 발송에 붙는다. 개발에서는 2,048개 메모리 큐를 둔 비동기 배치와 기존 CloudWatch Agent를 사용한다. 발송 스레드는 스팬 출력 완료를 기다리지 않는 대신, 큐가 가득 차거나 프로세스가 갑자기 종료되면 스팬 일부가 빠질 수 있다. 이때 `eventId` 또는 `trace_id`로 기존 발송 결과 로그를 대조한다.

로컬에서 누락 판정, 메시지 속성을 통한 부모 스팬 복원, 재수신, 기존 메시지 호환을 확인했다. 실제 AWS의 정상·누락 회차, Slack 수신, 데이터 부족 상태와 스팬 조회는 [개발 검증 절차](../../deploy/docs/notification-monitoring.md#개발-환경-주제-푸시-회차-결과-누락)에 따라 별도로 확인한다.
