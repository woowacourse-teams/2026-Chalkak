# 별도 Outbox 대신 알림함에 발행 상태를 저장한다

- 갱신일: 2026-10-14
- 관련 작업: [이슈 #492](https://github.com/woowacourse-teams/2026-Chalkak/issues/492), [이슈 #494](https://github.com/woowacourse-teams/2026-Chalkak/issues/494)

## 테이블을 줄이면서 서버 중단 후 발행 대상을 찾기

초기 설계에는 알림함과 별도 Outbox, 기기별 발송 시도 이력이 있었다. 사용자는 현재 서비스 규모에서 테이블과 처리 상태가 과하다고 지적했고, 팀원은 승인·반려 알림 행에서 보냈는지를 구분하는 방식을 제안했다.

승인·반려는 원래 알림함에 저장하므로 같은 행에 SQS 발행 상태를 둘 수 있다. 단순한 참·거짓만으로는 설정이 꺼져 발행할 필요가 없는 알림과 아직 발행하지 못한 알림을 구분하기 어려워, 합의한 #492에서는 발행 불필요·대기·완료·만료·실패를 구분한다. 별도 테이블은 추가하지 않는다.

이 상태는 SQS까지 전달했는지를 나타낸다. FCM 수락이나 기기 수신을 나타내지 않는다. 발행 횟수와 오류 이력은 로그에 남기고, 기기별 발송 이력은 DB에 저장하지 않는 방향이다. 한 사용자에게 여러 기기가 있을 때 일부 성공을 어떻게 처리할지도 이슈에 별도로 정했다.

## 알림함 저장과 푸시 수신 설정을 구분한다

푸시가 꺼져 있어도 승인·반려 기록은 알림함에 필요하다. 따라서 생성 당시 수신 설정으로 발행 필요 여부를 정하되 알림 자체를 생성하지 않는 방식은 사용하지 않는다. 나중에 설정을 켠 것이 과거 검수 결과의 발송 요청은 아니므로 기존 발행 불필요 알림을 대기로 바꾸지 않는다.

첫 커밋은 검수·감사 기록·알림·초기 발행 상태를 함께 저장하는 부분이다. 실제 SQS 발행과 FCM 발송은 다음 두 커밋의 범위다. 이 기록의 상태도 전체 전달 과정의 구현·검증이 끝날 때까지 방향 합의로 유지한다.

초기 코드에서는 Java 필드와 DB 컬럼에 발행 불필요 기본값을 두었다. 사용자는 생성 시 두 `if`로 상태를 직접 지정하도록 요청했고, 이후 DB 기본값도 없애는 방향을 승인했다. 기존 행만 마이그레이션에서 발행 불필요로 채우고, 새 저장은 발행 상태가 없으면 `NOT NULL`로 거부한다. 상태를 빠뜨린 새 알림이 조용히 발행 불필요로 저장되는 것을 막기 위한 선택이다.

현재 정책은 [NOTIFICATION-001](../../../docs/business-rules/rules/notification.md)을 따른다. 두 번째 단위에서는 발행 가능 시각이 된 알림을 한 건씩 잠근 뒤 SQS에 전달한다. 정상 작업은 1초 간격으로 최대 100건을 조회하고, 실패한 작업만 1분 뒤 시도하도록 DB에 남긴다. 30분 기한은 재시도로 늘리지 않는다. SQS SDK 내부 자동 재시도는 끄고 DB의 다음 시도 시각으로 관리한다. 개발 중 사용자가 DB → SQS 재발행 대기를 기존 5분에서 1분으로 변경하도록 요청했다. 이후 SQS 소비의 Visibility Timeout도 60초, 최대 수신 횟수는 최초 수신 포함 10회로 합의했다. 처리 중 숨김 시간 연장과 FCM SDK 내부 재시도는 SQS 수신 횟수와 구분한다.

SQS 수락 뒤 DB 반영을 실패시키는 테스트에서는 발행 대기가 남았고, 다시 실행하면 같은 사건 ID로 재발행했다. 한 건의 반영 실패가 다른 건의 완료를 취소하지 않는 것도 확인했다. 이는 중복 가능성을 없앴다는 결과가 아니라 중복이 발생할 수 있는 경계를 재현한 결과다.

SQS SDK의 요청·응답은 로컬 HTTP 서버로 검증했다. 사용자는 개발 큐 URL을 제공했고 AWS 권한 확인을 완료했다고 알렸다. 커밋·푸시만으로 개발 서버에 배포되지 않으므로, 이번 PR의 PushWorker·FCM 구현까지 마친 뒤 개발 서버에서 전체 연동을 검증하기로 했다. 사용자는 이후 #572의 개발 서버 주제 발행 → FCM 연동 검증 완료를 보고했다. 플랫폼별 수신 증거와 #494의 로그·경보·DLQ 검증까지 완료한 것으로 확장하지 않는다. 남은 운영 검증 때문에 문서 상태는 방향 합의를 유지한다.

## SDK 재시도와 SQS 재전달을 구분한다

세 번째 단위는 현재 등록 기기·최신 수신 설정·로그인 유효성·읽음·게시물 삭제·원래 발송 기한을 확인한다. 하나라도 FCM이 수락되면 사용자 작업을 완료하고, 전부 일시 실패하면 SQS에서 다시 전달받는다. 일부 실패를 따로 저장·재시도하지 않는 합의에 따라 기기별 이력 테이블을 추가하지 않는다.

SDK가 오류 응답에 추가 요청하는 동안 메시지를 삭제하지 않고 숨김 시간을 연장한다. SDK 수락 후에는 SQS를 완료하고, 휴대폰이 오프라인이면 FCM/APNs가 설정한 TTL·APNs 만료에 따라 전달을 처리한다. SDK 요청과 SQS 수신 횟수는 다르다. Firebase Admin Java 9.11.0 기본값(503에 최대 4회 추가 요청)을 확인했다. 초기에는 실제 HTTP 요청 직전 기한과 Android TTL을 다시 확인하는 전송 클래스를 연결하여 SDK 대기 중에도 원래 기한을 유지했다.

리뷰에서 이 정확도를 위해 HTTP 전송과 JSON 재작성·ThreadLocal까지 관리하는 부담이 제기됐다. 사용자는 발송 시작·SQS 재전달의 30분 검사는 유지하되, 이미 시작한 SDK 내부 재시도가 기한을 넘고 Android 만료가 늦어질 수 있는 예외를 받아들여 기본 SDK 전송으로 복귀하기로 했다. 승인·반려 결과는 알림함에서도 확인할 수 있어 현재 범위에서는 구조를 단순하게 유지하는 쪽을 선택했다. iOS의 절대 만료 시각은 유지한다. [현재 기한 정책의 결정](../../../docs/business-rules/decisions/2026-10-08-fcm-sdk-transport.md)을 따르며 실제 기기 수신·표시 시각을 보장하지 않는다.

로컬 PostgreSQL과 HTTP 서버에서 최신 조건·일부 수락·무효 토큰 제거·SDK 재시도·숨김 갱신·삭제 실패를 검증한다. 새 로그·경보의 실제 AWS 검증과 플랫폼별 수신 증거는 환경별로 확인해야 한다. 처리 지연·성능은 이 기록의 로컬 검증으로 확인한 결과가 아니다. 현재 문서 상태는 방향 합의를 유지한다.

## 발송 실패가 곧 기기 토큰의 무효를 뜻하지는 않는다

리뷰에서는 영구 오류에서도 기기를 남기면 다음 알림에서 같은 실패가 반복될 수 있다는 한계를 지적했다. 현재 [NOTIFICATION-008](../../../docs/business-rules/rules/notification.md#notification-008-검수-푸시-발송과-sqs-재처리)는 무효 토큰과 메시지·프로젝트·인증 오류를 구분한다. 이번 보완은 이 기준을 바꾸지 않고, 보존 이유와 검증을 명확히 하는 작업이다.

| FCM 오류 | 현재 처리와 이유 |
| --- | --- |
| `UNREGISTERED` | 발송한 토큰이 여전히 해당 기기에 연결돼 있으면 기기 행을 삭제한다. 등록 해제된 토큰으로 다음 알림을 보내지 않는다. |
| `INVALID_ARGUMENT` | 기기와 토큰을 보존한다. 토큰 오류 외에 메시지 형식·크기·TTL 오류도 포함하므로 이 코드만으로 토큰 무효를 확정하지 않는다. |
| `SENDER_ID_MISMATCH` | 기기와 토큰을 보존한다. 앱 토큰과 서버 발송 프로젝트의 불일치 여부를 조사한다. 서버 설정 문제로 정상 기기를 삭제할 위험을 피한다. |
| `THIRD_PARTY_AUTH_ERROR` | 기기와 토큰을 보존한다. APNs 등 전달 서비스의 인증 설정을 확인해야 하는 오류이며 토큰 무효 판정은 아니다. |

오류 의미는 [Firebase 공식 오류 문서](https://firebase.google.com/docs/cloud-messaging/error-codes)를 확인했다. 정상 기기를 잘못 제거하지 않는 대신, 실제로 잘못된 토큰이 `INVALID_ARGUMENT`을 반환하면 등록 기록이 남아 다음 알림에서도 실패할 수 있는 한계를 받아들인다. 이 세 영구 오류는 기존 오류 코드 로그로 조사하고, 다른 기기의 일시 실패가 없다면 현재 사용자 작업을 완료한다. 설정을 고쳐도 완료한 메시지를 자동으로 다시 보내지는 않는다.

기존 FCM 어댑터 테스트는 세 오류를 영구 실패로 분류하는지 확인한다. Worker의 PostgreSQL 테스트에는 세 코드 각각에서 기기 행·토큰 원문·해시가 유지되고 작업이 완료되는지 검증을 보강한다. 기존 `UNREGISTERED` 삭제와 발송 중 갱신된 토큰 보호 테스트도 유지한다. 실제 프로젝트·APNs 인증 오류와 운영 로그 수집은 개발 서버에서 별도로 확인해야 한다.

## 발행 로그와 DB 대기를 함께 보고 로그 보관 기간을 나눈다

별도 시도 테이블을 없애면서 사용자는 실패를 무엇으로 조사하는지 질문했다. #494에서는
같은 메시지의 로그에 SQS 메시지 ID·수신 횟수를 붙이고, 생략 이유와 기기 처리 집계를 남긴다.
MDC는 같은 처리 스레드의 로그에 공통 값을 넣으며 별도 연장 스레드는 식별자를 직접 기록한다.
이는 로그를 메모리에 계속 모으는 구조가 아니며, 처리 종료 후 문맥을 정리한다.

Relay 자체의 결과 로그는 실행하지 못한 발행을 알려주지 못한다. DB에는 PENDING이 남고 큐는
비어 있을 수 있어 대기 건수와 가장 오래 기다린 시간을 1분마다 별도로 관측한다.
COUNT·MIN 결과만 반환하고 알림 엔티티 목록을 가져오지 않는다. 쿼리와 로그 저장 부담은 늘며,
실제 조회 시간은 측정한 결과가 아니다. 큐·DB·FCM 단계의 경보를 함께 조사하도록 정했다.

사용자는 알림 전용 로그 그룹에 30일을 설정하는 방향을 이해하고 승인했다. 기존 일반 그룹의
개발 7일·운영 60일을 유지하면서 알림은 두 환경 모두 30일 조사하기 위한 분리다.
로그 파일·그룹·Agent 설정 관리가 늘고 요청부터 푸시까지 조사할 때는 두 그룹을 함께 조회한다.
새 알림은 일반 파일에 중복 기록하지 않는다. 기존 로그를 소급 이동하거나 삭제하지 않는다.

로컬 테스트는 MDC 연결·기기 결과·파일 분리·DB 집계·조회 실패를 확인했다.
실제 그룹 생성·Agent·경보·DLQ 조사는 배포 후 별도로 실행하고 사용자에게 화면 순서대로 안내한다.
[운영 조사 절차](../../deploy/docs/notification-investigation.md)를 근거로 남은 검증을 기록한다.
