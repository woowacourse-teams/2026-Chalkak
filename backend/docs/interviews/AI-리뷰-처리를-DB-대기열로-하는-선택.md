# AI 리뷰 처리는 요청 안에서 기다리지 않고 DB 행을 대기열로 쓴다

갱신: 2026-10-21 · [이슈 #689](https://github.com/woowacourse-teams/2026-Chalkak/issues/689) · [PR #716](https://github.com/woowacourse-teams/2026-Chalkak/pull/716) · [이슈 #690](https://github.com/woowacourse-teams/2026-Chalkak/issues/690)

## OpenAI 호출은 20~60초 걸리는데 요청이 그 시간을 기다려도 되는가

사진 AI 리뷰는 OpenAI 호출 한 번에 20~60초가 걸린다. 요청이 이 시간을 붙잡으면 모바일 연결이 중간에 끊길 수 있고, 끊겨도 서버 쪽 호출은 계속 돈다.
요청 스레드도 그만큼 묶이고, 사용자가 몰릴 때 OpenAI의 분당 요청·토큰 한도와 비용을 서버가 통제하기 어렵다.
그래서 요청은 접수만 하고, 처리는 서버가 속도를 정해 따로 하는 구조가 필요했다.

## 비교한 선택

| 선택 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 요청 안에서 동기 호출 | 가장 단순하다 | 위의 연결·스레드·한도 문제를 그대로 가진다 |
| `@Async` 메모리 큐 | 구현이 가볍다 | 재시작하면 대기 중인 건이 사라지고 동시 처리 수를 직접 챙겨야 한다 |
| 이벤트 + 보조 폴링 | 요청 직후 바로 시작할 수 있다 | 이벤트와 폴링이라는 두 경로를 함께 맞춰야 한다 |
| SQS | 큐가 재시도·보관을 맡는다 | 인프라가 늘고, 상태 조회와 큐 메시지의 일관성을 따로 맞춰야 한다 |
| PostgreSQL LISTEN/NOTIFY | 폴링 없이 깨울 수 있다 | 연결을 계속 붙잡아야 하고 알림이 유실될 수 있어 어차피 보조 폴링이 필요하다 |
| OpenAI background 모드 | 서버가 기다릴 필요가 없다 | `store:false`로 요청해도 OpenAI가 데이터를 약 10분 보관한다 |

## DB 행 하나를 작업 하나로 보고 한 줄 조건으로 가져간다

AI 리뷰 행이 곧 작업이다. 상태 조회에 쓰는 행이 대기열이므로 두 곳을 맞출 필요가 없고 기능에 인프라가 늘지 않는다.

- 가져가기: `FOR UPDATE SKIP LOCKED`로 가장 오래 기다린 행 하나를 짧은 트랜잭션에서 잠그고 임대(120초)를 건다. 임대는 OpenAI 연결·응답 제한 시간에 여유를 더한 값보다 짧게 둘 수 없도록 기동 때 검사한다.
- 결과 반영: 가져갈 때마다 시도 번호가 늘고, 반영은 번호가 같고 처리 중일 때만 한다. 임대가 끝나 다른 워커가 다시 가져간 뒤 늦게 끝난 워커의 결과는 버린다.
- 호출 동안에는 DB 연결과 행 잠금을 잡지 않는다. 가져가기와 반영, 두 개의 짧은 트랜잭션 사이에서 호출한다.
- 폴러는 하나이고 가상 스레드에 처리를 넘긴다. 동시 처리 수는 세마포어로 제한하며 10으로 yml에 고정한다. 이 상한은 서버 자원이 아니라 OpenAI의 RPM·TPM을 지키기 위한 값이라 환경에 따라 늘리지 않는다.
- 종료·interrupt·DB 오류처럼 호출 결과를 모르는 상황에서는 실패를 쓰지 않고 행을 처리 중으로 둔다. 임대가 끝나면 다시 가져가며, 반복해서 워커를 멈추게 하는 행은 가져간 횟수 상한에서 실패로 끝난다.
- 상한을 넘은 행을 실패로 끝내는 일과 정상 행을 가져가는 일은 트랜잭션을 나눈다. 상한을 넘은 행을 정리한 트랜잭션은 정상 행을 가져가지 않고 커밋하고, 그 행들의 종료 로그와 결과 알림을 남긴 뒤 새 트랜잭션에서 다시 가져간다. 한 트랜잭션에서 둘을 함께 하면 알림 저장이 느릴 때 아직 처리를 시작하지 않은 행의 임대(120초)가 줄어 같은 행을 다시 가져가고 OpenAI를 중복 호출한다.

background 모드는 서버 부담을 가장 줄이지만, 사진을 OpenAI에 저장하지 않도록 요청한다는 개인정보 방침과 맞지 않아 제외했다.

## 결과와 남은 것

- 대기열이 비어 있을 때의 비용은 작은 부분 인덱스에 대한 초당 1회 조회다. 가져오기까지 최대 약 1초 걸리지만 20~60초 호출에 비하면 사용자가 느끼지 못한다.
- 재시작, 임대 만료, 이후 [#690](https://github.com/woowacourse-teams/2026-Chalkak/issues/690)의 재시도가 모두 "가져갈 수 있는 행" 한 조건으로 처리된다. 별도의 복구 경로를 두지 않는다.
- 시도 번호가 가져간 횟수와 요청 구분 두 역할을 겸하는 문제는 #690에서 열을 나눠 풀었다. 아래 [재시도와 재요청을 같은 행에서 처리한다](#재시도와-재요청을-같은-행에서-처리한다)에 적었다.
- 실제 운영 부하는 관측하지 않았다. 1초 폴링의 DB 비용과 동시 10건의 한도 적합성은 운영 로그로 확인해야 한다.
- 다시 검토할 조건: 접수 직후 시작 지연이 문제가 되면 이벤트로 워커를 깨우는 방식을, 처리량이나 다중 서버 확장이 필요해지면 SQS를 검토한다.

## 재시도와 재요청을 같은 행에서 처리한다

#690에서 자동 재시도(서버)와 실패 후 재요청(사용자)을 붙이면서 새 테이블이나 새 큐를 만들지 않고 같은 행을 다시 대기열에 넣었다. "가져갈 수 있는 행" 조건에 "다음 시도 시각이 지난 대기 행"만 더하면 되기 때문이다. 정책(요청당 처리 시도 3번, 게시물당 요청 3번, 호출 상한 9회)은 [비즈니스 규칙](../../../docs/business-rules/rules/ai-review.md)에 있고, 여기에는 구조를 그렇게 정한 이유만 적는다.

- **회차 시도 수(`round_attempt`)와 전역 `attempt`를 나눈 이유**: `attempt`는 늦게 끝난 워커의 반영을 막는 번호라 줄거나 되돌아가면 안 된다. 반면 "이번 요청에서 몇 번째 시도인가"는 재요청 때 0으로 돌아가야 한다. 한 열이 두 일을 하면 재요청할 때 둘 중 하나가 깨진다. 그래서 `attempt`는 계속 늘리고, 상한 3은 재요청 때 0이 되는 회차 시도 수로 비교한다. 같은 이유로 사용자 요청 수(`request_count`)도 따로 센다.
- **재요청 때 같은 행을 재사용한 이유**: 게시물당 결과는 하나이고 조회·권한·공개 조건 판단이 모두 이 행 하나를 기준으로 한다. 재요청마다 새 행을 만들면 "최신 행은 무엇인가"를 매번 가려야 하고 게시물당 하나라는 제약을 풀어야 한다. 대신 회차가 섞이지 않게 시각·오류·사용량은 비우고, 최초 요청 시각과 요청 ID는 지표 때문에 남긴다. 회차의 요청 시각은 `last_requested_at`에 따로 둔다. 재요청 행이 오래된 최초 요청 시각 때문에 새 요청을 앞지르지 않게 가져가는 순서는 재시도 대기 행이면 다음 시도 시각, 나머지는 이 값을 따른다. 부분 인덱스도 같은 식(`COALESCE(next_attempt_at, last_requested_at)`, `id`)으로 만들어 정렬 노드 없이 첫 후보를 읽는다.
- **잠금 첫 읽기**: 재요청은 읽은 뒤 상태를 바꾸는 흐름이라 같은 POST가 동시에 오면 둘 다 "실패 상태"를 읽고 둘 다 재요청할 수 있다. 트랜잭션의 첫 읽기를 행 잠금 읽기로 하면 한쪽이 기다렸다 이미 대기로 바뀐 상태를 읽어 한 번만 반영된다. 잠금 없이 먼저 읽으면 영속성 컨텍스트에 남은 값 때문에 뒤의 잠금 읽기가 최신 값으로 갱신되지 않아 이 보호가 깨진다.
- **Retry-After를 최소 대기로만 쓰고 최대 60초로 둔 이유**: OpenAI가 알려 준 시간보다 일찍 다시 보내면 같은 429를 또 받아 시도만 쓴다. 그래서 백오프와 비교해 더 긴 쪽을 따른다. 다만 서버가 알려 준 값을 그대로 믿어 대기를 늘리면 사용자 화면이 오래 진행 중에 머문다. 앱의 폴링 창(약 5분)과 최악의 대기 시간을 지키려고 상한을 60초로 둔다. dev 실측(2026-10-21)에서 프로젝트 분당 요청 한도 초과 429가 `retry-after: 60`을 보냈다. 시간 초과나 완료 응답이 실패인 경우에는 헤더가 없어 백오프만 쓴다.
- **남은 것**: 실제 운영에서 재시도가 얼마나 일어나는지, 재요청 비율과 9회 상한이 적절한지는 관측하지 않았다. `review_retry_scheduled`와 `review_requested`의 `created=false` 로그로 확인한다.
