# 주제 시간을 자유롭게 정하면서 참여 기간 겹침을 막기

**갱신 날짜:** 2026-09-29

**관련 이슈:** [#486](https://github.com/woowacourse-teams/2026-Chalkak/issues/486)

## 두 주제가 동시에 열려 게시물 조회가 실패했다

운영에서 9월 28일 주제의 종료 시각을 9월 29일 23:59 KST로 설정했다. 9월 29일 주제는 같은 날 00:00 KST에 시작했다. 이 시간에는 두 주제가 모두 `OPEN`이어서 단일 주제를 기대하는 게시물 작성 여부 조회가 실패했다. 관리자가 운영 DB에서 앞 주제의 종료 시각을 9월 29일 00:00 KST로 고친 뒤 겹침이 해소됐다고 보고했다. 이 기록은 운영 DB를 직접 재조회한 결과는 아니다.

## 종료 시각을 자동 고정할지는 따로 판단했다

처음에는 주제 시작을 누르면 하루 뒤에 자동 종료하고 관리자에게 확인만 받는 방법을 고려했다. 그러나 주제 날짜는 **시작 시각의 KST 날짜**이며, 관리자는 시작·종료 시간을 유동적으로 정하고 싶다고 명확히 했다. 예를 들어 28일 주제를 28일 09:00부터 29일 09:00까지, 29일 주제를 29일 09:00부터 30일 09:00까지 편성할 수 있어야 한다. 따라서 자정이나 24시간 고정은 요구사항과 맞지 않는다.

선택한 방어선은 삭제되지 않은 주제 사이의 기간 겹침을 금지하는 것이다. 참여 기간을 `[시작, 종료)`로 해석해 앞 주제 종료와 다음 주제 시작이 같은 시각이면 허용한다. 주제 날짜가 달라도 겹치면 거절한다. 관리자가 편성 중 즉시 이해할 수 있도록 서비스에서 오류를 반환하고, 동시에 들어오는 요청도 막도록 PostgreSQL exclusion constraint를 둔다.

## 구현과 검증에서 확인한 범위

- 관리자 생성·수정 서비스가 다른 활성 주제의 기간을 검사한다. 수정할 주제 자신과 논리 삭제된 주제는 겹침 대상에서 제외한다.
- DB 제약은 동일한 반열린 구간 기준으로 활성 주제만 검사한다. 제약 위반은 기존 관리자 400 오류 형식으로 변환한다.
- 겹치는 생성·수정, 맞닿은 경계, 삭제된 주제, 직접 SQL 삽입, 기존 수정 상태 오류 순서를 테스트했다.
- 기존 캘린더·게시물 fixture의 겹치는 기간을 수정했다. 개인 `.env`의 로컬 관리자 설정이 기본 설정 테스트에 영향을 주는 것을 확인해 테스트 프로세스에서만 기본값으로 맞췄고, 전체 테스트 1,343개가 실패·건너뜀 없이 통과했다. 컨벤션과 하네스 구조 검사도 통과했다. 개인 `.env`에 필요한 키가 없어 환경변수 계약 검사는 전체 테스트 실행에서 제외했다.

DB 제약을 적용하기 전에 **기존 활성 주제 전체**의 겹침을 읽기 전용으로 확인해야 한다. 남아 있는 겹침이 있다면 마이그레이션이 실패하며, 운영 데이터 수정은 별도로 판단해야 한다.

```sql
SELECT a.id AS topic_a, a.title AS title_a,
       b.id AS topic_b, b.title AS title_b
FROM topics a
JOIN topics b
  ON a.id < b.id
 AND a.starts_at < b.ends_at
 AND b.starts_at < a.ends_at
WHERE a.deleted_at IS NULL
  AND b.deleted_at IS NULL;
```

현재 규칙은 [TOPIC-003](../../../docs/business-rules/rules/topic.md), 정책 변경의 짧은 근거는 [결정 기록](../../../docs/business-rules/decisions/2026-09-29-topic-period-overlap.md)에 둔다. 운영 전체 데이터 사전 점검과 실제 배포는 아직 확인하지 않았다.
