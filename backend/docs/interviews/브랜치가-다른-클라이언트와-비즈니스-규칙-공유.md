# 브랜치가 다른 클라이언트와 비즈니스 규칙을 공유하는 방법

갱신: 2026-09-23

관련 이슈: [#477](https://github.com/woowacourse-teams/2026-Chalkak/issues/477)

정책 문서뿐 아니라 공통 진입 지침·스킬·참조 문서를 전용 브랜치에서 공유하고, Android AI가 작업 시작·재개 시 관련 규칙을 읽어 적용 내용을 짧게 알리는 방향으로 정리했다. 사람에게는 변경 내용과 영향을 직접 공유한다. [설치·갱신 도구](../../scripts/shared_harness/README.md)를 구현하고 로컬 Git 통합 테스트를 진행했다. 자동 게시 대상은 `harness/shared`로 고정했다. `be/develop` 반영 후 GitHub Actions가 검사·추출·게시하도록 구현했다. 실제 원격 배포·팀원 설치와 AI 정책 적용은 아직 검증하지 않았다.

## 문제 — 공통 경로만 만들면 다른 브랜치에서도 읽을 수 있을까?

백엔드 인터뷰·개발에서 합의한 정책을 공통 Markdown에 반영하더라도 Android 작업 브랜치에 문서가 없다면 팀원과 AI가 읽을 수 없다. 같은 저장소라는 사실만으로 브랜치 사이의 파일이 공유되지는 않는다.

2026-09-23 GitHub 트리를 조회한 결과, `be/develop`에는 `docs/business-rules/`와 공통 정책 스킬이 있지만 `client/develop`에는 없었다. Android의 `AGENTS.md`와 `CLAUDE.md`에도 공통 비즈니스 규칙을 조회하는 절차가 없었다.

- [백엔드 확인 시점](https://github.com/woowacourse-teams/2026-Chalkak/tree/686c48aa8db54e30f74cb9f917829dde618137d4/docs/business-rules)
- [클라이언트 확인 시점](https://github.com/woowacourse-teams/2026-Chalkak/tree/4b5ba2b912c046d516c449df8f99477cc948e176)
- [Android AGENTS.md](https://github.com/woowacourse-teams/2026-Chalkak/blob/4b5ba2b912c046d516c449df8f99477cc948e176/client/android/AGENTS.md)
- [Android CLAUDE.md](https://github.com/woowacourse-teams/2026-Chalkak/blob/4b5ba2b912c046d516c449df8f99477cc948e176/client/android/CLAUDE.md)

이 문제를 해결할 배포·설치 기반은 구현했지만 Android AI의 실제 참조와 정책 변경 전달까지 완성했다고 표현하지 않는다.

## 해결 방향 — 공통 하네스 배포와 정책 변경 안내를 함께 연결한다

**정책 합의 → 코드·공통 문서·스킬을 같은 PR로 검토 → be/develop 병합 → 검사 후 공통 브랜치 자동 게시 → 각 컴퓨터의 공유 폴더 갱신 → 작업 정리 후 새 버전 적용 → AI가 관련 스킬·규칙 확인 및 적용 내용 안내 → 작업**으로 연결한다. 백엔드는 Android 팀원에게 변경 내용과 영향을 별도로 공유한다.

사람에게는 무엇이 바뀌었고 어떤 작업이 필요한지 알린다. AI에는 작업 시작·재개 때 무엇을 확인해야 하는지 지침을 둔다. 문서 존재, 최신 문서 반영, AI의 실제 읽기는 별개의 확인 대상이다.

## 비교한 방식 — 문서 전달 PR에서 공통 하네스 전용 브랜치로

백엔드 전체 병합은 정책 공유에 불필요한 변경까지 포함한다. Android AI가 매번 원격 백엔드 문서를 읽는 방식은 별도 복사 없이 최신 원본에 접근할 수 있지만, 매번 네트워크 접근이 필요하고 작업 중 참조 기준이 달라질 수 있다.

처음에는 `docs/business-rules/`만 `client/develop`에 전달하는 PR을 제안했다. 사용자는 [PR #320](https://github.com/woowacourse-teams/2026-Chalkak/pull/320)에 공통 `AGENTS.md`·`CLAUDE.md`·스킬도 함께 포함돼 있음을 지적하고, 공통 하네스 전용 브랜치에서 모두 받아 사용하는 방식을 제안했다. 공유 범위가 정책 문서만이 아니므로 전용 브랜치 방식으로 방향을 바꿨다.

- 배포 대상은 공통 진입 지침, Codex·Claude의 공통 `business-rules` 스킬, 해당 스킬의 참조 문서, 비즈니스 규칙과 결정 기록이다. 링크된 파일을 빠뜨리지 않고 검증한다.
- #320에는 백엔드 전용 지침·코드도 있으므로 PR 전체를 공통 규칙으로 취급하지 않는다. Java와 Android 규칙은 해당 플랫폼에 유지한다.
- 개발 브랜치에 전용 브랜치를 직접 pull해 병합하지 않는다. 별도 공유 폴더에서 하네스를 갱신하고, 프로젝트의 진입 지침과 지원되는 스킬 설치·연결 방식으로 참조한다. 각 도구의 공식 프로젝트 스킬 경로에 심볼릭 링크를 연결한다. 구조·참조 경로는 테스트했으며 실제 모델의 스킬 읽기는 별도 검증한다.
- 공통 배포의 원본 커밋·파일 해시와 작업에서 사용한 버전을 남긴다. 서로 다른 버전의 지침·스킬·문서가 섞이지 않도록 한 버전으로 배포한다.
- 먼저 수동 갱신과 실제 스킬 읽기를 검증한다. 이후 로그인 시 자동 갱신을 검토하고, 작업 시작·재개 때도 변경을 확인한다.
- 갱신 실패나 로컬 수정이 있으면 강제로 덮어쓰지 않는다. 진행 중인 작업의 기준은 고정하고, 새 버전은 다음 작업·재개 시 영향 확인 후 적용한다.

이 방식은 공통 문서를 매번 클라이언트 브랜치로 전달하는 과정을 대체한다. 다만 각 프로젝트에 최초 진입 연결이 필요하고, 공유 폴더의 파일 존재만으로 AI의 스킬 발견·실행이 보장되지는 않는다.

## 수동 파일 전달에서 병합 후 자동 게시로 바꾼 이유

처음 구현은 검토된 커밋에서 공통 파일을 추출하고 담당자가 전용 브랜치에 옮겨 커밋·푸시하는 방식이었다. 사용자는 기능 코드와 정책 문서를 함께 개발하는 백엔드 팀원이 이 단계를 반복해야 하는 점을 지적하고 자동화를 요청했다.

이에 백엔드는 코드·문서를 같은 PR로 리뷰받고 병합하면 되도록 바꿨다. GitHub Actions는 PR에서는 검사만 하고, `be/develop`에 관련 변경이 들어온 뒤 검사가 성공하면 `harness/shared`에 공통 파일의 추가·수정·삭제를 자동 반영한다. 일반 push를 사용하는 이벤트이므로 직접 push를 제한하는 팀 규칙은 GitHub 브랜치 보호 설정에서 관리해야 한다.

게시 도구는 앱 개발 브랜치를 전환하거나 원본 index를 수정하지 않고 별도 index로 배포 트리를 만든다. 최초에는 앱 이력 없이 배포 브랜치를 만들고, 이후에는 직전 배포 이력을 잇는다. 더 최신 원본이 이미 게시되어 있으면 오래된 작업을 건너뛰며, 동시 게시 충돌·검사 실패 시 강제 덮어쓰기를 하지 않는다.

GitHub의 자동 게시와 개인 컴퓨터의 자동 내려받기는 별개다. 각 Mac에 한 번 로그인 실행을 등록하면 macOS가 로그인할 때 공통 브랜치를 별도 폴더로 받아 검사·보관한다. Android 개발 폴더에서 git pull이나 merge를 실행하는 것이 아니다. 실제 적용은 진행 중 작업을 정리한 뒤 별도 명령으로 수행한다.

## Android가 정책을 바꾸고 싶을 때

공통 배포본은 읽기 전용 파일·디렉터리 권한으로 보호한다. 기존 Android 개발 지침과 백엔드 원본은 잠그지 않는다. 이 권한은 일반적인 수정 실수를 막으며 컴퓨터 소유자의 의도적 권한 변경까지 막는 보안 경계는 아니다. 변조는 해시 검사에서 별도로 감지한다.

정책에 문제가 있거나 개선하고 싶으면 현재 규칙·문제와 이유·원하는 변경·앱 영향을 정리해 백엔드에 전달한다. **백엔드와 합의 → 원본 코드·정책 수정 및 PR → 병합·재배포 → Android 새 버전 적용**으로 진행한다. AI는 공통 배포본을 직접 고치거나 권한을 풀어 우회하지 않으며 전달 문구를 작성한다. 이 흐름은 양쪽 팀이 서로 다른 기준으로 구현하는 일을 줄이기 위한 것이다.

## 사람에게 알릴 내용 — 변경과 적용 시점을 구분한다

백엔드 하네스는 정책 변경 작업에서 다음 공유 문구를 작성하도록 한다. 팀원에게는 기존 팀 채널이나 회의에서 사람이 전달한다. 메시지 자동 발송은 이번 합의에 포함하지 않는다.

- 변경된 규칙 ID·도메인과 변경 전후
- Android의 화면·요청·오류 처리에 미치는 영향
- 관련 정책 문서·백엔드 PR·공통 하네스 배포 버전
- 합의·구현·병합·배포 중 확인된 상태와 필요한 Android 작업
- 아직 결정되지 않았거나 확인하지 못한 사항

인터뷰에서 합의한 미래 동작을 이미 배포된 API처럼 안내하지 않는다. 문서 전달과 서버 배포도 서로 다른 상태다. 기존 Notion 수동 반영 안내와 Android 공유 안내를 구분한다.

## Android AI에 필요한 작업 시작·재개 절차

설치 시 저장소 최상위 `AGENTS.md`와 `CLAUDE.md`에 공통 진입 구간을 추가하고, 공통 스킬의 Android 실행 절차로 연결한다. 기존 `client/android/`의 지침 파일은 보존한다. 스킬 안에는 클라이언트의 읽기 전용 범위와 정책 확인·적용 안내를 명시한다.

1. 정책에 영향을 받는 작업이면 공통 `business-rules` 스킬과 관련 도메인의 활성 규칙만 읽는다.
2. 작업 시작·재개 시 설치된 공통 하네스 버전과 작업에서 마지막으로 읽은 기준을 확인한다. 최신 원격 상태를 조회할 수 있으면 관련 문서·스킬 변경 여부를 비교한다. 무관한 파일 변경만으로 정책 변경을 주장하지 않는다.
3. 최초 설치 누락·갱신 실패·공통 지침 연결 누락·버전 차이를 구분한다. 개발 브랜치의 자동 병합·리베이스로 해결하지 않는다.
4. 관련 규칙이 바뀌었다면 전후 차이와 현재 작업의 영향을 설명하고 다시 읽는다. 대화의 매 응답마다 전체 정책을 읽지는 않는다.
5. 문서가 없거나 최신 여부를 확인하지 못하면 그 상태를 알린다. API·코드·문서가 충돌하면 영향받는 정책 판단을 임의로 진행하지 않으며, 무관한 작업은 계속할 수 있다.
6. 공통 정책은 읽기 전용으로 활용하고, 마지막으로 읽은 문서 기준과 관련 규칙을 작업 기록에 남긴다.
7. 실제 읽기가 확인된 뒤 사용자에게 확인한 도메인·규칙, 이번 작업에 적용할 핵심 내용, 관련 변경 여부를 짧게 알린다. 필요하면 근거 문서 링크를 붙인다. 최신 여부를 조회하지 못했다면 설치된 버전을 읽었다는 사실과 미확인 상태를 구분한다. 매 응답에 같은 안내를 반복하지 않는다.

AI가 백그라운드에서 변경을 자동 인지하는 것이 아니라, 작업의 특정 시점에 확인하는 절차다.

## 결론과 남은 검증

### 실제 자동 게시 검증을 추가한 이유

사용자는 전용 브랜치에 파일이 실제로 게시됐는지, 문서를 수정했을 때 GitHub Actions가 감지해 자동 push하는지 확인해야 한다고 지적했다. 확인 시점에는 작업 브랜치도 로컬에만 있고 정식 `harness/shared`는 원격에 없다. 기존 로컬 fixture의 24개 테스트 통과를 실제 배포 완료와 구분해야 한다.

이에 현재 작업 브랜치의 push를 별도 `harness/validation-477`로 게시하는 임시 검증 경로를 추가했다. 공통 경로의 정책이 아닌 임시 문서를 추가·수정·삭제하고, 실제 Actions 실행·원본과 배포 SHA·manifest·파일 내용 및 임시 Android 설치를 대조한다. 검증 경로도 같은 검사·추출·게시 코드를 사용하지만 정식 원본·배포 브랜치를 변경하지 않는다.

현재는 검증 경로를 로컬에 준비한 단계이며 커밋·push 승인 전이므로 실제 Actions 결과는 없다. 검증 완료 후 임시 경로를 제거하고, 정식 병합 후 최초 배포를 다시 확인한다. 자세한 순서와 증거 항목은 [실제 검증 절차](../../scripts/shared_harness/README.md#실제-github-actions-사전-검증--준비됨-아직-미실행)에 남긴다. 포트폴리오에는 구현, 로컬 검증, 원격 검증, 팀 적용을 각각 확인된 상태로 구분해 쓴다.

공유를 완성하려면 문서 자동 작성에 더해 공통 하네스 배포, 사람에게 변경 안내, Android AI의 실제 스킬·문서 읽기와 적용 안내가 필요하다. 전용 브랜치는 개발 브랜치마다 문서를 병합하는 부담을 줄일 수 있지만 설치·버전·갱신 실패를 관리해야 한다.

도구는 공통 파일을 cache에 내려받고 프로젝트 내부에 버전별 사본을 만든다. 자동 갱신은 cache만 바꾸며 명시적 `apply`에서 active 연결 하나를 교체한다. 작업 중 정책이 바뀌지 않도록 AI 세션을 정리한 뒤 적용하고 새 세션에서 재개한다. 이는 실행 중인 AI를 자동 감지·종료하는 구조는 아니다.

공통 결정 기록에서 백엔드 캘린더 설계 기록을 참조하는 사실을 링크 검사로 발견해 해당 문서 한 개도 명시적 배포 허용 목록에 포함했다. 기존 지침·동일 이름의 스킬·로컬 수정은 덮어쓰지 않는다. 원격 실패 시 이전 정상 배포본을 유지하고 확인 실패를 구분한다. macOS 로그인용 plist 생성은 구현했으며 실제 등록은 진행하지 않았다.
