# 캘린더에 기록이 있는 달을 알려주는 방법

**상태:** 방향 합의 · 기능 구현 및 테스트 완료, 기존 포맷 검사 실패 확인

**갱신 날짜:** 2026-09-19

**관련 이슈:** [#443](https://github.com/woowacourse-teams/2026-Chalkak/issues/443)

## 처음에는 이전 달의 게시물 존재 여부만 필요하다고 생각했다

처음 구상은 월별 캘린더 응답에 `hasPreviousMonthPosts`를 추가하는 것이었다.

하지만 9월을 보고 있고 기록은 5월과 1월에만 있다면, 바로 전 달인 8월만 확인해서는 과거 기록을 알려줄 수 없다. 조회 범위를 과거 전체로 넓혀도 `true`만으로는 **어느 달에 기록이 있는지** 알 수 없다.

논의하면서 필요한 정보의 범위를 비교했다.

| 방식 | 알 수 있는 정보 | 한계 |
| --- | --- | --- |
| 이전 기록 존재 여부 | 과거에 기록이 있는지 | 기록이 있는 달을 알 수 없음 |
| 가장 가까운 이전 연월 | 다음으로 이동할 과거 기록의 위치 | 여러 달의 기록 여부를 한 번에 표시하기 어려움 |
| 기록이 있는 전체 연월 | 어느 연월에 기록이 있는지 | 게시물 변경 후 목록 갱신이 필요함 |

## 목적은 날짜 선택 화면에 기록 여부를 표시하는 것이다

달력에 처음 들어가면 현재 달이 나타나고, 기존 날짜 선택 버튼으로 다른 연월을 고르는 흐름은 유지한다.

새로 필요한 기능은 **날짜 선택 화면에서 기록이 있는 달을 색상 등으로 표시하는 것**이다. 예를 들어 5월과 1월에 기록이 있다면 해당 달에 표시를 붙인다. 기록이 없는 달도 계속 선택하고 조회할 수 있다.

따라서 서버는 기록이 있는 연월 목록을 제공하고, 구체적인 표시 방식은 안드로이드에서 정한다. 안드로이드 화면 구현은 이번 백엔드 작업에 포함하지 않는다.

## 연월 목록 API를 따로 추가한다

기존 월별 조회 응답에 목록을 넣는 방식도 고려했지만, 날짜 선택에 필요한 정보와 선택한 달의 게시물을 따로 조회하도록 결정했다.

| 역할 | API |
| --- | --- |
| 기록이 있는 연월 목록 조회 — 신규 | `GET /api/v1/posts/calendar/months` |
| 선택한 달의 게시물 조회 — 기존 유지 | `GET /api/v1/posts/calendar?year=2026&month=5` |

이렇게 하면 월을 바꿀 때마다 전체 연월 목록을 다시 받을 필요가 없다. 기존 API 계약을 유지하면서 엔드포인트를 추가하므로 **v1을 유지한다.**

새 API는 연월을 입력받지 않는다. 로그인한 사용자의 전체 기록에서 서버가 연월을 찾아 반환한다.

```json
{
  "months": [
    { "year": 2026, "month": 5 },
    { "year": 2026, "month": 1 },
    { "year": 2025, "month": 12 }
  ]
}
```

## ‘현재 캘린더에서 볼 수 있는 게시물이 있는 달’을 반환한다

과거에 사진을 올렸더라도 지금은 삭제되거나 반려됐다면, 해당 기록만 있는 달은 목록에서 제외한다. 표시된 달을 선택했을 때 실제 캘린더에서 볼 수 있는 기록과 기준을 맞추기 위해서다.

| 항목 | 합의한 기준 |
| --- | --- |
| 사용자 | 로그인한 본인 |
| 조회 기간 | 전체 기간 |
| 날짜 | 제출·승인 시각이 아닌 **주제 날짜** |
| 게시물 상태 | `PENDING`, `APPROVED` |
| 삭제 처리 | 게시물·주제·사진·작성자가 삭제된 경우 제외 |
| 중복 처리 | 같은 연월은 한 번만 반환 |
| 정렬 | 연도·월 기준 **최신순** |

게시물이 하나도 없으면 `200 OK`와 빈 배열을 반환한다.

```json
{
  "months": []
}
```

기록이 없는 현재 달을 목록에 임의로 넣지는 않는다. 목록이 비어 있어도 첫 화면은 기존처럼 현재 달을 보여준다.

## 사진 전체를 가져오지 않고 DB에서 연월만 추출한다

조회는 다음 방식으로 구현했다.

1. 해당 사용자의 게시물 중 조회 가능한 상태와 삭제 조건을 확인한다.
2. 연결된 주제 날짜에서 연도와 월을 추출한다.
3. DB에서 연월 중복을 제거하고 정렬한다.
4. 백엔드는 정리된 연월 목록만 받는다.

사진 테이블은 **삭제 여부를 확인하기 위해 연결**한다. 이미지 파일이나 게시물 전체를 애플리케이션으로 가져오는 방식은 아니다.

저장소 마이그레이션에는 `posts(user_id, moderation_status)` 인덱스가 있어 조회 조건에 활용될 수 있다. 다만 결과가 몇 개월뿐이어도 DB에서는 해당 사용자의 게시물과 연결 정보를 확인해야 한다.

별도 PostgreSQL 18.4 DB에서 합성 데이터로 `EXPLAIN (ANALYZE, BUFFERS)`를 실행했다. Hibernate가 실제 생성한 파라미터 SQL을 사용했으며, 게시물 상태는 `PENDING`과 `APPROVED`를 절반씩 배치했다.

| 측정 항목 | 결과 |
| --- | --- |
| 전체 데이터 | 사용자 100명, 게시물·사진 각각 365,000건, 주제 3,650건 |
| 조회 사용자 | 10년간 게시물 3,650건 |
| 반환 결과 | 연월 121개 |
| SQL 실행 시간 3회 | 24.947ms, 17.992ms, 16.913ms |
| 게시물 탐색 | 기존 `ix_posts_admin_user_moderation_status` 인덱스로 대상 사용자·상태 조회 |
| 사진 탐색 | 병렬 전체 스캔 후 해시 조인 |

이 측정에서는 새 인덱스·집계 테이블·캐시 없이 조회했다. 다만 사진 테이블 전체를 읽는 실행 계획이므로 전체 데이터가 커져도 비용이 일정하다고 볼 수 없다. 데이터 증가나 동시 요청으로 지연이 커지면 실행 계획과 인덱스·집계 필요성을 다시 검토한다.

위 수치는 로컬 합성 데이터의 SQL 실행 시간이며 인증·네트워크·응답 변환을 포함한 API 응답 시간이나 운영 부하 측정값이 아니다. 운영 DB의 인덱스 적용 상태와 실제 안드로이드 연동도 확인하지 않았다.

## 목록 조회 후 기록이 바뀔 수 있다

연월 목록과 월별 게시물은 별도 요청으로 조회한다.

예를 들어 목록을 받은 뒤 5월의 마지막 게시물이 삭제되면, 5월을 선택했을 때 빈 캘린더가 나올 수 있다. 두 요청 사이에 데이터가 바뀐 정상적인 상황이므로 앱에서 빈 결과를 처리해야 한다.

게시물 추가·삭제 후에는 연월 목록도 갱신할 수 있어야 한다.

## 구현과 검증에서 확인한 결과

`PostController → PostQueryService → PostRepositoryImpl → PostJpaRepository`로 새 조회를 연결했다. 저장소에서는 연월만 투영하고 `YearMonth` 목록으로 변환하며, 응답 DTO는 이를 숫자 `year`, `month`로 반환한다. 기존 월별 API의 계약은 유지했다.

저장소·서비스·API 순서로 테스트를 먼저 작성했다. 각각 메서드 부재에 따른 컴파일 실패와 경로 부재에 따른 `404`를 확인한 뒤 구현해 통과시켰다.

- 본인 게시물, 검수 상태, 게시물·주제·사진·작성자 삭제 조건을 검증했다.
- 주제 날짜 기준의 연월 추출, 같은 연월 중복 제거, 연도 구분, 최신순 정렬을 검증했다.
- 마지막 게시물 삭제 시 그 달이 빠지고, 기록이 없으면 현재 달을 추가하지 않는 빈 배열 응답을 검증했다.
- 인증 없는 요청·관리자 토큰·탈퇴 회원은 거절하고, 정지 회원은 기존 캘린더처럼 조회할 수 있음을 검증했다.
- 생성된 OpenAPI의 입력 파라미터 부재, 연월 배열 스키마, 인증·오류 계약을 검증했다.
- Swagger, POST-009 규칙과 정책 결정 기록을 갱신했다.

개인 `.env`와 기존 테스트 DB를 보존하기 위해 동일 소스를 임시 체크아웃과 전용 PostgreSQL DB로 옮겨 검증했다.

| 검사 | 결과 |
| --- | --- |
| 전체 테스트 | 1,313개 통과, 실패·건너뜀 없음 |
| 별도 아키텍처 테스트 | 7개 통과 |
| Checkstyle | 통과 |
| 환경변수 계약 검사와 검사기 사례 | 통과, 사례 20개 |
| 실행 JAR 빌드 | 통과 |
| 하네스 구조 검사·diff 공백 검사 | 통과 |
| Spotless | 실패 — 변경 전 `be/develop`에서도 재현되는 기존 포맷 위반 |

**전체 검증 명령은 Spotless 때문에 실패했다.** 포맷 검사 실패를 통과로 처리하거나 무관한 파일을 일괄 수정하지 않았다. 이 한계가 남아 있어 기록 상태는 `방향 합의`로 유지한다. 실제 안드로이드 연동과 운영 부하 검증은 수행하지 않았다. PR 병합과 배포 상태는 GitHub에서 별도로 확인한다.
