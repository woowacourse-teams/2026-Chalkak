# 기기 등록과 회원 탈퇴에서 로그인 잠금 순서를 맞추는 이유

**갱신 날짜:** 2026-09-30

**관련 이슈:** [#491](https://github.com/woowacourse-teams/2026-Chalkak/issues/491)

## 한 휴대폰에서도 자동 등록과 탈퇴 요청이 겹칠 수 있다

기기 등록 코드를 읽으면서 “로그인 ID를 왜 정렬해서 잠그는가”라는 질문이 나왔다. 서버가 한 대이고 사용자가 화면을 한 번에 하나씩 조작하더라도, 앱이 자동으로 보내는 기기 등록 요청과 사용자가 보내는 탈퇴 요청은 서버에서 동시에 처리될 수 있다.

설명에는 다음 가상 상황을 사용했다. 실제 운영에서 관찰한 장애는 아니다.

1. 같은 휴대폰의 앱에 FCM 토큰 `T`가 있고, DB에는 이전 로그인 `S1 → T` 연결이 남아 있다.
2. 사용자가 다시 로그인해서 새 로그인 ID `S2`가 생긴다. FCM 토큰은 계속 `T`인 경우다.
3. 앱이 자동으로 `S2`에 `T`를 등록하는 요청 A를 보낸다.
4. 자동 등록 요청이 처리 중인 동안 사용자가 탈퇴하여 요청 B도 도착한다.

`S1`과 `S2`는 로그인 ID이며, `T`는 앱의 푸시 발송 대상 토큰이다. 로그인 ID가 새로 만들어져도 FCM 토큰이 반드시 바뀌는 것은 아니다. 화면 분할이나 사용자의 동시 버튼 조작을 전제로 한 예시도 아니다.

현재 기기 등록 구현은 이전 연결을 비활성화하고 현재 로그인에 연결하기 위해 `S1`과 `S2`의 잠금을 함께 얻는다. 기존 탈퇴 구현은 해당 회원의 RT를 모두 폐기하기 전에 로그인별 잠금을 얻는다. 두 작업이 같은 두 로그인을 잠그는 상황에서 순서가 중요해진다.

## 현재 로그인부터 잠그면 탈퇴와 반대 순서가 될 수 있다

다음은 정렬을 없애고 등록 요청이 현재 로그인부터 잠근다고 가정한 예시다. 현재 작성한 등록 코드는 이미 정렬하므로, 이 표가 현재 코드에서 교착을 재현했다는 뜻은 아니다. ID 정렬상 `S1`이 `S2`보다 먼저라고 가정한다.

| 순서 | 요청 A: 기기 등록 | 요청 B: 회원 탈퇴 |
| --- | --- | --- |
| ① | 현재 로그인 S2 잠금 획득 | |
| ② | | 정렬 순서대로 S1 잠금 획득 |
| ③ | 이전 연결 S1을 잠그려 하지만 B가 가지고 있어 대기 | |
| ④ | | S2를 잠그려 하지만 A가 가지고 있어 대기 |

```text
A: S2를 가지고 S1을 기다림
B: S1을 가지고 S2를 기다림
```

두 요청이 상대방의 잠금 해제를 기다려 처리를 끝내지 못하는 교착 상태다. PostgreSQL은 교착을 감지하면 한 트랜잭션을 실패시켜 풀지만, 그 요청을 정상적으로 완료하려면 재시도 등의 처리가 필요해진다.

## 같은 순서로 잠그면 한 요청이 처리를 끝낼 수 있다

현재 구현은 등록과 탈퇴에서 로그인 ID 정렬 순서를 맞춘다. 위 예시에서는 둘 다 `S1 → S2` 순서다.

```text
① 등록 요청: S1 잠금 획득
② 탈퇴 요청: S1에서 대기
③ 등록 요청: S2도 잠근 뒤 처리 완료·잠금 해제
④ 탈퇴 요청: S1·S2를 잠그고 처리
```

등록 코드의 `TreeSet`은 현재 로그인 ID와 기존 연결의 로그인 ID를 중복 없이 모으고 정렬하는 역할을 한다. 같은 로그인에 재등록할 때는 하나만 남는다. `Comparator.comparing(UUID::toString)`은 기존 탈퇴 쿼리의 PostgreSQL UUID 정렬 순서에 맞춰 문자열 기준으로 정렬한다.

기존 탈퇴 쿼리는 `ORDER BY sessionId`로 조회한 로그인들을 차례로 잠근다. 여러 대상을 잠그는 경로들이 같은 순서를 사용한다는 것이 핵심이며, `TreeSet` 자체가 필수인 것은 아니다. 이 기준은 [PostgreSQL의 교착 예방 설명](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-DEADLOCKS)과도 일치한다.

이 논의는 이미 여러 로그인 잠금을 사용하는 구조에서 순서를 정하는 이유를 설명한다. 토큰 잠금 자체를 유지할지, 유니크 제약과 충돌 시 재시도로 바꿀지는 별도로 검토할 수 있다. 사용자는 위 예시를 이해하고 기록을 요청했으며, 잠금 전략 전체에 대한 추가 선택을 확정한 것으로 기록하지 않는다.

## 확인한 코드와 검증 범위

- [PushDeviceService#lockSessions](../../src/main/java/com/chalkak/backend/notification/service/PushDeviceService.java): 현재 로그인과 기존 연결의 로그인 ID를 모아 정렬한 뒤 잠근다. 로그인 유효성을 확인한 뒤 기기 연결을 저장한다.
- [UserRefreshTokenJpaRepository#findLiveSessionIdsByOwnerId](../../src/main/java/com/chalkak/backend/auth/infrastructure/persistence/UserRefreshTokenJpaRepository.java): 폐기되지 않은 RT의 로그인 ID를 정렬하여 반환한다. 만료된 RT라도 폐기 시각이 없으면 이 조회 대상에 들어갈 수 있다.
- [RefreshTokenService#revokeAll](../../src/main/java/com/chalkak/backend/auth/service/RefreshTokenService.java): 조회한 순서대로 로그인 잠금을 얻고 RT를 일괄 폐기한다. [UserService#completeWithdrawal](../../src/main/java/com/chalkak/backend/user/service/UserService.java)에서 호출한다.
- [PushDeviceConcurrencyTest](../../src/test/java/com/chalkak/backend/notification/service/PushDeviceConcurrencyTest.java): 같은 토큰의 동시 등록, 같은 로그인의 동시 등록, 두 로그인의 토큰 교환 등록이 통과했다. 순서를 맞춘 기기 등록 코드가 포함된 전체 테스트 1,402건도 통과했다.

위 동시성 테스트에는 **기기 등록과 실제 회원 탈퇴를 동시에 실행하는 사례가 아직 없다.** 정렬을 제거한 상태의 교착 재현이나 운영 발생 빈도 측정도 하지 않았다. 해당 경쟁을 직접 검증한 결과가 생기면 이 문서를 갱신한다.
