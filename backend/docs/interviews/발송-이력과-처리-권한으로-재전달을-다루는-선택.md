# 발송 결과는 기록하고 재처리 상한은 SQS에 맡긴다

- 갱신일: 2026-10-27
- 관련 작업: [#826](https://github.com/woowacourse-teams/2026-Chalkak/issues/826)

## 같은 사건인지 아는 것과 다시 보내지 않는 것은 다르다

회차 사건 ID를 유지하는 첫 단계는 같은 사건을 구분할 뿐이었다. FCM 수락 후 SQS 삭제가 실패하면 같은 메시지가 다시 올 수 있고, 이전 결과가 없으면 Worker는 FCM을 다시 호출한다. 따라서 사건·회원별 완료 기록을 확인하고, 완료한 사건은 새 기기를 등록했더라도 반복하지 않도록 한다.

회원 진행과 기기 결과를 두 테이블에 저장하는 안도 비교했다. 사용자는 한 테이블과 기기 JSON을 선택했다. 회원의 처리 권한과 기기 결과를 함께 찾을 수 있지만, JSON 내부 상태 검증과 부분 갱신을 애플리케이션이 책임져야 한다. 그래서 결과는 타입이 있는 불변 기록으로 읽고, SQL은 한 기기 항목만 갱신한다. 기기 FK는 두지 않아 로그아웃 후에도 결과를 남긴다.

## 사용자 완료보다 기기별 재처리를 우선하도록 바꾼다

초기 구현은 하나라도 수락하면 사용자 작업을 완료했다. 리뷰에서는 이 정책이라면 기기별 JSON의 활용이 작다는 지적을 받았다. 사용자와 재검토해 기기별 기록을 유지하고, 다른 기기의 수락 여부와 관계없이 일시 실패한 기기의 전달 기회를 다시 확보하기로 했다.

수락·영구 실패·무효 토큰·생략 기록이 있는 기기는 다시 보내지 않는다. 현재 등록 기기 중 일시 실패 또는 결과 불명인 기기는 최신 로그인·수신 설정·대상 조건을 확인한 뒤 원래 기한 안에서 재처리한다. 수락 기록 후 중단됐어도 나머지 기기가 남으면 이어 처리하며, 사용자 처리가 완료된 뒤 새로 등록된 기기로 과거 사건을 재발송하지는 않는다. 추가 횟수 제한이나 대상 스냅샷 테이블은 만들지 않는다.

이 변경은 기기별 발송 결과가 다음 동작을 결정하게 하지만, 기기마다 시작·결과 쓰기가 추가되는 비용과 결과 불명 재시도의 중복 가능성은 남긴다. 실제 기기 수신을 보장하는 정책은 아니다. 현재 규칙은 [기기별 재처리 결정](../../../docs/business-rules/decisions/2026-10-27-device-push-retry.md)에 연결한다. 호출 순서 캡슐화와 트랜잭션 통합 등 나머지 구조 리뷰는 다음 단계다.

## 재시도 한도를 여러 곳에 만들지 않는다

별도의 Worker 10회 제한과 결과 불명 2회 제한을 검토했지만, 기존 SQS 최대 수신 10회와 함께 쓰면 한도가 겹치고 이해하기 어려워졌다. 사용자와 이 별도 제한은 추가하지 않기로 했다. 시도 횟수는 조사용으로 기록하고, 일시 실패·결과 불명은 메시지를 남겨 SQS 재처리에 맡긴다. 원래 사건의 30분 기한도 유지한다. DLQ는 실패한 메시지를 격리하며, FCM의 과거 수락 여부나 배너 중복을 해결하는 장치는 아니다.

## 발송 중에는 짧은 DB Lease만 유지한다

두 Worker가 동시에 미완료로 판단하지 않도록 Lease를 확보한다. 유효 기간은 DB 시간 기준 60초이고, 전용 실행기가 30초마다 갱신한다. 기기별 발송 시작과 결과 저장은 현재 토큰과 유효 기간을 조건으로 수행한다. 갱신·기록을 확인하지 못하면 새 기기 발송을 시작하지 않는다. SQS Visibility Timeout과 Lease는 각각 관리하며, 같은 숫자여도 만료가 동시에 일어난다고 가정하지 않는다.

FCM 응답을 기다리는 동안 DB 트랜잭션을 잡아두지는 않는다. 대신 발송 직전 시작 기록과 직후 결과를 각각 저장하므로 DB 조회·쓰기·주기 갱신이 늘어난다. 추가 SQL 비용은 기존 업무 조건 조회 계측과 구분해 성능을 확인해야 한다.

## 실행 흐름과 Lease 관리, JPA 저장소를 구분한다

검토 과정에서 발송 이력 서비스 안에 Lease의 예약·갱신·종료까지 모여 있어 읽기 어렵다는 피드백을 받았다. `PushDeliveryService`에는 완료 기록 확인과 처리 흐름을 두고, `PushDeliveryLease`가 60초 유효 기간·30초 갱신·조건부 결과 저장·권한 반납을 관리하도록 분리했다. SQS 재처리 대기 시간과 DB Lease 유효 기간은 값이 같아도 별개 정책으로 표현한다.

저장소는 기존 프로젝트의 JPA 방식으로 통일한다. `PushDelivery`를 읽기 전용 엔티티로 매핑하고, `PushDeliveryJpaRepository`의 네이티브 쿼리로 현재 Lease 소유권을 검사하며 갱신한다. JSON의 한 기기만 바꾸는 조건은 그대로 유지한다. SQL 이후에는 영속성 컨텍스트를 비워 같은 트랜잭션에서도 이전 조회 결과를 재사용하지 않도록 한다. JDBC의 `RETURNING` 매핑 대신 획득 성공 후 JPA 조회를 사용하므로, 성공적인 권한 획득에는 조회 SQL 한 번이 추가된다.

갱신 실행기는 Worker의 FCM 응답 대기와 독립적으로 동작해야 한다. 전용 스레드 하나를 여러 Lease 갱신에 공유하며, DB 갱신이 늦어져 SQS Visibility Timeout 연장까지 함께 지연되지 않도록 기존 SQS 연장 실행기와 분리해 둔다. 실행기 공유 자체가 불가능한 것은 아니지만 대기 간섭과 종료 순서를 다시 검증해야 한다.

## 모든 중복이 사라졌다고 말하지 않는다

FCM 수락 직후 DB에 저장하기 전에 중단되면 결과를 확정할 수 없다. Lease 토큰도 이미 전송 중인 외부 요청을 취소하지 못한다. 이번 선택은 이 구간의 중복 가능성을 받아들이고 다시 보내는 것이다. 앱 Inbox가 백그라운드 배너 표시까지 막는지는 별도 검증이 필요하다.

## 실제 코드의 처리 흐름

```text
SqsPushService: SQS 메시지 수신·Visibility Timeout 연장 시작
    ↓
PushWorkerService: 메시지 형식·발송 기한 확인
    ↓
PushDeliveryService: 사건·회원의 완료 기록 확인
    ├─ 완료 기록 있음 → 발송 없이 종료 → SQS 삭제
    └─ 미완료 → 아래 기기 처리 진행
    ↓
PushWorkerService: 기기 조회·기기별 최신 발송 조건 확인
    ↓
PushDeliveryLease.startDevice(): 첫 실제 발송 직전에 Lease 획득
    ├─ 다른 Worker의 유효한 Lease → FCM 요청 없이 재처리 대기
    └─ 획득 성공 → 기기 SENDING 기록·커밋
    ↓
DevicePushSender: FCM 동기 요청·응답 대기
    ※ DB 연결은 계속 점유하지 않으며, 필요하면 별도 실행기가 Lease 갱신
    ↓
PushDeliveryLease.recordResult(): 내 토큰·유효 기간 확인 후 결과 저장
    ※ 예상하지 못한 SDK 예외는 recordUnknown()으로 결과 불명 기록
    ↓
PushWorkerService: 현재 대상 기기들의 결과 집계
    ↓
PushDeliveryService: 재시도할 현재 대상이 없으면 처리 완료, 남아 있으면 미완료 유지
    ↓
PushDeliveryLease.close(): 갱신 예약 취소·보유한 미완료 Lease 해제
    ↓
SqsPushService: Visibility Timeout 자동 연장 종료
    ├─ 완료 → 메시지 삭제
    └─ 재처리 → 메시지 유지·기존 정책의 대기 시간 설정
```

최신 조건에서 모든 기기가 생략되면 새 이력이나 Lease 없이 종료할 수 있다. 따라서 `COMPLETED`는 처리 종료이며 FCM 수락 여부와 구분한다. 기본 메시지 검증이나 기한 확인에서 종료한 경우도 SQS 메시지를 삭제한다.

코드는 [PushWorkerService](../../src/main/java/com/chalkak/backend/notification/service/PushWorkerService.java) → [PushDeliveryService](../../src/main/java/com/chalkak/backend/notification/service/PushDeliveryService.java) → [PushDeliveryLease](../../src/main/java/com/chalkak/backend/notification/service/PushDeliveryLease.java) → [조건부 저장 쿼리](../../src/main/java/com/chalkak/backend/notification/infrastructure/persistence/PushDeliveryJpaRepository.java) 순서로 읽는다.

## 먼저 처리 중으로 저장하면 충분한가

단순히 조회한 뒤 `SENDING`을 저장하면 두 Worker가 모두 비어 있는 상태를 읽을 수 있다. 현재 구현은 DB의 조건부 UPDATE로 미완료이고 Lease가 없거나 만료된 행만 확보한다. 변경된 행이 1개인 Worker만 진행하며, 다른 Worker는 계속 DB를 조회하며 기다리지 않고 현재 처리를 끝내 SQS 재전달에 맡긴다.

획득 시 `status=PROCESSING`, 이번 시도의 `lease_token`, DB 현재 시각부터 60초 뒤의 `lease_until`을 저장한다. 처리 중에는 30초마다 같은 토큰·아직 유효한 Lease인지 확인하며 만료 시각을 갱신한다. 조회 폴링이 아니라 주기적 갱신이며, 30초 전에 종료하면 갱신 요청은 실행되지 않는다. 갱신 실패 또는 권한 확인 불가 시 새 발송을 멈추고, 늦게 도착한 결과의 저장도 조건부 UPDATE로 거절한다.

행 잠금으로도 동시에 처리할 Worker를 제한할 수 있다. 다만 FCM 응답과 결과 저장까지 잠금을 유지하면 그동안 DB 연결도 점유한다. Lease는 이를 짧은 DB 작업으로 나누는 대신 토큰·만료·갱신·복구 코드와 추가 SQL 비용을 감수한 선택이다. Worker의 FCM 호출은 여전히 동기 방식이며, 일반 Worker 스레드는 응답을 기다리는 동안 해당 작업에 묶인다. Lease 도입 자체가 비동기 발송이나 더 나은 성능을 증명하는 것은 아니다.

## 보관과 확인한 범위

발송 이력도 현재 알림함과 같이 매일 04:50 KST에 정리한다. 일반·정지 회원은 이력 생성 후 30일, 탈퇴 회원은 탈퇴 후 30일을 보관한다. 정확한 경계에는 보관하고, 유효한 DB Lease가 있으면 만료·해제 후 다음 정리까지 남긴다. 기기 JSON은 행과 함께 삭제한다. `notifications`의 SQS 발행 상태와 별개이므로 알림함이 없는 주제·리마인더 이력도 독립적으로 정리한다.

로컬 PostgreSQL과 실제 Worker를 연결해 다음을 검증했다.

- 같은 사건·회원의 동시 획득과 완료 기록 재사용. 수락 기기 기록은 재전달에서 해당 기기의 재발송을 막는다.
- 시작 기록 저장 실패 시 FCM 미호출, 수락 결과 저장 실패 시 미완료 유지.
- SQS 삭제 실패 후 동일 메시지·새 메시지 ID로 재발행된 같은 사건 모두 FCM 재호출 없이 삭제 재시도.
- 중단 후 남은 `SENDING`·수락 기록을 구성하고 새 서비스 객체로 복구: 유효한 Lease 동안 대기, 만료 후 미확정 시도만 재발송.
- A의 만료 뒤 B가 처리 중일 때 A의 응답을 돌려주어, A의 결과 기록·종료가 B의 Lease와 상태를 덮어쓰지 못함을 확인.
- 일반·정지·탈퇴 회원의 보관 경계, 유효한 Lease 보호와 만료된 이력 삭제.

근거는 [Worker 테스트](../../src/test/java/com/chalkak/backend/notification/service/PushWorkerServiceTest.java), [Lease 테스트](../../src/test/java/com/chalkak/backend/notification/service/PushDeliveryServiceTest.java), [저장소 테스트](../../src/test/java/com/chalkak/backend/notification/infrastructure/persistence/PushDeliveryRepositoryImplTest.java), [정리 테스트](../../src/test/java/com/chalkak/backend/notification/infrastructure/infra/NotificationCleanupSchedulerTest.java)에 있다. 3단계 Worker 테스트 58개와 아키텍처 12개가 통과했다. 보관 변경에서는 정리 21개·저장소 10개를 확인했다. 개인 환경변수 계약 검사는 기존 누락 키 때문에 제외했다.

**검증 범위:** SQS·FCM은 모의 응답이고 프로세스 중단은 남는 DB 상태로 재현했다. 실제 프로세스 강제 종료·AWS 재전달·기기 배너·운영 부하 검증을 수행한 것은 아니다. 아직 미배포이며, Lease 갱신 지연과 추가 DB 비용은 운영 적용 전후 별도 확인해야 한다. 현재 정책은 [NOTIFICATION-008](../../../docs/business-rules/rules/notification.md), 조사 순서는 [발송 조사 문서](../../deploy/docs/notification-investigation.md)를 따른다.
