# 발송 결과는 기록하고 재처리 상한은 SQS에 맡긴다

- 갱신일: 2026-10-26
- 관련 작업: [#826](https://github.com/woowacourse-teams/2026-Chalkak/issues/826)

## 같은 사건인지 아는 것과 다시 보내지 않는 것은 다르다

회차 사건 ID를 유지하는 첫 단계는 같은 사건을 구분할 뿐이었다. FCM 수락 후 SQS 삭제가 실패하면 같은 메시지가 다시 올 수 있고, 이전 결과가 없으면 Worker는 FCM을 다시 호출한다. 따라서 사건·회원별 완료 기록을 확인하고, 완료한 사건은 새 기기를 등록했더라도 반복하지 않도록 한다.

회원 진행과 기기 결과를 두 테이블에 저장하는 안도 비교했다. 사용자는 한 테이블과 기기 JSON을 선택했다. 회원의 처리 권한과 기기 결과를 함께 찾을 수 있지만, JSON 내부 상태 검증과 부분 갱신을 애플리케이션이 책임져야 한다. 그래서 결과는 타입이 있는 불변 기록으로 읽고, SQL은 한 기기 항목만 갱신한다. 기기 FK는 두지 않아 로그아웃 후에도 결과를 남긴다.

## 재시도 한도를 여러 곳에 만들지 않는다

별도의 Worker 10회 제한과 결과 불명 2회 제한을 검토했지만, 기존 SQS 최대 수신 10회와 함께 쓰면 한도가 겹치고 이해하기 어려워졌다. 사용자와 이 별도 제한은 추가하지 않기로 했다. 시도 횟수는 조사용으로 기록하고, 일시 실패·결과 불명은 메시지를 남겨 SQS 재처리에 맡긴다. 원래 사건의 30분 기한도 유지한다. DLQ는 실패한 메시지를 격리하며, FCM의 과거 수락 여부나 배너 중복을 해결하는 장치는 아니다.

## 발송 중에는 짧은 DB Lease만 유지한다

두 Worker가 동시에 미완료로 판단하지 않도록 Lease를 확보한다. 유효 기간은 DB 시간 기준 60초이고, 전용 실행기가 30초마다 갱신한다. 기기별 발송 시작과 결과 저장은 현재 토큰과 유효 기간을 조건으로 수행한다. 갱신·기록을 확인하지 못하면 새 기기 발송을 시작하지 않는다. SQS Visibility Timeout과 Lease는 각각 관리하며, 같은 숫자여도 만료가 동시에 일어난다고 가정하지 않는다.

FCM 응답을 기다리는 동안 DB 트랜잭션을 잡아두지는 않는다. 대신 발송 직전 시작 기록과 직후 결과를 각각 저장하므로 DB 조회·쓰기·주기 갱신이 늘어난다. 추가 SQL 비용은 기존 업무 조건 조회 계측과 구분해 성능을 확인해야 한다.

## 실행 흐름과 Lease 관리, JPA 저장소를 구분한다

검토 과정에서 발송 이력 서비스 안에 Lease의 예약·갱신·종료까지 모여 있어 읽기 어렵다는 피드백을 받았다. `PushDeliveryService`에는 완료 기록 확인과 처리 흐름을 두고, `PushDeliveryLease`가 60초 유효 기간·30초 갱신·조건부 결과 저장·권한 반납을 관리하도록 분리했다. SQS 재처리 대기 시간과 DB Lease 유효 기간은 값이 같아도 별개 정책으로 표현한다.

저장소는 기존 프로젝트의 JPA 방식으로 통일한다. `PushDelivery`를 읽기 전용 엔티티로 매핑하고, `PushDeliveryJpaRepository`의 네이티브 쿼리로 현재 Lease 소유권을 검사하며 갱신한다. JSON의 한 기기만 바꾸는 조건은 그대로 유지한다. SQL 이후에는 영속성 컨텍스트를 비워 같은 트랜잭션에서도 이전 조회 결과를 재사용하지 않도록 한다. JDBC의 `RETURNING` 매핑 대신 획득 성공 후 JPA 조회를 사용하므로, 성공적인 권한 획득에는 조회 SQL 한 번이 추가된다.

갱신 실행기는 Worker의 FCM 응답 대기와 독립적으로 동작해야 한다. 전용 스레드 하나를 여러 Lease 갱신에 공유하며, DB 갱신이 늦어져 SQS Visibility Timeout 연장까지 함께 지연되지 않도록 기존 SQS 연장 실행기와 분리해 둔다. 실행기 공유 자체가 불가능한 것은 아니지만 대기 간섭과 종료 순서를 다시 검증해야 한다.

## 모든 중복이 사라졌다고 말하지 않는다

FCM 수락 직후 DB에 저장하기 전에 중단되면 결과를 확정할 수 없다. Lease 토큰도 이미 전송 중인 외부 요청을 취소하지 못한다. 이번 선택은 이 구간의 중복 가능성을 받아들이고 다시 보내는 것이다. 앱 Inbox가 백그라운드 배너 표시까지 막는지는 별도 검증이 필요하다.

2단계의 실제 PostgreSQL 테스트로 완료 기록 재사용·동시 획득·기기별 부분 성공·갱신과 만료·늦은 기록 거부를 확인했다. 시작 기록 저장 실패 시 FCM을 호출하지 않고, 수락 뒤 결과 저장이 실패하면 FCM 수락 로그를 유지하면서 완료로 확정하지 않는 경로도 검증한다. SQS 삭제 실패와 프로세스 중단의 추가 장애 재현은 3단계, 최종 문서 대조는 4단계에 남긴다. 보관·탈퇴 정리는 사용자 요청으로 앞당겨, 현재 알림함과 같은 30일 보관·매일 04:50 정리를 연결했다. 일반 회원은 이력 생성 시각, 탈퇴 회원은 탈퇴 시각을 기준으로 하며 유효한 Lease가 있는 기록은 보호한다. 현재 규칙과 한계는 [NOTIFICATION-008](../../../docs/business-rules/rules/notification.md)을 따른다. 실제 AWS·FCM·운영 검증 완료를 뜻하지 않는다.
