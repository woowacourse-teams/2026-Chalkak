# 발송 결과는 기록하고 재처리 상한은 SQS에 맡긴다

- 갱신일: 2026-10-27
- 관련 작업: [#826](https://github.com/woowacourse-teams/2026-Chalkak/issues/826), [#830](https://github.com/woowacourse-teams/2026-Chalkak/pull/830)

## 같은 사건인지 아는 것과 다시 보내지 않는 것은 다르다

같은 설정·예정 시각의 사건 ID를 유지하면 재시작 후 같은 회차를 구분할 수 있다. 하지만 FCM 수락 후 SQS 삭제가 실패하거나 Relay가 같은 사건을 재발행하면, Worker는 이전 발송 결과도 확인해야 한다. 단일 `push_deliveries`에 사건·회원별 한 행을 저장하고 기기 결과를 JSON으로 남기는 선택은 유지한다.

초기 구현은 하나라도 수락하면 사용자 작업을 완료했다. 리뷰에서 기기 JSON의 효용을 재검토했고, 사용자는 기기별 기록을 유지하며 일시 실패 기기를 다시 처리하기로 했다. 수락·영구 실패·무효 토큰·생략 결과가 있는 기기는 건너뛴다. 현재 등록 기기 중 일시 실패·결과 불명 기기는 최신 조건을 확인해 다시 처리한다. 재처리할 현재 대상이 없으면 사용자 작업을 완료한다. 완료 뒤 새 기기가 생겨도 과거 사건을 다시 보내지는 않는다.

대상 스냅샷이나 별도 기기 이력 테이블은 만들지 않는다. 기기 FK도 두지 않아 로그아웃 후 결과가 남는다. 도메인은 타입이 있는 불변 기기 결과를 검증하고, 저장소는 JSON 한 항목만 갱신한다. 저장 성공 후 메모리의 결과도 반영해 같은 실행에서 수락한 기기를 다시 시작하지 않는다.

## DB Lease가 꼭 필요한 운영 범위인가

처음에는 DB에 60초 처리 권한을 기록하고 30초마다 갱신했다. 조건부 UPDATE의 토큰·만료 검사로 동시에 처리할 Worker를 제한하고, 중단 후 권한 만료를 복구 기준으로 삼았다. FCM 대기 중 DB 행 잠금을 계속 유지하지 않는 대신 갱신 실행기·만료·인계·늦은 결과 거절 코드가 필요했다.

리뷰어는 실제 중복 빈도나 DB 비용의 측정 없이 이 복잡도를 도입할 근거가 있는지 지적했다. 사용자는 현재 앱 프로세스가 하나이고 Worker 스레드가 두 개라는 운영 전제를 확인했다. 그래서 기기 기록과 재처리 정책은 유지하면서, 현재 JVM의 스레드 간 동시 발송은 사건·회원별 Java 락으로 제어하기로 했다. Lease 없이도 중단된 작업의 재처리 기회는 SQS가 제공하며, 새 프로세스는 DB의 기기 결과로 다시 판단한다.

이 선택은 모든 중복 제어를 없애는 것이 아니다. 완료 기록 조회 전에 락을 획득해 두 스레드가 모두 미완료로 보고 발송하는 상황을 막는다. 같은 키가 진행 중이면 기다리며 Worker를 점유하지 않고 기존 SQS 재처리로 넘긴다. 다른 사건이나 회원은 병렬 처리한다. Java 락의 획득·해제·레지스트리 제거는 같은 짧은 모니터로 보호한다. 작업 도중 다른 락 객체가 생기는 경쟁을 막고, 끝난 키를 계속 메모리에 쌓지 않기 위해서다. FCM 호출 동안 레지스트리 모니터는 잡지 않는다.

## 어디에서 락을 잡고 DB 연결은 언제 반환하는가

```text
SqsPushService: 메시지 수신·Visibility Timeout 자동 연장
    ↓
PushWorkerService: 메시지 형식·원래 발송 기한 확인
    ↓
PushDeliveryService: eventId + userId의 Java 락 획득
    ├─ 이미 진행 중 → 메시지 유지·기존 SQS 재처리
    └─ 획득 → DB 완료 기록 조회 (행이 없어도 락 획득 가능)
         ├─ 완료 → FCM 재호출 없이 종료
         └─ 미완료 → 기기 목록·각 기기의 최신 발송 조건 확인
    ↓
PushDeliveryAttempt.send(): 이력 없으면 생성 + 기기 SENDING 저장을 함께 커밋
    ↓
DevicePushSender: FCM 동기 호출 (DB 트랜잭션 밖)
    ↓
PushDeliveryAttempt: 해당 기기 결과를 즉시 별도 저장
    ※ SDK 예외는 UNKNOWN 기록, 기록 저장 실패는 현재 사용자 처리를 중단
    ↓
현재 기기 결과 집계: 재처리 대상이 없으면 사용자 완료, 남으면 PENDING 유지
    ↓
finally: Java 락 해제·메모리에서 키 제거
    ↓
SqsPushService: 자동 연장 종료 → 완료면 삭제, 재처리면 메시지 유지
```

락은 DB 행이 아니라 JVM 메모리의 객체에 건다. FCM 응답을 기다리는 동안 Java 락은 유지하지만 저장소 메서드별 트랜잭션은 이미 종료돼 DB 연결을 계속 점유하지 않는다. 이력 생성과 SENDING 저장은 처음에는 따로 커밋했다. 이후 사용자가 통합 작업을 재개해 `TransactionTemplate`으로 첫 준비를 한 트랜잭션에 묶었다. 저장소의 기존 REQUIRED 트랜잭션은 이 준비 범위에 참여한다. 시작 기록이나 준비 커밋이 실패하면 신규 이력 생성도 롤백하고 FCM을 호출하지 않는다. 기존 기기의 수락 기록은 앞서 커밋됐으므로 후속 기기 준비 실패로 롤백하지 않는다. 이후 기기 결과는 즉시 별도 커밋하고, 전체 기기 처리 후 사용자 완료도 별도 커밋한다.

```text
[조회 트랜잭션들] 완료 이력·기기 목록·각 기기의 최신 조건 확인
[첫 준비 트랜잭션] 이력 없으면 생성 + SENDING 저장 → 함께 커밋
[트랜잭션 밖] FCM 요청·응답 대기
[결과 트랜잭션] 해당 기기 결과 저장 → 커밋
[완료 트랜잭션] 재처리할 기기가 없으면 사용자 완료 → 커밋
```

진입점에는 `Propagation.NEVER`를 적용했다. 상위 트랜잭션에 발송 흐름 전체가 합류해 FCM 대기 동안 DB 연결을 점유하지 않도록, 기존 트랜잭션이 있으면 발송 전 거절한다. 현재 Worker는 트랜잭션 밖에서 이 서비스를 호출한다. 이는 준비·결과 저장의 짧은 트랜잭션을 금지하는 설정이 아니다. 준비 제한은 기존 저장소와 같은 5초이며, FCM 전체 호출의 제한 시간은 아니다. 커밋 범위를 줄였다는 이유만으로 실제 성능 향상을 측정했다고 주장하지 않는다.

코드는 [Worker](../../src/main/java/com/chalkak/backend/notification/service/PushWorkerService.java) → [이력 서비스](../../src/main/java/com/chalkak/backend/notification/service/PushDeliveryService.java) → [Java 락](../../src/main/java/com/chalkak/backend/notification/service/PushDeliveryLocks.java) → [기기 발송 기록](../../src/main/java/com/chalkak/backend/notification/service/PushDeliveryAttempt.java) → [부분 갱신 쿼리](../../src/main/java/com/chalkak/backend/notification/infrastructure/persistence/PushDeliveryJpaRepository.java) 순서로 읽는다.

## 재시도 상한과 보관 정책은 유지한다

별도 Worker 10회·결과 불명 2회 제한은 추가하지 않는다. 일시 실패·결과 불명은 기존 SQS 최초 포함 최대 수신 10회, 원래 사건의 30분 기한, Retry-After 안에서 재처리한다. JSON의 시도 횟수는 시작 기록 수이며 SDK 내부 HTTP 횟수나 SQS 수신 횟수가 아니다. 최신 조건에서 기기가 모두 생략되면 새 이력 없이 종료할 수 있고, COMPLETED도 실제 기기 수신 성공이 아닌 처리 종료를 뜻한다.

SQS Visibility Timeout은 기존 60초·처리 중 40초마다 연장을 유지한다. DB Lease와 갱신 실행기는 제거한다. 새 마이그레이션은 이전 PROCESSING 행을 PENDING으로 바꾸고 기기 JSON·완료 이력을 보존한다. 이력 정리는 매일 04:50 KST, 일반·정지 회원 생성 후 30일·탈퇴 회원 탈퇴 후 30일이며 경계 시각은 보관한다. 현재 유효한 발송은 30분 기한이므로 정상 사건이 30일 전 이력을 발송 중인 상황을 전제로 하지 않는다. Lease에 따른 추가 보관 유예는 제거했다.

## 남는 한계와 검증 범위

이 Java 락은 같은 서비스 빈을 공유하는 하나의 JVM에만 유효하다. 프로세스를 늘리거나 배포 중 두 프로세스의 Worker를 겹쳐 실행하기 전에 제어 방식을 재검토해야 한다. 외부 요청 타임아웃도 필요하다. 이미 전송 중인 FCM 요청을 취소하거나 과거 수락 여부를 복원하는 기능은 아니다.

FCM 수락 후 DB 기록 전에 중단되면 수락 여부를 모른다. 다음 처리에서 다시 보내는 정책이므로 중복 가능성이 남는다. 앱 Inbox의 백그라운드 배너 중복 차단도 별도 확인 대상이다. Exactly-once 보장이나 추가 SQL 비용·실제 성능 개선을 주장하지 않는다.

검증 대상은 같은 키의 중복 진입·서로 다른 키의 병렬 처리, 예외 후 락 재사용과 유휴 키 제거, 기기별 결과 보존과 미완료 기기 재처리, SQS 삭제 실패 후 재전달·재발행, 재시작 뒤 남은 SENDING·수락 기록 복구, 보관 경계와 마이그레이션의 기기 결과 보존이다. 테스트는 [이력 서비스](../../src/test/java/com/chalkak/backend/notification/service/PushDeliveryServiceTest.java), [락 경쟁](../../src/test/java/com/chalkak/backend/notification/service/PushDeliveryLocksTest.java), [Worker](../../src/test/java/com/chalkak/backend/notification/service/PushWorkerServiceTest.java), [저장소](../../src/test/java/com/chalkak/backend/notification/infrastructure/persistence/PushDeliveryRepositoryImplTest.java)에 연결한다.

로컬 PostgreSQL과 모의 SQS·FCM으로 Java 락 전환에서 관련 테스트 833개와 아키텍처 12개, 컨벤션 검사가 통과했다. 이후 트랜잭션 통합에서는 신규·기존 수락 이력의 준비 롤백, 커밋 시점 실패, FCM 트랜잭션 밖 실행, 상위 트랜잭션 진입 거절까지 검증했고 관련 테스트 836개·아키텍처 12개·컨벤션 검사가 통과했다. 초기 병렬 테스트의 회원 fixture는 사인 저장 키가 중복되어 수정했다. 실제 강제 종료·AWS·기기 수신·운영 부하 검증과는 구분한다. 현재 규칙은 [NOTIFICATION-008](../../../docs/business-rules/rules/notification.md), 조사 순서는 [발송 조사 문서](../../deploy/docs/notification-investigation.md)를 따른다.
