# 로그인 폐기를 인증과 푸시가 함께 처리하는 방법

**갱신 날짜:** 2026-10-01

**관련 이슈·PR:** [#491](https://github.com/woowacourse-teams/2026-Chalkak/issues/491), [#508](https://github.com/woowacourse-teams/2026-Chalkak/pull/508)

## 로그인 ID 연결을 유지하면서 처리 책임을 정리한다

PR 리뷰에서 인증 서비스가 푸시 저장소를 직접 호출하고, 푸시 등록 서비스도 인증의 저장소와 잠금 구현을 직접 사용하는 구조를 지적했다. 재사용·만료 분기가 RT만 폐기하고 기기를 해제하지 않는 누락도 발견했다.

리뷰의 A안은 `login_sessions`를 제거하고 푸시 기기에 회원 ID와 로그인 ID를 직접 저장하는 방법이다. 테이블과 저장 순서는 줄지만 로그인 ID의 외래키 보장을 등록 시 서버 검증으로 대신해야 한다. B안은 인증이 로그인 종료 인터페이스를 호출하고 푸시가 구현하는 방법이다. 두 안은 함께 적용할 수 있지만 서로를 전제로 하지는 않는다. 폐기 누락의 직접 원인은 테이블 자체가 아니라 일부 분기가 기기 해제 경로를 거치지 않는 것이다.

사용자는 설명의 ② 의존 분리, ③ 폐기 경로 통합, ④ 토큰 생성·발급 정리를 순서대로 수정하고 각 단위를 검토한 뒤 커밋·푸시하도록 요청했다. 이번 범위에서는 `login_sessions`와 기존 JWT 호환을 유지한다. A안의 테이블 제거는 진행하지 않는다.

## 두 기기 해제 메서드는 기존 서비스에 둔다

처음 구현은 로그인 종료 인터페이스와 푸시 구현 클래스를 추가했다. 사용자는 이미 푸시 저장소를 가진 서비스가 있는데 두 기기 해제 메서드를 위해 별도 추상화와 클래스를 추가할 필요가 있는지 질문하고, 인터페이스 구현도 없이 기존 서비스의 행동으로 두도록 수정했다.

기존 푸시 저장소도 인터페이스여서 인증은 이미 DB 구현을 알지 못했다. 새 인터페이스가 추가로 숨기는 것은 DB 기술이 아니라 푸시라는 기능에 대한 직접 의존이다. 현재 연결 기능이 푸시 하나이고 각 정리가 단순한 저장소 호출이므로, 사용자는 그 의존을 유지하고 코드 탐색 단계와 클래스를 줄이는 방향을 선택했다.

[UserRefreshTokenService](../../src/main/java/com/chalkak/backend/auth/service/UserRefreshTokenService.java)는 [PushDeviceService](../../src/main/java/com/chalkak/backend/notification/service/PushDeviceService.java)의 `disableBySessionId`, `disableByUserId`를 직접 호출한다. 기기 비활성화와 FCM 원문·해시 제거는 이 서비스가 기존 저장소를 사용해 수행한다. 별도 리스너 인터페이스와 구현 클래스는 제거했다. 인증과 푸시의 패키지 의존을 단방향으로 만든 것은 아니며, 기기 저장소 직접 호출을 서비스 호출로 정리한 것이다.

호출은 비동기 이벤트가 아니라 같은 트랜잭션에서 수행하는 일반 메서드 호출이다. 기기 정리가 DB 오류로 실패하면 RT 폐기도 롤백하는 기존 규칙을 유지한다. 관리자 토큰 폐기는 회원 기기 정리와 연결하지 않는다.

기기 등록의 로그인 잠금·소유자·RT 유효성 검증은 [LoginSessionService](../../src/main/java/com/chalkak/backend/auth/service/LoginSessionService.java)가 담당한다. 여러 로그인 잠금은 기존 UUID 정렬 순서를 유지한다. 호출자가 시작한 트랜잭션을 필수로 사용하여 기기 저장까지 잠금이 유지되게 한다. 푸시는 대상 로그인 ID를 전달하며 advisory lock 키나 유효한 RT의 조건을 직접 사용하지 않는다.

## 폐기 누락과 코드 정리는 별도 단위로 검증한다

첫 단위는 기존 로그아웃·전체 폐기의 연결과 등록 검증 책임을 옮기는 구조 변경이다. 이 단위에서는 재사용·만료의 기기 정리를 변경하지 않았다.

수정한 첫 단위에서 전체 테스트 1,486건과 아키텍처 테스트 7건이 통과했다. 기존 등록 검증·토큰 이전·등록 동시성, 로그아웃과 탈퇴의 해제·DB 오류 롤백·동시 요청 테스트를 다시 실행했다. 기기 등록 서비스가 인증 저장소를 직접 참조하지 않는 것도 확인했다.

둘째 단위에서는 [PushDeviceRefreshRevocationTest](../../src/test/java/com/chalkak/backend/notification/service/PushDeviceRefreshRevocationTest.java)를 먼저 작성했다. 기존 코드에서 재사용·비활동 만료·절대 만료 요청이 모두 401을 반환하고 RT는 폐기됐지만 기기 비활성화 시각이 비어 있어 세 테스트가 실패했다. 환경 오류가 아니라 실제 기기 해제 누락을 재현한 결과다.

[RefreshTokenService#refresh](../../src/main/java/com/chalkak/backend/auth/service/RefreshTokenService.java)의 두 실패 분기와 로그아웃은 이제 공통 `revokeSession` 메서드를 호출한다. 회원 구현은 부모의 RT 폐기 후 푸시 서비스를 호출하고, 관리자는 부모의 RT 폐기만 수행한다. 전체 폐기는 기존 `revokeOwner` 경로를 유지한다. 재사용·만료의 인증 오류에도 정리를 커밋하는 기존 `noRollbackFor`를 유지하며, 기기 해제의 DB 오류는 함께 롤백한다.

새 회귀 테스트 10건은 401 응답 후 커밋, 정리 실패 시 롤백, 다른 로그인 유지, 정상 갱신, 기기 미등록, FCM 연결 이전, 반복 갱신 거절을 검증했다. 수정 후 전체 테스트 1,496건과 아키텍처 테스트 7건이 통과했다. 기기 해제의 현재 규칙은 [NOTIFICATION-005](../../../docs/business-rules/rules/notification.md#notification-005-현재-로그인-기기-등록해제)에 반영했다.

첫 커밋의 원격 Backend CI에서는 최신 대상 브랜치에 추가된 `AccessLogTest`가 작업 브랜치에서 제거한 1인자 액세스 토큰 발급 메서드를 호출해 테스트 컴파일이 실패했다. 최신 `be/develop`을 병합하고 테스트에 로그인 ID를 전달하는 수정과 원격 코드의 포맷 정리를 함께 커밋했다. `4cb58a6`의 Backend CI와 공통 하네스 검사는 통과했다. 아래 마지막 리팩터링은 아직 커밋·푸시 전이며 원격 CI 결과와 구분한다.

## 토큰 저장 흐름은 유지하고 발급 이름과 생성자를 정리한다

리뷰는 회원 `createToken`이 객체 생성뿐 아니라 로그인 행도 저장하는 점을 지적했다. 마지막 단위에서 저장을 `saveInitialToken`으로 분리했지만, 사용자는 부모의 발급 호출을 두 줄로 나누고 저장 메서드를 추가하는 것이 얼마나 의미 있는지 질문했다. 생성과 저장을 구분하는 효과는 있으나 현재 `createToken`은 최초 발급 한 곳에서만 호출되고, 새 메서드를 따라가는 단계도 늘어난다. 버그나 성능을 해결하는 필수 수정은 아니므로 사용자는 이 분리를 되돌리도록 요청했다.

회원 `createToken`에서 로그인 행을 저장하고 토큰 객체를 반환하면 부모의 `issue`가 RT를 저장하는 기존 흐름으로 복구했다. 추가한 `saveInitialToken`은 부모와 자식에서 모두 제거했다. 생성 메서드 안의 DB 저장은 유지하는 선택이며, 리뷰의 모든 제안을 적용한 것은 아니다. `login_sessions` 외래키와 기존 `saveAndFlush`도 유지한다. RT가 로그인 ID를 UUID로 참조하므로 로그인 INSERT를 먼저 실행해야 한다. 회전은 기존 로그인 ID로 후속 RT만 저장하며 로그인 행을 새로 만들지 않는다.

회원 액세스 토큰 발급은 [AccessTokenIssuer](../../src/main/java/com/chalkak/backend/auth/service/AccessTokenIssuer.java)의 `issueForSession(userId, sessionId)`로 이름을 구분했다. 회원 로그인·가입·갱신과 관련 테스트 호출부를 함께 변경했다. 관리자 및 기존 JWT 호환 검증에서 사용하는 scope 기반 `issue`는 유지했다. JWT 클레임, 만료, API 요청·응답은 바꾸지 않았다.

[IssuedRefreshToken](../../src/main/java/com/chalkak/backend/auth/domain/IssuedRefreshToken.java)의 2인자 생성자는 로그인 ID를 null로 채웠고 운영 코드에서는 사용하지 않았다. 이 생성자를 제거하고 테스트 fixture 6곳에 로그인 ID를 명시했다. 이전 JWT를 받는 `AuthenticatedUser`의 nullable 로그인 ID까지 없애는 변경은 아니다. 로그인 ID가 없는 이전 JWT의 자동 갱신 계약은 유지한다.

마지막 단위의 전체 테스트 1,535건과 아키텍처 테스트 7건이 통과했고 컨벤션 검사와 `bootJar` 빌드도 통과했다. 기존 최초 발급·로그인 FK 저장, 회원·관리자 갱신, JWT 클레임·검증, 이전 JWT 식별, 기기 등록과 폐기 회귀 테스트를 재사용했다. 신규 동작을 추가하지 않아 같은 구현을 따라 쓰는 테스트는 추가하지 않았다. 개인 `.env`의 기존 필수 키 누락 때문에 환경 계약 검사는 제외했고 `.env`를 수정하지 않았다. 마지막 변경의 원격 CI는 승인 후 푸시해야 확인할 수 있다.

자연 만료 시각이 됐다는 이유만으로 기기를 즉시 자동 해제하는 기능이나 실제 FCM 발송은 이번 범위가 아니다. 발송 작업자의 로그인 유효성 확인은 후속 작업에서 다뤄야 한다.
