# 배너 코드의 응집성과 소유 경계를 비교한다

- 갱신일: 2026-10-19
- 관련 이슈: [등록·목록 조회 #676](https://github.com/woowacourse-teams/2026-Chalkak/issues/676), [삭제 #677](https://github.com/woowacourse-teams/2026-Chalkak/issues/677), [앱 조회 #678](https://github.com/woowacourse-teams/2026-Chalkak/issues/678)

앱에서 외부 웹페이지를 배너로 보여주기 위해 제목·부제목·웹뷰 URL·썸네일 URL을 서버에 등록한다. 외부 페이지 배포는 관리자가 별도로 수행한다. 홍보 이외의 콘텐츠도 담으므로 목적을 제한하는 `promotion`이나 앱의 표시 기술인 `webview` 대신 화면에서 보이는 형태인 `banner`를 선택했다.

## 독립 도메인보다 기능을 한곳에서 읽는 데 무게를 뒀다

초기 제안은 엔티티와 앱 조회를 최상위 `banner`에 두고 관리자 서비스를 기존 `admin` 아래에 두는 구조였다. 사용자는 같은 기능이 두 패키지에 분산되는 점을 지적했다. 최상위 `banner` 안에 관리자 Controller까지 모으는 대안도 비교했으나, 처음에는 관리자가 등록·삭제하고 앱은 조회만 하는 단순 콘텐츠라는 점에서 `admin/banner` 아래에 관련 코드를 모으기로 합의했다.

관리자용과 앱용 Controller는 이름과 URI로 구분하고, 공개 API의 접근 권한은 Java 패키지 이름이 아니라 보안 설정으로 결정한다는 점은 유지한다.

## 폴더 검사에서 배너의 경로만 추가한다

기존 아키텍처 테스트는 한 단계 도메인 아래의 Controller와 JPA 저장소만 허용했다. 등록 구현을 검사했을 때 `admin/banner` 경로가 이 조건과 충돌했다. 사용자는 폴더 검사의 이유를 확인한 뒤, 배너 경로를 허용하도록 보완하는 방향을 승인했다.

기존 규칙은 유지하고 `admin/banner`의 Controller·JPA 저장소 위치만 추가했다. 하위 저장소 포트가 JPA를 직접 상속하는 경우도 검사하도록 범위를 보완했다. 기존 위치와 배너 위치의 정상 fixture를 허용하고, 양쪽에서 요청 record·서비스 의존성·저장소·Controller 배치 위반을 각각 거절하는 테스트를 작성했다.

## 리뷰에서 관리자와 앱이 공유하는 콘텐츠의 소유 경계를 다시 정했다

[PR #684](https://github.com/woowacourse-teams/2026-Chalkak/pull/684) 리뷰에서는 배너만 중첩 패키지를 사용해 검사 예외가 필요하고, 앱 조회 코드까지 관리자 하위에 놓이는 점이 지적됐다. 사용자는 기존 선례와 검사 규칙을 제외한 실무적 판단을 요청했다. 관리자와 앱이 함께 사용하는 콘텐츠라는 점에서 엔티티·저장소는 최상위 `banner`가 소유하고, 관리자 Controller·서비스는 `admin`이 담당하는 방향을 선택했다. 코드가 두 곳에 나뉘는 불편을 감수하되 관리 작업의 인증·감사와 배너 자체의 규칙을 구분한다.

현재 엔티티와 저장소를 `banner/domain`, `banner/repository`, `banner/infrastructure/persistence`로, 관리자 API와 서비스는 `admin/api/v1`, `admin/service/banner`로 옮겼다. 저장소가 관리자용 `AdminPage`에 의존하지 않도록 `BannerPage`를 반환한다. 앱 조회 클래스는 후속 #678에서 구현하며 미사용 뼈대를 만들지 않는다. 배너 전용 아키텍처 허용 경로는 제거하고 기존 다섯 규칙을 적용한다. 정상·위반 fixture도 새 배치에 맞춰 검증한다.

페이지 Request는 기본값과 바인딩만 담당하고 페이지 번호·크기·offset 검증은 Service 한곳에 모았다. Swagger에는 허용 범위를 남기며 HTTP 오류 응답이 유지되는지 실제 API 테스트로 확인한다.

## 등록은 사전 중복 검사와 save를 사용한다

처음 구현은 `saveAndFlush`로 고유 제약 오류를 저장소 안에서 변환했다. 사용자는 일반적인 중복도 DB 오류와 로그를 발생시키는 점을 물었고, 사전 검사와 DB 고유 제약의 역할을 구분했다. 사전 검사는 이미 있는 URL을 먼저 거절하고, DB 제약은 검사 이후 겹친 요청을 막는다. URL은 도메인에서 공백을 제거한 뒤 전체 문자열로 조회한다. 초기 구현은 고유 인덱스와 같은 해시 표현식을 조회에도 사용했으나, 리뷰 후 배너 규모를 고려해 단순한 메서드 이름 기반 존재 조회로 변경했다. DB 고유 인덱스는 유지하고 목록 정렬용 인덱스는 제거한다.

AI는 저장소에서 오류를 변환하려면 즉시 flush가 필요하다고 설명했지만, 현재 배너의 DB 생성 UUID 매핑을 확인하지 않은 일반화였다. 별도 임시 테스트로 `save()` 중 INSERT가 실행돼 UUID·생성 시각이 확보되고, 중복도 호출 안에서 발생하며 감사 저장이 가능한 것을 확인해 설명을 정정했다. 사용자가 배너부터 진행하도록 한 뒤 사전 검사와 `save()`로 구현을 정리했다. 저장소의 고유 제약 오류 변환은 유지한다. 이 선택은 현재 신규 배너 매핑에 대한 것이며, 다른 엔티티나 수정 경로의 flush 제거를 승인하거나 검증한 것으로 확대하지 않는다.

현재 등록·관리자 목록 조회의 두 커밋과 PR을 작성했고 리뷰를 반영 중이다. 전체 등록·목록·삭제·앱 조회 기능이 완료된 상태가 아니므로 기록은 방향 합의로 유지한다. 현재 서비스 정책은 [배너 규칙](../../../docs/business-rules/rules/banner.md)이 기준이며, 운영 서버 배포는 아직 수행하지 않았다.

## 남은 리뷰에서는 검증의 실제 실패 경로를 확인했다

유니코드 공백·포트 상한·URL별 오류 메시지는 먼저 실패 테스트를 실행해 문제를 재현했다. 기존 공백 제거 동작을 유지하면서 유니코드 공백을 추가로 제거하고, 명시된 포트의 65535 초과를 거절한다. 웹뷰·썸네일 오류 메시지도 구분한다. 배너와 공지의 해시는 `AdminAuditHash`에서 UTF-8 SHA-256으로 계산하며, 원문 노출과 감사 민감값 검사에 따른 등록 실패를 피하는 기존 정책은 유지한다.

동시성 테스트의 시작 barrier만으로는 두 요청의 사전 조회가 모두 미존재로 끝났는지 보장할 수 없었다. 테스트용 저장소 wrapper는 실제 저장소 조회 결과가 둘 다 false인 시점에 barrier를 통과시키며, 서비스는 요청별 실제 트랜잭션에서 실행한다. 실제 DB로 저장을 위임해 두 번의 저장 시도·한 번의 DB 중복 오류 변환·배너와 감사 각 한 건을 확인했다. 운영 코드에 테스트용 동기화나 Mock 저장소를 넣지 않았다. 인덱스 bytea 변환과 한글 호스트 허용 범위는 사용자와 합의해 유지한다.
