# 기본 GC 로그는 유지하고 조사용 관측은 검증 후 정리한다

갱신: 2026-10-16 KST
관련: [이슈 #654](https://github.com/woowacourse-teams/2026-Chalkak/issues/654), [PR #657](https://github.com/woowacourse-teams/2026-Chalkak/pull/657)

GC 정지와 스왑 활동을 대조하기 위해 기존 memwatch를 보완했다. 처음 이슈에는 영구 systemd 타이머, 증가량 자동 계산, iowait까지 포함했지만, 조사 목적에 비해 작업이 커져 기존 임시 타이머와 누적값 방식을 유지하기로 범위를 줄였다. 리뷰에서는 원래 이슈와 구현의 차이, 인계 문서의 procstat 대체 계획과 실제 memwatch 유지의 모순이 지적됐다.

사용자는 일반 배포가 수집을 끊는지와 조사 도구를 영구 유지할 필요가 있는지를 확인했다. 앱만 재시작하는 일반 배포는 별도 memwatch 타이머를 없애지 않는다. EC2 재부팅이나 중지 후 시작은 임시 타이머를 없애므로 수동 재등록 전까지 관측 공백이 생긴다. 영구 타이머는 이 공백을 줄이지만 조사 기간에만 사용할 도구의 설치·관리 범위를 늘린다.

기본 GC 로그는 다음 지연 사건을 사후 분석할 근거로 유지하기로 했다. 반면 memwatch와 추가 상세 GC·safepoint 로그는 이번 원인 조사와 개선 효과 검증에 사용하고, 검증 후 필요한 근거를 보관한 뒤 제거하거나 기본 수준으로 줄인다. 이 목적에 맞춰 영구 타이머는 추가하지 않고, 조사 중 서버 재부팅 시 재등록과 로그 유입 확인을 필수 수동 작업으로 둔다. 증가량은 동일 실행 구간의 누적값 차이로 분석하며 iowait·procstat은 추가하지 않는다.

운영에서 memwatch와 임시 GC 로그의 CloudWatch 유입, 지표 0과 경보 OK, Slack 수신은 확인했다. 정식 배포 후 GC 시작 옵션 유지와 실제 ALARM 전환 전달은 아직 검증하지 않았다. 조사 종료와 수집 정리도 아직 수행하지 않았다. memwatch의 영구 운영이 필요해지면 자동 복구 여부를 다시 판단한다. 적용·정리 절차는 [GC 관측 런북](../../deploy/docs/gc-monitoring.md)이 기준이다.
