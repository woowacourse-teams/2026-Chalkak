# 알림 폴링 대기를 줄이고 Worker 2개로 시작한다

갱신: 2026-10-15 · [이슈 #655](https://github.com/woowacourse-teams/2026-Chalkak/issues/655)

## 주제 알림이 몰릴 때 승인·반려는 얼마나 기다리는가

주제·승인·반려가 같은 큐와 Worker를 사용한다. 기존에는 한 건을 처리한 뒤 1초를 쉬었다.
주제 100건과 5초 뒤 승인 10건·반려 10건을 넣어, 먼저 쌓인 작업이 후속 알림에 주는 영향을 측정했다.
사용자 약 140명을 고려한 실험 시나리오이며, 실제 최대 동시 유입량을 관측한 수치는 아니다.

실제 개발 SQS와 개발 DB, 100ms 지연을 주는 가짜 FCM을 사용했다. 각 조건에서 워밍업 2회와 본 측정 10회를 진행했다.
1초 대기 단일 Worker의 전체 완료 시간 중앙값은 약 133.85초였다. 대기를 1ms로 줄이면 약 14.60초였다.
이후 같은 CPU·DB 계측을 적용해 Worker 수를 비교했다.

| 계측 조건 | Worker 1개 | Worker 2개 | Worker 4개 |
| --- | ---: | ---: | ---: |
| 전체 완료 시간 중앙값 | 15.19초 | 7.71초 | 5.73초 |
| 승인 지연: 회차별 p95 중앙값 | 9.80초 | 2.39초 | 0.44초 |
| 반려 지연: 회차별 p95 중앙값 | 9.99초 | 2.49초 | 0.51초 |
| 서버 CPU: 회차별 평균의 중앙값 | 15.55% | 26.31% | 32.33% |
| DB 연결 획득 최대 시간 | 2.44ms | 3.05ms | 5.97ms |

지연은 SQS 투입 요청부터 가짜 FCM 수락까지다. 전체 표본을 합친 p95나 휴대폰 수신 시간이 아니다.
서버 CPU에는 DB와 투입 도구도 포함된다. DB 수치는 쿼리 시간이 아닌 Hikari 연결 획득 시간이며, 모든 조건에서 연결 시간초과는 0건이었다.

## 현재는 1ms·Worker 2개를 적용한다

사진 참여자는 주제 알림에서 제외되고, 주제 발송은 하루 많아도 약 3회다.
2개에서 승인·반려 지연이 크게 감소했고, 현재는 동시 외부 요청을 2건으로 제한하는 방향을 선택했다.
4개에서 CPU·DB 포화를 관측한 것은 아니며, 이 결과만으로 2개가 운영 최적값이라고 확정하지 않는다.
2개 실험의 반려 회차별 p95 최대는 3.006초였으므로 모든 회차가 3초 미만을 만족했다고 쓰지 않는다.

전용 스레드 수와 독립 폴링 작업 수를 함께 2개로 맞춘다. 같은 작업 하나의 풀 크기만 늘리면 순차 실행이 유지되기 때문이다.
각 작업은 한 건씩 처리한 뒤 1ms 쉬며, 큐가 비면 기존 20초 롱 폴링을 사용한다. 수신 오류는 별도로 1초 대기해 빠른 오류 반복을 억제한다.

처음에는 `ScheduledTaskRegistrar` 빈에 두 작업을 직접 등록했다. 리뷰에서 컨텍스트 초기화가 끝나기 전에 폴링이 시작될 수 있음을 확인했고, 초기화 실패를 재현한 테스트에서도 두 Worker가 먼저 수신을 시작했다.
[PushWorkerConfiguration](../../src/main/java/com/chalkak/backend/notification/infrastructure/infra/PushWorkerConfiguration.java)에서
[SqsPollingScheduler](../../src/main/java/com/chalkak/backend/notification/infrastructure/infra/SqsPollingScheduler.java) 빈을 두 개 생성하는 방식으로 바꾼다.
각 빈의 `@Scheduled`가 컨텍스트 초기화 완료 후 별도 폴링 작업으로 등록되고, 전용 스케줄러의 종료 관리도 유지된다.
[SqsPushService](../../src/main/java/com/chalkak/backend/notification/infrastructure/infra/SqsPushService.java)는
메시지마다 숨김 연장과 완료 상태를 따로 만들고, 로그 문맥은 처리 스레드에서 복원한다.
Worker 또는 전체 스케줄링을 끄면 폴링 작업을 등록하지 않는다.

## 숨김 연장 실행기는 우선 1개를 유지한다

숨김 시간은 60초이고 40초마다 연장한다. 각 SQS 연장 요청에는 전체·개별 시도 모두 5초 타임아웃이 이미 적용되어 있다.
두 요청이 순서대로 각각 5초를 사용해도 계산상 20초 여유 안에 들어가므로, 이번에는 연장 실행기까지 늘리지 않는다.

로컬 HTTP 서버가 첫 연장 응답을 보류한 상태에서 SDK가 요청을 타임아웃하고, 같은 실행기가 두 번째 메시지의 연장을 이어가는지 검증한다.
테스트는 40초 예약 주기를 기다리는 대신 연장 콜백을 직접 실행한다. 실제 AWS 지연이나 JVM 정지까지 재현하지 않으며, 연장에 실패한 메시지의 재전달을 막는다는 보장도 아니다.

## 검증한 것과 남은 것

- 로컬 가짜 SQS와 Spring 컨텍스트로 두 폴링의 실제 동시 실행, 공용 스케줄러 분리, 작업 비활성화를 검증한다. 초기화 중·초기화 실패 시 수신하지 않는지와 종료 단계에서 다음 폴링을 시작하지 않는지도 확인한다.
- 동시에 처리하는 메시지의 삭제 핸들·숨김 연장·로그 문맥이 분리되고 한쪽 오류가 다른 메시지에 영향을 주지 않는지 회귀 테스트로 확인한다.
- 기존 SQS Standard의 재전달 가능성은 그대로다. 이번 변경이 정확히 한 번 발송을 보장하지 않는다.
- 최종 적용 코드의 CI와 성능 재확인, 실제 FCM·운영 API 동시 부하 검증은 남아 있다. 로컬 전체 검사에는 기존 환경 키·타 영역 포맷 오류가 있다.
- 지속 적체 또는 지연 목표 미달 시 실제 유입량, FCM 응답·제한, DB 대기와 CPU 크레딧을 함께 확인하고 4개 등 대안을 재검토한다.
