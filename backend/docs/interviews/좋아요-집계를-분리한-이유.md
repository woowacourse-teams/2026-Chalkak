# 좋아요 개수를 별도 테이블에서 즉시 집계한 이유

갱신: 2026-11-02 · [이슈 #891](https://github.com/woowacourse-teams/2026-Chalkak/issues/891) · [PR #892](https://github.com/woowacourse-teams/2026-Chalkak/pull/892)

**반복 COUNT의 비용은 개수를 저장해 줄이고, 좋아요 중복·취소 판단은 관계 테이블에 맡긴다.** 별도 집계 테이블은 게시물 행을 직접 증감하지 않기 위한 선택이다. 게시물 수정과의 잠금 충돌까지 없어지는 것은 아니다.

## 출발점은 인기순의 반복 계산 비용이었다

`post_likes`는 누가 어느 게시물에 좋아요했는지 저장한다. 기존 인기순은 해당 주제의 후보 게시물에 연결된 좋아요를 매번 집계한 뒤 정렬했다. 과거 EC2 비교 실험에서는 관계 14만 행의 집계가 집계 테이블 700행 조회로 바뀌며 인기순 지연과 DB CPU가 함께 줄었다. 측정 조건과 결과는 아래에 정리했다.

`post_likes`를 없애면 중복 등록·내 좋아요 여부·취소 대상을 판단할 원본이 사라진다. 관계는 유지하고 `post_like_counts`에 게시물당 한 행을 추가했다. 실제 관계가 추가·삭제된 경우에만 원자적으로 `+1 / -1` 하며, 관계 변경과 집계 갱신은 같은 트랜잭션에서 성공하거나 함께 롤백한다.

## 코드를 따라가면 게시물 잠금이 먼저다

| 작업 | 현재 처리 순서 |
| --- | --- |
| 좋아요 등록·취소 | 공개 게시물 공유 잠금 → 관계 INSERT·DELETE → 실제 변경 시 집계 UPDATE → 개수 조회 → 커밋 |
| 제목 수정 | 게시물 쓰기 잠금 → 제목 변경 → 커밋 |
| 작성자·관리자 삭제 | 게시물 쓰기 잠금 → 게시물·사진 소프트 삭제 → 관계 DELETE → 집계 0으로 초기화 → 커밋 |
| 게시물 생성 | 게시물 `saveAndFlush` → 집계 0행 INSERT → 커밋 |

코드 근거는 [좋아요 서비스](../../src/main/java/com/chalkak/backend/like/service/PostLikeService.java), [게시물 명령 서비스](../../src/main/java/com/chalkak/backend/post/service/PostCommandService.java), [관리자 삭제](../../src/main/java/com/chalkak/backend/admin/service/post/AdminPostCommandService.java), [잠금 선언](../../src/main/java/com/chalkak/backend/post/infrastructure/persistence/PostJpaRepository.java), [집계 SQL](../../src/main/java/com/chalkak/backend/like/infrastructure/persistence/PostLikeCounterJpaRepository.java)이다.

2026-11-02 별도 로컬 PostgreSQL 18.4에서 기존 `PostLikeCounterTransactionTest` 12개가 통과했다. 그중 동시 등록·취소, 작성자 삭제, 관리자 삭제 3개를 SQL 로깅으로 추가 확인했다. 좋아요에서 `FOR SHARE OF p1_0`, 삭제에서 `FOR NO KEY UPDATE OF p1_0`와 집계 UPDATE가 실행됐다. JPA의 `PESSIMISTIC_WRITE`가 항상 SQL의 `FOR UPDATE` 문구로 나오는 것은 아니다. 제목 수정은 같은 저장소의 쓰기 잠금 선언을 코드로 확인했으며, 이번 SQL 관찰 3개에는 포함하지 않았다.

## 분리의 이유와 남아 있는 대기를 구분한다

기존 설명인 **“게시물 수정과 좋아요 갱신 사이의 잠금 충돌을 줄였다”는 표현은 현재 코드의 근거로 사용하지 않는다.** 좋아요의 공유 잠금은 제목 수정·삭제의 쓰기 잠금과 여전히 충돌한다. 먼저 잠근 트랜잭션이 끝날 때까지 다른 작업이 기다릴 수 있다. 이는 좋아요 처리 중 게시물이 삭제되는 상황을 조율하는 기존 장치다.

별도 테이블에서는 좋아요 요청이 `posts`의 공유 잠금을 유지한 채 `post_like_counts`의 개수를 갱신한다. 게시물 공유 잠금을 게시물 쓰기 잠금으로 승격할 필요가 없다. 같은 게시물의 두 좋아요 요청은 공유 잠금을 함께 얻을 수 있고, 집계 UPDATE는 같은 집계 행에서 순서대로 진행된다.

반대로 `posts.like_count`를 두고 현재 공유 잠금 흐름을 그대로 유지한다면, 두 요청이 게시물 공유 잠금을 모두 얻은 뒤 같은 게시물 행을 UPDATE하려고 서로 기다리는 승격 교착이 생길 수 있다. **이는 현재 코드와 PostgreSQL 잠금 충돌표에 따른 설계 분석이며, 게시물 컬럼 방식의 비교 구현·교착 재현 실험을 했다는 뜻은 아니다.** PostgreSQL의 [행 잠금 충돌표와 교착 설명](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)을 기준으로 판단했다.

따라서 선택 이유는 **“현재 게시물 잠금 흐름을 유지하면서 개수 변경 대상을 별도 행으로 분리한다”**이다. 테이블·초기 이관·정합성 관리가 추가되는 비용을 받아들였다. 같은 게시물 집계 행의 UPDATE 경합은 남고, 모든 교착이나 잠금 대기를 해결했다는 보장은 하지 않는다.

## 기존 EC2 비교에서 확인한 효과

합성 사용자 **1,000명·게시물 700개·게시물마다 좋아요 200개(총 14만)**, 같은 로그인 사용자·첫 페이지 20개·**10 RPS**를 고정했다. 최신순과 인기순을 따로 실행하고, 각 구현·정렬마다 워밍업 1분 뒤 3분씩 3회 측정했다. 앱은 같은 테스트 `t4g.small`·JDK 25.0.4·G1·연결 풀 10, DB는 같은 테스트 RDS PostgreSQL 18.4였다. 앱 좋아요 캐시는 없었다.

| 정렬·구현 | p95 / p99 중앙값 | DB CPU | 인기순 순위 SQL 평균 |
| --- | ---: | ---: | ---: |
| 최신순 COUNT | 14.33 / 21.38ms | 6.04% | 해당 없음 |
| 최신순 즉시 집계 | 18.30 / 49.96ms | 6.54% | 해당 없음 |
| 인기순 COUNT | 252.63 / 447.78ms | 81.34% | 164.735ms |
| 인기순 즉시 집계 | 18.87 / 41.79ms | 7.34% | 3.160ms |

인기순 p95는 약 **92.5% 단축**됐다. 표는 회차별 지표 3개의 중앙값이며 전체 요청을 합친 p95가 아니다. 네 조건 모두 HTTP 오류·응답 검사 실패·실행 누락은 0이었다. DB CPU는 본 측정 안에 완전히 들어온 1분 평균 표본 기준이고 순간 최고치가 아니다. 최신순의 API 지연은 개선되지 않았다.

**왜 반복 집계를 병목으로 판단했나?** 같은 데이터에서 인기순 COUNT의 요청을 10 → 12 RPS로 늘리자 p95 2,405.86ms·DB CPU 97.18%·연결 대기 관측 최대 21로 커졌다. 완주 1회는 기준 미달이었고 별도 1회는 오류율 기준으로 중단했다. 당시 완주 회차의 VU 최대 30은 상한 120보다 작았다. 즉시 집계 12 RPS는 3회 통과했고 p95 중앙값은 18.45ms였다. 반복 수가 달라 동등한 3회 개선율로 쓰지는 않지만, SQL 시간·CPU·대기가 함께 커진 구간을 확인한 근거다.

별도 `EXPLAIN ANALYZE`에서도 COUNT 인기순은 인덱스를 사용하면서 좋아요 14만 행을 읽어 700개 게시물로 집계했고, 즉시 집계는 집계 700행을 조인·정렬했다. 이 계획의 실행 시간 190.798 → 3.642ms는 부하 종료 후 따로 측정한 값으로 API p95·측정 중 SQL 평균과 구분한다. 목록 20개의 표시용 COUNT는 4,000관계를 계산했으며, 모든 COUNT가 같은 비용이라는 뜻은 아니다.

## 원본 위치와 비교의 한계

COUNT는 **`1c8e93a0`(2026-10-21)**, 즉시 집계는 **`10b1768e`(2026-10-22)**의 과거 실험이다. 원본은 수정하지 않고 실험 worktree의 `backend/load-test/results/`에 유지했다. 이번에는 10 RPS의 12회 k6 요약과 p95/p99·요청 수를 대조하고 중앙값을 다시 계산했다. JSON·CSV를 이 PR에 복사하지 않고 원본 위치만 남긴다.

원본 루트: `~/.codex/worktrees/chalkak-like-loadtest/2026-Chalkak/backend/load-test/results/`

- `ec2-sync-12rps-u1000-p700-l200-20261022/`: `count10-summary.json`·`sync10-summary.json`, 12 RPS 비교와 안전 중단 기록.
- `ec2-sync-10rps-u1000-p700-l200-20261022/`: 비교 보고서·회차별 k6·DB·런타임 증거·집계 실행 계획.
- `ec2-count-like-density-u1000-p700-20261021/`: COUNT 회차별 원본과 `evidence/likes-200/execution-plans.json`.

운영 사용자 수나 현재 운영 부하가 아닌 **균등한 합성 데이터·워밍업한 같은 첫 페이지**의 결과다. 측정 날짜·JIT·DB 캐시 상태가 다르고, 집계 배포 전 테스트 RDS 내부 관리 DB의 SQL 통계를 한 번 정리한 뒤 누락 감지를 추가했다. 모든 내부 조건이 동일했다고 보장하지 않는다. 현재 운영 데이터 규모를 다시 조회하거나 새 부하를 실행하지 않았다.

## 확인한 범위와 다음 경계

과거 실험은 인기순 COUNT 비용을 줄이는 선택의 근거다. 최신순 API까지 빨라졌다는 결과는 아니며, 이번 PR 통합 코드의 성능 보장이나 운영 트래픽에서의 효과로 표현하지 않는다. 원자적 갱신·롤백·중복·동시 요청은 현재 코드의 기능 테스트와 구분해 확인했다.

현재 좋아요 규칙은 [LIKE-003~005](../../../docs/business-rules/rules/like.md)를 유지한다. 이번 보완에서 Java 코드나 잠금 정책은 바꾸지 않았다. 첫 배포의 구·신버전 쓰기 중첩 문제와 복구 절차 보완은 별도 리뷰 단계에 남아 있다. [전환 문서](../../deploy/docs/like-count-migration.md)의 수동 절차가 자동 배포를 막는 장치라고 해석하지 않는다.
