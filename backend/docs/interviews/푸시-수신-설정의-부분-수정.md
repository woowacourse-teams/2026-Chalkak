# 푸시 수신 설정은 바꾼 항목만 보낸다

- 갱신일: 2026-09-30
- 관련 이슈: [#491](https://github.com/woowacourse-teams/2026-Chalkak/issues/491)
- 현재 정책: [NOTIFICATION-006](../../../docs/business-rules/rules/notification.md#notification-006-본인-푸시-수신-설정-조회수정)

## 두 스위치를 함께 보내면 오래된 값도 저장한다

주제 푸시와 승인·반려 푸시는 회원 계정의 설정이다. 수정 API에서 바꾼 항목만 보내는 A와 두 값을 항상 보내는 B를 비교했다. B는 검증과 저장이 단순하지만 앱이 들고 있던 다른 설정의 오래된 값까지 함께 보낼 수 있다.

예를 들어 다른 휴대폰에서 승인·반려 푸시를 끈 뒤 현재 휴대폰에서 주제 푸시만 끄면, B는 현재 휴대폰에 남은 이전 값을 보내 승인·반려 푸시를 다시 켤 수 있다. 이 예시는 가상의 상황이며 실제 사용자 장애 사례는 아니다. 사용자는 각 스위치를 독립적으로 변경하는 A를 선택했다.

## DTO의 null은 DB에 저장할 값이 아니다

부분 수정의 Request DTO는 primitive boolean 대신 Boolean을 쓴다. true는 켜기, false는 끄기, 생략 또는 null은 변경하지 않음이다. 사용자가 DTO의 null이 괜찮은지 확인한 뒤 이 방식과 두 항목 모두 값이 없을 때의 400 거부를 승인했다. 생략과 명시적인 null을 구분하지 않으므로 별도의 JSON 존재 여부 처리는 필요하지 않다.

서버는 기존 값과 요청 값을 합쳐 도메인의 기존 변경 메서드를 호출한다. DB 필드는 계속 NOT NULL이고 null을 저장하지 않는다. 성공 응답은 기존 수정 API와 같은 본문 없는 204다.

## 부분 수정도 동시에 처리하면 최신 값을 읽어야 한다

바꾼 항목만 보내더라도 두 요청이 같은 이전 값을 읽은 뒤 전체 엔티티를 저장하면 다른 변경을 덮어쓸 수 있다. 구현에서는 기존 회원 행 잠금 조회를 재사용해 최신 설정을 읽고 변경한다. 서로 다른 항목은 모두 유지하고 같은 항목은 나중에 처리된 요청의 값으로 저장한다.

요청 검증·DB 저장·회원 접근·생성된 OpenAPI를 검증했다. PostgreSQL 경쟁 테스트에서는 두 번째 요청의 실제 DB 잠금 대기를 확인한 뒤 첫 번째 요청을 커밋하고 두 설정의 변경이 모두 남는지 검증했다. 운영 부하와 실제 앱 연동은 아직 확인하지 않았다. 이 단위는 설정 저장까지이며 실제 푸시 발송을 구현하지 않는다.
