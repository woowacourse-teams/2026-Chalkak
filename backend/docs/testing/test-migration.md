공개 주제 서비스의 응답 매핑은 고정된 과거 주제로 확인해 실행 날짜의 영향을 줄였다. OPEN과 CLOSED의 실제 상태 규칙과 DB 매핑 검증은 기존 도메인 및 Repository 테스트에 남긴다.

인증과 회원 Repository 6개, 배너 Repository, 알림 Repository 4개, AI Repository 2개와 좋아요 집계 Repository를 실제 PostgreSQL 슬라이스로 좁혔다. 각 테스트의 기존 DB assertion은 유지한다. 수신자와 관리자 회원 목록은 다른 통합 실행의 저장 데이터에 영향을 받지 않도록 테스트 트랜잭션 안에서 DatabaseCleaner로 시작 상태를 격리한다. 기기 Repository의 준비 데이터는 실제 User와 UserRefreshToken을 저장하며 토큰 발급 서비스는 로딩하지 않는다.

OpenAI 허용 모델의 설정 바인딩 테스트는 ApplicationContextRunner로 필요한 설정 객체만 로딩한다. 전체 서버와 DB를 사용하지 않으며 실제 application.yml의 바인딩 검증은 유지한다.

게시물 도메인 테스트에 남아 있던 User와 Topic Mock도 실제 객체로 교체했다. Spring과 DB는 사용하지 않으며 기존 비즈니스 규칙 assertion을 유지한다.

실행 환경이 다른 피드 DB 검증을 위한 클래스 하나를 추가하고, 단일 메서드였던 주제 Repository 통합 클래스를 기존 슬라이스에 합쳤다. 조회 이관 당시 테스트 클래스 수는 342개였다. 개수 자체를 감소 목표로 삼지는 않는다.

다음 검증은 실제 DB를 사용하는 통합 테스트로 유지한다.

- 동시 요청, 행 잠금과 조건부 갱신, 커밋과 롤백, AFTER_COMMIT과 REQUIRES_NEW
- 가입과 탈퇴, 사진 처리 및 검수, 관리자 변경과 감사 기록처럼 여러 저장의 연결을 확인하는 흐름
- Worker의 실제 claim, 재시도와 중복 처리, 발송과 DB 기록의 실행 경계
- 실제 조회 수와 N+1, 저장 변경 후 재조회, 스키마 마이그레이션

쓰기 서비스와 Worker의 후속 정리는 아래에 기록한다. 실제 저장과 실행 경계를 확인하는 통합 테스트는 유지한다.

## 조회 이관 당시 검증

- 서비스 11개를 Repository Mock 단위 테스트로, Repository 14개를 실제 PostgreSQL 슬라이스로 전환했다.
- 전체 회귀 테스트 3,682개가 실패, 오류, 생략 없이 통과했다. 마지막 기기 슬라이스와 설정 바인딩 변경도 관련 테스트와 형식 검사를 통과했다.
- 전환한 서비스 11개와 기존 앱 버전 단위, 게시물 도메인, 설정 바인딩은 DB 접속 포트를 1로 지정한 별도 실행에서도 163개 모두 통과했다.
- 개인 `.env`의 누락 키 때문에 `checkEnvContract`는 제외했다. 환경변수 계약 검사기는 개인 `.env`를 제외한 임시 검증 환경에서 통과했다. 개인 파일은 변경하지 않았다.
- 로컬 기본 인증 설정 검증은 개인 `.env`와 섞이지 않도록 실행 시 `ADMIN_DEVELOPMENT_BYPASS_ENABLED=true`를 지정한다.
- 전용 테스트 DB `chalkak_test_893_4b7d`와 포트 5433을 사용한다. 속도 개선 수치는 전후 측정을 하지 않았으므로 제시하지 않는다.

## 분야별 역할 분류

다음 표는 분야별 역할을 분류한 것이다. 모든 개별 테스트의 불필요한 반복까지 제거했다는 뜻은 아니다. 기존 단위, 웹 슬라이스와 보안 테스트는 역할에 맞게 유지하고, 저장과 실행 경계가 필요한 테스트는 PostgreSQL 통합으로 유지한다.

| 순서 | 검토 범위 | 보호할 흐름 |
| --- | --- | --- |
| 1 | 공통, 도메인, 설정, 예외와 문서 계약 | 기존 단위와 슬라이스를 유지하고 공통 오류와 보안 검증의 중복을 점검 |
| 2 | 인증, 사용자와 관리자 인증 | 로그인, 가입, 갱신, 탈퇴, 기기 폐기 연결과 토큰 경쟁 |
| 3 | 게시물, 사진, 좋아요와 관리자 게시물 | 제출, 콜백, 검수, 공개, 수정과 삭제의 저장 및 경쟁 요청 |
| 4 | 주제, 배너, 앱 버전, 피드백, 지표와 대응 관리자 기능 | 조회 조건, 관리 변경, 감사 기록과 저장 원자성 |
| 5 | AI 리뷰와 관리자 AI 기능 | 요청 자격, 버전 선택, 재시도, Worker 처리와 중복 실행 방지 |
| 6 | 알림과 관리자 알림 기능 | 알림함, 수신 설정, 기기, Relay, Worker, 공지, 리마인더와 주제 발송 |

기기 폐기처럼 여러 분야에 걸친 흐름은 관련 연결 검증을 함께 유지한다. 이후 새로운 기능을 개발할 때도 같은 판단 기준을 적용한다.

## 각 작업의 완료 확인

- 변경 전 테스트가 보호하는 정상, 거부, 경계, 저장과 부수효과를 확인한다.
- 옮기거나 삭제한 시나리오마다 남은 검증 위치를 PR에 적는다. 삭제하지 않은 테스트까지 별도 표로 복제하지 않는다.
- 같은 목적의 테스트는 묶고, 입력만 다른 경우 파라미터화한다. 실행 환경이나 책임이 다를 때만 새 클래스를 만든다.
- 단위 전환 대상은 DB 없이 실행되는지 확인한다. 남겨 둔 DB 테스트는 테스트 PostgreSQL로 실제 실행한다.
- 관련 테스트와 형식 검사를 실행하고, 해당 변경으로 영향받는 전체 테스트의 회귀를 확인한다. 실패와 미실행은 그대로 기록한다.
- 클래스 수나 속도 개선은 실제 전후를 측정한 경우에만 성과로 적는다. 현재는 삭제 목표 수나 속도 개선 수치를 정하지 않는다.

## 반복 본문과 컨텍스트 재사용

전체 속도를 직접 비교하니 이관 직후에는 오히려 느려졌다. 같은 환경에서 컴파일과 형식 검사를 제외한 test 태스크를 각각 3회 실행했다. 작업 중인 코드를 보존하려고 별도 소스 복사본과 전용 PostgreSQL DB를 사용했다.

DB 슬라이스마다 다른 구현체를 import하면서 컨텍스트가 나뉜 것이 비용을 늘렸다. 기존 28개 슬라이스가 사용하는 저장 계층 구현 22개를 PostgresRepositoryTest 하나로 모았다. 서비스와 외부 연동은 로딩하지 않으며, 각 테스트의 기존 롤백 격리는 유지한다. 동시성과 트랜잭션 통합 클래스에는 적용하지 않는다. 관련 실행에서 28개 슬라이스의 DB 풀이 하나였고, 전체 실행의 관찰 풀 수는 48개에서 25개로 줄었다.

같은 클래스 안에서 본문이 같던 4그룹은 입력표를 합쳤다. 관리자 AI 조회의 잘못된 페이지와 필터, 관리자 게시물의 잘못된 페이지와 필터, 잘못된 검수 요청, StoreUrl의 잘못된 원문 입력이다. 모든 입력을 보존해 관련 테스트 실행은 전후 351개로 같았다. DB 슬라이스 28개의 클래스 본문도 대조해 바뀌지 않은 것을 확인했다.

본문이 같은 나머지 8그룹은 대상 API, 알림 종류나 도메인이 서로 다르다. 각각의 계약을 지키는 검증으로 유지한다. 이 수치는 공백과 주석을 제외한 본문 정확 일치 검사이며, 모든 의미적 중복이 없음을 보장하는 수치는 아니다.

## 증가분과 검증 필요성 재검토

계층을 분리하고 기존 assertion을 보존하는 데 치우쳐, 단순 변환과 같은 경계의 반복을 충분히 줄이지 못했다. 앞서 정리 완료로 표현한 범위는 과했다. 이번에는 순증가분과 실행 시간이 긴 상위 테스트를 중심으로 실제 준비 코드와 보호하는 동작을 다시 읽었다. 전체 코드의 불필요한 부분이 0이라고 보장하는 검토는 아니다.

직전 최초 대비 557줄의 순증가는 다음과 같다. 회원과 Worker의 큰 새 파일은 대부분 이동한 코드이므로 파일 크기 전체를 추가로 세지 않았다.

| 범위 | 당시 순증가 | 증가 이유 |
| --- | ---: | --- |
| 피드 조회 단위와 DB 분리 | 266줄 | 실제 쿼리 수와 재조회 검증을 남기면서 Mock용 객체 준비와 DB용 준비가 각각 필요해졌다. |
| 관리자 AI 조회 | 157줄 | DB가 조립하던 점수, 프롬프트, 작성자, 사용량 등 25개 필드의 조회 결과를 단위 테스트에서 직접 준비하게 됐다. |
| Push Worker와 공통 준비 | 134줄 | 입력 거부를 DB 밖에서 확인하는 테스트와 그 의존 객체 준비를 분리했다. |
| 그 외 합계 | 0줄 | 다른 파일의 증가와 감소가 상쇄됐다. |

이번에 다음 반복을 정리했다.

- 피드 DB 준비의 긴 SQL 나열은 실제 User, Topic, 업로드, Photo와 Post를 저장하는 작은 준비 메서드로 바꿨다. 실제 FK와 DB 조회 수 assertion은 유지한다.
- 배너의 단순 필드 복사만 보는 서비스 테스트를 없애고, 이미 존재하는 실제 HTTP 조회 시나리오에 필드와 페이지 계약을 합쳤다.
- AI 조회의 페이지 크기 준비 두 묶음은 기존 정상 조회를 1과 100으로 파라미터화해 합쳤다. 숨김 여부, 실패 결과와 원출력 해석 검증은 유지한다.
- 같은 관리자 로그인으로 JWT와 리프레시 토큰을 확인하던 두 통합 시나리오는 한 번의 실제 로그인에 합쳤다.
- Repository Mock이 연속으로 새 값을 반환하는 앱 버전 테스트를 제거하고, 실제 저장 통합 시나리오에서 변경 전 값을 읽은 뒤 변경 후 값을 확인하도록 보강했다. Mock만으로 Spring 캐시까지 검증했다고 보지 않는다.
- Worker의 같은 만료 분기를 모든 종류에서 반복하는 대신 직접 발행과 알림함의 두 경로를 확인한다. 정각과 직후의 상세 경계는 PushDeadlinePolicyTest에, 각 저장 알림의 실제 발송은 해당 DB 테스트에 남긴다.
- 동일한 기본 컨텍스트의 저장 통합 테스트가 이미 기동을 확인하므로 본문이 빈 contextLoads 템플릿은 제거했다. 이 삭제가 컨텍스트 초기화 비용 자체를 없애지는 않는다.
- OpenAI 실제 읽기 타임아웃 200ms는 유지하고 가짜 서버의 고정 1.5초 대기를 latch로 바꿨다. 제한 시간 실패를 확인한 뒤 정리 때 응답을 해제하며, 전체 요청에는 3초 상한을 둔다. 두 테스트가 전체 실행에서 약 0.47초에 통과했다. SQS의 실제 5초 요청 제한과 최소 1초 재대기는 운영 복구 조건이므로 유지한다.

전체 테스트 Java는 84,292줄에서 84,085줄로 207줄 순감소했다. 최초 83,735줄 대비 순증가는 350줄이다. 메서드 선언은 2,441개, 테스트 클래스는 343개, 실제 실행은 3,677개이며 실패, 오류와 생략 없이 통과했다. 동시성과 트랜잭션 테스트, 운영 코드와 환경변수 값은 변경하지 않았다.

이번 전체 test 태스크는 단회 86.119초였다. 이전 3회 중앙값과 직접 비교해 추가 속도 개선을 주장하지 않는다. 이번 실행의 클래스별 시간 합은 전체 Spring 통합 약 47.7초, 웹 슬라이스 약 10.5초, DB 슬라이스 약 3.3초, 작은 설정 컨텍스트 약 2.1초, 단위와 Adapter 및 아키텍처 약 20.7초였다. 이 시간에는 해당 클래스의 준비와 실행이 함께 포함된다. 전체 실행 비용의 주된 부분은 여전히 Spring 통합 구성과 실제 연결 검증에 있다.
